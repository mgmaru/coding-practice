# AIとの役割分担 — 「AIプロダクトオーナー方式」

本リポジトリにおける学習の中核となる運用ルール。毎週のチケット発行時に参照する。
AIにチケットを切らせる際は、このファイルをそのままプロンプトに添付して「この方針に従って」と依頼してよい。

実装力を鍛えるための核となる運用方針。**誰が何を決めるか**を以下のように固定する。

## 役割分担の4レベル

| レベル | 決めるもの | 担当 | 理由 |
|--------|-----------|------|------|
| 1. プロジェクト | 何を作るか（題材） | **自分** | 継続力・モチベーションの源泉。ここは譲らない |
| 2. チケット | 次にどの機能を作るか | **AI（PO役）** | 自分で決めると「書けそうな機能」を無意識に選ぶバイアスが入る。実務の「仕様が与えられる」感覚を再現する |
| 3. 受け入れ条件 | どうなったら完成か | **AI（チケットとセットで）** | 完成基準が外部から与えられることで、自己検収の練習になる |
| 4. 実装・検証 | どう作るか、正しいか | **自分** | ここが鍛えたい本体。AIはレビュアーとしてのみ使う |

> AIにレビューさせるときの **観点は [review-rubric.md](./review-rubric.md) に定義** してある。先に自分で同じ観点で自己レビューし、後でAIの指摘との差分を読むこと。

## 2つのトラック ― 目的とサイクルの定義

学習は **ドリル** と **プロジェクト/ツール** の2トラックで回す。**workflow（自分で書く → 自己レビュー → PR → AIレビュー → 自分でマージ）は両トラック共通**で、AIレビューはどちらも必須（観点は [review-rubric.md](./review-rubric.md)）。2つを分けるのは workflow ではなく **目的** と **題材の出どころ**。

### 目的

- **ドリル**: プログラムを組む「**道具**」を、単体で・反復して習得する。対象は——文法/イディオム、標準ライブラリの使い方、データ構造（リスト・辞書・集合）の操作、型、計算量・アルゴリズムの改善、例外処理 など「**部品**」レベルの技能。題材は小さく模範解答があり、答え合わせができる。設計判断はほぼ問わない。
- **プロジェクト/ツール**: ドリルで習得した道具を使って、**設計を含む実装**を一気通貫で完走する。要件の解釈 → 設計（関数分割・データ構造選択・責務・依存の向き）→ 実装 → テスト → 自己検収。題材は自分が決め、機能チケットは AI が PO 役で発行（受け入れ条件付き・答えは無い＝実務再現）。

> 狙い（「設計はできるが実装が薄い」人向け）: ドリルで**空の道具箱を埋め**、プロジェクト/ツールで**既にある設計力に道具を接続**して成果物にする。

### 共通の学習サイクル（器）

1. **まず自分で書く**（先にAIに書かせない）
2. **自己レビュー**（review-rubric の該当観点）
3. **PR作成 → AIレビュー**（review-rubric、must / should / nice）→ 指摘・差分を読む
4. **検収**: ドリル＝模範解答／AIの書き方との差分を理解 ／ ツール＝受け入れ条件で自己検収
5. **説明できるまで質問** → 自分でマージ

### 中身の違い（payload）

| | ドリル | プロジェクト/ツール |
|---|---|---|
| 目的 | 道具の習得（部品）| 設計を含む実装（組み立て）|
| 題材の出どころ | 外部教材・**模範解答あり** | 自分＋**AI(PO)がチケット発行・模範解答なし** |
| AIレビューの焦点 | review-rubric の **①土台 ＋ ②道具の良し悪し**（イディオム・計算量・データ構造の選択）| review-rubric の **適用マトリクス「ツール」列**＝現Phaseまでに解禁した層1観点 ＋ 層2（命名・SRP・テスト・**設計判断**・セキュリティ）|
| 検収 | 模範解答との差分理解 | 受け入れ条件で自己検収 |
| 規模・継続 | 小・単発 | 大・フェーズを跨いで継続 |

### 運用の注意（ドリルの量を殺さない）

ドリルは高頻度（週の3〜4割）。「1問＝1PR」を厳格にやると ceremony 過多で量が死ぬ。**「AIレビュー無しでコミットしない」は守りつつ、運用は軽く**:

- ドリルは **週まとめで1PR**（その週の分をまとめてAIレビュー）でも可
- ドリルのAIレビューは **軽め（Phase1観点中心）** でよい

配分目安: **ドリル 3〜4割 / プロジェクト 6〜7割**。

## 実装中のAIの使い方（道中の線引き）

> 4レベルの表は「最初の一行は自分／レビューはAI」という **入口** と **出口** を決めている。この節は、その間の **道中**（自力で書いている最中にAIをどこまで使ってよいか）を定義する。

```
入口             道中（この節）          出口
自分で書く   →   AI使用の線引き   →   AIレビュー（review-rubric）
```

**原則 — 鍛えたい能力＝ボトルネックにAIを触れさせない**

- ボトルネックは2つだけ: **①ロジックを組む ②バグを特定する**。この2つは常に手動。
- それ以外の摩擦（文法の想起・ライブラリの所在・概念・エラーの和訳）は **AIで削ってよい**（鍛えたい力ではないため、ここで悩んでも目的の力は伸びない）。

### 3色の線引き

| 色 | いつ使う | 具体例 |
|----|---------|--------|
| 🟢 **常時OK**<br>知識・道具の所在 | ボトルネックに触れない | ・ライブラリ/標準ライブラリの**存在**調査<br>・API・シグネチャの確認<br>・概念の説明（例「list と deque の違い」）<br>・**エラーメッセージの和訳・解説**<br>・環境/ツールの設定 |
| 🟡 **自力の後だけOK**<br>タイムボックス経過後 | 自分の案を出した後の補強 | ・デバッグの**ヒント**（「答えは言わず、どこを疑うかだけ」）<br>・設計の健全性チェック（自分の分割案を固めた後にぶつける）<br>・実装方針の選択肢出し（自分の「入力→処理→出力」を書いた後） |
| 🔴 **実装中は禁止**<br>鍛えたい能力そのもの | ボトルネックを直接代替 | ・ロジックの**最初のドラフト**を書かせる<br>・関数分割・データ構造を**決めさせる**<br>・バグの**修正そのもの**（特定する前に「直し方」を聞く） |

> **「エラーを聞いてよいか」は種類で分かれる**: 和訳・解説＝🟢 ／ 原因特定のヒント＝🟡（自力の後）／ 修正そのもの＝🔴。

### 迷ったときの一問

> **聞く前に、答えの「形」を予想できるか？**
> - 予想できる（＝事実確認・想起の高速化）→ 🟢 使ってよい
> - 予想できない（＝AIの答えがそのまま自分の思考になる）→ 🔴 自分でやる領域

### エディタのAI補完

「まず自分で書く」を**無意識に破る最大の穴**。チャットと違って意識されないため、明示的に切る。

| 補完の種類 | 扱い |
|-----------|------|
| 行・関数の**ロジック生成**（Copilot 等） | ❌ 学習中はオフ |
| 型・メソッド名・import 補完（LSP） | ✅ 残す（道具の所在＝🟢相当） |

### トラックで濃さを変える

原則: **AI使用への "税" は、その助けが今鍛えている技能に近いほど重くする。**

| | ドリル | プロジェクト/ツール |
|---|--------|-------------------|
| 🟢 の範囲 | 文法・API確認も「まず自分で想起 → 詰まったら確認」と一段厳しく | 文法・ライブラリ調査は**最初から自由** |
| 🟡 の発動 | **10分**悩んだら | **30分**悩んだら |
| 理由 | 道具の**想起そのもの**が目的 | 認知負荷を**設計・組み立て**に割きたい |

## フェーズ移行でもAIは「検収役」を兼ねる

上の4レベルは「チケット1枚」の粒度の役割分担。**フェーズの移行**（次のPhaseへ進むか）でも、同じ「AIが検収・最終判断は自分」の構造をそのまま使う。

| 高度 | 受け入れ条件 | 検収する | 最終決定 |
|------|-------------|---------|---------|
| チケット | AI（PO役）| 自分 ＋ AIレビュー | 自分 |
| フェーズ | 各Phaseの DoD | 自分 ＋ **AI（検収役）** | 自分 |

フェーズには「進む許可を出す外部者」がいないため、**自己検収 → AI検収（go / no-go）→ 自分が昇格判断** というチェックポイントを置いて自己バイアスを防ぐ。基準（DoD）と手順は [roadmap.md の「フェーズ移行レビュー」](./roadmap.md) を参照。

## 週次の運用フロー

1. **チケット発行（週初め）**: AIに次のように依頼する
   > 「このリポジトリの現状を踏まえて、プロダクトオーナーとして次の機能要求を受け入れ条件付きのIssueとして2〜3個書いて。**1つはわざと仕様に曖昧さを残して**」
2. **Issue登録**: 出てきたチケットをGitHubのIssueとして実際に登録する
3. **仕様の質疑**: 実装前に仕様の曖昧な点を洗い出し、Issueのコメント欄でAIに質問する
   - 「この場合の挙動はどうしますか？」「入力が空のときは？」
   - ※ 実務の難しさの半分は仕様の隙間にある。**曖昧さに気づいて質問を返す**こと自体が訓練
4. **実装**: ブランチを切り、自分で実装する（共通ルール通り、先にAIに書かせない）
5. **自己検収**: 受け入れ条件と照らして自分で検証し、PRを作成 → CI・CodeQLの指摘に対応 → マージしてIssueを閉じる

このサイクルで「仕様を読み取る → 曖昧さに質問を返す → 実装する → 受け入れ条件で検収する」という実務の開発サイクルを忠実に再現できる。

## なぜ「与えられた課題」と「作りたいもの」の両取りになるか

- 演習サイトの課題は要件が完全で、解けることが保証されており、実務の再現にならない
- 完全に自分で決めると、苦手分野を避けるバイアスが入り、興味も偏る
- この方式なら **題材は自分の興味（継続力を確保）× 仕様は与えられる（実務の再現）** を両立できる

## 補助ルール

- **バイアス検査（月1回）**: AIに「今月の私のコードと会話を踏まえて、避けているトピックは何か」を聞き、それを翌月のチケットに混ぜさせる
- **視点の入れ替え（たまに）**: 逆に自分が課題を決め、AIと一緒に受け入れ条件へ落とす演習も混ぜる。「曖昧な意図を仕様に固める」発注側（PO・設計者）の訓練になり、設計経験との相乗効果がある
- **ドリルとの併用**: ドリルとプロジェクト/ツールの **目的・サイクル・配分** は上記「2つのトラック ― 目的とサイクルの定義」節に定義（配分目安: ドリル3〜4割 / プロジェクト6〜7割）
