# git: 過去のコードは消えない — 履歴から取り出す

本リポジトリ共通の運用メモ。**「ファイルを直接修正して main にマージすると、修正前のコードが残らないのでは？」** という不安への回答と、過去のコードを取り出す手順を定義する。

結論を先に言うと **消えない**。コミット済みのコードは、いつでも・確実に取り出せる。したがって**元コードを残すための手動コピーは不要**で、ファイルは原本を直接修正してよい。

> 関連: [pr-workflow.md](./pr-workflow.md)（PR運用）/ [branch-naming.md](./branch-naming.md)（ブランチ運用）/ [notes/git-diverged-recovery.md](./notes/git-diverged-recovery.md)（分岐からの復旧）

---

## TL;DR（30秒で読む要点）

| 項目 | 内容 |
|------|------|
| **不安** | ファイルを直接修正して main にマージすると、修正前のコードが残らない気がする |
| **結論** | **残る。** コミットした時点で、その内容は履歴に永久保存されている |
| **理由** | git は「最新の1枚」ではなく、**各コミット時点のスナップショット（写真）を全部**保持する |
| **取り出し方** | `git show <ハッシュ>:<ファイルパス>` で、その時点のファイルをそのまま表示 |
| **運用** | 元コードを残すための**手動コピーは作らない**（git が自動でやっている）。原本を直接修正してよい |

---

## 1. なぜ「消える気がする」のか（不安の正体）

直感はこうなりがち:

> ファイルを上書き修正 → マージ → **元の中身は上書きされて消えた**

しかしこれは「**作業ツリー（今見えている1枚）**」と「**コミット履歴（過去の全バージョン）**」を混同している。

| | 何を指すか | 修正・マージで |
|---|---|---|
| **作業ツリー** | 今エディタで見えているファイル | 上書きされる（最新だけ見える）|
| **コミット履歴** | 過去にコミットした全スナップショット | **一切変わらない**（過去は不変）|

上書きされるのは作業ツリーだけ。**過去のコミットには手が触れていない。**

---

## 2. git の考え方（写真のアルバム）

git のコミットは「**その瞬間のリポジトリ全体を撮った写真**」。コミットするたびに1枚アルバムに増えていく。

```
       <コミットA>          (将来のマージ後)
      「ソース作成」    →     main の最新
     ┌──────────┐         ┌──────────┐
     │ main.go  │         │ main.go  │
     │（元コード）│         │ 修正後   │
     └──────────┘         └──────────┘
       写真①                写真②
        ↑ この写真は②を撮っても・マージしても変わらない
```

最新の写真②を撮っても、**写真①（元コード）はアルバムにそのまま残る**。後から①を引っ張り出せば、いつでも元コードが見られる。

---

## 3. 取り出し方（コマンド）

`<ハッシュ>` は「どの写真を見るか」、`:` の後ろは「その写真の中のどのファイルか」。`<path>` はリポジトリのルートからのパス。

```bash
# ① 元コードをそのまま表示する
git show <ハッシュ>:<path>

# ② 修正前 → 修正後の「差分」を見る
git diff <ハッシュ> HEAD -- <path>

# ③ 元コードを別名でファイルに復元する（手元で見比べたいとき）
git show <ハッシュ>:<path> > /tmp/original_backup
```

実例（`logstat` の最初の実装コミットを見る場合）:

```bash
git show 94edf4d:go/phase1/tools/logstat/src/main.go
```

> `:` の左右の意味 —— `git show <ハッシュ>:<path>`
> 　左 = **どの写真か**（コミット）／右 = **その写真の中のどのファイルか**

### ハッシュ以外の「写真の指し方」

「どの写真か」はハッシュ以外でも書ける。仕組みは全部同じ（写真を1枚選んでいるだけ）。

| 書き方 | 指すもの |
|--------|---------|
| `<ハッシュ>:<path>` | そのハッシュのコミット（最も確実・一意なID）|
| `HEAD:<path>` | 今いる最新コミット |
| `HEAD~3:<path>` | 今から3つ前のコミット |
| `<タグ名>:<path>` | 自分で名前を付けたコミット（次節）|

---

## 4. 任意：タグで名前を付けておく

毎回ハッシュを打つのが面倒なら、**読みやすい名札（タグ）**を貼れる。

```bash
git tag <わかりやすい名前> <ハッシュ>
# 例
git tag logstat-v1-before-review 94edf4d
# 以降はこう書ける
git show logstat-v1-before-review:go/phase1/tools/logstat/src/main.go
```

タグは完全に任意。**貼らなくても履歴は消えない。** 「あの実装」を後で何度も参照したいときの近道、というだけ。

---

## 5. だから「コピーファイル」は作らない（運用方針）

元コードを残すために `main_old.go` のようなコピーを手で作るのは、**git が自動でやっていることの手作業での再発明**。デメリットもある:

- Go では `func main()` が2つになり**ビルドが衝突**する
- どちらが最新か曖昧になり、放置されて腐る
- PR の差分にノイズが乗る

| | 手動コピー | git（推奨）|
|---|---|---|
| 元コードの保存 | 自分でコピーを管理 | コミットで自動保存 |
| 修正前/後の比較 | 2ファイルを目で見比べる | `git diff` が出す |
| `main.go` の衝突 | 2つの `main` で**ビルド不能** | 起きない |
| PR との連携 | なし | PR 画面に差分が永久に残る |

**方針: 1ファイル＝1つの真実**に保ち、過去は git に預ける。レビュー後の修正も、原本を直接（ブランチ上で）修正してよい。

## 6. 用語ミニ辞典

| 用語 | 意味 |
|------|------|
| **作業ツリー（working tree）** | 今エディタで見えている、修正中のファイル群 |
| **コミット** | その瞬間のリポジトリ全体のスナップショット（写真）|
| **ハッシュ** | 各コミットを一意に指す ID（指紋のようなもの。例 `94edf4d`）|
| **`git show <写真>:<path>`** | 指定した写真の中の1ファイルを表示する |
| **`git diff A B -- <path>`** | コミット A と B の、そのファイルの差分を表示する |
| **タグ** | コミットに付ける読みやすい名札（任意）|
| **reflog** | HEAD が動いた履歴。誤操作からの復旧にも使える命綱 |

> 補足: 万一コミット前の変更を消してしまっても、**`git reflog`** にしばらく履歴が残り、復旧できることが多い。「取り返しがつかない」と思い込まないこと（[notes/git-diverged-recovery.md](./notes/git-diverged-recovery.md) 4章と同じ）。
