# Issueの書き方

**1枚のIssueをどう書くか**（構造）を定義する。
**誰が・いつ** Issueを発行するか（AIプロダクトオーナー方式・週次フロー）は [ai-workflow.md](./ai-workflow.md) にある。ここは「**書き方**」だけを扱う。

## 構造

| 要素 | 中身 | 必須 |
|------|------|------|
| タイトル | 何をするか（動詞 + 対象）を簡潔に。例: 「CSV出力機能を追加する」 | ◯ |
| 背景・目的 | **なぜ**やるか。解きたい課題・きっかけ | ◯ |
| 受け入れ条件 | **どうなったら完成か**（後述）| ◯ |
| スコープ外 | 今回やらないこと（やり過ぎ防止）| 任意 |

## 受け入れ条件の書き方

**「ユーザーが観察できる pass/fail」** で、チェックボックスで書く。実装の手段ではなく**結果**を書く。

```markdown
## 受け入れ条件
- [ ] `--format csv` を付けると結果がCSVで出力される
- [ ] 入力が空のとき、エラーで落ちず「データなし」を表示する
- [ ] 不正な形式の行はスキップし、件数を最後に報告する
```

- ◯「CSVで出力される」（観察できる）／ ✗「`csv` モジュールを使う」（実装手段・観察できない）
- 正常系だけでなく **異常系・境界値**（空入力・不正形式）も条件に入れる（[review-rubric.md](./review-rubric.md) の3点セットと対応）。

### 受け入れ条件 ≠ DoD

混同しやすいので区別する。

| | 受け入れ条件 | DoD（完了の定義）|
|---|---|---|
| 粒度 | **Issue/機能ごと**（毎回変わる）| **フェーズ/プロジェクト固定**（毎回同じ）|
| 例 | 「CSV出力できる」 | 「テスト・型・CIが緑」|
| 置き場所 | このIssue | [roadmap.md](./roadmap.md) の各Phase DoD |

## このリポジトリ特有のルール

- **わざと曖昧さを残す**: AI（PO役）が複数Issueを切るとき、**1つは仕様にあえて曖昧さを残す**。実装前に曖昧さに気づいて質問を返すこと自体が訓練（[ai-workflow.md](./ai-workflow.md)）。
- **質疑はIssueコメントに残す**: 「入力が空のときは？」等の仕様確認はIssueのコメント欄でやり取りする（口頭・チャットで消さない）。
- **ラベル（任意）**: 付けるなら [branch-naming.md](./branch-naming.md) と同じ type 語彙（`feat` / `fix` / `docs` …）に揃える。

## マージで自動クローズ

Issueは、対応PRの本文に `Closes #<番号>` を書いてマージすると自動で閉じる（書き方は [pr-writing.md](./pr-writing.md)）。

## 最小の例

```markdown
タイトル: ログ集計に日付フィルタを追加する

## 背景・目的
全期間の集計しかできず、特定日の傾向を見られない。

## 受け入れ条件
- [ ] `--since 2026-06-01` で指定日以降だけ集計する
- [ ] 日付形式が不正なら、エラーメッセージを出して終了コード1で終わる
- [ ] `--since` 未指定なら従来どおり全期間を集計する

## スコープ外
- 時刻（時分秒）での絞り込みは今回やらない
```
