# データ構造の選択判断 — 実装時リファレンス

ツール実装時に「どのデータ構造を使うか」を判断するための作業用ノート。
次回のツール作成時、データを保持する箇所ごとにこれを開いて使う。

---

## 0. 核となる原則

**構造から考えず、アクセスパターンから逆算する。**

選択判断とは、データ構造の性質を暗記していることではなく、
「目の前の問題で**どの操作を・どれくらいの頻度で行い・どれを速くしたいか**」を読み取り、
それに合う構造へ写像すること。Big-O の表を覚えても判断はできるようにならない。
鍛えるのは「問題 → 支配的な操作 → 構造」の対応付け。

> 性質の勉強は必要だが、判断練習と **並行** して行う。
> 性質は「自分が下した選択に紐づいた時」に定着する。表だけ先に詰めても抜ける。

---

## もう一つの軸：データサイズ

アクセスパターンが「どの操作を速くしたいか」を決めるのに対し、
**サイズは「Big-O を信じていいか、それとも定数項・メモリ効果が支配するか」を決める。**
Big-O は漸近的な振る舞いの記述なので、定数項・メモリ確保コスト・キャッシュ効果を隠す。
その隠れた部分がサイズで表に出る。だから判断は「操作 × 規模」の2軸で見る。

### 規模で効く軸が変わる

| 規模 | 効く軸 | 指針 |
| --- | --- | --- |
| 小（〜数十件） | 定数項・単純さ | Big-O を気にせず素朴な配列/slice で十分。map・ヒープは過剰になりやすい |
| 中（〜数万件） | キャッシュ局所性 | 連続構造を優先。キー引きが支配的なら map。ポインタ構造は測定してから |
| 大（10^5〜） | 漸近計算量＋メモリ | §2 逆引き表がそのまま効く。加えてメモリ overhead と溢れに注意 |

### 押さえるべき3点

1. **小さい N では「速い」構造が逆に遅い。**
   線形探索は要素数 ~100 程度まで二分探索と同等以上。~30 未満ならどの構造でも大差なく、
   単純さとメモリ効率で素朴な配列が良い。数十件のキー引きに map を出すのは過剰になりがち
   （特に文字列キーはハッシュ計算が重く、損益分岐点が上にずれる）。
   - 逆の罠: 小さいと平気でも、うっかり O(n²) を書くと大きい N で一気に破綻する。

2. **中〜大では連続メモリ（キャッシュ局所性）が主役。**
   配列/slice/Vec は、ポインタを辿る構造（連結リスト等）に Big-O で負けていても勝つことがある。
   CPU が連続データをプリフェッチでき、より多くがキャッシュに乗るため。
   「データがキャッシュに収まるか溢れるか」というサイズの閾値で、性能に段差が出る。
   - 既定は連続構造。連結リスト等は「測定して速いと分かった時」だけ使う。

3. **大きい N ではメモリ overhead が効く。**
   ノードベース構造（連結リスト・木）やハッシュマップは要素ごとに固定費（ポインタ・余白）を持つ。
   N が大きいとメモリ footprint とキャッシュ効率の両方に響く。

### メタ原則

- **小さい N で「速い」構造を先回りで使わない。** 計測前の最適化はむしろ遅くする。
- **閾値・損益分岐点はハードウェア・キー種別・言語で動く。** 効くと思ったら自分のデータで測る。
  上の数字（~30、~100）は目安であって、自分のデータで計測した値が正。

## 1. 実装中の自問チェックリスト

データを保持する箇所が出てきたら、まずこれを順に問う。

1. **キーで引くか？** → ハッシュマップ
2. **一意性が要るか？／含有判定を繰り返すか？** → ハッシュセット
3. **順序が要るか？** → 挿入順か、ソート順かを区別する
4. **両端で追加・削除するか？** → スタック / キュー / deque
5. **最小・最大を繰り返し取り出すか？** → ヒープ（優先度付きキュー）
6. **ソート済みで走査・範囲検索したいか？** → ソート済みマップ（木）
7. **読み・書きの比率は？ 規模（件数）は？** → 規模で判断が変わる。「もう一つの軸：データサイズ」を参照

支配的な操作が決まれば、構造はほぼ自動的に落ちてくる。ただし規模が小さいと、その判断より「素朴な配列で十分」が優先されることがある。

## 2. 逆引き表（◯◯したいならコレ）

アプリ開発のコードの大半は、この6つで足りる。各構造で覚えるのは
「安い操作」と「罠になる操作」だけ。内部実装の導出までは不要。

| やりたいこと | 構造 | 安い操作 | 罠（避ける／注意） |
| --- | --- | --- | --- |
| 末尾に足して順に回す | 動的配列 | 末尾追加・添字アクセス・順次走査 | 先頭/中間への挿入・削除は O(n)／含有判定は O(n) |
| キーで引く・数える・集約 | ハッシュマップ | 挿入・取得・削除（平均 O(1)） | イテレーション順は保証されない（言語依存） |
| 重複を消す・含むか判定 | ハッシュセット | 追加・含有判定（平均 O(1)） | 順序を持たない |
| ソート順で走査・範囲検索 | ソート済みマップ（木） | 順序走査・範囲検索・最小/最大 | 各操作 O(log n)。ハッシュマップより遅い |
| 両端を出し入れ | スタック/キュー/deque | 両端の追加・削除 O(1) | 中間へのランダムアクセスは不可/遅い |
| 最小or最大を繰り返し取る | ヒープ（優先度付きキュー） | 最小or最大の取り出し・挿入 O(log n) | 任意要素の検索・削除は苦手／全体ソートではない |

## 3. 言語別の実体（4言語マッピング）

同じ構造でも、標準で用意されているかは言語で違う。
「標準にない」＝設計時に代替を考える必要があるサイン。

| 構造 | Go | Python | Rust | TypeScript |
| --- | --- | --- | --- | --- |
| 動的配列 | `slice` | `list` | `Vec` | `Array` |
| ハッシュマップ | `map` | `dict` | `HashMap` | `Map`（キーが文字列なら `object`） |
| ハッシュセット | `map[K]struct{}` | `set` | `HashSet` | `Set` |
| ソート済みマップ | 標準なし（ソート済みslice／3rd party） | 標準なし（`sortedcontainers`） | `BTreeMap` | 標準なし |
| スタック/キュー/deque | `slice`（両端は要工夫） | `collections.deque` | `VecDeque` | `Array`（`push`/`pop`/`shift`） |
| ヒープ | `container/heap` | `heapq` | `BinaryHeap` | 標準なし（自前 or ライブラリ） |

> Go・TS はヒープやソート済みマップが手薄。これらが要る設計だと実装コストが上がるので、
> 設計段階で「本当にその構造が要るか」を問い直す材料になる。

## 4. 選定メモのテンプレ

実装前に、データを保持する箇所ごとに一行〜数行で残す。
これで暗黙の判断が、AIにレビューさせられる成果物になる。コミットや Issue にも残す。

```
## データ構造選定: <機能名 / 保持するデータ>
- 扱うデータ: <何を持つか>
- 支配的な操作: <最も頻繁な操作 / 最も速くしたい操作>
- 規模: 件数 ~N、読み:書き = <比率>
- 選択: <構造>
- 理由: 支配的な操作が◯◯なので
- 却下案: <別構造> — なぜ却下したか
```

例:

```
## データ構造選定: ログのレベル別集計
- 扱うデータ: {日付, レベル} のログ行
- 支配的な操作: 日付×レベルでカウントを足し込む
- 規模: ~10^5 行、書き込み主体・最後に1回読む
- 選択: map[日付]map[レベル]int（二段ハッシュマップ）
- 理由: キーで引いて加算が支配的。順序は出力時にソートすれば足りる
- 却下案: ソート済みマップ — 集計中は順序不要なのでO(log n)が無駄
```

## 5. 判断を鍛える4つの練習法

判断は読書では身につかない。**選択を可視化してフィードバックを回す**ことで身につく。

1. **実装前に選定メモを書く**（上のテンプレ）
   選択理由を言語化してから書く。AIレビューに乗せられる形にするのが肝。

2. **同じ問題を2つの構造で解く**
   「素直な構造」と「あえて不適切な構造」の両方を書き、コスト差を体で覚える。
   （ドリル3の線形探索 vs set化がこの最小形。これを一般化する）

3. **AIに"答えを反転させる制約"を後付けさせる**
   同じ問題に「ルックアップが10^6回走る」「ソート順でも欲しくなった」等を足させると、
   正解の構造が変わる。どの信号が支配的かへの感度が鍛えられる。PO役のAIと相性が良い。

4. **実ツールで事後レビューする**
   実装後に「別構造の方が良かったか？ 想定したアクセスパターンと、
   書き終えた後の実際のパターンは一致したか？」を振り返る。
   アクセスパターンは書き終えて初めて見えることが多く、この差分の振り返りが一番効く。

## 6. ツール作成時の使い方（フロー）

1. 機能ごとに、**データを保持する箇所**を洗い出す（変数・フィールド・コレクション）。
2. 各箇所で **§1 のチェックリスト** を回し、支配的な操作を特定する。
3. 迷ったら **§2 の逆引き表**、言語実体は **§3** で確認。規模が小さい/大きい場合は **「もう一つの軸：データサイズ」** で帯を確認する。
4. **§4 の選定メモ**を一行残してから実装する。
5. 実装後に **§5-4 の事後レビュー**。想定と実際のアクセスパターンの差分を learning-log に1行残す。

## 7. ロードマップ上の位置

- 15問のドリル（`exercises/01_basics`）は map / set / list の **流暢さ** を作る段階。
- 選択判断は、それらが反射になってから上に重ねるのが順序として正しい
  （まだ振るえない道具の中から選んでも判断にならない）。
- 現実的には **15問のGo一周目をやりながら、各問に選定メモ一行を足し始める** のが入口。
  慣れたら専用の選択ドリルを少し。Phase 1 → 2 にきれいに収まる。
