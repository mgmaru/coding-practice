# PRの書き方

**PRのタイトル・本文に何を書くか**を定義する。
branch→PR→マージの **手順・コマンド**（`gh pr create` 等）は [pr-workflow.md](./pr-workflow.md) にある。ここは「**書き方**」だけを扱う。

## タイトル = コミットメッセージ

形式は [Conventional Commits](https://www.conventionalcommits.org/) に揃える。type 語彙は [branch-naming.md](./branch-naming.md)（`feat` / `fix` / `docs` …）と共通。

```
<type>: <要約（何をなぜ変えたか・命令形で簡潔に）>
```

例: `feat: CSV出力に日付フィルタを追加`, `docs: ブランチ命名規則を追加`

> ⚠️ **このリポジトリは `--squash` でマージする** → **PRタイトルがそのまま main のコミットメッセージになる**。だからPRタイトルは丁寧に書く。これで「PRタイトル規約」と「コミットメッセージ規約」は一体（別途コミット規約は設けない）。
> ブランチ内の途中コミット（`wip` 等）は squash で消えるので作業ログでよい。**main に残るのはPRタイトル1行**だと意識する。

## 本文の構造

| 要素 | 中身 | 必須 |
|------|------|------|
| 何を / なぜ | この変更の概要と理由（タイトルの補足）| ◯ |
| 検証したこと | どう動作確認したか（実行コマンド・テスト・手で確認した点）| ◯ |
| `Closes #<番号>` | 対応Issueがあれば。マージでIssueが自動クローズ | Issueがあれば◯ |
| AI採用の明記 | AIが書いたコードを採用したなら、その旨と**自分が検証した内容**（[運用ルール](../README.md#運用ルール)5）| 該当時◯ |

> `gh pr create --fill` はコミットから本文を自動生成する。それで足りなければ `--body` で上記を補う。

## 小さく・1PR1目的

- 1つのPRは1つの目的に絞る（レビューしやすく、`--squash` 後の履歴も追いやすい）。
- 自己レビューの観点は [review-rubric.md](./review-rubric.md)。**自分で観点に沿って見直してから** AIレビューに出す（順番が命）。
- 軽微な設定/チョア（タイポ・`.gitignore` 調整など、レビュー価値のない機械的変更）はPRを省いて直 main 可（例外。判断基準は [pr-workflow.md](./pr-workflow.md)「このリポジトリ特有の注意」）。

## 最小の例

```markdown
タイトル: feat: ログ集計に日付フィルタを追加

## 何を / なぜ
特定日以降だけを集計できるよう `--since` オプションを追加した。
全期間しか見られず日次の傾向を追えなかったため。

## 検証したこと
- `python main.py --since 2026-06-01` で6/1以降だけ集計されることを確認
- 不正な日付 `--since xxx` でエラー終了（コード1）になることを確認
- `--since` 未指定で従来どおり全期間集計になることを確認

Closes #12
```
