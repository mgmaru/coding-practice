# AIレビュアーのレビュー観点（ルーブリック）

本リポジトリで **AIをレビュアーとして使うときの観点** を定義する。
目的は「AIに網羅的なレビューをさせる」ことではなく、**自分がコードの品質・セキュリティを判断する軸を学ぶ** こと。
観点を繰り返し使って内面化し、最終的にAI無しでもレビューできる状態を目指す。

## 大原則

1. **ツールと重複させない**: format / lint / 型 / SAST は自動ツール（Ruff・mypy・Bandit・CodeQL）が見る。AIレビューは **ツールが見られない層** に集中させる。
2. **Phase連動**: 観点はPhaseに応じて段階的に増やす。Phase 1で安全性まで問うと過負荷になる。
3. **自己レビューを先にやる**: いきなりAIに渡すとAIが機械的に走るだけで自分が考えなくなる。**①自分で観点に沿って自己レビュー → ②AIにレビューさせる → ③差分を読む** の順を守る（ロードマップの「先にAIに書かせない／順番が命」と同じ思想）。

## 観点の3層

### 層0: 自動（ツールが見る）— AIに見させない

| 観点 | ツール |
|------|--------|
| フォーマット・lint | Ruff |
| 型の整合 | mypy / pyright |
| 既知の脆弱パターン（SAST） | Bandit / Semgrep / CodeQL |

> ツール名は Python の例。他言語は同等物に読み替える（lint/format・型チェッカ・SAST）。Rust の SAST は `cargo-audit` + `clippy`（CodeQL 対応はプレビュー段階）。詳細は [roadmap.md](./roadmap.md) の言語戦略。
> ここを人間やAIが手でレビューするのは時間の無駄。CIに任せ、指摘が出たら直す。

### 層1: AIレビュアーが見る（ツールが見られない層）

Phaseが上がるほど観点が増える。下のPhaseに進んでも、上のPhaseの観点は引き続き見る。

**［Phase 1〜］ロジックの土台**

- [ ] 「入力 → 処理 → 出力」が明確か
- [ ] 1関数1責務になっているか
- [ ] エラーケース（ファイルが無い・形式が不正・入力が空）を最低1つ扱えているか

**［Phase 2〜］可読性・テスト・設計**

- [ ] 命名が意図を表しているか（変数・関数・引数）
- [ ] 関数の長さ・責務は適切か（SRP）。分割すべき箇所はないか
- [ ] マジックナンバー・重複コードはないか
- [ ] テスト: 正常系・異常系・境界値の3点があるか
- [ ] テストが実装の写経になっていないか（意味のあるアサーションか）
- [ ] データ構造の選択は妥当か / 関心は分離されているか

**［Phase 3〜］セキュリティ・設計上の安全性**

- [ ] 入力検証はあるか / 信頼境界はどこか
- [ ] 機密情報の扱い（APIキーをコードに埋めていないか、`.env` + `.gitignore`）
- [ ] インジェクション対策（プレースホルダ・エスケープ・検証）
- [ ] **ツールでは検出できない設計上の問題** はないか（権限設計・信頼境界・認可漏れ）

### 層2: 最後に自分が問う

- なぜこの構造にしたか、自分の言葉で説明できるか
- 設計判断（データ構造・分割・依存の向き）は妥当か
- AIの指摘のうち、納得できないものはどれか。なぜか

## AIへの依頼テンプレート

> 「このコードを次の観点でレビューして。各指摘に **重大度（must / should / nice）と理由** を付けて。
> 観点: <該当Phaseの層1チェック項目を貼る>。
> ※ format / lint / 型はツールで見ているので指摘不要。」

依頼の前に必ず **自分で同じ観点で自己レビュー** を済ませ、後でAIの指摘との差分を読むこと。
