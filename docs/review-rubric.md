# AIレビュアーのレビュー観点（ルーブリック）

本リポジトリで **AIをレビュアーとして使うときの観点** を定義する。
目的は「AIに網羅的なレビューをさせる」ことではなく、**自分がコードの品質・セキュリティを判断する軸を学ぶ** こと。
観点を繰り返し使って内面化し、最終的にAI無しでもレビューできる状態を目指す。

## 大原則

1. **ツールと重複させない**: format / lint / 型 / SAST / 依存スキャン は自動ツールが見る（言語別の対応は下の **層0の表**）。AIレビューは **ツールが見られない層** に集中させる。
2. **Phase × Track 連動**: 観点の **上限はPhase**（学んだ知識）、**適用範囲はTrack**（ドリルは薄く・ツールは厚く）で決まる。
   - craft（命名・SRP・マジックナンバー等）は **知識不要** → ツールなら **Phase 1 から**見る（だから50〜200行のツールでも甘くならない）。
   - テスト（pytest）＝Phase 2〜、セキュリティ（OWASP）＝Phase 3〜 は **学んでから**問う。
   - 具体的にどのグループを見るかは、層1の **適用マトリクス** で「Phase × Track」から選ぶ。
3. **自己レビューを先にやる**: いきなりAIに渡すとAIが機械的に走るだけで自分が考えなくなる。**①自分で観点に沿って自己レビュー → ②AIにレビューさせる → ③差分を読む** の順を守る（ロードマップの「先にAIに書かせない／順番が命」と同じ思想）。

## 観点の3層

### 層0: 自動（ツールが見る）— AIに見させない

> ここを人間やAIが手でレビューするのは時間の無駄。CIに任せ、指摘が出たら直す。**各言語は独立した「世界」**なので、自分が使う言語の表だけ見ればよい。

#### Python（`python/`・uv）

| 観点 | ツール |
|------|--------|
| フォーマット・lint | Ruff（`ruff format` / `ruff check`）|
| 型の整合 | mypy または pyright |
| 既知の脆弱パターン（SAST）| Bandit / Semgrep / CodeQL |
| 依存の脆弱性（SCA）| pip-audit（ローカル）/ Dependabot（GitHub）|

#### TypeScript（`typescript/`・pnpm）

| 観点 | ツール |
|------|--------|
| フォーマット・lint | ESLint + Prettier（モダン代替: Biome 1本）|
| 型の整合 | tsc（`tsc --noEmit`）※TypeScript 自体が型チェッカ |
| 既知の脆弱パターン（SAST）| CodeQL / Semgrep |
| 依存の脆弱性（SCA）| `pnpm audit` / Dependabot |

#### Go（`go/`・modules）

| 観点 | ツール |
|------|--------|
| フォーマット・lint | gofmt（or gofumpt）+ go vet / golangci-lint（メタlinter、staticcheck 等を束ねる）|
| 型の整合 | コンパイラ内蔵（`go build`）※独立した型チェッカ不要 |
| 既知の脆弱パターン（SAST）| gosec / CodeQL / Semgrep |
| 依存の脆弱性（SCA）| govulncheck（Go公式・到達可能な脆弱性のみ報告）/ Dependabot |

#### Rust（`rust/`・Cargo）

| 観点 | ツール |
|------|--------|
| フォーマット・lint | rustfmt（`cargo fmt`）+ Clippy（`cargo clippy`）|
| 型の整合 | コンパイラ内蔵（`cargo check`・借用検査含む）※独立した型チェッカ不要 |
| 既知の脆弱パターン（SAST）| CodeQL（2025-10 GA）|
| 依存の脆弱性（SCA）| cargo-audit（RustSec DB）/ cargo-deny / Dependabot |

> 💡 **Go / Rust の「型の整合」はコンパイラが兼ねる**（`go build` / `cargo check`）ため、Python/TS の mypy・tsc に当たる独立した型チェッカは要らない。
> 📌 **CodeQL は4言語すべてに対応**（Rust は 2025年10月に GA）。この層0の表を **言語別ツールの正本**とし、roadmap など他ドキュメントはここを参照する。

### 層1: AIレビュアーが見る（ツールが見られない層）

観点を **5グループ**に分け、下の **適用マトリクス**で「Phase（学んだ知識）× Track（ドリル/ツール）」から見るグループを選ぶ。下のPhaseに進んでも、上のPhaseの観点は引き続き見る。

**① 土台（ロジック）** ［P1〜・両トラック・知識不要］

- [ ] 「入力 → 処理 → 出力」が明確か
- [ ] 1関数1責務になっているか
- [ ] エラーケース（ファイルが無い・形式が不正・入力が空）を最低1つ扱えているか

**② 道具の良し悪し** ［ドリルの主レンズ］

- [ ] イディオム（その言語らしい書き方）になっているか
- [ ] 計算量（Big-O）に無駄はないか
- [ ] データ構造の選択は妥当か（list / dict / set など）

**③ 可読性・構造（craft）** ［ツールは P1〜・知識不要］

- [ ] 命名が意図を表しているか（変数・関数・引数）
- [ ] 関数の長さ・責務は適切か（SRP）。分割すべき箇所はないか
- [ ] マジックナンバー・重複コードはないか
- [ ] 関心は分離されているか

**④ テスト** ［P2〜・知識依存］

- [ ] 正常系・異常系・境界値の3点があるか
- [ ] テストが実装の写経になっていないか（意味のあるアサーションか）

**⑤ セキュリティ・設計上の安全性** ［P3〜・知識依存］

- [ ] 入力検証はあるか / 信頼境界はどこか
- [ ] 機密情報の扱い（APIキーをコードに埋めていないか、`.env` + `.gitignore`）
- [ ] インジェクション対策（プレースホルダ・エスケープ・検証）
- [ ] **ツールでは検出できない設計上の問題** はないか（権限設計・認可漏れ）

#### 適用マトリクス（どのグループを見るか）

| Phase ＼ Track | ドリル（薄め）| ツール/プロジェクト（厚め）|
|---|---|---|
| **Phase 1** | ① + ② | ① + ② + ③ + 層2 |
| **Phase 2** | ① + ②（テストのドリルなら ④）| ① + ② + ③ + ④ + 層2 |
| **Phase 3** | ① + ②（OWASPドリルなら ⑤）| ① + ② + ③ + ④ + ⑤ + 層2 |

> **要点**: **ツールはドリルの観点（①②）の上位集合**。そこに craft（③）・設計（層2）を **Phase 1 から**厚く重ねる（だから50〜200行のツールでも甘くならない）。テスト（④）＝P2〜・セキュリティ（⑤）＝P3〜 は **学んでから**問う。ドリルは常に ①② 中心で薄く保ち、過負荷を防ぐ。

### 層2: 最後に自分が問う（ツールは常に・マトリクスの「層2」列）

- なぜこの構造にしたか、自分の言葉で説明できるか
- 設計判断（データ構造・分割・依存の向き）は妥当か
- AIの指摘のうち、納得できないものはどれか。なぜか

## AIへの依頼テンプレート

> 「このコードを次の観点でレビューして。各指摘に **重大度（must / should / nice）と理由** を付けて。
> 観点: <適用マトリクスで選んだグループのチェック項目を貼る（例: Phase 1 ツール → ①土台 ＋ ②道具の良し悪し ＋ ③可読性・構造 ＋ 層2）>。
> ※ format / lint / 型 / SAST / 依存 はツール（層0）で見ているので指摘不要。」

依頼の前に必ず **自分で同じ観点で自己レビュー** を済ませ、後でAIの指摘との差分を読むこと。
