# コーディング学習ロードマップ（設計経験者向け・週15時間以上）

## 前提と方針

- **対象**: 設計経験はあるが実装経験がほぼない4年目エンジニア
- **ゴール**: ①自分でロジックを組んで実装できる、②AIや他人のコードを読んで正否（品質・セキュリティ）を判断できる
- **言語戦略**: まず **Python を軸に1言語を深く**。Go / TypeScript / Rust に興味がある場合も、最初の3〜4ヶ月はPythonに集中することを強く推奨。
  - 理由: ロジックを組む力・テスト・セキュリティの考え方は言語をまたいで転用できる。複数言語の並行学習は「文法の暗記」に時間が溶けて、肝心の「ロジックを組む練習」が進まない。
  - 2言語目はPhase 4以降に。用途が決まっていないなら、**Go**（CLI・バックエンド、文法がシンプルで2言語目に最適）か **TypeScript**（Web方面）を推奨。**Rust** は所有権など概念の難度が高いため3言語目以降が無難。
- **AIの使い方（全Phase共通ルール）**:
  1. まず自分で書く（汚くてOK）
  2. AIにレビューさせる（「改善点と理由を説明して」）
  3. AIに同じものを書かせて差分を読む
  4. 「なぜそう書くのか」を説明できるまで質問する
  - ※ 先にAIに書かせるのは禁止。順番が命。

週15時間の目安配分: 実装10h / インプット（本・記事・コードリーディング）3h / 振り返り・学習ログ2h

## Phase 0: 環境構築と土台（1週目）

**ゴール: 「書いて、コミットして、pushする」が日常動作になる**

- [ ] Python環境構築（uv または pyenv + venv を推奨）
- [ ] VS Code + 拡張（Python, Ruff）
- [ ] Git基本操作: clone / add / commit / push / branch / merge
- [ ] GitHubに学習用リポジトリ作成（**Public**にする — CodeQLを無料で使うため）
- [ ] 最初のコミット: README.md に学習の目的を書く

> 設計経験者向けメモ: ここで完璧な環境を追求しない。YAGNIの精神で、動いたら次へ。

## Phase 1: ロジックを組む基礎体力（1〜2ヶ月目）

**ゴール: 50〜200行のプログラムを、設計→実装→動作確認まで自力で完走できる**

- 文法学習は最小限（公式チュートリアル or 入門書を1冊、2週間以内に流す）
- 以降はひたすら小さいツールを作る。題材例:
  - ログファイルから特定パターンの行を抽出・集計するスクリプト
  - CSVを読んで整形・集計して出力するツール
  - フォルダ内のファイルを規則に従ってリネームするツール
  - Web APIを叩いて結果を整形表示するCLI
- 各ツールで意識すること:
  - 書く前に「入力→処理→出力」を3行で書き出す（設計力を実装に接続する練習）
  - 関数に分ける。1関数1責務を最初から意識する
  - エラーケース（ファイルがない、形式が不正）を1つは処理する
- 学習項目: 変数・制御構文・関数 / リスト・辞書 / ファイルI/O / 例外処理 / 標準ライブラリ（pathlib, argparse, json, csv）

**マイルストーン: 自分の日常の面倒事を1つ自動化したツールが完成している**

## Phase 2: 「実務で通用するコード」への引き上げ（2〜3ヶ月目）

**ゴール: 可読性・テスト・型を備えたコードが書ける。AIのコードの良し悪しを言語化できる**

- **可読性とリファクタリング**: Phase 1で書いたコードを自分でリファクタリングする
  - 命名の改善 / 関数の分割 / マジックナンバーの排除 / 単一責任原則（SRP）
  - 参考書: 『リーダブルコード』→ 余裕があれば『良いコード/悪いコードで学ぶ設計入門』
- **テスト（pytest）**: 新しく書くツールは必ずテスト付きで書く
  - 正常系・異常系・境界値の3点セット
  - 「AIが書いたコードにテストを書いて検証する」演習もここで
- **静的チェックの導入**: Ruff（lint + format）、mypy or pyright（型チェック）、型ヒントを常用する
- **コードリーディング**: 小さめのOSS（標準ライブラリや小規模CLIツール）を読み、「なぜこう書くのか」をメモする
- **GitHub Actions入門①**: push時に pytest + Ruff が自動実行されるCIを自分で書く（ci.yml）
- **AIプロダクトオーナー方式を開始**（このPhase後半から）: 自分のツールに対してAIにチケットを切らせる週次フローを回し始める（冒頭の「AIとの役割分担」参照）

**マイルストーン: テスト・型・CI付きのツールが1本ある。AIのコードに対して改善点を3つ指摘できる。AI発行のIssueをPRで閉じるサイクルが1周している**

## Phase 3: セキュリティを意識したコード（3〜4ヶ月目）

**ゴール: OWASP Top 10 を足場に、コードの脆弱性を見抜き・直せる**

- **OWASP Top 10 を1項目ずつ「壊して直す」**（週1〜2項目ペース）:
  1. 攻撃の仕組みを学ぶ
  2. わざと脆弱なコードを書く
  3. 実際に攻撃文字列で壊れることを確認する
  4. 安全な書き方に直す（プレースホルダ、エスケープ、検証など）
  5. ツールが両者をどう判定するか確認する
- 優先度の高い項目: SQLインジェクション / XSS / アクセス制御の不備 / 機密情報の扱い（APIキーをコードに埋めない、.env + .gitignore）/ 安全でない依存関係
- **ツール導入**:
  - ローカル: Bandit（Python向けSAST）、Semgrep
  - GitHub: **CodeQL（Code Scanning）をデフォルトセットアップで有効化** → わざと脆弱なPRを出してアラートを確認 → 修正してアラートが消えるのを確認
  - Dependabot（依存パッケージの脆弱性通知）も有効化
- **GitHub Actions入門②**: CodeQLのワークフローYAMLを読み、トリガー条件を理解する
- 演習環境: OWASP Juice Shop（意図的に脆弱なアプリ）で攻撃側の視点を体験
- 設計力の接続: 各演習の最後に「ツールでは検出できない設計上の問題はないか（権限、信頼境界）」を自問する → 簡易な脅威モデリングへ

**マイルストーン: CodeQL + テストCIが動くリポジトリ運用が定着。脆弱コードと修正版のペアが5項目分以上ある**

## Phase 4: 統合プロジェクト（4〜6ヶ月目）

**ゴール: 設計〜実装〜テスト〜セキュリティ〜CIまで一気通貫の「見せられる」成果物を作る**

- 題材例（興味が湧くものを1つ。まだ用途未定なら a を推奨）:
  - a. 多機能CLIツール（例: 学習ログ集計、ファイル整理、API連携ツール）
  - b. FastAPIで小さなWeb API（DB付き）→ SQLインジェクション対策やバリデーションを実地で
  - c. LLM APIを使った小ツール（AI時代のスキルと実装練習を同時に）
- 必須要件:
  - **開発は全面的に「AIプロダクトオーナー方式」で進める**（チケット発行→質疑→実装→自己検収のサイクル。冒頭の「AIとの役割分担」参照）
  - README（目的・使い方・設計の意図を書く）
  - テストカバレッジを意識した pytest
  - 型ヒント + Ruff + mypy をCIで強制
  - CodeQL + Dependabot 有効
  - 簡易脅威モデリング（何を守るか、信頼境界はどこか）をdocsに1枚書く
- 並行して: 2言語目（Go or TypeScript）の学習を開始してもよい。Phase 1相当を圧縮して回す（2言語目は速い）

**マイルストーン: 第三者（転職先の面接官を想定）に見せられるリポジトリが1つ完成**

## Phase 5 以降（6ヶ月目〜・任意）

- 2言語目の深掘り（Go: 並行処理・Webサーバ / TypeScript: フロント or Node）
- Rustに挑戦（所有権・borrow checker。低レイヤやCLIに興味があれば）
- セキュリティ深化: 脅威モデリング手法（STRIDE）、セキュアコーディング規格、CTF（picoCTF等）
- OSSへの小さなコントリビュート（ドキュメント修正からでOK）

# 学習用リポジトリの構成案

## 方針

- **リポジトリは2つに分ける**: ①日々の練習・演習用の「学習リポジトリ」、②Phase 4の「プロジェクトリポジトリ」（成果物として独立させ、見せられる品質にする）
- 学習リポジトリは **Public** 推奨（CodeQLが無料で使える + 公開前提だと機密情報管理の練習になる）
- コミットメッセージも練習対象（「何をなぜ変えたか」を書く）

## ① 学習リポジトリ（例: `coding-practice`）

```
coding-practice/
├── README.md                  # 学習の目的・ロードマップ・進捗
├── .gitignore                 # .env, __pycache__ などを除外
├── pyproject.toml             # 依存関係・Ruff/mypy設定を一元管理
├── .github/
│   └── workflows/
│       ├── ci.yml             # pytest + Ruff + mypy（Phase 2で追加）
│       └── codeql.yml         # CodeQL（Phase 3で追加 / デフォルトセットアップなら不要）
├── docs/
│   ├── learning-log/          # 週次の学習ログ（YYYY-WW.md）
│   └── notes/                 # 概念メモ（例: srp.md, sql-injection.md）
├── exercises/                 # 小さな演習・ドリル
│   ├── 01_basics/             # Phase 1: 文法・小スクリプト
│   ├── 02_refactoring/        # Phase 2: リファクタ前後をペアで残す
│   ├── 03_testing/            # Phase 2: pytest演習
│   └── 04_security/           # Phase 3: 脆弱版と修正版をペアで残す
│       ├── sql_injection/
│       │   ├── vulnerable.py
│       │   ├── fixed.py
│       │   └── README.md      # 何が問題で、どう直したか
│       └── xss/ ...
├── tools/                     # Phase 1〜2で作る実用ミニツール群
│   ├── log_analyzer/
│   │   ├── __init__.py
│   │   ├── main.py
│   │   └── tests/
│   └── csv_summary/ ...
└── tests/                     # 共通テスト（tools配下に置く形でも可）
```

### 運用ルール（推奨）

1. **作業はブランチ + Pull Request で行い、自分でマージする**
   - PRにすることでCI・CodeQLの指摘がレビューコメントとして付き、実務のフローがそのまま練習になる
2. **ツール開発はIssue駆動にする（Phase 2後半〜）**: AIがPO役として発行したチケットをIssueに登録し、仕様の質疑もIssueコメントに残し、PRで閉じる（「AIとの役割分担」参照）。質疑の記録は後から「仕様の曖昧さにどう気づいたか」の振り返り材料になる
3. **脆弱コードは `04_security/` 内に隔離し、READMEに「意図的に脆弱」と明記**
4. **週1回、docs/learning-log/ に「やったこと・学んだこと・次にやること」を書く**
5. **AIに書かせたコードを採用した場合は、コミットメッセージかコメントにその旨と「自分が検証した内容」を残す**

## ② プロジェクトリポジトリ（Phase 4で作成、例: `log-pilot` など固有名）

```
log-pilot/
├── README.md                  # 目的・インストール・使い方・設計意図
├── pyproject.toml
├── .github/workflows/         # ci.yml + codeql.yml
├── docs/
│   ├── design.md              # 設計判断の記録（ADR的に）
│   └── threat-model.md        # 簡易脅威モデリング
├── src/
│   └── logpilot/              # src レイアウト（実務で一般的）
├── tests/
└── .env.example               # 必要な環境変数の雛形（実値は置かない）
```

# 週次の回し方テンプレート（15時間の例）

| 曜日 | 内容 | 時間 |
|------|------|------|
| 週初め | AIにチケットを発行させIssue登録 → 仕様の質疑 | 1h |
| 平日×4 | 実装（ドリル or Issue対応）+ AIレビューの差分読み | 2h×4 |
| 週末1 | インプット（本・OSSリーディング・セキュリティ学習） | 3h |
| 週末2 | 受け入れ条件で自己検収 → PRマージ → 学習ログ記入 | 3h |

# 詰まったときの指針

- 30分悩んだらAIに「答え」ではなく「ヒント」を求める（「答えは言わずに、どこを疑うべきかだけ教えて」）
- エラーは消す前に読む。エラーメッセージを翻訳・解説させるのは良いAIの使い方
- 完璧主義に注意。動く→読みやすく→安全に、の順で良い
