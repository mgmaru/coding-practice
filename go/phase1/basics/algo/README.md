# algo — アルゴリズム＆データ構造ドリル

「正しさが微妙で、書かないとバグる」かつ「その考え方が実務／OSS で繰り返し出てくる」——その条件を両方満たすアルゴリズムだけを、自力実装で習得するドリル。全12問（Tier 1〜3 の10問＋Tier 4 の2問）。

> 全体の学習方針（Tier 0〜4 のロードマップ・教材・AIの使い方）は [ROADMAP.md](./ROADMAP.md) にあります。この README は、その中の Tier 1〜3 を「手を動かす課題」に落としたものです。

---

## このドリルの目的

- **第一目的は「自分で正しいロジックを組み立て、書けるようになる」こと。** [collections](../collections/) で組み込みコレクションの手の速さは鍛えた。次は、正しさを自分で保証する手つき（不変条件・境界・計算量）を鍛える。
- **「正しいアルゴリズムの理解」が主、「自作実装」はその検証手段。** 実務で自作ソートやヒープを書くことはまずない。ここで実装するのは「理解したつもり」を潰すため。[collections/notes.md](../collections/notes.md) の #14 移動平均で詰まったのは、概念ではなく「境界を正しいロジックに落とす」部分だった。それを書いて炙り出す。
- **実装対象を絞る。** 全ソートの網羅（バブル・選択の写経）はしない。転移しない反復は避け、`二分探索 / 尺取り / 分割統治 / ヒープ / ハッシュ表 / Union-Find` のように「考え方が実システムに再登場するもの」に時間を寄せる。
- **各問に「実システムでの顔」を書いてある。** これが「実務のロジック構築に繋がるのか」への答え。実装しただけで終わらせず、`notes.md` に転移メモを1行残すことで、「アルゴリズムを1個書いた」を「どの構造・どのロジックが要るか判断できる」に変える。

**設計力（構造の判断）は主目的ではない。** それは [tools/](../../tools/) で CLI を作りながら別途鍛える。ここはあくまでロジック構築の反復。

---

## 進め方（1問あたり）

collections の回し方（TDD → 自力実装 → AIレビュー → notes.md）に、**前後2ステップを足す**。この2つが「写経で終わらせない」ための芯。

1. **【追加】まず理解する。** けんちょん本／図で、その解法の **不変条件**（ループの各時点で常に成り立つ性質）と **計算量** をなぞる。例: 二分探索なら「答えが存在するなら、それは常に探索範囲 `[lo, hi)` の中に居る」。
2. **テストを先に書く。** 入力／出力例と、下に列挙した **境界条件**（空・1件・重複・見つからない 等）をケースにする。
3. **自力実装する。** ただし手を動かす前に、**不変条件をコメントで宣言してから**書く。AI に実装させない（[ROADMAP.md](./ROADMAP.md) のルール1）。
4. **AIレビューさせる。** 「**私の実装が壊れる反例を作って**」「**なぜこの構造でないとダメか説明して**」の2つを必ず聞く（ルール3・4）。誤った理解の固定化を潰す。
5. **【追加】転移メモを残す。** `notes.md` に「この考え方は実システムのどこに出るか」を1行。これが実務への橋。

## Tier 1 — 不変条件で正しさを詰める

境界（off-by-one）で壊れやすい題材。「探索範囲」を不変条件として言語化してから書く練習。

### 1. 二分探索
昇順ソート済みの配列から目的値の位置（インデックス）を O(log n) で求める。無ければ `-1`。

- 狙い: 探索範囲を不変条件（「答えがあるなら常にこの範囲内」）として保ちながら半分に絞る。off-by-one を潰す。
- 実システムでの顔: ソート済みデータ全般の検索。DB インデックス探索の基礎。
- 入力: `a = [1, 3, 5, 7, 9, 11]`, `target = 7`
- 出力: `3`
- 境界:
  - 見つからない: `target = 4` → `-1`
  - 先頭 / 末尾: `target = 1` → `0`, `target = 11` → `5`
  - 空配列: `[]` → `-1`
  - 1要素: `a = [5], target = 5` → `0` / `target = 3` → `-1`
- 補足: `mid` は `lo + (hi-lo)/2` で求める（`(lo+hi)/2` はオーバーフローの温床）。重複要素があるとき「どのインデックスを返すか」は基本形では不問だが、最左／最右を返す派生も余裕があれば。

### 2. 答えで二分探索（整数平方根）
非負整数 `n` に対し、`k*k <= n` を満たす最大の整数 `k`（＝ `floor(sqrt(n))`）を二分探索で求める。標準ライブラリの `sqrt` は使わない。

- 狙い: 配列ではなく **答えの値そのもの** を二分探索する型（めぐる式）。判定 `k*k <= n` が `k` について単調（ある境界まで真、その先すべて偽）なのが核。
- 実システムでの顔: 「条件を満たす最小／最大の閾値」を求める汎用テク。容量計画・レート制限のしきい値決定など、単調な判定関数を持つ問題すべて。
- 入力: `n = 26`
- 出力: `5`（`5*5 = 25 <= 26 < 36 = 6*6`）
- 境界:
  - `n = 0` → `0`
  - `n = 1` → `1`
  - 完全平方数: `n = 4` → `2`, `n = 25` → `5`
  - 大きな `n`: `k*k` が溢れないか注意（`k <= n/k` の形に書き換える手もある）
- 補足: 一般化すると「単調な判定関数 `ok(x)` の、真と偽の境界を二分探索で探す」。この問題ではその `ok` が `k*k <= n`。

### 3. 尺取り法（可変長ウィンドウ）
正の整数の配列 `a` と正の整数 `target`。**和が `target` 以上**になる**連続部分列**のうち、最短の長さを返す。存在しなければ `0`。

- 狙い: 右端を伸ばして条件を満たしたら左端を縮める。各要素は高々2回しか触られず O(n)。#14 移動平均（固定幅の窓）の、幅が可変になった発展形。
- 実システムでの顔: ログ／ストリームの区間集計、「直近◯◯を満たす最小区間」系のクエリ前処理。
- 入力: `a = [2, 3, 1, 2, 4, 3]`, `target = 7`
- 出力: `2`（部分列 `[4, 3]`）
- 境界:
  - どの部分列も届かない: `a = [1, 1, 1], target = 100` → `0`
  - 1要素で満たす: `a = [10], target = 7` → `1`
  - 空配列: `[]` → `0`
- 補足: **「正の整数」という前提が尺取り法の単調性を保証する**（右端を伸ばすと和は増える／左端を縮めると和は減る）。負数が混じるとこの単調性が崩れて尺取りは使えない。この前提を必ずテスト仕様のコメントに書くこと。

## Tier 2 — 分割統治と正しい再帰

「停止条件」と「部分問題への分解」を正しく書く練習。再帰のスタック深さも意識する。

### 4. マージ（2つのソート済み列を統合）
ソート済みの2本の配列を、1本のソート済み配列に統合する。O(n + m)。

- 狙い: 2本のインデックスを進めながら、常に小さい方を取る。マージソートと外部ソートの心臓部を単体で。
- 実システムでの顔: 外部ソート（メモリに載らないデータ）、ソート済みストリーム／SSTable のマージ。
- 入力: `a = [1, 3, 5, 7]`, `b = [2, 4, 6]`
- 出力: `[1, 2, 3, 4, 5, 6, 7]`
- 境界:
  - 片方が空: `a = [], b = [1, 2]` → `[1, 2]`
  - 重複: `a = [1, 1], b = [1]` → `[1, 1, 1]`
  - 長さが違う（上の基本例）
- 補足: 同値のとき `a` 側を先に出すか `b` 側を先に出すかで **安定性** が決まる。どちらか決めてテストに揃える（`a` 優先なら安定）。不変条件は「`a[:i]` と `b[:j]` は既に出力済み」。

### 5. マージソート
配列を半分に分割 → 各半分を再帰的にソート → #4 でマージ。分割統治の原型。

- 狙い: 停止条件（長さ ≤ 1）と分割 → 統治 → 統合の型。安定・O(n log n)・最悪でも O(n log n)。
- 実システムでの顔: 安定ソートの原型（`sort.SliceStable`（collections #8）の内部）。
- 入力: `[5, 2, 8, 1, 9, 3, 7, 4, 6]`
- 出力: `[1, 2, 3, 4, 5, 6, 7, 8, 9]`
- 境界:
  - 空: `[]` → `[]`
  - 1要素: `[5]` → `[5]`（停止条件）
  - 重複あり: `[3, 1, 2, 3, 1]` → `[1, 1, 2, 3, 3]`
  - 既ソート / 逆ソート
- 補足: 非破壊（元を壊さず新スライスを返す）か破壊的かを決めて、テストと揃える（collections #8 の破壊／非破壊の議論と地続き）。`mid = len/2`。

### 6. quickselect（k番目に小さい値）
配列から、小さい方から `k` 番目（`k = 1` が最小、1-indexed）の値を、全ソートせずに平均 O(n) で求める。

- 狙い: partition（ピボットで大小2つに分ける）を書き、`k` がどちら側かで **再帰する側を1つに絞る**。クイックソートと違い片側だけ潜る。
- 実システムでの顔: 全ソート不要な Top-K・中央値・パーセンタイル算出。
- 入力: `a = [7, 2, 9, 1, 5, 3]`, `k = 4`
- 出力: `5`（ソートすると `[1, 2, 3, 5, 7, 9]`、4番目は `5`）
- 境界:
  - `k = 1`（最小） / `k = len(a)`（最大）
  - `k` が範囲外（`0` や `len+1`）→ 仕様を決める（エラー or panic）
  - 重複値: `a = [3, 3, 3], k = 2` → `3`
- 補足: 最悪 O(n²)（毎回偏るピボットを引く場合）になる点を notes に1行。破壊的に並べ替えてよいか決める（元配列を壊すなら仕様に明記）。

## Tier 3 — どの構造を選ぶか（構造の中身を書く）

「map で足りるのか、ヒープが要るのか」を、中身を書くことで body で理解する。collections で使った `map` / `sort` の正体。

### 7. スタック／キュー
slice でスタック（LIFO）とキュー（FIFO）を実装し、push / pop / peek / 空判定を O(1)（償却）で。スタックの動作確認として **括弧の対応チェック** を書く。

- 狙い: 「直近の未処理を後入れ先出しで管理する」典型。スタックが自然に嵌まる問題を体で覚える。
- 実システムでの顔: 呼び出しスタック、ジョブキュー、式の評価、DFS の明示スタック化。
- 入力 → 出力（括弧チェック。対応が取れていれば `true`）:
  - `"([]{})"` → `true`
  - `"([)]"` → `false`（種類が交差）
  - `"("` → `false`（閉じられていない）
  - `""` → `true`（空は対応済みとみなす）
  - `")"` → `false`（閉じが先）
- 補足: **キューを slice の先頭 pop（`q = q[1:]` や先頭削除）で書くと O(n) になる罠**（先頭を消すと全要素シフト、または解放されないメモリが伸び続ける）。head インデックスを持つ／リングバッファ／`container/list` などの選択肢を1行残す。

### 8. 二分ヒープ → Top-K 再実装
配列表現の二分ヒープ（push / pop が O(log n)）を実装し、それを使って **collections #15 の Top-N をヒープで解き直す**。

- 狙い: 「サイズ K の min-heap を保ち、全要素を流し込む。K を超えたら根（＝K個中の最小）を捨てる」で、上位 K を O(n log K) で得る。全ソート O(n log n) との差を体感し、#15 で残した「ヒープ／部分ソートという選択肢」を回収する。
- 実システムでの顔: スケジューラ（優先度付きキュー）、レート制限、ストリームからの Top-K 抽出。
- 入力: 頻度 `{"a": 5, "b": 2, "c": 8, "d": 1, "e": 7}`, `K = 3`
- 出力: `[("c", 8), ("e", 7), ("a", 5)]`（頻度の多い順）
- 境界:
  - `K >= 要素数`: 全件を多い順で返す
  - `K = 0` → 空
  - `K < 0` → 仕様を決める（空 or エラー）
  - 同頻度のタイブレーク: #15 と同じく **頻度が同じなら名前の昇順**
- 補足: 「上位 K が欲しいのに、なぜ max-heap でなく min-heap か」を自分の言葉で説明できること（根＝捨てる候補＝今保持している K 個の最小、を追い出していく）。配列表現の親子インデックス（親 `(i-1)/2`、子 `2i+1` / `2i+2`）を正確に。**ヒープの比較関数を、出力の順序規則（頻度→名前）と整合させる**こと。整合していないと同頻度の境界で取りこぼす。最後にヒープに残った K 個を多い順に整えてから返す。

### 9. ハッシュ表（チェイン法）
`map` の正体を自分で書く。バケット配列＋各バケットに連結リスト（or slice）で衝突を吸収し、要素が増えたらリサイズ（rehash）する。

- 狙い: ハッシュ関数・衝突解決・負荷率・リサイズという「`map` が内部でやっていること」を実装する。collections #15 で残った「map と構造体の使い分け」がここで腑に落ちる。
- 実システムでの顔: `map` / `HashMap` そのもの。最頻出のデータ構造。
- API: `Put(key string, val int)` / `Get(key string) (int, bool)` / `Delete(key string)`
- 入力（操作列）→ 出力:
  - `Put("a", 1)`, `Put("b", 2)`, `Put("a", 3)` の後: `Get("a")` → `(3, true)`（上書き）, `Get("b")` → `(2, true)`, `Get("z")` → `(0, false)`
  - さらに `Delete("a")` の後: `Get("a")` → `(0, false)`
- 境界:
  - 存在しないキーの `Get` → `(0, false)`（collections #7 の `v, ok := m[k]` と地続き）
  - 同じキーの上書き（要素数は増えない）
  - 削除後の再取得
  - **衝突するキー**（意図的に同じバケットに落ちる2キー）で両方引けること
  - **リサイズをまたいでも** 全キーが引けること
- 補足: ハッシュ関数は自前の簡単なもの（各文字コードの多項式ローリング、FNV 風など）でよい。**負荷率（load factor）の閾値**を決め、超えたらバケット数を倍にして全要素を rehash。「衝突がなぜ避けられないか（鳩の巣原理）」を1行。

### 10. Union-Find（素集合）
`n` 個の要素の素集合を管理し、「同じグループか？」と「グループ併合」をほぼ O(1)（アッカーマン逆関数）で。経路圧縮＋ランク（or サイズ）併合。

- 狙い: `Find`（代表元）で経路圧縮、`Union` でランク併合という2つの最適化を書く。木を平らに保つ発想。
- 実システムでの顔: 連結性判定、クラスタリング、最小全域木（Kruskal）、「同じ集合か」を高速に問う場面。
- API: `Find(x) int`（代表元） / `Union(x, y)` / `Same(x, y) bool`
- 入力（要素 0..4、操作列）→ 出力:
  - `Union(0, 1)`, `Union(2, 3)`, `Union(1, 2)` の後: `Same(0, 3)` → `true`, `Same(0, 4)` → `false`
- 境界:
  - 自分自身との `Union(1, 1)`（何も起きない）
  - 既に同じグループの `Union`（何も起きない）
  - 経路圧縮の前後で `Same` の結果が変わらない
- 補足: 経路圧縮（`Find` のとき通ったノードの親を根へ張り替え）とランク／サイズ併合は片方だけでも動くが、両方でほぼ定数になる。連結成分の個数を数える応用も1行。

## Tier 4 — グラフ探索（次フェーズ）

Tier 1〜3（特に #7 キュー・#8 ヒープ）が終わってから。依存関係・ネットワーク・データフローはすべてグラフ。

### 11. BFS（重みなし最短路）
隣接リストで表したグラフを幅優先探索し、始点から終点までの **最短距離（辺の本数）** を返す。到達不能なら `-1`。キュー（#7）を使う。

- 狙い: 「先に見つけた＝辺数最小」なので、重みなしグラフでは BFS がそのまま最短路になる。訪問済み管理を正しく。
- 実システムでの顔: 探索全般、最短ホップ数、依存の到達可能性。
- 入力: 頂点 `0..5`、無向辺 `{0-1, 0-2, 1-3, 2-3, 3-4, 4-5}`、`start = 0`, `goal = 5`
- 出力: `4`（例: `0→2→3→4→5`、辺4本）
- 境界:
  - 到達不能 → `-1`
  - `start == goal` → `0`
  - 非連結グラフ
- 補足: **訪問済みフラグは enqueue した時点で立てる**（dequeue 時だと同じ頂点が重複して積まれる）。visited が無いと無限ループ。

### 12. DFS＋トポロジカルソート（閉路検出）
有向グラフ（依存関係）の、辺 `u→v` すべてで `u` が `v` より前に来る順序を1つ求める。閉路があれば「順序づけ不能」を報告する。

- 狙い: 依存解決の順序づけと、閉路（循環依存）の検出。DFS の帰りがけ順の逆、または Kahn 法（入次数0から削る）。
- 実システムでの顔: ビルド依存、マイグレーションの適用順、タスクスケジューリング（DAG）、デッドロック検出。
- 入力（DAG）: 有向辺 `A→B`, `A→C`, `B→D`, `C→D`
- 出力: 制約を満たす順序の一例 `[A, B, C, D]`（`A` が `B,C` より前、`D` が `B,C` より後）
- 閉路の例: `A→B`, `B→C`, `C→A` → 「閉路あり（順序づけ不能）」
- 境界:
  - 閉路の検出
  - 孤立頂点（辺を持たない頂点も出力に含める）
  - **妥当な順序が複数ある**（一意でない）
- 補足: 出力が一意でないので、**テストは完全一致で検証しない**。「全ての辺 `u→v` で `u` が `v` より前にあるか」を検証する（collections #4 の「map は順序非決定だから完全一致に頼らない」と同じ発想）。

## Go で自力実装するときの注意

collections で踏んだ罠の続き。実装前に一度目を通す。

| 論点 | 注意 |
| --- | --- |
| オーバーフロー | `mid = lo + (hi-lo)/2`（`(lo+hi)/2` は避ける）。#2 の `k*k` も溢れに注意（`k <= n/k` へ書き換え可）。 |
| 再帰の深さ | マージソート（#5）・DFS（#12）はスタックを消費。深い入力で落ちないか。必要なら明示スタックで反復化。 |
| append の償却 | 事前に `make([]T, 0, n)` で容量を見積もる（collections #10 / #11 で学んだ）。 |
| 破壊 / 非破壊 | ソート・quickselect は元を壊すか決めて仕様に明記（collections #8）。 |
| `v, ok := m[k]` | 存在判定はゼロ値と区別する（collections #7）。ハッシュ表 #9 の `Get` の契約そのもの。 |
| まず具体型で | `int` / `string` で正しく書いてから、必要ならジェネリクスへ。最初から一般化して詰まらない。 |
