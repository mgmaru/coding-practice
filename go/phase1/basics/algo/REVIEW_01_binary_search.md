# レビュー: `01_binary_search` —「昇順ソート済み配列を O(log n) で探す」。主眼は "分岐の構造（`for{}`＋3つの裸`if`＋各分岐でmid再計算）" と "重複最左を線形スキャンで取ってO(log n)を壊した ―― lower_bound で解ける"

`01_binary_search`（algo ドリル、**Tier 1 の1問目・記念すべき最初のアルゴリズム自作**）のレビュー。
お題は「**昇順ソート済み**配列 `[]int` から `target` の位置を **O(log n)** で求める。無ければ `-1`。境界（空・1件・重複・見つからない・先頭/末尾）を潰す」。README #1 の狙いは **「探索範囲を不変条件として保ちながら半分に絞り、off-by-one を潰す」**。collections で手の速さを鍛えた次の段階 ―― **正しさを自分のロジックで保証する手つき**を作る回。

結論から言うと **アルゴリズムは正当・コードは正しく、緑も信用してよい**。
- **静的な検証**: ループは毎回 `[l,h]` を厳密に狭め（`l` は必ず増える／`h` は必ず減る）、交差したら `-1`。`m` は常に `[l,h]` 内なので範囲外アクセスも無い。**停止するし、落ちない。**
- **動的な検証（反例探し）**: 長さ0〜7の**ランダム昇順配列（重複・負数込み）を約20万本 × ターゲット9通り＝約180万ケース**、線形スキャンの最左オラクルと**全一致**。README ルール「私の実装が壊れる反例を作って」を実際に回した結果、**反例なし**。
- `gofmt` 差分なし・`go vet` クリーン・`-count=3` で 12 サブテスト全緑。

つまり **バグは無い**。今回の主題は「動くコードを、次は "正しいと一目でわかる構造" と "O(log n) を守る最左取得" に引き上げる」こと。柱は3つ:

1. **観点1【②道具・主眼】構造**: `for {}`（無限ループ）＋ **3つの独立した `if`（`else if` でない）** ＋ **各分岐で `m` を再計算**、という組み立て。これは **1イテレーション中に `m` を書き換えて、同じ回の次の `if` が書き換え後の `input[m]` を読む**（＝1回で二度更新される）挙動を生む。**正しさは保てているが、"なぜ正しいか" が自明でない**。二分探索の教科書型 `for lo <= hi { mid := ...; switch }` に載せ替えると、この危うさが構造ごと消える。
2. **観点2【②道具・アルゴリズムの正当性・notes の宿題】重複の最左**: 見つけた後に **`m` から左へ1つずつ線形スキャン**して最左を取っている。これは **全部同じ値の配列で O(n)** ―― せっかくの O(log n) を壊す。notes.md で「二重ループになって二分探索の意味がない気がした」と自分で言語化した詰まりは、**lower_bound（境界二分探索）** で線形スキャンなしに O(log n) のまま解ける。**今回いちばん学びの大きい点。**
3. **観点3【②道具・README が明示した約束】mid の式**: `m = (l+h)/2`。README の「Go で自力実装するときの注意」は **`mid = lo + (hi-lo)/2`（`(lo+hi)/2` はオーバーフローの温床）** と名指しで指定している。ここは**課題の指定に反している**（実害は極端な巨大配列だけだが、この回の主題＝オーバーフロー/off-by-one 規律そのもの）。

> 大原則（review-rubric）: ①正しく動くか ②道具の良し悪し（イディオムか・計算量に無駄はないか・不変条件を保てているか）③テストは妥当か。
> 前提: `go test -run TestGetTargetIndex ./phase1/basics/algo` が **12 サブテスト × 3回 緑**。`gofmt` 差分なし・`go vet` クリーン。さらに**約180万ケースの差分テストで反例なし**。

## 観点1【②道具・主眼】分岐の構造 ―― `for{}`＋3つの裸`if`＋各分岐でmid再計算 は「一度に二度更新」する

今回いちばん構造を作り替える価値のある指摘。ループ本体はこうなっている:

```go
m = (l + h) / 2
for {
	if target == input[m] { ... return m }        // ①
	if target > input[m] {                          // ②（else if でない）
		l = m + 1
		m = (l + h) / 2                             //   ここで m を書き換える
		if l > h { return -1 }
	}
	if target < input[m] {                          // ③ ←②で書き換えた m を読む！
		h = m - 1
		m = (l + h) / 2
		if h < l { return -1 }
	}
}
```

問題は **②と③が `else if` でなく独立した `if`** で、しかも **②の中で `m` を書き換えてから③が `input[m]` を読む**こと。つまり**同じ1イテレーションで②と③が両方発火し、`m` が2回更新される**ことがある。

### 実際に二度更新される具体例（target=6, `[1,3,5,7,9,11]`）

```
初期     l=0 h=5 m=2  input[2]=5
 ②発火:  6>5  → l=3, m=(3+5)/2=4  input[4]=9   (l>h? no)
 ③発火:  6<9  → h=3, m=(3+3)/2=3  input[3]=7   (h<l? no)   ← 同じ回で②の後に③も走った
次の回   l=3 h=3 m=3  input[3]=7
 ③発火:  6<7  → h=2, m=2                         (h<l? 2<3 yes) → return -1  ✅
```

結果は正しい（6 は無い→ -1）。**なぜ壊れないか**は追える: ②の後 `m` は必ず右へ動く（`l=旧m+1` なので `input[新m] >= input[旧m]`）。もし `target < input[新m]` なら target は `(旧m, 新m)` の間 ―― だから③の `h=新m-1` は**たまたま正しい絞り込み**になる。実際、静的にも約180万ケースでも破綻しない。

**だが「たまたま正しい」は道具として弱い。** 読み手（未来の自分）は「②で更新した `m` を③が読むのは意図か？バグか？」を毎回考えさせられる。二分探索が off-by-one の温床なのは、まさにこの種の「1イテレーションで状態がいくつ動くか」が曖昧になるから。**"正しいと一目でわかる" 構造**に載せ替えるべき。

### 教科書型: `for lo <= hi` ＋ mid は先頭で1回 ＋ 単一ディスパッチ

```go
func getTargetIndexBinarySearch(input []int, target int) int {
	// 不変条件: target があるなら、そのインデックスは常に閉区間 [lo, hi] の中に居る。
	lo, hi := 0, len(input)-1
	for lo <= hi {                    // 範囲が空になったら抜ける（空配列 len-1=-1 でも即 false）
		mid := lo + (hi - lo) / 2     // ★ mid は各周の先頭で1回だけ・オーバーフロー安全
		switch {
		case input[mid] == target:
			return mid
		case input[mid] < target:
			lo = mid + 1              // 左半分（mid 含む）を捨てる
		default: // input[mid] > target
			hi = mid - 1              // 右半分（mid 含む）を捨てる
		}
	}
	return -1
}
```

この型が今の実装より優れている点:
- **`for lo <= hi` が停止条件を一手に握る**。今の実装は `-1` を **2箇所（②と③の中）に散らして**いて、しかも分岐の内側。空配列ガード `if n==0` も**この条件に吸収される**（`hi=-1 < lo=0` で即 false → `-1`）ので、専用の早期 return が要らなくなる。
- **`mid` は先頭で1回だけ**計算。「1イテレーションで状態がいくつ動くか」が `lo` か `hi` の**どちらか一方**に確定する。観点1冒頭の「二度更新」が構造的に起きない。
- **`switch`（または `else if`）で3分岐が排他**。裸の `if` 3連は「②の後に③」を許すが、`switch` は1つ選んだら抜ける。
- `n := len(input)` の**事前退避も不要**（`len` は O(1)、後述・観点5）。

> 合言葉（この回で作る芯）: **二分探索は「`for lo <= hi` ＋ mid を先頭で1回 ＋ 3分岐は排他（switch/else if）」の型で書く。`-1` は1箇所（ループを抜けた後）。`for{}`＋散らした return＋分岐内 mid 再計算は、"一度に状態がいくつ動くか" を曖昧にして off-by-one を呼ぶ。**

### `continue` を足せば直る ―― でも「排他は自分で守る」より「構文に守らせる」方が事故らない（今回の核心の学び）

レビュー中の指摘: **「②の末尾に `continue` を書けば、`m` を更新した直後にループ先頭へ戻れて、③は評価されないのでは？」** ―― これは**完全に正しい**。実際に確かめた（`continue` 版も約180万ケースで反例なし）:

```go
if target > input[m] {
	l = m + 1
	m = (l + h) / 2
	if l > h { return -1 }
	continue          // ★ ここで先頭へ。③（target < input[m]）を評価させない
}
if target < input[m] {
	h = m - 1
	m = (l + h) / 2
	if h < l { return -1 }
	// ③は body の末尾なので continue は有っても無くても同じ
}
```

`continue` 有りだと **1周につき更新は必ず1回**になり、観点1の「二度更新」は消える。これは二分探索の「1周＝1ステップ」という素直な形で、教科書型に一歩近づく。**現状版（`continue` 無し）にバグは無いが、`continue` 版は "なぜ正しいか" を追わなくてよくなる**分だけ強い。

ここに、この回でいちばん持ち帰るべき学びがある ―― **今回の「二度更新」は、まさに `continue` が "無かった" ことで起きている**。つまり:

> **排他性を「制御フロー（`continue`）」で守る設計は、`continue` を1個書き忘れた瞬間に、今回とまったく同じ二度発火バグに戻る。** `continue` のつけ忘れは実際に過去にもバグを生んでいる、典型的で再発しやすい人為ミス。

これに対し **`else if` / `switch` は "排他" を言語の構文が保証する**。「1つ選んだら他は評価しない」がタダで付いてくるので、**書き忘れる余地そのものが無い**:

```go
switch {                       // 排他は構文が保証 ―― continue の付け忘れが起こり得ない
case input[mid] == target:
	return mid
case input[mid] < target:
	lo = mid + 1
default: // input[mid] > target
	hi = mid - 1
}
```

**notes.md との接続**: notes に「`for{}` に `continue` は不要（終了条件に達しなければ自動でループが回るため）」と書いたのは、`continue` の **"ループを回し直す" 用途**については正しい。だが `continue` には **"今の周の残り（＝兄弟の `if`）を飛ばす" 用途**もあり、②で効くのはこちら。③（body の末尾）の `continue` は前者の意味で確かに不要 ―― **場所によって「要る／要らない」が分かれる**。この2用途を分けて意識できると、`continue` を「なんとなく付ける／消す」から卒業できる。

> 合言葉（今回の核心）: **「3つのうち1つだけ発火」を、`continue` で自分の手で守るのではなく、`else if`/`switch` の構文に守らせる。手で守る設計は "書き忘れ" が事故の入口になる ―― 今回の二度更新も、過去に踏んだ `continue` 付け忘れも、同じ根。構文で排他が保証されるなら、人為ミスの余地が最初から消える。**

## 観点2【②道具・アルゴリズムの正当性・notes の宿題再来】重複の最左は "線形スキャン" でなく "lower_bound" ―― O(log n) を守れる

notes.md の「わからなかったこと」に、この回いちばん大事な一文がある:

> **「重複があった場合に、一番インデックスが小さいものを返す実装がパッと思いつかなかった。mから左に1ずつずらす方法を思いついたが、二重ループになって二分探索で計算量を減らしている意味がないと感じた」**

この直感は**完全に正しい**。今の実装:

```go
if target == input[m] {
	for i := m - 1; i >= 0; i-- {   // ★ m から左へ線形スキャン
		if target == input[i] { m = i; continue }
		break
	}
	return m
}
```

`AllInputSameElementAndIncludedTarget`（`[3,3,3,3,3,3]`, target=3）を通すと、`m=2` から `i=1,0` と**線形に**降りて `0` を返す。**全部同じ値なら最悪 O(n)**。二分探索が O(log n) で効くのに、最後の最左確定で O(n) を足してしまい、**トータル O(n)**。狙い（O(log n)）が半分崩れる。

### 答え: lower_bound（境界二分探索）―― 線形スキャンを二分探索に置き換える

「target と一致する最小インデックス」は、**「target 以上が現れる最初の位置（lower bound）」を二分探索で探す**ことで O(log n) のまま求まる。ミソは **`input[mid] == target` でも即 return せず、`hi` 側を縮めて "もっと左にもあるか" を探し続ける**こと:

```go
func getTargetIndexBinarySearch(input []int, target int) int {
	// 不変条件: 「target 以上が始まる位置」は常に [lo, hi] の中に居る（半開 [lo, hi)）。
	lo, hi := 0, len(input) // ★ 半開区間 [lo, hi)。hi は「まだ未確定」の番兵
	for lo < hi {
		mid := lo + (hi-lo)/2
		if input[mid] < target {
			lo = mid + 1 // mid は target 未満 → 確実に捨てる
		} else {
			hi = mid     // mid は target 以上 → 候補。捨てずに範囲を左へ縮める
		}
	}
	// lo は「target 以上が始まる最初の位置」。そこが target なら最左、違えば不在。
	if lo < len(input) && input[lo] == target {
		return lo
	}
	return -1
}
```

**なぜ最左が取れるか**: ループ終了時 `lo` は「`input[lo] >= target` を満たす最小の `lo`」（= lower bound）。もし target が配列にあるなら、その**最左の出現位置がちょうどここ**。だから `input[lo]==target` なら最左、そうでなければ（`input[lo] > target` か範囲外なら）不在。**線形スキャンが消えて、全部同じ値でも O(log n)**。notes の「二重ループになるのが嫌」を、構造で解消できる。

> 合言葉（notes の宿題への回答）: **「最左（最右）が欲しい」を線形スキャンで足すと O(n) に戻る。`==` で即 return せず境界側（`hi=mid`）を縮め続ける lower_bound にすれば、二分探索1本＝O(log n) のまま最左が取れる。「見つけたら止まる」ではなく「見つけても、もっと端があるか探す」。**

補足（発展・余裕があれば）: 最右（upper bound 系）は「`input[mid] <= target` なら `lo=mid+1`」に変える。lower/upper を書き分けられると、README #1 の「最左／最右の派生」を両方回収できる。

### 実務での顔（転移メモ・README ⑤）

この lower_bound は標準ライブラリそのもの:
- `sort.SearchInts(a, x)` ―― x を挿入できる最小の位置（＝ lower bound）を返す。
- `slices.BinarySearch(a, x)`（Go 1.21+）―― `(index, found)` を返し、`index` は lower bound。

**実務では自作せずこれらを使う**。今回手で書くのは「中で何が起きているか」を潰すため。**notes.md の転移メモに1行**、例えば「lower_bound = ソート済みデータへの範囲クエリ（"x 以上の最初"）／DB のインデックス range scan の基礎。`sort.SearchInts` の正体」を残しておくと、この回が実務に橋渡しされる。

## 観点3【②道具・README の明示指定】mid は `lo + (hi-lo)/2` ―― `(l+h)/2` はオーバーフローの温床（課題が名指しで指定）

```go
m = (l + h) / 2   // ← README「Go で自力実装するときの注意」が避けろと名指しした式
```

README の表にこうある:

> | オーバーフロー | `mid = lo + (hi-lo)/2`（`(lo+hi)/2` は避ける）。 |

`l + h` は、`l` と `h` がともに大きいと `int` の最大値を超えて**負に回り込む**（オーバーフロー）。`lo + (hi-lo)/2` は `hi-lo`（必ず `hi` 以下）を先に半分にしてから足すので、途中でオーバーフローしない。

**実害があるのは `len(input)` が int 上限の半分（64bit で ~4.6×10^18）を超えるときだけ**で、Go の実スライスではまず到達しない。だが**この回の主題はまさに「off-by-one とオーバーフローの規律」**であり、README が名指しで指定した以上、**ここは "実害の有無" ではなく "規律として揃える" 話**。教科書型（観点1・2のコード）に載せ替えれば自然に `lo + (hi-lo)/2` になる。

> 合言葉: **mid は反射的に `lo + (hi-lo)/2`。`(lo+hi)/2` は「今は動く」だけ。二分探索を書く手癖として、溢れない式を指に覚えさせる。**

## 観点4【②道具・設計】`getTargetIndexOriginal`（map版）は O(n)/O(n) で二分探索ではない ―― ただし "オラクル" として超優秀

`getTargetIndexOriginal` は map に「値→最小インデックス」を詰めて引く実装。これ自体は:
- **時間 O(n)・空間 O(n)**。しかも**ソート済みという前提を1ミリも使っていない**（未ソートでも動く）。つまり**二分探索の主眼（ソート済みを活かして O(log n)）とは別物**。ドリルの主役ではない。

…のだが、**捨てるにはもったいない良さ**がある: これは**独立した正しい実装＝オラクル**。実際、今回のレビューで反例を探した約180万ケースの差分テストは、まさに「単純だが確実に正しい実装」と二分探索を突き合わせる手法（**differential / property-based testing**）。`getTargetIndexOriginal` はその役に**そのまま使える**。

**提案**: 2つを別々の固定ケースで検証している今のテストに、**「ランダム昇順配列で両者が一致する」プロパティテストを1本足す**と、手書きケースが見落とす境界（下で述べる観点6の穴）を**自動で**埋められる。map版を「劣った初回実装」で終わらせず「二分探索の番人」に昇格させる発想。

```go
// 例: ランダム昇順配列で original と binary search が必ず一致する
func TestBinarySearch_MatchesOracle(t *testing.T) {
	rng := rand.New(rand.NewSource(1)) // 固定シードで再現可能
	for i := 0; i < 5000; i++ {
		n := rng.Intn(10)
		a := make([]int, n)
		for j := range a { a[j] = rng.Intn(8) - 3 } // 重複・負数を誘発
		sort.Ints(a)
		for target := -5; target <= 5; target++ {
			if getTargetIndexBinarySearch(a, target) != getTargetIndexOriginal(a, target) {
				t.Fatalf("不一致 a=%v target=%d", a, target)
			}
		}
	}
}
```

> 注記: この提案は「map版を残す」前提。もし「algo ドリルとしては二分探索1本に絞りたい」なら map版は削ってよい。ただし**オラクルとして残す価値の方が高い**と考える（“無駄なテストは逆によくない気がする” という notes の不安への答え ―― **オラクル比較は "無駄なテスト" ではなく "手書きケースの穴を埋める本命"**）。

## 観点5【altitude・可読性】宣言スタイルと "len は O(1)"（原則の適用先を取り違えたコメント）

正しさに影響はないが、道具の解像度に関わる3点。

**(1) 退避の原則は正しい ―― ただし Go の `len` は O(1) なので、この原則の "適用対象外"。**
```go
n := len(input) // nは固定値なので、あらかじめ変数に格納しておく（nが大キックなった時にいちいち、lenでサイズを計算すると計算量が爆増するため）
```
このコメントの背景にある原則 ―― **「重い長さ計算をループ条件で毎回呼ぶな」** ―― は**正しく、身につける価値がある**。おそらく C/C++ の **`strlen`** の例で学んだもので、それは**本物の O(n²) 罠**（"Shlemiel the painter" として有名）:

```c
for (int i = 0; i < strlen(str); i++) { ... }  // strlen は毎回 '\0' まで数え直す O(n) → 全体 O(n²)
```

C の文字列は `char*` ＋ 終端 `'\0'` で、**長さを保持しておらず毎回スキャンして数え直す**。だからループ条件で呼ぶと O(n) × n 周 = O(n²)。**ここまでの理解は完全に正しい。**

**ズレは「その原則を Go の `len` に当てはめたこと」1点だけ。** 分かれ目は **「毎回スキャンし直す」か「保持している値を読むだけ」か**:

| 種類 | 例 | 計算量 | ループ条件で毎回呼ぶと |
|---|---|---|---|
| **長さをスキャンし直す** | C の `strlen(char*)` | **O(n)** | **O(n²) ―― これが罠** |
| **長さを保持していて読むだけ** | Go の `len(slice/string/map/chan)`、C++ の `vector::size()` / `string::size()` | **O(1)** | 問題なし |

Go の `len` が O(1) なのは、**スライスが「長さを内部に持った構造体」だから**。スライスの実体は `{先頭ポインタ, len, cap}` の3ワードのヘッダで、`len(input)` は**その `len` フィールドを1回読むだけ**（string は `{ポインタ, len}`、map/chan は要素数フィールドを保持、配列に至っては `len` はコンパイル時定数）。**スキャンは一切走らない**。だから Go では毎周 `len(input)` を書いても O(1) のままで、"爆増" は起きない。

> C++ の補足: 罠になるのは `strlen`（C文字列）と、歴史的に **C++11 以前の `std::list::size()`** くらい。`std::vector::size()` / `std::string::size()` は Go の `len` と同じく **O(1)**（size を内部保持）。つまり「`size()` 系が毎回重い」のではなく、**"数え直す" 関数だけが罠**。

**結論**: `n` に退避すること自体は無害（可読性で有り得る）だが、**コメントの理由づけ「n が大きくなると `len` の計算量が爆増する」は Go の `len` には当てはまらない**。ここで直すべきは「コードより理解」―― **「その `length()` は "数え直す" のか "読むだけ" なのか?」を型ごとに問う**手癖に更新する。`strlen` や自作の「毎回走査するカウント関数」なら退避が効く／Go の `len`・C++ の `vector::size()` なら退避しても複雑度は変わらない（コンパイラも最適化する）。なお教科書型（観点1）では `for lo <= hi` に `len(input)-1` を1回書くだけで `n` の退避すら要らない。
> （余談: 誤字 “大**キック**なった” → “大きくなった”。コメントは未来の自分への手紙なので直す。）

**(2) `var l int; var h int; var m int` → 後で代入、は冗長。**
```go
var l int
var h int
var m int
...
l = 0
h = n - 1
m = (l + h) / 2
```
Go のイディオムは**宣言と初期化をまとめる**: `lo, hi := 0, len(input)-1`。`m`（mid）は**ループ内でしか意味を持たない**ので、教科書型のように `for` の中で `mid := ...` と宣言するのが自然（スコープを最小に）。これは collections で繰り返した「段取りを前に積まない」altitude 掃除と同じ。

**(3) 閉区間 `[lo, hi]` を使うなら、それを宣言に書く。**
スキャフォールドのコメントは半開 `[lo, hi)` だが、実装は閉区間 `[lo, hi]`（`h = n-1`）。**どちらも正解**だが、二分探索の off-by-one 事故は**「途中で区間の約束を取り違える」**ことで起きる。進め方③の「不変条件をコメントで宣言してから書く」は、まさにこの取り違えを防ぐための儀式。実装の頭に一行 ―― 例「// 不変条件: target があるなら常に閉区間 [lo, hi] 内」―― を自分の言葉で書く癖をつけたい。

## 観点6【テストの穴】網羅は厚い。あと2種類の境界と、比較の道具

現状12ケースは手厚い（見つかる/見つからない・先頭/末尾・空・nil・1件×2・重複×2・全同一×2）。良い。足すなら:

- **「全要素より小さい／大きい target」が未カバー**。今の "見つからない" は `target=4`（配列の**内側**の隙間）だけ。`[1,3,5,7,9,11]` に対し **`target=0`（最小未満）→ -1** と **`target=100`（最大超）→ -1** は、`hi` が下限を割る経路 / `lo` が上限を超える経路という**別の off-by-one 経路**を叩く。二分探索でいちばん壊れやすい両端の外側なので1件ずつ欲しい。
  ```go
  {name: "TargetSmallerThanAll", input: []int{1, 3, 5, 7, 9, 11}, target: 0, want: -1},
  {name: "TargetLargerThanAll",  input: []int{1, 3, 5, 7, 9, 11}, target: 100, want: -1},
  ```
- **偶数長・2要素**が未カバー。`mid` の丸め（切り捨て）が効くのは偶数長。`[1,2]` で `target=1→0 / target=2→1 / target=3→-1` を1組。1件・6件はあるが「2件」は mid の左右非対称が出やすい最小ケース。
- **（notes の宿題の回収）ソート済みの負数ケースを復活**。`[1,-3,5,-7,9,-11]` を「未ソートだから」と**丸ごと削除**したのは判断として半分正しく半分もったいない。正しくは「**ソートすればよい**」。`[-11,-7,-3,1,5,9]` で `target=-7→1` を入れると、負数でも比較が壊れないことを固定できる（削除した意図＝二分探索の前提"昇順"は守りつつ、負数カバレッジは取り戻す）。
- **`reflect.DeepEqual` は int 比較には過剰**。返り値は `int` なので `if gotValue != c.want` で十分。`DeepEqual` はスライス/構造体など複合型のための道具で、collections（出力がスライス）から**そのまま持ち込んだ手癖**。int には素の `!=` が読みやすく速い。
- **本命は観点4のオラクル比較**。上の個別ケースを足すより、`getTargetIndexOriginal` との**ランダム差分テスト1本**の方が穴を機械的に塞ぐ（“無駄なテストが不安” への答え ＝ 手で並べるより性質で縛る）。

> `!=` でよい根拠 = 返り値が `int`（順序も構造も無いスカラ）。`DeepEqual` が要るのは「順序込みのスライス」など（`15_top_n` はそちら側）。**型で道具を選ぶ**。
