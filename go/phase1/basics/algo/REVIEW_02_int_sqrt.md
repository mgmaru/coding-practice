# レビュー: `02_int_sqrt` —「答えで二分探索（整数平方根）」。主眼は "`mid == n/mid` は完全平方数ではない（正しい答えを間違った理由で返している）" と "notes の疑問点『(lo,hi] はダメなのか』の実測回答 ―― アリだが mid を天井にしないと n=26 でハングする"

`02_int_sqrt`（algo ドリル、**Tier 1 の2問目**）のレビュー。
お題は「**非負整数 `n`** に対し `k*k <= n` を満たす**最大の整数 `k`**（＝ `floor(sqrt(n))`）を二分探索で求める。標準ライブラリの `sqrt` は使わない」。README #2 の狙いは **「配列ではなく "答えの値そのもの" を二分探索する型（めぐる式）。判定 `k*k <= n` が `k` について単調なのが核」**。#1 が「並んでいるモノを探す」なら、#2 は **「探索対象が最初からどこにも存在しない（答えの候補空間を自分で作る）」** 回。

結論から言うと **アルゴリズムは正当・コードは正しく、緑も信用してよい**。しかも **`01` のレビューで得た学びが、実装に4つはっきり反映されている**（後述）。

## 観点1【①正しさの根拠・最重要】`mid == n/mid` は「完全平方数」ではない ―― 正しい答えを、間違った理由で返している

今回いちばん理解の解像度が上がる指摘。

```go
if mid == n/mid { // 完全平方数
    return mid
}
```

**このコメントは誤り。** 実測で確かめた ―― `n = 2..200000` の範囲でこの早期 return が発火したのは **99,872 件**、そのうち **完全平方数はわずか 446 件（0.45%）**、**99,426 件（99.55%）は完全平方数ではない**:

```
非平方数なのに早期returnした例:
  n=5  → 2   (2*2=4  ≠ 5)
  n=10 → 3   (3*3=9  ≠ 10)
  n=11 → 3
  n=17,18,19 → 4
  n=26 → 5   ← ★ README の例題そのもの。26 は完全平方数ではない
  n=27 → 5
```

**`n=26` のテストケース `{name: "normal", n: 26, want: 5}` が緑なのは、まさにこの「完全平方数コメント」が付いた分岐を通っているから。** 例題が「完全平方数でないケース」の代表なのに、そこを「完全平方数」と書かれた行が処理している。

### では `mid == n/mid` は何を意味するのか

Go の `/` は整数除算（切り捨て）なので `n/mid = floor(n/mid)`。よって:

```
mid == floor(n/mid)
  ⟺ mid <= n/mid < mid+1        （実数の割り算として）
  ⟺ mid² <= n < mid² + mid       （両辺に mid > 0 を掛ける）
```

一方、求める答えの定義は:

```
mid == floor(sqrt(n))
  ⟺ mid² <= n < (mid+1)² = mid² + 2·mid + 1
```

つまり:

| | 条件 | `n` の範囲（mid=3 のとき） |
|---|---|---|
| `mid == n/mid` が真 | `mid² <= n < mid² + mid` | `9 <= n < 12` → n = 9,10,11 |
| `mid == floor(sqrt(n))` | `mid² <= n < mid² + 2mid + 1` | `9 <= n < 16` → n = 9〜15 |

**`mid == n/mid` は `mid == floor(sqrt(n))` の "十分条件だが必要条件ではない"。**
- **十分**（＝ここで `return mid` して正しい）: `mid² <= n < mid²+mid ⊂ mid² <= n < (mid+1)²`。だから**返り値は常に正しい** ✅
- **必要でない**（＝取りこぼす）: `n = 12,13,14,15` のとき答えは 3 だが、この分岐は発火しない。**取りこぼした分は `k` が拾う**（実際 `n=12` は `k=3` 経由で返る）

**まとめ**: この行は「完全平方数を検出する分岐」ではなく **「たまたま早めに答えが確定したときのショートカット」**。約50%の `n` で発火し（`mid` ごとに `2mid+1` 通り中 `mid` 通り）、残り50%は `k` が答えを持つ。**健全（sound）だが不完全（incomplete）なショートカット**。

### 帰結: このショートカットは「無くても正しい」―― 3分岐を2分岐に畳める

早期 return は正しさに**不要**（`k` が全部拾える）。`==` を `<` 側に吸収して `<=` にすると、分岐が3→2 に減る:

```go
if mid <= n/mid {   // mid² <= n → mid は答えの候補。もっと右を探す
    lo = mid + 1
    k = mid
} else {            // mid² > n  → mid は答えになり得ない。捨てる
    hi = mid
}
```

これを **`n = 0 〜 5,000,000` の全数 ＋ `n = MaxInt` で検証 → 不一致 0**。完全に等価。

得られるもの:
- **誤解を招くコメントが消える**（「完全平方数」という説明そのものが不要になる）
- **分岐が2つ＝二分探索の本質（単調な述語 `ok(mid)` の真/偽）と1対1になる**。README が言う「単調な判定関数 `ok(x)` の、真と偽の境界を探す」の `ok` がコード上に `mid <= n/mid` として**1箇所だけ**現れる形
- **除算が減る**（観点6）

> 合言葉（観点1の芯）: **`==` を特別扱いした瞬間、「その `==` は何の同値関係か」を証明する義務が生まれる。今回それは "完全平方数" ではなく "`mid² <= n < mid²+mid`" という中途半端な区間だった。二分探索の述語 `ok(x)` は `<=` ひとつで単調にできる ―― 述語を1本にすれば、証明すべき命題も1本になる。**

## 観点2【notes.md の疑問点への回答】`(lo, hi]` で考えるのはダメなのか? ―― **アリ。ただしそのままだと `n=26` でハングする**

notes.md 2026-07-29 の「疑問点」を全文引用する:

> **半開空間 `[lo, hi)` で考えたが、`(lo, hi]` で考えるのはダメなのか？**
> - `m > n/m` の場合： `hi = m - 1`
> - `m < n/m` の場合： `lo = m`
> - ループの継続条件： `lo < hi`
> - 理由：`m > n/m` の場合に、更新を `hi = m` とすると、見つける整数候補に m が入るが、実際、これは候補とはならないことは自明。なので、`hi = m - 1` としても問題ないのでは？

**問いの立て方も、`hi = m-1` の理由づけも、正しい。** `m > n/m` なら `m` は答えになり得ないので、範囲から外して構わない ―― ここは完全に合っている。**そして「答えは最大の k」だから、候補を残すのは `lo` 側であるべき**、という発想も筋が良い（`[lo,hi)` は "最小の偽" を探す形、`(lo,hi]` は "最大の真" を探す形で、**後者の方が今回の問題には素直**）。

**だが、書かれたとおりに実装すると無限ループする。** 実測（`mid` は床のまま `lo + (hi-lo)/2`、1000反復でハング判定）:

| `n` | 結果 |
|---|---|
| 2 | 🔴 **無限ループ** |
| 3 | OK → 1 |
| 5 | OK → 2 |
| 6 | 🔴 **無限ループ** |
| 8 | 🔴 **無限ループ** |
| **26** | 🔴 **無限ループ**（README の例題） |
| 27 | 🔴 **無限ループ** |
| 10 | OK → 3 |

### 原因: `lo = m` は「lo を前進させない」―― 床の `mid` と組み合わさると停止しない

`mid = lo + (hi-lo)/2` は**切り捨て**なので、`hi = lo + 1` のとき:

```
lo=1, hi=2  →  mid = 1 + (2-1)/2 = 1 + 0 = 1   ← mid == lo
```

ここで `m < n/m` が真だと `lo = m = 1` ―― **`lo` が動かない。`hi` も動かない。継続条件 `lo < hi` は真のまま。** 状態がまったく変化せず、永久に回る。

**トレース（`n = 2`）**:
```
lo=0, hi=2
 周1: m = 0+(2-0)/2 = 1.  n/m = 2/1 = 2.  m < n/m (1<2) → lo = m = 1
 周2: lo=1, hi=2.  m = 1+(2-1)/2 = 1+0 = 1.  m < n/m → lo = m = 1   ← 何も変わらない
 周3: 同上 ... 無限ループ 🔴
```

これは **`01` の追記1（`[7,7,7]` で無限ループ）とまったく同じ根**。notes の「学び」節 4番で自分が書いた原則がそのまま当てはまる:

> **「毎周ちゃんと縮むか（`hi-lo` が減るか）」を必ず確認。**

`[lo, hi)` 側では `hi = mid` でも縮む。なぜなら `lo < hi` のとき床の `mid` は**必ず `mid < hi`** を満たすから。だが `lo = mid` は **`mid == lo` になり得る**ので縮まない。**非対称なのは "床の除算" のせい。**

### 直し: 候補を残す側に `mid` を寄せる ―― 天井の mid

`lo = mid`（候補を残す）を使うなら、`mid` を**天井**にする:

```go
mid := lo + (hi-lo+1)/2   // ★ 天井（+1）。lo < hi のとき必ず mid > lo
```

これで `lo = mid` は必ず前進する。実装するとこうなる:

```go
func intSqrt(n int) int {
	if n < 2 {
		return n // 0→0, 1→1（負は契約外・観点3）
	}
	// 不変条件: 答え floor(sqrt(n)) は常に左開区間 (lo-1, hi] ＝ 実質 [lo, hi] の中に居る。
	//           lo は「真であることが確定した候補」、hi は「まだ偽と分かっていない上限」。
	lo, hi := 1, n
	for lo < hi {
		mid := lo + (hi-lo+1)/2 // ★ 天井。lo = mid が必ず前進するため
		if mid > n/mid {
			hi = mid - 1 // mid² > n → mid は答えになり得ない。捨てる（notes の理由づけどおり）
		} else {
			lo = mid // mid² <= n → mid は候補。残す
		}
	}
	return lo // ループを抜けた時 lo == hi ＝ 「真である最大の値」
}
```

**検証: `n = 0 〜 2,000,000` の全数で不一致0・ハング0。`n = MaxInt` → `3037000499`（正解）。**

つまり **`(lo, hi]` は「ダメ」ではなく「アリ」―― むしろ「最大の真を探す」今回の問題には `[lo, hi)` より素直**（答え変数 `k` が不要になり、`lo` がそのまま答えになる）。疑問の筋は良い。**落とし穴は区間規約ではなく `mid` の丸め方向にあった。**

### 4つの規約を1枚に

| 規約 | 継続条件 | mid | 候補を残す側の更新 | 捨てる側の更新 | 答え |
|---|---|---|---|---|---|
| 半開 `[lo, hi)`「**最小の偽**」を探す | `for lo < hi` | **床** `lo+(hi-lo)/2` | `hi = mid` | `lo = mid+1` | `lo - 1`（＝最大の真） |
| 左開 `(lo, hi]`「**最大の真**」を探す | `for lo < hi` | **天井** `lo+(hi-lo+1)/2` | `lo = mid` | `hi = mid-1` | `lo` |
| 閉 `[lo, hi]` ＋ 答え変数 | `for lo <= hi` | 床 | `ans = mid; lo = mid+1` | `hi = mid-1` | `ans` |
| 閉 `[lo, hi]` ＋ 答え変数（最小を探す版） | `for lo <= hi` | 床 | `ans = mid; hi = mid-1` | `lo = mid+1` | `ans` |

**現在の実装は1行目（半開）で正しく書けている。** notes の疑問は2行目のこと ―― 有効だが `mid` を天井にする必要がある。

> 合言葉（観点2の芯・notes の疑問への回答）: **「候補を残す側」に `mid` を寄せる。`hi = mid`（候補を hi 側に残す）なら mid は床、`lo = mid`（候補を lo 側に残す）なら mid は天井。整数除算の切り捨ては `lo` 側に寄るので、`lo = mid` と床 mid を組むと `mid == lo` で前進せず必ずハングする。区間規約・継続条件・更新式の3点セット（`01` の学び）に、実は "mid の丸め方向" という4点目がある。**

## 観点3【②道具・隠れた地雷】ガード `if n < 0 || n == 1` の `n == 1` は "load-bearing" ―― 外すと panic する

```go
if n < 0 || n == 1 {
    return n
}
```

直前のコミットが `fix: ガード処理を集約`。集約それ自体は良い方向だが、**集約したことで「この条件がなぜ消せないか」が読み取れなくなった**。実測で分解する:

| ガードから外すもの | `n=1` | `n=-1` | `n=-100` | `n=MinInt` |
|---|---|---|---|---|
| `n == 1` を外す | 🔴 **panic: integer divide by zero** | – | – | – |
| `n < 0` を外す | – | `0` を返す（panic なし） | `0` | `0` |

**この2つは、まったく性質の違う条件が1行に同居している**:

- **`n == 1` は "安全性" ―― 外すとクラッシュする。**
  `n=1` だと `lo=0, hi=1` でループに入り、`mid = 0 + (1-0)/2 = 0`。次の行が `n/mid` ＝ **`1/0`** で `integer divide by zero`。
  ついでに `hi = n = 1` は半開区間 `[0, 1)` を意味するが、**答えの `1` はその区間に入っていない**（区間規約としても破綻している）。**2重に効いているガード**。
- **`n < 0` は "契約" ―― 外しても落ちない（`0` を返す）。** README は「非負整数 `n` に対し」と書いているので、負数は**契約外**。何を返すかは実装者の選択。

### なぜ `n >= 2` なら `mid == 0` にならないのか（安全性の証明）

`mid = 0` になるには `lo = 0` かつ `hi <= 1` が必要。
- 初期は `lo=0, hi=n`。`n >= 2` なので初回 `mid = n/2 >= 1` ✅
- `hi` は `hi = mid`（`mid > n/mid` のとき）でしか減らない。`mid = 1` だと `n/1 = n >= 2` なので `1 > 2` は偽 ―― **`hi` が 1 になることはない**
- `lo` は増える一方

∴ **`n >= 2` の間は `mid >= 1` が保証される。** だから `n <= 1` を先に弾く必要がある。実際、`n=0` はループに入らない（`lo < hi` が `0 < 0` で偽）ので、**明示的に弾く必要があるのは `n == 1` だけ**。

### 直し: 意味で分ける ＋ 「なぜ」を書く

```go
// 契約: n は非負整数。負が来たら呼び出し側のバグとして扱う。
if n < 0 {
    panic("intSqrt: n must be non-negative") // または: return -1（不正入力の番兵）
}
// n < 2 は答えが n 自身。同時に、ループ内の n/mid で mid==0 の除算を防ぐガードでもある
// （n>=2 のとき初回 mid = n/2 >= 1 が保証され、以後 mid が 0 になることはない）。
if n < 2 {
    return n
}
```

なお **`if n < 2 { return n }` は現在の `if n < 0 || n == 1 { return n }` と完全に等価**（`n=0` は現状ループに入らず `k=0` を返し、新版は `return n = 0`。`n<0` も `n<2` に含まれ `return n` で同じ）。**1条件に減って、しかも「`n >= 2` から先が本体」という前提が読み手に見える。**

### 負数の契約をどう決めるか（3択・要判断）

現状は `return n` ―― `intSqrt(-100) == -100` という**恒等写像**になる。テストにも `{name:"NisNegativeInteger", n:-1, want:-1}` として固定されている。これは「決めて、テストで固定した」点は良いが、**契約としては最も説明しにくい**（`floor(sqrt(-100))` が `-100` である理由がない）。

| 選択肢 | 長所 | 短所 |
|---|---|---|
| `panic("n must be non-negative")` | **契約違反を呼び出し側に即座に知らせる**。標準ライブラリ的（`slices` の範囲外など） | テストで `recover` が要る |
| `return -1`（番兵） | `01` の「見つからない = -1」と揃う | `-1` が正常値と紛れない保証が要る（今回は `k>=0` なので紛れない） |
| `return n`（現状） | 何も書かなくて済む | **意味がない**。`-100 → -100` を説明できない |
| `func intSqrt(n uint64) uint64` | **型で契約を表現 ―― 負数が呼べなくなる** | 呼び出し側の変換が要る。ドリルとしては大げさ |

**推奨は `panic` か `-1`。** どちらでもよいが、**「なぜその値なのか」がコメント1行で説明できる方**を選ぶ。

> 合言葉（観点3の芯）: **ガードを集約するときは "同じ理由のものだけ" 集約する。`n==1` は panic 回避（安全性）、`n<0` は契約 ―― 理由が違うものを `||` で繋ぐと、「なぜこの行が消せないのか」が消える。ガードには "何を弾くか" ではなく "弾かないと何が起きるか" をコメントする。**

## 観点4【②道具・README の主眼】オーバーフロー ―― **本丸は自力で倒せている**。だが検証テストが1件も無い（＋`(lo+hi)/2` は実はこの問題では溢れない）

README #2 は名指しでこう書いている:

> - 大きな `n`: `k*k` が溢れないか注意（`k <= n/k` の形に書き換える手もある）

**これを自力でやっている。** notes.md にも:

> `mid*mid > n` の計算について、`mid*mid` とすると、オーバーフローが発生してしまうと考えたため、`mid > n/mid` とした。

**この書き換えは数学的に厳密に等価**（`mid >= 1` のとき）:

```
mid <= floor(n/mid)  ⟺  mid <= n/mid（実数）  ⟺  mid² <= n
```
（`mid` は整数なので `mid <= floor(x) ⟺ mid <= x`。逆向きも同様に成立し、**取りこぼしも誤検出も無い**。）

実測でも **`n = MaxInt`（9223372036854775807）→ `3037000499`** を正しく返す。`3037000499² = 9223372030926249001 <= MaxInt < 3037000500²` ✅。**乗算版なら確実に破綻する領域を通せている。**

### 🔴 しかし ―― その対策を検証するテストが1件も無い

```go
{name: "largenN", n: 2000000000, want: 44721}, // int: -2,147,483,648 - 2,147,483,647
```

**このコメントは `int32` の範囲。Go の `int` は 64bit 環境では 64bit（`math.MaxInt = 9223372036854775807`）。** つまり:

- `n = 2e9` は Go の `int` にとって**まったく大きくない**（上限の約 4.6億分の1）
- `mid*mid` の最大値は `44721² ≈ 2e9` ―― **`int64` では余裕で収まる**
- ∴ **`mid > n/mid` を `mid*mid > n` に書き戻しても、このテストは緑のまま通る**

**苦労して入れたオーバーフロー対策が、1ケースも検証されていない。** これは「対策を書いた」と「対策が効いている」の間のギャップで、`01` の学び7番「停止性と正当性は別々に壊れるので別々に検証」の同型 ―― **"実装した" と "検証した" は別**。

**足すべきケース**（実測で全て正しい値を返すことを確認済み。選定根拠は観点7-2）:

```go
{name: "maxInt",           n: math.MaxInt,                  want: 3037000499}, // 型の限界ちょうど
{name: "largestSquare",    n: 3037000499 * 3037000499,      want: 3037000499}, // 9223372030926249001
{name: "justBelowLargest", n: 3037000499*3037000499 - 1,    want: 3037000498}, // ★答えが1減る境界
{name: "twoPow62",         n: 1 << 62,                      want: 2147483648}, // 期待値が 2^31 と暗算できる
```

**`mid*mid` に戻すと、これらがどう壊れるか**（実測）:

| n | `mid > n/mid`（正） | `mid*mid > n`（対策なし） |
|---|---|---|
| `1 << 62` | 2147483648 | **4611686018427387903** |
| `math.MaxInt` | 3037000499 | **9223372036854775806** |

探索途中で `mid ≈ 2⁶¹` になると `mid*mid ≈ 2¹²²` が **64bit を溢れてちょうど `0`** になり、`mid*mid > n` が `0 > n` ＝ **偽**と判定されて探索が逆方向へ進みます。**panic もエラーも出ず、約20億倍ずれた値を平然と返す** ―― だからこそテストで固定する価値があります。

`import "math"` が要る。**`math.MaxInt` を使うことで「32bit 環境でも 64bit 環境でも "その環境の上限" を突く」テストになる**（値をベタ書きすると 32bit 環境でコンパイルエラーになる ―― ただし `want` は 64bit 前提の値なので、厳密にやるなら `math.MaxInt` から動的に期待値を作るか、`//go:build 64bit` 相当の割り切りを1行コメントで宣言する）。

### 補足: `(lo+hi)/2` は README の指定どおり回避されている ―― が、**この問題では実は溢れない**

`mid = lo + (hi-lo)/2` を正しく使っている ✅（README 指定・`01` 観点3の学び）。**手癖としてこれが正解**なので変えなくてよい。

ただし正確を期すと、**このアルゴリズムに限れば `(lo+hi)/2` でも溢れない**。実測した `lo > 0` になって以降の `max(lo+hi)`:

| `n` | `lo>0` 以降の `max(lo+hi)` | MaxInt 比 |
|---|---|---|
| `MaxInt` | 6,442,450,943（64億） | 7×10⁻¹⁰ |
| `2^62` | 0（`lo` が動く前に終了） | – |
| `2e9` | 91,553 | 1×10⁻¹⁴ |

理由: **`lo` は `mid < n/mid`（＝ `mid < sqrt(n)`）のときしか増えないので `lo <= sqrt(n)+1`。そして `lo` が初めて正になる時点で `hi` は既に `2·sqrt(n)` 程度まで縮んでいる**（`mid >= hi/2` なので、`mid < sqrt(n)` になるには `hi < 2·sqrt(n)` が必要）。初回反復だけは `lo=0, hi=n` で和が `n` ＝ **`MaxInt` でもちょうど収まる**。∴ `lo+hi <= 3·sqrt(n)` 程度で頭打ち。

**変異テストでも `(lo+hi)/2` 版は `n=MaxInt` を含む全ケースを通過した。**

これは「だから `(lo+hi)/2` でよい」という話**ではない**。むしろ学びは逆:

> **`01` で指摘された `(lo+hi)/2` は "配列の添字を二分探索するとき" の話（`lo`,`hi` がどちらも `len` 近くまで育つ）。`02` は "答えの値を二分探索する" ので、`lo` と `hi` の育ち方が非対称になり、同じ式でも危険度が変わる。** そして **`02` の真の危険は `mid*mid`** ―― **同じ「オーバーフロー」でも、問題の形が変われば危ない場所が移る**。それを自力で見つけて `mid > n/mid` にしたのが今回の実力。

> 合言葉（観点4の芯）: **オーバーフロー対策は「書いた」で終わらせず、「対策なしなら落ちる入力」でテストする。`n = 2e9` は Go の `int`（64bit）では小さい ―― `math.MaxInt` を叩いて初めて `mid*mid → mid > n/mid` の書き換えが検証される。「64bit の int にとって大きい数」の相場観（≈9.2×10¹⁸ / `sqrt` は ≈3.04×10⁹）を指に入れる。**

## 観点5【②道具・altitude】答えを取り出す経路が3つある ―― `k` は常に `lo-1`（冗長）

```go
lo := 0
hi := n
k := 0 //　求める最大の整数
for lo < hi {
    mid := lo + (hi-lo)/2
    if mid == n/mid { return mid }        // 経路① 早期return
    if mid < n/mid { lo = mid + 1; k = mid } // 経路② k に記録
    if mid > n/mid { hi = mid }
}
return k                                   // 経路② の回収
```

いま、**答えが出てくる経路が3つある**:

1. **`return mid`（早期 return）** ―― 観点1で見たとおり「健全だが不完全なショートカット」
2. **`k`（答え変数）** ―― 取りこぼしを拾う
3. **`lo - 1`** ―― 半開 `[lo,hi)` の境界探索としての正規の答え（コードでは未使用）

**`k` は常に `lo - 1` と一致する**（`n = 2..300,000` の全反復で違反0を実測）。理由: `k = mid` は必ず `lo = mid + 1` と同時に実行されるので、代入直後に `k == lo-1`。`hi` の更新は `k` も `lo` も動かさない。∴ **恒久的に `k == lo-1`。**

つまり `k` は**冗長**。読み手は「①②③が全部一致することを確認する」義務を負う。

### ただし ―― 「答え変数」自体は "答えで二分探索" の正統イディオム

誤解しないでほしいのは、**`ans`/`k` のような答え変数は、めぐる式二分探索では非常に一般的で、むしろ推奨されることも多い**。`hi = mid-1` で候補を捨てても `ans` に控えがあるので安全、という設計。

問題は**混ぜていること**:

| 設計 | 候補の扱い | 答えの取り出し | 答え変数 |
|---|---|---|---|
| 半開 `[lo,hi)`（現在の `hi = mid`） | **区間に残す** | `lo - 1` | **不要** |
| 閉 `[lo,hi]` ＋ `hi = mid-1` | **区間から捨てる** | `ans` | **必須** |

**現在の実装は「区間に残す」設計なのに「捨てる設計用の答え変数」も持っている。** 二重の安全装置で、正しいが冗長。どちらか一方に寄せる:

**案A: 半開のまま `k` を消す**（最小の変更・現在の設計を素直に完成させる）
```go
func intSqrt(n int) int {
	if n < 2 {
		return n
	}
	// 不変条件: 半開区間 [lo, hi) は「答えの候補」を常に含む。
	//           ループ終了時 lo == hi == 「mid² > n となる最小の値」なので、答えはその1つ手前。
	lo, hi := 1, n
	for lo < hi {
		mid := lo + (hi-lo)/2
		if mid <= n/mid {
			lo = mid + 1 // mid² <= n → 答えは mid より右（mid 自身も含みうるが lo-1 で回収）
		} else {
			hi = mid // mid² > n → mid 以降は全部ダメ
		}
	}
	return lo - 1
}
```

**案B: 閉区間 ＋ 答え変数**（`k` を主役にする・めぐる式の教科書型）
```go
func intSqrt(n int) int {
	if n < 2 {
		return n
	}
	// 不変条件: 答えは常に閉区間 [lo, hi] の中に居る。ans は「真と確認済みの最大候補」。
	lo, hi := 1, n/2+1 // n>=2 なら floor(sqrt(n)) <= n/2+1
	ans := 1
	for lo <= hi {
		mid := lo + (hi-lo)/2
		if mid <= n/mid {
			ans = mid // 候補を確保
			lo = mid + 1
		} else {
			hi = mid - 1 // 捨てる（ans に控えがあるので安全）
		}
	}
	return ans
}
```
（案B は `n = 0〜5,000,000` の全数 ＋ `MaxInt` ＋ `2^62` で不一致0を確認済み。）

**案C は観点2の `(lo, hi]` ＋ 天井 mid**。3案とも正しい。**どれを選ぶかより、"1つの規約に統一する" ことが本題。**

### ついでに: `hi := n` は上界として緩い

`n >= 2` なら `floor(sqrt(n)) <= n/2` なので `hi = n/2 + 1` で足りる。実測の反復回数:

| `n` | `hi = n` | `hi = n/2+1` |
|---|---|---|
| 26 | 5回 | 4回 |
| 2e9 | 31回 | 30回 |
| MaxInt | 63回 | 62回 |

**1回しか変わらない**（当然 ―― 上界を半分にすると `log2` は1減るだけ）。**性能上の意味はほぼ無い**。ただし「答えが `[lo, hi)` に入っている」という**不変条件を宣言するとき、上界を自分で見積もる**のは良い訓練になる（`n=1` が `[0,1)` に入らない問題＝観点3も、この見積もりを意識していれば先に気づけた）。

> 合言葉（観点5の芯）: **「答えを取り出す経路」は1本にする。半開 `[lo,hi)`（候補を区間に残す）なら答えは `lo-1` で答え変数は不要、閉区間＋`hi=mid-1`（候補を捨てる）なら答え変数が必須。両方持つと "3つの経路が全部一致すること" を読み手が検証させられる。冗長は "安全" ではなく "確認コスト"。**

## 観点6【②道具・構造】3つの裸 `if` ―― `01` 観点1の再来。**今回は安全側**。除算はコンパイラが畳むが、分岐の数は残る

```go
if mid == n/mid { ... }
if mid < n/mid { ... }
if mid > n/mid { ... }
```

`01` の観点1で徹底的にやった「3つの裸 `if`」がまた出ている。**ただし今回は `01` と決定的に違う**:

- **`mid` を分岐内で書き換えていない**（周の頭で1回・assign-once）
- **`n` も不変**
- ∴ `==` / `<` / `>` は**三分律（trichotomy）により必ずちょうど1つだけ真**

**つまり "二度発火" は構造的に起こり得ない。バグではない。** notes の「学び」1番（可変状態を減らす・assign-once）を自分で適用した結果 ―― **`01` の教訓が効いている証拠**。

残る問題は2つ、どちらも**正しさではなく道具の質**:

### (1) 除算 `n/mid` はソース上3回書かれている ―― **ただしコンパイラが1回に畳んでいる**（実測）

ソース上は `n/mid` が3つの `if` に3回現れる。整数除算は CPU で最も遅い算術命令のひとつ（加算の 10〜40 倍）なので**一見3倍のコスト**に見える。実際、ソースレベルで数えると 1周あたり最大3回・`n=2e9` で合計88回になる。

**しかし生成コードを確認すると、Go コンパイラが共通部分式除去（CSE）で1回に畳んでいる**（darwin/arm64・`go build -gcflags=-S`）:

| 版 | 生成された除算命令（`SDIV`） |
|---|---|
| A 現状（裸 `if`×3・`n/mid` を3回記述） | **1個** |
| B `q := n/mid` に退避 | **1個** |
| C 早期return を畳んだ2分岐 | **1個** |

`n` も `mid` もローカルな `int` で分岐の間に変化しないため、コンパイラは3つの `n/mid` が同一値だと証明でき、**除算は1回しか発行されない**。

実測ベンチ（ランダム n を 2〜2⁶²、200万回・darwin/arm64）:

| 版 | ns/op | 平均反復 |
|---|---|---|
| A 現状 | 231.6 | 60.11 |
| B `q := n/mid` に退避 | 220.6（−4.8%） | 60.11 |
| C **早期returnなし・2分岐** | **211.5（−8.7%）** | 60.61 |

**差は「除算の回数」ではなく「比較と分岐の数」から来ている。** 注目すべきは **C が反復を 0.5 回多く回しているのに 8.7% 速い**こと ―― 早期return は反復をわずかに減らすが、その代償の比較・分岐の方が高くつく（観点1で見た「効果0.8%」の裏付け）。

```go
for lo < hi {
    mid := lo + (hi-lo)/2
    q := n / mid          // 「同じ値である」ことを名前で宣言する（性能ではなく可読性のため）
    switch {
    case mid == q: return mid
    case mid < q:  lo = mid + 1; k = mid
    default:       hi = mid
    }
}
```

**`q` への退避は依然として推奨**。ただし理由は **性能ではなく可読性・堅牢性**:
- 「3箇所の `n/mid` は同じ値だ」という前提が**名前として明示される**（読み手が推論しなくてよい）
- **CSE が効く保証は状況依存**。今回は `n`・`mid` がローカルな不変値だから畳めたが、間に関数呼び出し・ポインタ経由の読み・グローバル変数・インターフェース呼び出しが1つ挟まると、コンパイラは「値が変わっていない」と証明できず**畳めなくなる**。退避しておけば構造的に1回が保証される

> 注: これは `01` 観点5で扱った「`len` の退避」と**同じ判定基準に行き着く**。あのとき立てた問いは「その式は**毎回計算する**のか、**保持値を読むだけ**か」だった。今回それに**もう一段**足りない部分があった ―― **「毎回計算する式に見えても、コンパイラが1回に畳んでいるかもしれない」**。つまり判定は3段階:
> 1. その式は本当に計算を伴うか（`len` は違う／`n/mid` は伴う）
> 2. **コンパイラが畳めるか**（今回は畳めた ―― ローカルな不変値だから）
> 3. 畳めるとしても、退避すべきか（**可読性**と、将来 CSE が効かなくなるリスクへの保険として **Yes**）
>
> **教訓: 「重い演算だから退避すると速くなる」は推論であって観測ではない。生成コードかベンチマークで確かめてから "速くなった" と言う。**

### (2) `switch` / `else if` にすれば「1つだけ発火」が構文で保証される

現状は**三分律という数学的事実**に依存して排他性を保っている。正しいが、**読み手はその事実を毎回自分で確認する**。`switch` なら構文が保証する ―― `01` 観点1の合言葉「**排他を "自分で" 守るのではなく "構文に" 守らせる**」がそのまま当てはまる。

**そして観点1を適用すれば分岐は2つになる**ので、`switch` すら不要で `if/else` で済む:

```go
for lo < hi {
    mid := lo + (hi-lo)/2
    if mid <= n/mid {   // 除算1回・分岐2つ・述語1本
        lo = mid + 1
    } else {
        hi = mid
    }
}
return lo - 1
```

**除算 `n/mid` は1周につき1回**（`if/else` なので `else` 側では再評価されない）、**分岐は2つ**、**答えの経路は1本**。観点1・5・6が同時に片付く。

## 観点7【③テストは妥当か】変異テストで測る ―― 8つの変異体のうち**4つがすり抜ける**（変異スコア 50%）

「テストをたくさん書けばよいのか分からない／無駄なテストは逆によくない気がする」という `01` notes の不安への、**測定による答え**。

**変異テスト（mutation testing）**: 実装にわざとバグを1つ入れた「変異体」を作り、**テストがそれを検出できるか**を見る。検出できなければ、そのテストはその種のバグに対して**無力**。「ケース数」ではなく「**どの間違いを捕まえられるか**」で測れる。

現状の7ケース（`26, 0, 1, 4, 25, 2000000000, -1`）に対する実測:

## 観点7-2【③テストは妥当か・選定の作法】**なぜこの4件で、なぜ `math.MaxInt - 1` は入れないのか**

> この節はレビュー後の対話から追加。当初レビューは `{name:"maxIntMinus1", n: math.MaxInt-1, want: 3037000499}` を挙げていたが、**測ったら重複だったので撤回した**記録。「ケースを増やせば安心」でも「減らせば洗練」でもなく、**測って決める**という作法そのものが本題。

### 測り方: 「このケースだけが殺せる変異があるか」

大きな `n` の候補それぞれについて、5種の実装ミスを検出できるか実測した:

| テストケース | M-a<br>溢れる式 | M-b<br>`hi=mid-1` | M-c<br>`return lo` | M-d<br>ハング | M-e<br>off-by-one | 期待値 |
|---|---|---|---|---|---|---|
| `math.MaxInt` | ✅ | ・ | ✅ | ✅ | ✅ | 3037000499 |
| **`math.MaxInt - 1`** | ✅ | ・ | ✅ | ✅ | ✅ | 3037000499 |
| `1 << 62` | ✅ | **✅** | ・ | ・ | ・ | 2147483648 |
| `K*K`（K=3037000499） | ✅ | **✅** | ・ | ・ | ・ | 3037000499 |
| `K*K - 1` | ✅ | ・ | ✅ | ✅ | ✅ | **3037000498** |
| `K*K + 1` | ✅ | **✅** | ・ | ・ | ・ | 3037000499 |

**`math.MaxInt - 1` は `math.MaxInt` と1文字も違わない結果**（殺せる変異も期待値も同一）。**足す価値がない。**

### 🔴 `math.MaxInt - 1` が「境界値」になっていない理由 ―― 答えが変わらない

境界値テストの本質は **「答えが変わる点を挟むこと」**。ところが:

```
n = 9223372036854775806 (MaxInt-1) → 3037000499
n = 9223372036854775807 (MaxInt)   → 3037000499   ← 変わらない。ただ隣り合っているだけ
```

本当に答えが変わるのはここ:

```
n = 9223372030926249000 (K²-1) → 3037000498
n = 9223372030926249001 (K²)   → 3037000499   ← ★ここで +1 される
```

**`n` が「大きい」ことと「境界である」ことは別物。** 当初レビューは「上限の近く」という理由だけで `MaxInt-1` を挙げており、**答えが変わる点を確認していなかった**。

### 「境界の隣もテストする」という原則は正しい ―― ただし**効く条件がある**

> 「よく、境界値が `n=0` だった場合に `n=1` を確かめるのはやると思うが、そういう意図では?」

**その原則は正しく、小さい側では実際に決定的だった。** 実装バリエーションで実測:

| 実装ミス | n=0 | **n=1** | **n=2** | n=3 | **MaxInt** | **MaxInt-1** | MaxInt-2 |
|---|---|---|---|---|---|---|---|
| V6 ガードを `n<1` に（`n=1` を漏らす） | ・ | **✅** | ・ | ・ | ・ | ・ | ・ |
| V7 ガードを `n<3` に（`n=2` を誤る） | ・ | ・ | **✅** | ・ | ・ | ・ | ・ |
| **V1 `hi := n+1`**（半開で +1 したくなる） | ・ | ・ | ・ | ・ | **✅** | **・** | ・ |
| V5 `(lo+hi)/2` かつ `hi := n+1` | ・ | ・ | ・ | ・ | **✅** | **・** | ・ |
| V2 閉区間版 / V3 上界を `n/2+1` に / V4 `(lo+hi)/2` | ・ | ・ | ・ | ・ | ・ | ・ | ・ |

**V6 は `n=1` でしか、V7 は `n=2` でしか死なない。** 小さい側で `0,1,2` を並べる価値は完全に実証されている。

**分かれ目は「その境界が、コードの中に比較として存在するか」**:

```go
if n < 2 { return n }   // ← 0/1/2 の境界は、コードの中にある「比較」
                        //    `<` を `<=` に、`2` を `1` や `3` に間違えうる
                        //    → 両隣が別々の意味を持つ（V6/V7 が実証）
```

一方、**コードのどこにも `MaxInt` と比較している箇所は無い**。`MaxInt` は「型が表せる限界」であって、コードが判断に使っている値ではない。**比較相手が無いので、`MaxInt-1` が突く対象がそもそも存在しない。**

| 境界の種類 | 例 | 隣（B±1）の価値 |
|---|---|---|
| **コード中の比較** | `if n < 2` | **★高い** ―― `<`/`<=` の取り違えを検出（V6/V7） |
| **ループ回数が変わる点** | 0回 / 1回 / 2回 | **★高い** |
| **答えが変わる点** | `K²-1` → `K²` で答えが +1 | **★高い** |
| **型の表現限界** | `math.MaxInt` | **B 自体は必須。B-1 は無価値**（比較相手が無い） |

> **原則はそのまま正しく、適用先を「型の限界」から「答えが変わる点」に付け替えるだけ。** 大きい側で「隣」をやるなら `MaxInt-1` ではなく **`K²-1` と `K²`**。

### ✅ 逆に `math.MaxInt` は極めて重要だった ―― `MaxInt-1` では代用できない

表の **V1（`hi := n + 1`）** に注目。これは**半開区間で書こうとすれば自然に出てくる書き方**:

```
n = 9223372036854775807 (MaxInt)   → hi = n+1 = -9223372036854775808  🔴 負に一周
                                   → 結果 0（正解 3037000499）

n = 9223372036854775806 (MaxInt-1) → hi = n+1 =  9223372036854775807  ✅ セーフ
                                   → 結果 3037000499（正解・すり抜ける）
```

**`MaxInt-1` はこのバグを見逃す。** つまり `MaxInt-1` が不要なのは「重複だから」だけでなく、**`MaxInt` が突いている当のもの（`n+1` の溢れ）を突けないから**。

> **「上限の近く」ではダメで、「上限ちょうど」でなければ意味がない。**

### 大きな `n` は2グループに分かれる ―― 両方から1件ずつ要る

上の変異表をよく見ると、大きな `n` は殺せる変異で2つに割れている:

| グループ | 殺せる変異 | 該当 | 通る経路 |
|---|---|---|---|
| **①** | M-a, M-c, M-d, M-e | `MaxInt`, `MaxInt-1`, `K²-1` | **`return k`**（早期 return が発火しない） |
| **②** | M-a, **M-b** | `1<<62`, `K²`, `K²+1` | **`return mid`**（早期 return が発火する） |

分かれ目は **早期 return（`mid == n/mid`）が発火するかどうか**（観点1で見た `mid² ≤ n < mid²+mid` に入るか）。**同じ「巨大な n」でも通るコードが違う**ので、**両グループから最低1件ずつ**必要。片方だけだと、もう片方の経路のバグ（M-b や M-c）を見逃す。

### さらに強い道具: プロパティテスト（`01` 観点4の再来）

個別ケースを並べるより、**「答えの定義そのもの」を性質として書く**方が穴が機械的に埋まる。整数平方根は定義が2つの不等式に落ちるので、**オラクル無しで検証できる**（`01` の `getTargetIndexOriginal` すら要らない）:

```go
// k = floor(sqrt(n)) の定義: k*k <= n かつ (k+1)*(k+1) > n
func TestFindLargestInteger_Property(t *testing.T) {
	rng := rand.New(rand.NewSource(1)) // 固定シードで再現可能
	// ここに MaxInt-1 を入れるのは構わない（観点7-2 とは矛盾しない・後述）
	ns := []int{0, 1, 2, 3, 1 << 62, math.MaxInt, math.MaxInt - 1}
	for i := 0; i < 200000; i++ {
		ns = append(ns, rng.Intn(1<<62))
	}
	for _, n := range ns {
		k := findLargestInteger(n)
		if k < 0 {
			t.Fatalf("n=%d: k=%d が負", n, k)
		}
		if k > 0 && k > n/k { // k*k <= n を溢れずに判定
			t.Fatalf("n=%d: k=%d で k*k > n（大きすぎる）", n, k)
		}
		if (k + 1) <= n/(k+1) { // (k+1)*(k+1) <= n
			t.Fatalf("n=%d: k=%d で (k+1)² <= n（小さすぎる）", n, k)
		}
	}
}
```

**`k > n/k` と `(k+1) <= n/(k+1)` の2行が「floor(sqrt) の定義」そのもの。** 期待値を人間が計算する必要がなく、`MaxInt` 近傍まで含めて自動で検証できる。

### なぜここでは `math.MaxInt - 1` を入れてよいのか（観点7-2 と矛盾しない理由）

観点7-2 で「テーブルに `MaxInt-1` を足すな」と言いつつ、プロパティテストの種には入れている ―― これは**重複のコストが両者で違う**から:

| | 期待値 | 重複1件のコスト | 判断 |
|---|---|---|---|
| **テーブル駆動テスト** | **人間が手で書く**（`want: 3037000499`） | 読む人が「これは何のため?」と考える／期待値を間違えるリスク／将来の変更で全部直す | **重複は削る** |
| **プロパティテスト** | **性質から自動判定**（人間は書かない） | ほぼゼロ（実行時間が1件分増えるだけ） | **迷ったら入れてよい** |

**「期待値を人間が書くか」が分かれ目。** 人間が書く場所では1件ごとに理由が要り、書かない場所では「念のため」が許される。

> 注: `go test -timeout 30s` を付けると**無限ループが「ハング」ではなく「失敗」として現れる**（M2 のような変異が明示的に落ちる）。ドリルでは付ける価値がある。

### テストコードそのものへの指摘（細部）

- `// TODO: テストを書く`（13行目）が**残っている**。書き終えたら消す。
- `n int // n` ―― コメントが情報ゼロ。`n int // 入力（非負整数）` / `want int // floor(sqrt(n))` に。
- `// int: -2,147,483,648 - 2,147,483,647` ―― **`int32` の範囲。Go の `int` は 64bit**（観点4）。誤解を固定するので直す。
- 名前 `nNisZero` / `largenN` ―― `n` が重複してタイポ気味（`nIsZero` / `largeN`）。テスト名は失敗時に一番先に読む文字列なので整える。
- ✅ **`reflect.DeepEqual` ではなく `!=` で比較できている** ―― `01` 観点6の指摘が反映済み。
- ✅ **テーブル駆動 ＋ `t.Run` でサブテスト化** ―― 失敗時にどのケースか即分かる。良い。

> 合言葉（観点7の芯）: **テストの良し悪しは "ケース数" ではなく "どの間違いを殺せるか"。現状7ケースのうちループ本体を通る4件は全部早期 return で抜けていて、`return k` の経路を1件も通っていない ―― だから `n=2` という最小ケースが欠けた瞬間に「無限ループ」と「オフバイワン」の両方が見逃される。「無駄なテストが不安」の答えは "減らす" ではなく "変異を殺せるかで測る"。**

## 観点8【altitude・可読性】命名・コメント ―― 「未来の自分への手紙」の精度

正しさには影響しないが、`01` の心残り（A6: コメントと実装の食い違い）がそのまま再来している。

### (1) 🔴 冒頭コメントの不変条件が**誤っている**

```go
// アルゴリズム整理
// k*k < n となるような最大の整数kを求める　-> k*k < n と k*k > n と切り替わる境目を見つける
```

- **`k*k < n` は誤り。正しくは `k*k <= n`**（README・スキャフォールドとも `<=`）。`<` だと `n=25` の答えは **4** になってしまう（`5*5 = 25` は `< 25` を満たさない）。**テストの `{n:25, want:5}` はこのコメントと矛盾している。**
- **「`k*k < n` と `k*k > n` の切り替わる境目」も誤り** ―― `k*k == n` の場合が抜け落ちている。**そして、この "抜け落ちた `==`" こそが、観点1の `if mid == n/mid { // 完全平方数 }` という余計な分岐を生んだ原因**。述語を `k*k <= n`（真/偽の2値）と最初に書けていれば、分岐は最初から2つで済んだ。

**コメントの誤りが実装の構造にそのまま出ている。** 「進め方③（不変条件をコメントで宣言してから書く）」が効く理由がここにある ―― **宣言が正確なら、実装はそれをなぞるだけ**。

正しく書くなら:

```go
// 述語 ok(k) := (k*k <= n) は k について単調（k=0..K で真、K+1 以降ずっと偽）。
// 求めるのは「ok(k) が真である最大の k」＝ 真→偽 が切り替わる境界の1つ手前。
// オーバーフロー回避のため ok(k) は k*k <= n ではなく k <= n/k で判定する（k>=1 のとき等価）。
//
// 不変条件: 答え K は常に半開区間 [lo, hi) に含まれる。
//   ok(mid) 真 → K >= mid なので lo = mid+1（mid 自身は lo-1 として回収）
//   ok(mid) 偽 → K <  mid なので hi = mid
```

### (2) 関数名 `findLargestInteger` ―― 「何の」最大整数か分からない

`findLargestInteger(26)` を見て `5` が返ると予想できる人はいない。**この関数の主語は "平方根" なのに、名前にどこにも出てこない。**

推奨: **`intSqrt`** / `floorSqrt` / `isqrt`（Python の `math.isqrt`、Rust の `isqrt` と揃う実名）。
テスト関数も `TestIntSqrt` に追従。

> `01` の `getTargetIndexBinarySearch` は「何を探すか（TargetIndex）」＋「どう探すか（BinarySearch）」が両方入っていて良い名前だった。同じ基準で見ると `findLargestInteger` は**「どう探すか」も「何を探すか」も入っていない**。

### (3) スキャフォールドの `// TODO: 自分で実装する`（6行目）が残存

実装済みなので削除。テスト側の `// TODO: テストを書く`（13行目）も同様。**TODO が残っていると grep で「未着手」に見える。**

### (4) 変数名 `k` の役割コメント

```go
k := 0 //　求める最大の整数
```
コメントの意図は正しいが、`//` の直後が**全角スペース**（`01` にも同じ癖あり）。`gofmt` は通るが、他の行と揃わない。

### (5) 全角スペース混入

3行目・25行目などに全角スペース `　` が混じっている（`// midを最初に更新して複数の分岐に入らないようにする` の前など）。`gofmt` は文字列・コメント内を触らないので**検出されない**。エディタで「不可視文字を表示」にしておくと気づける。

# 付録A: コンパイラ最適化「共通部分式除去（CSE）」―― 「重い演算だから退避すれば速くなる」は推論であって観測ではない

> この付録は、レビュー後の対話から生まれた節。**レビュアー（AI）が最初に間違え、実測で訂正された**過程をそのまま残す。`01` 観点5の「`len` は O(1) なので退避不要」の**続き**にあたる内容で、実務でいちばん転用が効く部分。

## A-1. きっかけ ―― 「除算が3倍走っているのでは?」という誤った指摘

観点6で、レビュアーは最初こう書いた:

> 除算 `n/mid` が1周に最大3回走る。整数除算は CPU で最も遅い算術命令のひとつなので、`O(log n)` は変わらないが**定数倍が3倍**。

根拠として出した「実測値」がこれ:

| `n` | 反復 | 除算回数 |
|---|---|---|
| 2e9 | 30 | **88** |

**この数字は間違っていた。** 正確には「間違い」ではなく **「測っているものが違った」** ―― これは **`n/mid` というソースコードの記述を何回通過したか**を数えたもので、**CPU が除算命令を何回実行したか**ではない。

それに対して出た問いが「**では `q := n/mid` と変数に退避すれば速くなるのでは?**」。**推論としては完全に正しい。** だが確かめたら、**Go コンパイラが既にやっていた。**

## A-2. 共通部分式除去（Common Subexpression Elimination / CSE）とは

**同じ式が複数回書かれていて、その間に値が変わらないと証明できるなら、計算は1回だけにして結果を使い回す**というコンパイラ最適化。

```go
// あなたが書いたコード
if mid == n/mid { ... }
if mid < n/mid  { ... }
if mid > n/mid  { ... }

// コンパイラが実際に生成するコード（イメージ）
tmp := n / mid          // ★ 除算はここ1回だけ
if mid == tmp { ... }
if mid < tmp  { ... }
if mid > tmp  { ... }
```

**つまり「`q := n/mid` に退避する」という最適化を、コンパイラが勝手にやってくれている。** 「Go にそんな機能が」と思うかもしれないが、これは Go 固有ではなく **C/C++/Java/Rust など最適化コンパイラを持つ言語ならほぼ共通**の、非常に基本的な最適化。ソースの見た目と実行される機械語は**1対1ではない**。

## A-3. 自分の目で確かめる方法（3つの道具）

「たぶん最適化される」で終わらせず、**確かめる手順を覚えるのがこの付録の本題**。

### 道具1: 生成された機械語を見る ―― `go build -gcflags=-S`

```bash
go build -gcflags=-S ./... 2> asm.txt
```

`-S` は「アセンブリを出力せよ」の意味。**標準エラー出力**に出るので `2>` でリダイレクトする（`>` だと何も取れない）。

除算命令の名前は CPU アーキテクチャで違う:

| アーキテクチャ | 符号付き整数除算の命令名 | 該当環境 |
|---|---|---|
| **arm64** | `SDIV` | Apple Silicon の Mac（今回の環境）、最近の Linux サーバ |
| **amd64（x86-64）** | `IDIVQ` | Intel/AMD の PC・多くのクラウドVM |

自分の環境は `go env GOARCH` で分かる。今回は `arm64` だった。

```bash
go env GOARCH          # → arm64
grep -c SDIV asm.txt   # 除算命令が何個生成されたか
```

> ⚠️ 最初の計測ではここで `IDIVQ`（x86 の命令名）を grep してしまい、**「除算0個」という明らかにおかしい結果**が出た。**「0個のはずがない」と気づけるかどうか**が、計測を信じてよいかの分かれ目になる。**測定結果が直感とあまりに違うときは、まず測定方法を疑う。**

### 道具2: 関数ごとに絞り込む

`-S` の出力は全関数がまとめて出るので、見たい関数だけ抜き出す:

```bash
# TEXT 行（関数の開始）から次の TEXT 行までを取り出す
awk -v fn="mypkg.MyFunc(SB)" '/TEXT/{p=(index($0,fn)>0)} p' asm.txt | grep -c SDIV
```

出力はこう読む:

```
0x0060 00096 (isqrt.go:9)  CBZ   R4, 144      ← ゼロ除算チェック（mid==0 なら panic へ飛ぶ）
0x0064 00100 (isqrt.go:9)  SDIV  R4, R1, R5   ← ★除算はここ1回だけ
0x0068 00104 (isqrt.go:9)  CMP   R5, R4       ← 結果 R5 を使って比較
0x006c 00108 (isqrt.go:9)  BNE   64
0x0044 00068 (isqrt.go:11) CSINC GE, R2, R4, R2  ← 11行目は R5 を再利用（除算していない）
0x0048 00072 (isqrt.go:11) CSEL  LT, R4, R3, R3
```

`isqrt.go:9`（1つ目の `if`）で `SDIV` が1回走り、`isqrt.go:11`（2つ目の `if`）には `SDIV` が無い ―― **結果 `R5` を使い回している**のが読み取れる。これが CSE の現場。

> 補足: `CBZ`（Compare and Branch if Zero）は Go が挿入する**ゼロ除算チェック**。`mid == 0` なら `panic: integer divide by zero` へ飛ぶ。観点3で `n==1` のとき実際にここへ飛んでいた、まさにその命令。

### 道具3: 実時間で測る ―― `go test -bench`

機械語が読めなくても、**実時間の差**なら誰でも測れる。ただし**書き方に罠がある**:

```go
package bench

//go:noinline                       // ★罠1: これが無いとインライン展開され、
func VerA(n int) int { ... }        //        呼び出しごと最適化で消える可能性がある

var sink int                        // ★罠2: 戻り値を捨てると「結果を使っていない」と
                                    //        判断されて計算ごと削除されうる（dead code elimination）

func BenchmarkA(b *testing.B) {
	for i := 0; i < b.N; i++ {
		sink = VerA(ns[i&4095])     // ★罠3: 毎回同じ入力だと結果がキャッシュ的に効いてしまう
	}                               //        → 事前に作ったランダム配列を回す
}
```

```bash
go test -bench=. -benchtime=2000000x -run=XXX
```

- `-benchtime=2000000x` … 「2,000,000回実行せよ」。回数を固定すると版どうしの比較が安定する
- `-run=XXX` … 通常のテストを実行しない（存在しない名前を指定するのが定石）

**「ベンチマークは、油断すると "何も測っていない" 結果が出る」** ―― コンパイラは「結果を使わない計算」を丸ごと削除できるため。上の3つの罠はその対策。

## A-4. 実測結果 ―― 3版とも除算は「1個」

観点1・6で比較した3つの版を、この手順で測ったのがこれ:

| 版 | ソース上の `n/mid` の記述 | **生成された `SDIV`** | ns/op | 平均反復 |
|---|---|---|---|---|
| A 現状（裸 `if`×3） | **3回** | **1個** | 231.6 | 60.11 |
| B `q := n/mid` に退避 | 1回 | **1個** | 220.6（−4.8%） | 60.11 |
| C 早期returnなし・2分岐 | 1回 | **1個** | **211.5（−8.7%）** | 60.61 |

**3版とも除算命令は1個。** つまり **`q` への退避で除算が減ることは無かった**。5〜9%の差は除算ではなく**比較と分岐の数**から来ている。

そして最も示唆的なのが **C**: **反復を 0.5 回「多く」回しているのに 8.7% 速い**。観点1で見た「早期returnの効果は0.8%」を実時間の側から裏付けている ―― **早期returnが省く仕事より、そのために毎周払う比較の方が高くつく。**

## A-5. では CSE はいつ効かないのか ―― 「変わらないと証明できる」が条件

CSE の条件は **「2回目の評価までに値が変わらないと、コンパイラが証明できること」**。証明できなければ**畳めない**。同じ「除算をソースに3回書いたコード」で、形だけ変えて実測した:

| 書き方 | ソース上の記述 | **生成された `SDIV`** | 畳めたか |
|---|---|---|---|
| **ローカル変数だけ**（`n`, `mid` とも局所変数）**← 今回の実装** | 3回 | **1個** | ✅ 畳めた |
| グローバル変数 `G/mid`（間に何もなし） | 3回 | **1個** | ✅ 畳めた |
| **グローバル `G/mid` ＋ 間に関数呼び出し** | 3回 | **🔴 3個** | ❌ 畳めない |
| **ポインタ経由 `*p/mid` ＋ 間に関数呼び出し** | 3回 | **🔴 3個** | ❌ 畳めない |
| ↑ を `q := *p/mid` に退避して直した版 | 1回 | **1個** | ✅（人力で保証） |

**なぜ関数呼び出しが挟まると畳めなくなるのか**: `nop()` が中で `G` を書き換えたり、`p` の指す先を変えたりする**可能性を排除できない**から。コンパイラは「たぶん変わらない」では最適化できず、**「絶対に変わらない」と証明できたときだけ**畳む。

- ✅ **ローカル変数**は、アドレスを取られていない限り**他から書き換えられないことが証明できる** → 畳める
- ❌ **グローバル変数・ポインタの指す先**は、関数呼び出し1つ挟まるだけで**書き換えられた可能性**が生じる → 畳めない

**今回の実装が畳めたのは「`n` も `mid` もローカルな `int` で、分岐の間に関数呼び出しが1つも無い」という条件を満たしていたから** ―― 幸運ではなく、条件を満たしていたということ。

## A-6. 結論: `q := n/mid` はやるべき。ただし理由は性能ではない

| 理由 | 妥当か |
|---|---|
| ❌ 除算が3回→1回になって速くなる | **違う**（コンパイラが既に1回にしている） |
| ✅ 「3箇所の `n/mid` は同じ値」を**名前で宣言**できる | **妥当**。現状は読み手が「`n` も `mid` も変わらないから同じはず」と毎回推論している。`01` の学び1番（assign-once）と同じ発想 |
| ✅ 将来 CSE が効かない形に変わったときの**保険** | **妥当**。A-5 のとおり、間に関数呼び出しが1つ入るだけで畳めなくなる。退避しておけば構造的に1回が保証される |

**「性能のため」ではなく「意味を明示するため」に書く。** 結果的に将来の性能も守られる、という順序。

## A-7. `01` 観点5（`len` の話）が、もう一段深くなった

`01` ではこう学んだ:

> 「重い長さ計算をループ条件で毎回呼ぶな」の原則は正しい（C の `strlen` の O(n²) 罠）。だが Go の `len` は O(1)（保持値を読むだけ）なので当てはまらない。**問うべきは「その式は "数え直す" のか "読むだけ" か」。**

今回、その問いに**もう一段**あることが分かった:

```
1. その式は本当に計算を伴うか？          → len は伴わない（読むだけ）／ n/mid は伴う
2. コンパイラが畳んでいないか？            → ★今回はここ。畳んでいた
3. 畳めるとしても、退避すべきか？          → Yes（可読性 ＋ 将来 CSE が効かなくなる保険）
```

そして構図がまったく同じであることに注目してほしい:

| | `01` の `len` | `02` の `n/mid` |
|---|---|---|
| 持っていた知識 | 「`strlen` は O(n) だから退避すべき」 | 「整数除算は重いから退避すべき」 |
| **知識そのものは** | **正しい** | **正しい** |
| ズレていたのは | **その原則を Go の `len` に適用したこと** | **その原則を "コンパイラが畳む式" に適用したこと** |
| 確かめる方法 | 型の実装を知る（スライスは `{ptr, len, cap}`） | **生成コードを見る／ベンチを取る** |

**どちらも「正しい原則を、当てはまらない場所に当てはめた」という同じ形の間違い。** そして `02` では**レビュアー（AI）の側がそれをやった** ―― 原則を知っているほど、確認を飛ばして当てはめてしまう。

> 合言葉（付録の芯）: **「重い演算だから退避すれば速くなる」は推論であって観測ではない。**
> 性能について「速くなる／遅くなる」と言う前に、**生成コード（`go build -gcflags=-S`）かベンチマーク（`go test -bench`）で確かめる**。ソースコードの見た目と実行される機械語は1対1ではなく、**その差を埋めるのがコンパイラの仕事**。
> そして最適化の前提は常に **「コンパイラが "値が変わらない" と証明できるか」** ―― ローカル変数なら証明できる、グローバル／ポインタ＋関数呼び出しなら証明できない。**この一線を知っていると、"どこは任せてよく、どこは自分で書くべきか" が判断できるようになる。**

# 付録B: テスト設計 —— 観点設計と変異テスト

> この付録もレビュー後の対話から生まれた。**「テストを何件書けばいいのか」「そのケースは要るのか」への、測定にもとづく答え**。`01` notes の「なんとなく、無駄なテストは逆によくない気がする」という不安が、ここでようやく道具になる。
> レビュアー（AI）が**同じ誤りを2度踏んだ**記録も含む ―― 1度目は `math.MaxInt - 1`（16変異で撤回）、2度目はその代替に挙げた3件（35変異で撤回）。**「測って決める」と書いた直後に、測らずに足した**という経過そのものが学びになる。

## B-1. 変異テストとは何か —— **実装を検証する道具ではない**

いちばん誤解しやすい点から。

```
❌ 実装を壊してテストが赤くなった → 実装が正しいと確認できた
✅ 実装を壊してテストが赤くなった → テストがその種の間違いを見張れている
```

**変異テストは実装の正しさを一切検証しない。** むしろ **「元の実装は正しい」を前提として要求する**:

```
① 実装の正しさは、別の手段で先に確認しておく
     ← 本レビューでは「全数500万件 ＋ 境界60万件をオラクルと突き合わせ」でやった
②  その上で、実装を壊して赤くなるかを見る
     ← ここで測っているのは「テストの十分性」だけ
```

①を飛ばして元の実装が間違っていたら、変異テストは **「間違った実装を守るのにテストが十分か」** を測るだけになる。順序が本質。

### 3つの手法の役割分担

| 手法 | 何を確かめる | 手順 | 嬉しい結果 |
|---|---|---|---|
| **通常のテスト** | **実装**が正しいか | 実装 → テスト実行 | **緑** |
| **オラクル差分 / 全数検証** | **実装**が正しいか（強い版） | 単純で確実な実装と大量入力で突き合わせ | 不一致0 |
| **回帰テスト** | 変更で壊れていないか | 変更前後で同じテストを実行 | **緑** |
| **変異テスト** | **テストが十分か** | **実装をわざと壊す** → テスト実行 | **🔴 赤** |

**変異テストだけが「赤くなったら嬉しい」**。この符号の反転が、慣れるまで一番戸惑うところ。

## B-2. 手順は5ステップ

```
① 正しい実装 ＋ 緑のテスト を用意する
② 実装を1箇所だけわざと壊す        ← これを「変異体（mutant）」と呼ぶ
③ テストを走らせる
④ 赤くなった  → 変異体を「殺せた（killed）」 ✅ テストは仕事をしている
   緑のまま    → 変異体が「生き残った（survived）」🔴 ここが着目点
⑤ 壊した実装は捨てる（リポジトリには何も残さない）
```

**⑤が重要。** 変異体はコミットしない。**測定のために一時的に壊すだけ**で、測り終わったら元に戻す。

### 用語

| 用語 | 意味 |
|---|---|
| **変異体（mutant）** | わざと1箇所壊した実装 |
| **殺す（kill）** | テストがその変異体を検出して赤くなる |
| **生き残る（survive）** | 壊れているのにテストが緑 ―― **ここを調べる** |
| **変異スコア** | 殺せた数 ÷ 全変異体数 |
| **等価変異体** | 壊したつもりが意味が変わらないもの。**どんなテストでも殺せない**（B-4） |

> 実務的な小ネタ: 実験中、`return k` を消して**コンパイルエラー**にしてしまった（`k` が未使用になる）。**コンパイルできない変異体は測定対象外として捨てる** ―― これも通常の作法。

## B-3. 実演: この課題の実ファイルで「変異体が生き残る」瞬間

`02_int_sqrt.go` の**最後の1行だけ**を壊した（`return k` → `return lo`）。それ以外は一切変えていない。

```

A) テスト追加前（7件）で走らせる
   ok   demo/algo   0.330s
   → 実装は壊れているのに緑。変異体が【生き残った】🔴

B) テスト追加後（12件）で走らせる

   --- FAIL: TestFindLargestInteger/maxInt

```

**観点7 で「`n=2` を1件足せば `return k` のオフバイワンが死ぬ」と書いたことの、動く証拠。**

そして出力Bは**重複も可視化している** ―― 同じ1つの変異体を `nisTwo` / `maxInt` / `justBelowLargest` の**3件が同時に殺している**（`largestSquare` と `twoPow62` は落ちていない）。表で見ると抽象的だった「重複」が、テスト出力では一目で分かる。

## B-4. ★ カバレッジ100%でも変異体は生き残る

追加前の7件でカバレッジを測ると:

```
ok  demo/algo  coverage: 100.0% of statements
```

**行カバレッジは100%。全部の行を通っている。** それでも上の変異体は緑のまま通り抜けた。

```
カバレッジ  = その行を【通ったか】
変異テスト  = その行が【間違っていたら気づくか】
```

**通るだけなら、何もアサートしていなくても100%になる。** 「カバレッジ100%だから安心」は成立しない ―― 変異テストはその一段深いところを測る。

## B-5. 生き残った変異体は2種類 —— 危険なのは片方だけ

> 「実装を変更してもテストが緑になる場合があると思う。そのような場合は逆に危ないような気がする」

**この直感は正しく、それがまさに変異テストの検出対象。** ただし緑のままになる理由は2つある:

| 生き残った理由 | 危険か | 対処 |
|---|---|---|
| **(a) テストの穴** | 🔴 **危険** | テストを足す |
| **(b) 等価変異体** | ✅ 無害 | 何もしない（**原理的に殺せない**） |

**(b) 等価変異体**の例（この実装内）:

```go
if mid == n/mid { return mid }   // ← ここで == は return している
if mid < n/mid  { ... }          // だから到達時点で mid != n/mid
                                 // → `<` を `<=` に変えても振る舞いは同一
```

### 見分け方は機械的にできる

**元の実装と変異体を、大量の入力で突き合わせる**（＝差分テスト）:

- 全入力で一致 → **等価変異体**（無害。テストを足しても殺せない）
- どこかで違う → **本物の穴**。しかも**最小の反例がその場で得られ、それがそのまま追加すべきテストケースになる**

## B-6. この実装の変異点は **35個** —— 全件測定した結果

`02_int_sqrt.go` の変異点を機械的に列挙し（**ソース中の数値リテラルと比較演算子に全部印をつける**）、**リポジトリ現在の12ケース**で判定した:

```
殺せた: 29 / 生き残り: 6  →  変異スコア 83%
生き残り6件を差分テストにかけると → 全部 (b) 等価変異体
∴ 実効変異スコア = 29/29 = 100%   本物の穴は1つも無い ✅
```

### 生き残った6件（すべて等価変異体・無害）

| 生き残った変異 | なぜ等価か |
|---|---|
| `n<0` → `n<=0` | `n=0` はどちらの経路でも `0` を返す |
| `lo := 0` → `1` | `n≥2` なら答えは1以上なので影響なし |
| `for lo<hi` → `lo!=hi` | **この実装では `lo` が `hi` を追い越さない**ので同じ |
| `lo+(hi-lo)/2` → `(lo+hi)/2` | **この問題では溢れない**（観点4・付録Aで実測） |
| `mid<q` → `mid<=q` | `==` が既に return 済み |
| `mid>q` → `mid>=q` | 同上 |

> ✅ **副産物: 等価変異体は「性質の機械的な証明」になっている。**
> - `lo!=hi` が等価 = **`lo` と `hi` は交差しない**（`01` 追記1の無限ループが構造的に起きない）
> - `(lo+hi)/2` が等価 = **この問題では `lo+hi` は溢れない**（観点4の主張の裏付け）
> - `<`→`<=` が等価 = **3つの裸 `if` が本当に排他**（観点6の主張の裏付け）
>
> **変異テストは、テストの穴探しと同時に、実装の性質の検証にもなる。**

## B-7. どこを壊すか —— 3層の勘所

### 第1層: 標準の変異オペレータ（ツールが自動でやる範囲）

| オペレータ | 変換 |
|---|---|
| **比較演算子の置換 (ROR)** | `<` ↔ `<=`、`>` ↔ `>=`、`==` ↔ `!=` |
| **算術演算子の置換 (AOR)** | `+` ↔ `-`、`*` ↔ `/` |
| **定数の変更** | `0` ↔ `1`、`+1` → `-1`、`+1` を削除 |
| **条件の反転** | `if cond` → `if !cond`、`true`/`false` に固定 |
| **文の削除** | 代入や1文を丸ごと消す |
| **返り値の置換** | `return x` → `return 0` / 別の変数 |

**機械的なルール: ソース中の「数値リテラル」と「比較演算子」に全部印をつける。それが変異点の全部。** この22行の関数で35箇所だった。

### 第2層: 二分探索の7つの急所（この問題での実測）

| # | 壊す場所 | 例 | 殺したケース |
|---|---|---|---|
| 1 | **ガードの閾値** | `n<0`→`n<=0`、`n==1` 削除、`n<3` | `n=1`, `n=2`, `n=-1` |
| 2 | **初期値** | `hi := n` → `n+1` / `n-1` / `n/2` | `n=0`, `n=2`, `n=4`, `maxInt` |
| 3 | **ループ継続条件** | `lo<hi` → `lo<=hi` / `lo!=hi` | `n=0`, `n=2` |
| 4 | **`mid` の丸め** | 床→天井、`+1`、`-1`、`hi-(hi-lo)/2` | `n=25`, `n=26`, `n=2`, `maxInt` |
| 5 | **比較演算子（4箇所）** | `<`↔`<=`、`>`↔`>=`、`==`↔`!=`、早期return削除 | `n=4`, `n=25`, `n=26` |
| 6 | **更新式の `±1`** | `lo=mid+1`→`mid`/`mid+2`、`hi=mid`→`mid±1`、`k=mid`→`mid±1` | `n=2`, `n=26`, `maxInt` |
| 7 | **返り値** | `return k` → `lo` / `lo-1` / `k+1`、早期return `mid±1` | `n=0`, `n=2`, `maxInt` |

### 第3層: ★ ドメイン固有 —— **ツールが生成しない変異**

```go
mid > n/mid   →   mid*mid > n
```

これは**「オーバーフロー対策を書き戻す」変異**で、比較演算子の置換でも定数の変更でもない。**ツールは自動生成しない。**

そして測ると、これを殺せるのは**巨大値のケースだけ**。**この問題で最も重要な変異が、最も自動化しにくい。**

### 第3層を思いつく最良の材料 = **自分が迷った記録**

notes.md には迷った記録が全部残っている。**「迷った ＝ 間違えうる ＝ 変異点」**:

| notes に書いた迷い | 対応する変異 | 実測 |
|---|---|---|
| `hi = mid` か `hi = mid-1` か（01） | `hi=mid` → `hi=mid-1` | ✅ `n=26` が殺す |
| `for lo != hi` で無限ループした（01） | `lo<hi` → `lo!=hi` | ✅ 等価と判明（この実装では安全） |
| 半開 `[lo,hi)` か左開 `(lo,hi]` か（02） | 返り値 `k`→`lo`/`lo-1` | ✅ `n=2` が殺す |
| 床か天井か（02） | `mid` の丸め変更 | ✅ `n=25`, `n=2` が殺す |
| `mid*mid` が溢れると思った（02） | `mid>n/mid` → `mid*mid>n` | ✅ `maxInt` が殺す |

**人間が実際にやるミスは、ツールが機械的に生成する変異よりも当たりが良い。** その記録が notes.md にあるのが、このドリルの強み ―― **notes を書くこと自体が、次のテスト設計の材料になっている。**

## B-8. 観点設計と変異テストは役割が違う（両方必要）

> **「テスト観点を決めた上で、その観点に沿ってテストを書くのが良い。観点がなく、とりあえず巨大値を追加するのは意味がなく時間がかかるだけ」**

この原則は正しく、業界標準のテスト設計そのもの（テスト観点 → テスト条件 → テストケース）。**そして本レビューが2度踏んだ誤りを、この原則で説明できる。**

ただし正確な診断は「観点がなかった」ではない:

| 撤回したケース | 挙げた理由 | それは観点か | 実際の問題 |
|---|---|---|---|
| `math.MaxInt - 1` | 「上限の近く」 | ❌ 観点ではない | 大きさは観点ではない |
| `K² - 1` | 「答えが変わる境界」 | ✅ **正当な観点** | **既に `8/9/10`, `24/25/26` でカバー済み**（観点の重複） |
| `K²` | 「早期return経路を巨大スケールで」 | ✅ **正当な観点** | **既に `4/25/26` でカバー済み**（観点の重複） |
| `1 << 62` | 「期待値が `2³¹` と暗算できる」 | ❌ 観点ではない | 書き手の都合（書きやすさ）。検出力とは無関係 |

> **「観点があるか」だけでは足りない。「その観点はまだカバーされていないか」まで要る。**
> しかも厄介なことに、**観点があるぶん正当化されやすい** ―― 「答えが変わる境界だから必要」と書かれたケースは、レビューで削りにくい。**観点なしのケースより、重複した観点を持つケースの方が生き残ってしまう。**

### 重複を見えるようにするには、観点の抽象度を下げる

```
❌ 「答えが変わる境界を確かめる」                        ← この高さでは小さい側との重複が見えない
✅ 「`k = mid` を `k = mid-1` と書き間違えたら落ちるか」   ← ここまで下ろすと n=8 で既に死ぬと分かる
```

**観点は「実装のどの間違いを捕まえるか」まで下ろす。** 逆に「境界を確かめる」「大きい値を確かめる」に留まると、**同じ観点を別の値で何度も足せてしまう。**

### 上流（観点設計）と下流（変異テスト）

| | いつ | 何をする | 単独での限界 |
|---|---|---|---|
| **観点設計** | 書く**前** | 何を確かめるかを列挙し、ケースを導出 | **重複に気づけない**（観点があったのに4件足した） |
| **変異テスト** | 書いた**後** | 「このケースだけが殺せるものがあるか」を測る | **書いた変異の範囲しか保証しない** |

**片方だけでは足りない。** 観点だけでは「立派な観点を持った重複ケース」を止められず、変異テストだけでは「35件の外」が見えない。

### この課題のテスト観点一覧（8観点・ケースと1対1）

| # | 観点（何を確かめるか） | 捕まえる実装ミス | ケース | 状態 |
|---|---|---|---|---|
| 1 | 契約外の入力の扱い | 負数を素通しする | `n = -1` | ✅ 既存 |
| 2 | ガードの境界（ループに入る/入らない） | ガードを `n<1` / `n<3` と書き間違える | `n = 0, 1, 2` | ✅ `2` 追加済み |
| 3 | **早期return で抜ける経路** | `hi = mid` を `hi = mid-1` にする | `n = 4, 25, 26` | ✅ 既存 |
| 4 | **ループ後の `k` で返る経路** | `return k` を `return lo` にする | `n = 2, 8` | ⚠ `2` のみ。`8` 未追加 |
| 5 | 答えが変わる境界（`k²-1 / k² / k²+1`） | `k = mid±1` の off-by-one | `n = 8, 9, 10`（＋既存 `24,25,26`） | ⚠ 未追加 |
| 6 | **乗算オーバーフロー耐性** | `mid > n/mid` を `mid*mid > n` に戻す | **`n = math.MaxInt`（1件で足りる）** | ✅ 追加済み |
| 7 | 停止性（無限ループしない） | `lo = mid+1` を `lo = mid` にする | `n = 2` ＋ `-timeout 30s` | ⚠ timeout 未設定 |
| 8 | 答えの定義そのもの | 上記すべての取りこぼし | プロパティテスト（`k² ≤ n < (k+1)²`） | ⚠ 未追加 |

**観点6 は「巨大値を試す」ではなく「乗算が溢れないことを確かめる」と書く。** この粒度にすれば、必要な件数が自然に1件だと分かる ―― 溢れるのは「桁が大きい」からであり、**大きい値を何個並べても確かめているのは同じ1つのこと**。当初レビューが4件並べたのは、観点6を「巨大値の観点」と粗く持っていたから。**観点の粒度が粗いと、ケースが増える。**

## B-9. 実務での使い方（3段階）

| | 実行タイミング | コスト | 用途 |
|---|---|---|---|
| **軽量** | 新しいテストを足すか迷ったとき | 数秒 | **1箇所壊して `go test` を1回打つ** → 「そのケースは要るか」が即分かる |
| **中量** | 節目・テスト設計の見直し | 30分程度 | 急所リスト（B-7 第2層）を手で1周（今回やったのがこれ・35変異） |
| **重量** | 週次 / 夜間 CI | テスト時間 × 変異体数 | ツールで全自動 |

ツール: Go は `gremlins` / `go-mutesting`。他言語は PIT（Java）、Stryker（JS/TS）、mutmut（Python）。

**ドリルでは手でやるのが一番学べる。** 「1行壊して `go test`」だけなので、**迷ったときに1回やれば数秒で決着する。**

## B-10. 結論 —— この課題のテストは実効100%。あと削れるのが3件

```
現状（12ケース）: 35変異中29殺 ＋ 生き残り6件は全部等価変異体
                → 実効変異スコア 100%・本物の穴は無し ✅
```

| やること | 内容 |
|---|---|
| **削る（3件）** | `largestSquare` / `justBelowLargest` / `twoPow62` ―― 単独で殺せる変異が1つも無い。巨大値は `maxInt` の1件で足りる |
| **足す（観点4・5・7・8）** | `n=8, 9, 10`（答えが変わる境界＋`k` 経路）／`-timeout 30s`（停止性を「失敗」として可視化）／プロパティテスト |

> 合言葉（付録Bの芯）: **変異テストは「実装が正しいか」ではなく「テストが十分か」を測る道具。だから元の実装の正しさは先に別手段で確認しておく。**
> そして **「壊したのに緑」は2種類ある** ―― 本物の穴（テストを足す）と等価変異体（原理的に殺せない・無害）。**大量入力の差分テストで機械的に見分けられ、本物の穴なら最小の反例＝追加すべきテストケースがその場で手に入る。**
> **テストを足す条件は「名前の付いた具体的な実装ミスを1つ以上、単独で殺せるか」。** 「大きいから」「境界の隣だから」「暗算できるから」は理由ではなく、確認していない仮説 ―― 本レビューはそれで2度足して2度撤回した。
> **上流に観点設計（何を確かめるか）、下流に変異テスト（本当に効いているか）。観点は「実装のどの間違いを捕まえるか」まで下ろすと、重複が自動的に見える。**
