# 二分探索アルゴリズムまとめ

一致検索（値そのものを探す）と境界検索（lower_bound）の 2 パターンを整理する。

---

## 0. 成立条件は「ソート済み」ではなく「単調性」

二分探索が使える本当の条件は、**判定結果が一方向にしか変化しないこと**（単調性）。

| 階層 | 内容 | 役割 |
|---|---|---|
| データの性質 | 要素が昇順に並んでいる | 述語の単調性を作り出すための**材料** |
| 問いの性質 | 述語が 偽…偽 真…真 の順に並ぶ | 二分探索が直接使っている**条件** |

ソート済みであることは十分条件のひとつにすぎない。述語の単調性さえ得られれば、探索対象が配列である必要すらない。

## 1. 共通の道具立て

### 1.1 不変条件（invariant）

境界の ±1 を勘で決めないための最重要ツール。ループ中ずっと成り立ち続ける性質を、最初に日本語で宣言してしまう。

> 「求める答えが存在するなら、それは必ず区間 `[l, h]`（または `[l, h)`）の中にある」

この一文が真であり続けるように `l` と `h` を更新する、と考えると、更新式は不変条件から自動的に導ける。

### 1.2 区間表記：閉区間と半開区間

数学の区間表記そのもの。角カッコが「含む」、丸カッコが「含まない」。

- `[a, b]` … **閉区間**。両端とも含む（a 以上 b 以下）
- `[a, b)` … **半開区間**。左端は含み、右端は含まない（a 以上 b 未満）

要素数 5 の配列で `h` が指す位置が変わる。

```
closed [l, h]      idx      0    1    2    3    4
                   val      2    5    8   12   16
                            l                   h
                            h is the LAST element (included)

half-open [l, h)   idx      0    1    2    3    4   (5)
                   val      2    5    8   12   16    -
                            l                        h
                            h is ONE PAST the last (excluded)
```

| 項目 | 閉区間 `[l, h]` | 半開区間 `[l, h)` |
|---|---|---|
| `h` の初期値 | `n - 1` | `n` |
| ループ継続条件 | `l <= h` | `l < h` |
| 空区間の表現 | `h = l - 1`（不自然・負値の危険） | `l == h`（自然） |
| 要素数 | `h - l + 1` | `h - l` |
| 区間の連結 | 境界で ±1 の調整が必要 | `[0,3)` + `[3,5)` = `[0,5)` と綺麗 |

**初期値と継続条件はペア。1 つのループの中で 2 つの流儀を混ぜない。**

### 1.3 なぜ半開区間が好まれるのか

#### 発想の転換：添字はマスではなく「目盛り」

半開区間が直感に反して感じられる原因は、**添字を「配列のマスにつけた番号」だと思っている**ことにある。その前提だと、5 要素の配列に添字 5 のマスは存在しないので `h = 5` が宙に浮く。

半開区間の世界では、添字は**マスとマスの境目（目盛り）**に振られていると考える。定規と同じ。

```
tick     0    1    2    3    4    5      <- indices label the BOUNDARIES
         |    |    |    |    |    |
         +----+----+----+----+----+
cell     | 2  | 5  | 8  | 12 | 16 |      <- 5 elements
         +----+----+----+----+----+
              |<------------>|
              [1, 4) -> 3 elements  (= 4 - 1)
```

この見方に切り替えると、`h = 5` は「存在しない 6 番目のマス」ではなく「配列の右端という**実在する境目**」になる。存在しないものを指しているわけではない。

これは lower_bound における「境界は n+1 通りある」（→ 3.3）とまったく同じ構造。**半開区間と lower_bound は別々の知識ではなく、同じ構造の別の顔**である。

#### 4 つの構造的な利点

「バグが減る」のは結果であって理由ではない。原因は以下の 4 点。

| # | 利点 | 内容 |
|---|---|---|
| 1 | **要素数が引き算 1 回で出る** | `h - l` がそのまま個数。閉区間の `h - l + 1` の「+1」書き忘れが典型的な off-by-one。目盛りの見方なら「5cm から 2cm まで＝3cm」と同じで、+1 が発生する余地がない |
| 2 | **空の表現に負の数が要らない** | 閉区間で空は `h = l - 1`。`l = 0` なら `h = -1` となり、**添字として不正な値を正常な状態を表すのに使う**ことになる（符号なし整数なら破綻）。半開区間は `l == h` で、不正な値が一度も登場しない |
| 3 | **連結で境界が重複も欠落もしない** | `[0,3)` + `[3,5)` = `[0,5)` で `3` がちょうど 1 回だけ現れる。閉区間だと `[0,2]` と `[3,4]` で境界が飛び、分割のたびに ±1 の調整が要る |
| 4 | **境界そのものを答えにできる** | 半開区間なら `0`〜`n` のすべてが正当な返り値になるので lower_bound が書ける。閉区間の枠組みには「全要素より大きい」という答えを置く場所がない |

このうち **2 が最もバグ削減に効いている**。「異常値を正常系の表現に流用しない」という設計原則そのものであり、負値・符号なし整数・範囲外アクセスといった別種の問題を芋づる式に防いでいる。

#### ただし常に半開区間が優れているわけではない

一致検索**だけ**を書くなら閉区間でも何ら問題はなく、閉区間で書かれた正しい二分探索はいくらでもある。

半開区間の優位が出るのは上表の 2〜4、すなわち**空区間・連結・境界を扱うようになったとき**。逆に言えば、そこに踏み込まない限り差は体感しにくい。

#### 語彙

| 出典 | 内容 |
|---|---|
| Go のスライス式 `a[1:4]` | 上の図そのもの。要素数が `4 - 1` で出て、`a[i:i]` が空になる |
| C++ の `begin()` / `end()` | `end()` は最後の要素の 1 つ後ろ。「終端イテレータは要素を指さない」という設計の由来 |
| Dijkstra "EWD831" | 「なぜ添字は 0 から始めるべきか」を論じた短文。半開区間が最良である理由を上表の 1〜3 とほぼ同じ論法で議論している |

### 1.4 mid の求め方と丸め方向

- `(l + h) / 2` は理論上オーバーフローしうるので `l + (h - l) / 2` が定石
- 整数除算は切り捨てなので、要素が偶数個のとき中央 2 つの**左側**が選ばれる

分割が不均等になること自体は正しさに影響しない（捨てる側が「絶対にありえない」ことさえ保証されていればよい）。**丸め方向が問題になるのは更新式との組み合わせ。**

| 更新式の形 | 必要な丸め | 理由 |
|---|---|---|
| `l = m + 1` / `h = m - 1` | 切り捨てでよい | m を必ずどちらかから除外するので区間が必ず縮む |
| `l = m + 1` / `h = m` | 切り捨てでよい | l 側が必ず進むので区間が必ず縮む |
| `l = m` / `h = m - 1` | **切り上げが必要** | 区間が 2 要素のとき m が l と一致し、永久に縮まない |

一般化すると「**m を残す側とは反対方向に丸める**」。

#### 閉区間と半開区間で m の位置は変わるか

**変わることがある。** 同じ探索範囲を表していても `h` の値が 1 違うため、`(l + h) / 2` の結果が変わる。

`[2, 5, 8, 12]`（4 要素）の全体を範囲としたとき：

| | `l` | `h` | `m = (l+h)/2` | 指す要素 |
|---|---|---|---|---|
| 閉区間 `[0, 3]` | 0 | 3 | **1** | `5`（中央 2 つの左） |
| 半開区間 `[0, 4)` | 0 | 4 | **2** | `8`（中央 2 つの右） |

| 区間の要素数 | 閉区間 | 半開区間 |
|---|---|---|
| 奇数 | 同じ位置（真の中央） | 同じ位置（真の中央） |
| 偶数 | 中央 2 つの**左** | 中央 2 つの**右** |

閉区間は左寄り、半開区間は右寄り。ただし分割が不均等になること自体は正しさに影響しない。

なお `l + (h - l) / 2` はオーバーフロー対策であって、計算結果は `(l + h) / 2` と数学的に同一。書き換えても寄り方は変わらない。

#### ★ 半開区間の隠れた安全性

この右寄りが重要な性質を生んでいる。**半開区間では `l < h` である限り、必ず次が成り立つ。**

```
l <= m < h        (m は絶対に h に届かない)
```

したがって **`h = m` という更新は、必ず `h` を真に小さくすることが構造的に保証される**。

- 半開区間 + `h = m` … 切り捨てのままで**無限ループが起きない**
- 閉区間 + `h = m` … `l == h` のとき `m == l == h` となり `h = m` が何も変えず、**無限ループが発生しうる**

lower_bound が `h = m`（m を捨てない更新）を使いながら素直に書けるのは、この性質のおかげ。「m を残す側とは反対に丸める」という注意は、閉区間側でこの保証が失われる状況への対処だった。

**覚えるべき対応関係：`h = m` を使いたいなら半開区間を選ぶ。**

## 2. パターンA：一致検索

### 2.1 目的

target と**等しい要素の添字**を返す。存在しなければ `-1`。同じ値が複数ある場合、どれが返るかは保証されない。

### 2.2 動作

`target = 38` を `[2, 5, 8, 12, 16, 23, 38, 56]` から探す。

```
idx      0    1    2    3    4    5    6    7
val      2    5    8   12   16   23   38   56

step1    2    5    8   12   16   23   38   56
         l              m                   h
         38 > 12  ->  discard left half AND m

step2    .    .    .    .   16   23   38   56
                            l         m     h
         38 > 23  ->  discard left half AND m

step3    .    .    .    .    .    .   38   56
                                      lm    h
         38 == 38  ->  return idx 6
```

1 回の比較で候補が半分になる。8 要素が 3 回で決着。

### 2.3 仕様

| 項目 | 内容 |
|---|---|
| 探索対象 | **要素**（n 個） |
| 不変条件 | target が存在するなら `[l, h]` の中にある |
| 初期値 | `l = 0`, `h = n - 1` |
| 分岐 | `<` / `==` / `>` の**三分岐** |
| 更新式 | `target > val[m]` → `l = m + 1` ／ `target < val[m]` → `h = m - 1` |
| 終了条件 | **`m` と target が一致**（成功） ／ **区間が空**（失敗） |
| 出口 | **2 本**（早期脱出あり） |
| 比較回数 | 最良 1 回、最悪 `⌈log₂(n+1)⌉` 回 |

### 2.4 落とし穴

- **「見つからなかった」側の出口を忘れる。** 三分岐がすべて `return` / `continue` すると、失敗時の脱出経路が消えて無限ループか範囲外アクセスになる
- **区間が空になったことを検査せずに `val[m]` を読む。** 検査は読んだ後ではなく**読む前**に置く
- **`l == h` は「見つからなかった」ではない。** 候補がまだ 1 個残っている状態。閉区間で候補が尽きるのは `l > h`
- **`m` を状態として持ち回らない。** `m` は `l` と `h` から一意に決まる従属変数。ループ先頭で 1 回だけ導出する形にすると、その直前が終了判定の自然な置き場所になる

## 3. パターンB：境界検索（lower_bound）

### 3.1 目的

**target 以上である最初の要素の添字**を返す。target が存在しなければ、そこに挿入すべき位置を返す。

- 一致しても即座に打ち切らない（重複の「最初の 1 つ」を保証するため）
- 「見つからなかった」という戻り値が存在しない。常に `0` 以上 `n` 以下を返す

### 3.2 動作：探しているのは要素ではなく「境界」

`target = 3` を `[1, 3, 3, 3, 5, 8]` から探す。述語は「`val[i] >= 3`」。

```
idx      0    1    2    3    4    5
val      1    3    3    3    5    8
pred     F    T    T    T    T    T
              ^
              +-- lower_bound = 1  (first position where pred is true)
```

ソート済みなら述語の値は必ず `F...F T...T` の形に並ぶ。この**偽から真への切り替わり点**が答え。

### 3.3 探索空間が n+1 通りになる理由

境界は「要素」ではなく「隙間」なので、要素が n 個なら候補位置は n+1 個ある。

```
        [ 1 ][ 3 ][ 5 ]
        ^    ^    ^    ^
        0    1    2    3     <- boundary positions: n+1 = 4
          0    1    2        <- element indices:    n   = 3
```

全要素が target より小さければ答えは `n` になる。だから `h` の初期値は `n - 1` ではなく **`n`**。

### 3.4 仕様

| 項目 | 内容 |
|---|---|
| 探索対象 | **境界位置**（n+1 通り） |
| 不変条件 | 求める境界は `l` 以上 `h` 以下にある |
| 初期値 | `l = 0`, `h = n` |
| 分岐 | 述語の真偽の**二分岐** |
| 更新式 | `val[m] < target` → `l = m + 1` ／ それ以外 → `h = m`（**m を捨てない**） |
| 終了条件 | **`l == h` に収束**したとき。その値が答え |
| 出口 | **1 本**（早期脱出なし） |
| 比較回数 | 常に `⌈log₂(n+1)⌉` 回で一定 |

`h = m` は m を残す更新だが、`l` 側が必ず `m + 1` で進むため、切り捨てのままで区間は必ず縮む。

### 3.5 派生

述語を差し替えるだけで別物になる。

| 目的 | 述語 / 式 |
|---|---|
| lower_bound | `val[i] >= target` … target 以上の最初の位置 |
| upper_bound | `val[i] > target` … target より大きい最初の位置 |
| 出現回数 | `upper_bound - lower_bound` |
| 存在判定 | 結果が `n` 未満 かつ `val[結果] == target` |
| 挿入位置 | 返り値の位置に挿入すればソート順が保たれる |

### 3.6 落とし穴

- **`h = n - 1` で始めてしまう。** 答えが `n` になるケース（全要素が target より小さい）を取りこぼす
- **一致した時点で return してしまう。** 重複があるとき「最初の 1 つ」の保証が壊れる
- **重複の先頭を丸め方向で取ろうとする。** どの重複に当たるかは丸めではなく**更新式（不変条件の立て方）**で決まる

## 4. 2 パターンの比較

| 観点 | 一致検索 | 境界検索（lower_bound） |
|---|---|---|
| 何を絞り込むか | 要素（n 個） | 境界位置（n+1 個） |
| `h` の初期値 | `n - 1` | `n` |
| 分岐数 | 三分岐（`<` `==` `>`） | 二分岐（述語の真偽） |
| 終了条件 | `m` が target と一致 | `l` と `h` が一致 |
| 早期脱出 | あり | なし |
| ループの出口 | 2 本 | 1 本 |
| 見つからない場合 | `-1` を返す | 挿入位置（`0`〜`n`）を返す |
| 比較回数 | 最良 1 回・最悪 log₂n 回 | 常に log₂n 回 |
| 重複時の保証 | どれが返るか不定 | 必ず先頭 |

### 抽象度の関係

- **lower_bound があれば一致検索は作れる**（境界を求め、その位置の要素が target と等しいか 1 回確かめるだけ）
- **一致検索から lower_bound は作れない**（「どれか 1 つ」しか返さないため、重複の先頭情報が失われている）

lower_bound のほうがより一般的で原始的な操作。一致検索は**特殊化された派生形**であり、特殊化のためにループの出口が 2 本に増えて壊れやすくなっている。

C++ 標準ライブラリが `lower_bound` / `upper_bound` を基本部品として提供し `binary_search` をその上に薄く乗せている構成、Go の `sort.Search` が値ではなく**述語**を受け取る設計も、この階層関係を反映している。

## 5. 述語と規約 —— コードが「何に依存しているか」を見分ける

> ここまでは二分探索の書き方の話。この節は、そこから取り出せる**コーディング一般に効く考え方**を扱う。
> ※ この節では実装に合わせて `lo` / `hi` / `mid` と表記する（0〜4 節の `l` / `h` / `m` と同じもの）。

### 5.1 二分探索は 2 つの層でできている

同じコードの中に、**性質のまったく違う 2 種類の決定**が混ざっている。

```
┌─────────────────────────────────────────────┐
│  述語の層 …… 「この値は答えの資格があるか?」  │  ← 問題が決める
│      ok(k) = (k*k <= n)                     │
├─────────────────────────────────────────────┤
│  規約の層 …… 「まだ調べていない範囲の表し方」  │  ← 自分が決める
│      半開 [lo,hi) / 閉 [lo,hi] / 左開 (lo,hi]│
└─────────────────────────────────────────────┘
```

| | **述語**（predicate） | **規約**（convention） |
|---|---|---|
| 何か | 値を渡すと 真/偽 を返すもの（`func(x) bool`） | 探索範囲をどう表すかの取り決め |
| 例 | `k*k <= n`、`val[i] >= target` | `[lo,hi)` / `[lo,hi]` / `(lo,hi]` |
| **誰が決めるか** | **問題（仕様）** | **自分（実装者）** |
| **選択肢** | **無い**（変えたら別の問題） | **3 つ以上ある**（どれでも正しく書ける） |
| **変化率** | **低い** | **高い**（リファクタで実際に乗り換える） |

「述語」は論理学の用語で、国語の主語・述語とは別物。**はい/いいえを答える関数**のこと。Go の `sort.Search(n, func(i int) bool {...})` が受け取っているのがまさにこれ（→ 4 節末）。

### 5.2 コードのどの行がどちらの層か

```go
if mid <= n/mid {    // ★ 述語の評価 ―― 「mid は答えの資格があるか?」
    lo = mid + 1     // ← 規約 ―― 「半開だから mid を捨てて lo を進める」
    k = mid          // ★ 述語が真だった、という記録
} else {
    hi = mid         // ← 規約 ―― 「半開だから mid を残して hi を縮める」
}
return k             // ★ 述語側の値を返す
```

**同じ述語を 3 規約で書き比べると、境目がはっきり見える。**

```
--- 半開 [lo,hi) ---          --- 閉 [lo,hi] ---           --- 左開 (lo,hi] ---
lo, hi := 0, n        ←違う   lo, hi := 1, n        ←違う   lo, hi := 1, n         ←違う
for lo < hi {         ←違う   for lo <= hi {        ←違う   for lo < hi {          ←違う
  mid := lo+(hi-lo)/2 ←違う     mid := lo+(hi-lo)/2 ←違う     mid := lo+(hi-lo+1)/2←違う
  if mid <= n/mid {   ★同一     if mid <= n/mid {   ★同一     if mid <= n/mid {    ★同一
    lo = mid + 1      ←違う       k = mid           ★同一       lo = mid           ←違う
    k = mid           ★同一       lo = mid + 1      ←違う       k = mid            ★同一
  } else {                      } else {                     } else {
    hi = mid          ←違う       hi = mid - 1      ←違う       hi = mid - 1       ←違う
  }                             }                            }
}                             }                            }
return k              ★同一   return k              ★同一   return k               ★同一
```

- **★（述語の評価・真だった記録・返り値）は 3 つとも 1 文字も違わない**
- **←（初期値・継続条件・`mid` の丸め・更新式）は 3 つとも全部違う**

### 5.3 だから何が嬉しいのか —— `return k` と `return lo - 1`

整数平方根（`floor(sqrt(n))`）の実装で、答えの返し方に 2 通りある。

```go
return k         // 述語側: 「述語が真だと確認できた最大の mid」
return lo - 1    // 規約側: 「半開区間だから、境界の 1 つ手前」
```

**どちらも正しく動く**（全数 500 万件で検証済み）。バグの話ではなく、**何に依存して書くかの選択**の話。

#### ① 読むときの差（日常的にはこれが一番大きい）

| | 読み手がすること |
|---|---|
| `return k` | 課題文に「`k*k <= n` を満たす最大の整数 `k`」とある。その `k` を返している ―― **推論 0 段** |
| `return lo - 1` | 「`lo` は最初に偽になる値で止まる」→「だから 1 つ前」→「`lo >= 1` なので `lo-1 >= 0`」 ―― **推論 3 段** |

`return lo - 1` を読むには **「今どの規約で書いていたか」を思い出す**必要がある。`return k` には要らない。

#### ② 規約を変えたときの差（実測）

区間規約を乗り換えて、両者がどうなるか測った（`n = 0〜300,000` 全数）。

| 規約 | `return k` | `return lo - 1` |
|---|---|---|
| 半開 `[lo,hi)` | ✅ 不一致 0 | ✅ 不一致 0 |
| 閉 `[lo,hi]` | ✅ 不一致 0 | ✅ 不一致 0 |
| **左開 `(lo,hi]`** | 🔴 **2 件**（`n=2,3`・初期値のズレ） | 🔴 **299,999 件（ほぼ全滅）** |

原因は **`lo` の意味が規約ごとに変わる**こと。

| 規約 | ループ終了時の `lo` の意味 | 答えの取り出し方 |
|---|---|---|
| 半開 `[lo,hi)` | 最初に**偽**になる値 | `lo - 1` |
| 閉 `[lo,hi]` | 最初に**偽**になる値 | `lo - 1` |
| 左開 `(lo,hi]` | **最後に真である値（答えそのもの）** | **`lo`** |

「`lo` 側に候補を残すか捨てるか」が規約の定義そのものなので、`lo` の意味は規約と一緒に動く。**`lo` から作った式も一緒に壊れる。**

> なお `k` の 2 件は初期値 `k := 0` が原因で、**`k := lo` と書けば 3 規約すべてで不一致 0** になる。「`k` は `lo` と同じ確信度から始まる」と書けば、規約の初期値を自動で追随する。

#### 結論

**述語側（`return k`）に寄せるのが良い。** ただし条件が 1 つ。

```go
// k: 述語 mid <= n/mid（= mid*mid <= n）を満たすと確認できた最大の mid。
//    ループを抜けた時点でこれが答え。
k := lo
```

`k` を残す唯一のコストは「この `k` は常に最新か?」を読み手が疑えること。**不変条件を 1 行書けば消える**（→ 1.1）。

### 5.4 一般化 —— コードの正しさは、どの前提に依存しているか

```
どんなコードも、必ず何らかの「前提」の上で正しい。
その前提を特定し、【誰が決めたか】で分類する。

   問題（仕様）が決めた前提に依存    → 強い。仕様が変わらない限り壊れない
   自分（実装）が決めた前提に依存    → 弱い。実装方針を変えると壊れる
```

#### 実践手順（4 ステップ）

| # | やること |
|---|---|
| ① | **この行が正しい根拠を書き出す** |
| ② | 各根拠は「仕様由来」か「自分の判断由来」か |
| ③ | 判断由来に依存しているなら、**仕様由来のものに付け替えられないか** |
| ④ | 付け替えられないなら、**その前提をコメントで明示する**（＝不変条件の宣言） |

`return lo - 1` に①を当てると:

```
根拠1: lo は「最初に偽になる値」で止まる   ← ★自分の判断（半開規約を選んだから）
根拠2: よって答えはその 1 つ前
```

`return k` に当てると:

```
根拠1: k には述語が真だった mid しか入らない  ← 仕様由来
根拠2: 真側では mid が増加していく            ← 二分探索の性質（規約非依存）
```

**③が効かないときは④に落とす** ―― これが「不変条件を最初に日本語で宣言する」（→ 1.1）の正体。**不変条件を書くとは、依存している前提を可視化することだった。**

#### ★ いちばん実用的な系: 「同じ値だから消せる」の罠

`k == lo - 1` は常に成り立つ。ここで「冗長だから `k` を消そう」と考えるのは**category error**。

```
❌ k == lo-1 だから、k は lo-1 から導出される値 → 消せる
✅ k == lo-1 は「今の規約のもとで偶然一致している」だけ → 消すと規約変更で壊れる
```

`k` は `lo` から導かれているのではなく、**独立に「述語が真だった最大の mid」と定義されている**値。たまたま今の規約で `lo-1` と一致している（左開規約なら `lo` と一致する）。

> **一般則: 「同じ値だから片方消せる」の前に、"なぜ同じ値なのか" を確認する。**
>
> | なぜ同じか | 判断 |
> |---|---|
> | **定義から必然的に同じ**（真の導出） | 消してよい。計算式に置き換える。例: `count` を持たず `len(s)` を使う |
> | **今の実装判断のもとで偶然一致** | **消すな**。その判断を変えた瞬間に壊れる |

これは「導出値をフィールドに持つな」という一般的な助言の**例外条件**にもなっている。`len()` は定義から必然なので持つ必要がない。`k` は偶然の一致なので持つ意味がある。

### 5.5 二分探索以外での現れ方

同じ構図はあちこちに出てくる。

**① 区間の端点**

```go
return endTime - 1*time.Second   // 弱い: 「閉区間だから最後の 1 秒前」＝規約に紐づく
return endTime                   // 強い: 排他境界として定義（仕様に紐づく）
```

半開区間 `[start, end)` が Go のスライス・Python のスライス・HTTP Range で標準なのは、**端点の意味が実装に依存しないから**（→ 1.3）。

**② ページング**

```sql
OFFSET (page - 1) * size            -- 弱い: page が 1-based か、size 固定かに依存
WHERE created_at > :lastSeenAt      -- 強い: データそのものに紐づく（キーセット）
```

キーセットページングが壊れにくいのは、ページ番号という**取り決め**ではなく**データ**に紐づいているから。

**③ API の戻り値**

```go
func LastIndex() int    // 弱い: 内部が配列であることに紐づく
func Count() int        // 強い: 呼び出し側が知りたいこと（仕様）に紐づく
func Last() (Item, bool)
```

内部をリンクリストや map に変えた瞬間、`LastIndex()` は意味を失う。

### 5.6 いつ意識すると得か / いつ気にしなくていいか

| 意識するメリットが大きい場面 | 理由 |
|---|---|
| **実装方針を変える（リファクタ）とき** | 規約に紐づいた式が壊れる。壊れる箇所が事前に分かる |
| **他人（未来の自分）が読むとき** | 仕様の語彙で書かれていれば、実装の文脈を思い出さなくて済む |
| **「これ冗長では?」と指摘されたとき** | 消す前に「なぜ同じ値か」を確認する判断材料になる |
| **公開 API / DB スキーマ / 外部インターフェース** | 壊れた影響が外に漏れるので、**同じ判断ミスの代償が桁違い** |

| 気にしなくていい場面 | 理由 |
|---|---|
| 使い捨てスクリプト | 変更されないので、変化率の議論に意味がない |
| **真の導出**（`len()`、`a == b` の否定など） | 定義から必然なので、規約が変わっても壊れない |
| 前提が本当に不変なもの | 例: 1 バイトは 8 ビット |

**やりすぎ注意 3 点**

- **「変数を足せば強くなる」ではない。** 原則が言うのは「**消す前に依存先を確認せよ**」だけ
- **スケールで重みが違う。** 関数内のローカル変数なら壊れても即テストが赤くなる（左開に変えた失敗は `n=2` のテスト 1 件で捕まった）。API なら回復コストが跳ね上がる
- **「変化率が低い」の見積もりは外れる。** 「仕様は変わらない」と思った前提が変わることは普通にある。だから④（コメントで明示）が保険として要る

### 5.7 既に名前が付いている考え方

この節の内容は、既存の設計原則を関数内の 1 行のレベルまで下ろしたものと言える。

| 原則 | 言っていること |
|---|---|
| **情報隠蔽**（Parnas, 1972） | モジュール分割の基準は「**変わりそうなもの**を隠すこと」。機能単位ではなく**変化の単位**で分ける ―― この考えの元祖 |
| **Stable Dependencies Principle** | 依存は**安定な方向へ**向けよ |
| **ユビキタス言語**（DDD） | コードは**ドメイン（仕様）の語彙**で書く。`k`（課題文の語彙）vs `lo-1`（実装の語彙）はまさにこれ |

### 5.8 まとめ

```
述語 = 問題が決めたこと（変わらない）
規約 = 自分が決めたこと（変わりうる）

  → 変わらないものに紐づけた変数は、変わるものに紐づけた式より壊れにくい
  → 付け替えられないなら、依存している前提をコメントで明示する
```

- [ ] 判断由来なら、仕様由来のものに付け替えられないか
- [ ] 付け替えられないなら、その前提をコメントに書いたか
