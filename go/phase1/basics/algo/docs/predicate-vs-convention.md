# 述語と規約 —— コードが「何に依存しているか」を見分ける

> **対象**: ジュニアエンジニア
> **前提知識**: 二分探索の基本（→ [binary-search-notes.md](./binary-search-notes.md)）。ただし二分探索を知らなくても 4 節以降だけ読めば伝わるように書いてある。
> **出どころ**: `02_int_sqrt`（整数平方根）のレビュー中に出てきた「`return k` と `return lo - 1`、どちらで書くべきか」という具体的な問いから、一般化できる考え方を取り出したもの。

---

## この文書で言いたいこと

```
どんなコードも、必ず何らかの「前提」の上で正しい。

   問題（仕様）が決めた前提に依存    → 強い。仕様が変わらない限り壊れない
   自分（実装）が決めた前提に依存    → 弱い。実装方針を変えると壊れる

  → 前者に寄せて書く。寄せられないなら、その前提をコメントで明示する。
```

以下、二分探索という具体例で「述語」と「規約」という 2 つの層を切り分け、そこから一般論を取り出す。

---

## 1. 二分探索は 2 つの層でできている

同じコードの中に、**性質のまったく違う 2 種類の決定**が混ざっている。

```
┌──────────────────────────────────────────────┐
│  述語の層 …… 「この値は答えの資格があるか?」   │  ← 問題が決める
│      ok(k) = (k*k <= n)                      │
├──────────────────────────────────────────────┤
│  規約の層 …… 「まだ調べていない範囲」の表し方  │  ← 自分が決める
│      半開 [lo,hi) / 閉 [lo,hi] / 左開 (lo,hi] │
└──────────────────────────────────────────────┘
```

| | **述語**（predicate） | **規約**（convention） |
|---|---|---|
| 何か | 値を渡すと 真/偽 を返すもの（`func(x) bool`） | 探索範囲をどう表すかの取り決め |
| 例 | `k*k <= n`、`val[i] >= target` | `[lo,hi)` / `[lo,hi]` / `(lo,hi]` |
| **誰が決めるか** | **問題（仕様）** | **自分（実装者）** |
| **選択肢** | **無い**（変えたら別の問題） | **3 つ以上ある**（どれでも正しく書ける） |
| **変化率** | **低い** | **高い**（リファクタで実際に乗り換える） |

### 「述語」という言葉について

論理学・プログラミングの用語で、国語の主語・述語とは別物。**はい/いいえを答える関数**のこと。

```go
sort.Search(n, func(i int) bool { ... })   // ← この func(i int) bool が述語
```

Go の `sort.Search` が「探す値」ではなく「**述語**」を受け取る設計になっているのは、述語こそが問題の本体だから。

### 具体例: 述語を全部の値で評価してみる

`n = 26` のとき、述語 `ok(k) = (k*k <= 26)`:

| k | k*k | `k*k <= 26` ? |
|---|---|---|
| 0 | 0 | ○ 真 |
| 1 | 1 | ○ 真 |
| 2 | 4 | ○ 真 |
| 3 | 9 | ○ 真 |
| 4 | 16 | ○ 真 |
| **5** | **25** | **○ 真 ← 最後の「真」＝ これが答え** |
| 6 | 36 | × 偽 |
| 7 | 49 | × 偽 |

```
真 真 真 真 真 真 │ 偽 偽 偽 偽 ...
                 ↑
            ここが境目。答えは「最後の真」= 5
```

**「答えで二分探索」がやっているのは、この真偽の並びの境目を探すこと。** 課題文の「`k*k <= n` を満たす最大の整数 `k`」がそのまま述語になっている。

## 2. コードのどの行がどちらの層か

```go
if mid <= n/mid {    // ★ 述語の評価 ―― 「mid は答えの資格があるか?」
    lo = mid + 1     // ← 規約 ―― 「半開だから mid を捨てて lo を進める」
    k = mid          // ★ 述語が真だった、という記録
} else {
    hi = mid         // ← 規約 ―― 「半開だから mid を残して hi を縮める」
}
return k             // ★ 述語側の値を返す
```

> `mid <= n/mid` は `mid*mid <= n` をオーバーフローしない形に書き換えたもの。述語としては同じ。

**同じ述語を 3 規約で書き比べると、境目がはっきり見える。**

```
--- 半開 [lo,hi) ---          --- 閉 [lo,hi] ---           --- 左開 (lo,hi] ---
lo, hi := 0, n        ←違う   lo, hi := 1, n        ←違う   lo, hi := 1, n         ←違う
for lo < hi {         ←違う   for lo <= hi {        ←違う   for lo < hi {          ←違う
  mid := lo+(hi-lo)/2 ←違う     mid := lo+(hi-lo)/2 ←違う     mid := lo+(hi-lo+1)/2←違う
  if mid <= n/mid {   ★同一     if mid <= n/mid {   ★同一     if mid <= n/mid {    ★同一
    lo = mid + 1      ←違う       k = mid           ★同一       lo = mid           ←違う
    k = mid           ★同一       lo = mid + 1      ←違う       k = mid            ★同一
  } else {                      } else {                     } else {
    hi = mid          ←違う       hi = mid - 1      ←違う       hi = mid - 1       ←違う
  }                             }                            }
}                             }                            }
return k              ★同一   return k              ★同一   return k               ★同一
```

- **★（述語の評価・真だった記録・返り値）は 3 つとも 1 文字も違わない**
- **←（初期値・継続条件・`mid` の丸め・更新式）は 3 つとも全部違う**

## 3. だから何が嬉しいのか —— `return k` と `return lo - 1`

整数平方根（`floor(sqrt(n))`）の実装で、答えの返し方に 2 通りある。

```go
return k         // 述語側: 「述語が真だと確認できた最大の mid」
return lo - 1    // 規約側: 「半開区間だから、境界の 1 つ手前」
```

**どちらも正しく動く**（全数 500 万件で検証済み）。**バグの話ではなく、何に依存して書くかの選択の話。**

### ① 読むときの差（日常的にはこれが一番大きい）

| | 読み手がすること |
|---|---|
| `return k` | 課題文に「`k*k <= n` を満たす最大の整数 `k`」とある。その `k` を返している ―― **推論 0 段** |
| `return lo - 1` | 「`lo` は最初に偽になる値で止まる」→「だから 1 つ前」→「`lo >= 1` なので `lo-1 >= 0`」 ―― **推論 3 段** |

`return lo - 1` を読むには **「今どの規約で書いていたか」を思い出す**必要がある。`return k` には要らない。

### ② 規約を変えたときの差（実測）

区間規約を乗り換えて、両者がどうなるか測った（`n = 0〜300,000` 全数）。

| 規約 | `return k` | `return lo - 1` |
|---|---|---|
| 半開 `[lo,hi)` | ✅ 不一致 0 | ✅ 不一致 0 |
| 閉 `[lo,hi]` | ✅ 不一致 0 | ✅ 不一致 0 |
| **左開 `(lo,hi]`** | 🔴 **2 件**（`n=2,3`・初期値のズレ） | 🔴 **299,999 件（ほぼ全滅）** |

原因は **`lo` の意味が規約ごとに変わる**こと。

| 規約 | ループ終了時の `lo` の意味 | 答えの取り出し方 |
|---|---|---|
| 半開 `[lo,hi)` | 最初に**偽**になる値 | `lo - 1` |
| 閉 `[lo,hi]` | 最初に**偽**になる値 | `lo - 1` |
| 左開 `(lo,hi]` | **最後に真である値（答えそのもの）** | **`lo`** |

「`lo` 側に候補を残すか捨てるか」が規約の定義そのものなので、**`lo` の意味は規約と一緒に動く。`lo` から作った式も一緒に壊れる。**

> `k` の 2 件は初期値 `k := 0` が原因で、**`k := lo` と書けば 3 規約すべてで不一致 0** になる。「`k` は `lo` と同じ確信度から始まる」と書けば、規約の初期値を自動で追随する。

### 結論

**述語側（`return k`）に寄せるのが良い。** ただし条件が 1 つ。

```go
// k: 述語 mid <= n/mid（= mid*mid <= n）を満たすと確認できた最大の mid。
//    ループを抜けた時点でこれが答え。
k := lo
```

`k` を残す唯一のコストは「この `k` は常に最新か?」を読み手が疑えること。**不変条件を 1 行書けば消える。**

## 4. 一般化 —— コードの正しさは、どの前提に依存しているか

ここからは二分探索を離れた一般論。

### 実践手順（4 ステップ）

| # | やること |
|---|---|
| ① | **この行が正しい根拠を書き出す** |
| ② | 各根拠は「仕様由来」か「自分の判断由来」か |
| ③ | 判断由来に依存しているなら、**仕様由来のものに付け替えられないか** |
| ④ | 付け替えられないなら、**その前提をコメントで明示する**（＝不変条件の宣言） |

`return lo - 1` に①を当てると:

```
根拠1: lo は「最初に偽になる値」で止まる   ← ★自分の判断（半開規約を選んだから）
根拠2: よって答えはその 1 つ前
```

`return k` に当てると:

```
根拠1: k には述語が真だった mid しか入らない  ← 仕様由来
根拠2: 真側では mid が増加していく            ← 二分探索の性質（規約非依存）
```

**③が効かないときは④に落とす。** ―― これが「不変条件を最初に日本語で宣言する」の正体。**不変条件を書くとは、依存している前提を可視化すること。**

### ★ いちばん実用的な系: 「同じ値だから消せる」の罠

`k == lo - 1` は常に成り立つ。ここで「冗長だから `k` を消そう」と考えるのは**判断の種類を間違えている**。

```
❌ k == lo-1 だから、k は lo-1 から導出される値 → 消せる
✅ k == lo-1 は「今の規約のもとで偶然一致している」だけ → 消すと規約変更で壊れる
```

`k` は `lo` から導かれているのではなく、**独立に「述語が真だった最大の mid」と定義されている**値。たまたま今の規約で `lo-1` と一致している（左開規約なら `lo` と一致する）。

> **一般則: 「同じ値だから片方消せる」の前に、"なぜ同じ値なのか" を確認する。**
>
> | なぜ同じか | 判断 |
> |---|---|
> | **定義から必然的に同じ**（真の導出） | 消してよい。計算式に置き換える。例: `count` を持たず `len(s)` を使う |
> | **今の実装判断のもとで偶然一致** | **消すな**。その判断を変えた瞬間に壊れる |

これは「導出値をフィールドに持つな」という一般的な助言の**例外条件**にもなっている。`len()` は定義から必然なので持つ必要がない。`k` は偶然の一致なので持つ意味がある。

## 5. 二分探索以外での現れ方

同じ構図はあちこちに出てくる。

### ① 区間の端点

```go
return endTime - 1*time.Second   // 弱い: 「閉区間だから最後の 1 秒前」＝規約に紐づく
return endTime                   // 強い: 排他境界として定義（仕様に紐づく）
```

半開区間 `[start, end)` が Go のスライス・Python のスライス・HTTP Range で標準なのは、**端点の意味が実装に依存しないから**。

### ② ページング

```sql
OFFSET (page - 1) * size            -- 弱い: page が 1-based か、size 固定かに依存
WHERE created_at > :lastSeenAt      -- 強い: データそのものに紐づく（キーセット）
```

キーセットページングが壊れにくいのは、ページ番号という**取り決め**ではなく**データ**に紐づいているから。

### ③ API の戻り値

```go
func LastIndex() int    // 弱い: 内部が配列であることに紐づく
func Count() int        // 強い: 呼び出し側が知りたいこと（仕様）に紐づく
func Last() (Item, bool)
```

内部をリンクリストや map に変えた瞬間、`LastIndex()` は意味を失う。

## 6. いつ意識すると得か / いつ気にしなくていいか

| 意識するメリットが大きい場面 | 理由 |
|---|---|
| **実装方針を変える（リファクタ）とき** | 規約に紐づいた式が壊れる。壊れる箇所が事前に分かる |
| **他人（未来の自分）が読むとき** | 仕様の語彙で書かれていれば、実装の文脈を思い出さなくて済む |
| **「これ冗長では?」と指摘されたとき** | 消す前に「なぜ同じ値か」を確認する判断材料になる |
| **公開 API / DB スキーマ / 外部インターフェース** | 壊れた影響が外に漏れるので、**同じ判断ミスの代償が桁違い** |

| 気にしなくていい場面 | 理由 |
|---|---|
| 使い捨てスクリプト | 変更されないので、変化率の議論に意味がない |
| **真の導出**（`len()`、単純な否定など） | 定義から必然なので、規約が変わっても壊れない |
| 前提が本当に不変なもの | 例: 1 バイトは 8 ビット |

### やりすぎ注意 3 点

- **「変数を足せば強くなる」ではない。** 原則が言うのは「**消す前に依存先を確認せよ**」だけ
- **スケールで重みが違う。** 関数内のローカル変数なら壊れても即テストが赤くなる（左開に変えた失敗は `n=2` のテスト 1 件で捕まった）。API なら回復コストが跳ね上がる
- **「変化率が低い」の見積もりは外れる。** 「仕様は変わらない」と思った前提が変わることは普通にある。だから④（コメントで明示）が保険として要る

## 7. 既に名前が付いている考え方

この文書の内容は、既存の設計原則を関数内の 1 行のレベルまで下ろしたものと言える。

| 原則 | 言っていること |
|---|---|
| **情報隠蔽**（Parnas, 1972） | モジュール分割の基準は「**変わりそうなもの**を隠すこと」。機能単位ではなく**変化の単位**で分ける ―― この考えの元祖 |
| **Stable Dependencies Principle** | 依存は**安定な方向へ**向けよ |
| **ユビキタス言語**（DDD） | コードは**ドメイン（仕様）の語彙**で書く。`k`（課題文の語彙）vs `lo-1`（実装の語彙）はまさにこれ |

---

## 8. まとめ

```
述語 = 問題が決めたこと（変わらない）
規約 = 自分が決めたこと（変わりうる）

  → 変わらないものに紐づけた変数は、変わるものに紐づけた式より壊れにくい
  → 付け替えられないなら、依存している前提をコメントで明示する
```

### チェックリスト（コードを書く / レビューするとき）

- [ ] この式が正しい根拠は、**仕様由来**か **自分の実装判断由来**か
- [ ] 判断由来なら、仕様由来のものに付け替えられないか
- [ ] 付け替えられないなら、その前提をコメントに書いたか
- [ ] 「同じ値だから消せる」と思ったら、**必然か偶然か**を確認したか
- [ ] 変数名は**仕様の語彙**か（`k`）、**実装の語彙**か（`lo-1`）

> **ひとことで**: コードの正しさが「問題が決めたこと」に依っているか「自分が決めたこと」に依っているかを見分ける。後者に依っているなら、前者に付け替えるか、コメントで明示する。
