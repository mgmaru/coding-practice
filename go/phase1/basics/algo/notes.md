### レビュー前実装
1. 初回実装
```go
func getTargetIndex(input []int, target int) int {
	m := make(map[int]int, len(input))
	// キー：要素、値：indexとしてmapに格納
	for i, v := range input { // 計算量O(n)
		if _, ok := m[v]; !ok { // 要素がmapに含まれていたら、重複なのでスキップ（一番小さいインデックスの要素が適用される）
			m[v] = i
		}
	}
	if _, ok := m[target]; !ok { // targetが含まれていない場合は-1を返す
		return -1
	}
	return m[target] // 計算量O(1)
}
```
2. 追加実装（初期実装に追加）
- アルゴリズム整理
  1. スライスの要素の基準`mid`を計算する。
  2. 二分探索アルゴリズム
    - もし、`target == mid`
      - ただし、targetとなる要素が見つかったが、これが最小インデックスかどうかはわからないので、midから１つずつ左へずらして、確認する。
    - もし、`target > mid`　-> `mid`を含む左半分を捨てる。midの１つ右の要素を探索範囲の最小要素に更新する。同時にmidを更新する（最大要素は変わらない）。
      - ただし、更新した最小要素のインデックスが最大要素のインデックスを超えた場合は、見つからない場合なので、-1を返す。
    - もし、`target < mid` -> `mid`を含まない右半分を捨てる。midの１つ左の要素を探索範囲の最大要素に更新する。同時にmidを更新する（最小要素は変わらない）。
      - ただし、更新した最大要素のインデックスが最小要素のインデックスよりも小さくなった場合は、見つからない場合なので、-1を返す。
  
- 実装（以下）
```go
func getTargetIndexBinarySearch(input []int, target int) int {

	var l int // 探索範囲の最小要素のインデックス
	var h int // 探索範囲の最大要素のインデックス
	var m int // 探索範囲の真ん中の要素のインデックス
	
	n := len(input) // nは固定値なので、あらかじめ変数に格納しておく（nが大キックなった時にいちいち、lenでサイズを計算すると計算量が爆増するため）
	if n == 0 {
		return -1
	}
	// 初期値
	l = 0
	h = n - 1
	m = (l + h) / 2
	for {
		if target == input[m] { // targetがinput[m]と同じ場合はその時点で探索終了
			for i := m - 1; i >= 0; i-- { // mから左に１ずつずらしていく
				if target == input[i] {
					m = i // 同じであればmを更新
					continue
				}
				break // 違えばループを抜ける（重複要素の最小インデックスを確定）
			}
			return m
		}
		if target > input[m] { // もし、targetがmidより大きい場合、midを含む左側の要素を削除し、最小要素と真ん中のインデックスを更新
			l = m + 1       // 最小を更新(midの１つ右の要素が最小要素)
			m = (l + h) / 2 // 真ん中の要素を更新
			// 最大要素は変わらない
			if l > h { // 最小要素のインデックスが最大要素のインデックスを超えた場合、見つからないとして-1を返す
				return -1
			}
		}
		if target < input[m] { // もし、targetがmidよりも小さい場合、midを含む右側の要素を削除し、最大要素と真ん中のインデックスを更新
			h = m - 1       // 最大を更新（midの１つ左の要素が最大要素）
			m = (l + h) / 2 // 真ん中の要素を更新
			// 最小要素は変わらない
			if h < l { // 最大要素のインデックスが最小要素のインデックスよりも小さくなった場合、見つからないとして-1を返す
				return -1
			}
		}
	}
}
```
#### 間違っていたこと
- `input[m]`がinputのm-1のインデックスの要素を取り出していると勘違いしていた。。。
  - `input[:m]`であれば、インデックスm-1までの要素をとりだすことになる。←これと勘違いしていた。
- **`target`が`input`のどの要素よりも大きい場合（見つからない場合）、最小要素が最大要素のインデックスを超える場合がある（最小要素のインデックスを+1で更新するため）** -> 超えた場合は、見つからなかったとして-1を返す
- **`target`が`input`のどの要素よりも小さい場合（見つからない場合）、最大要素のインデックスが最小要素のインデックスよりも小さくなる場合がある（最大要素のインデックスを-1で更新するため）** -> 小さくなった場合は、見つからなかったとして-1を返す
- `for{}`（終了条件なし）に`continue`は不要　-> 終了条件に達しなければ、自動的にループ処理が更新されるため。
- 最初、テストケースに`input = []int{1, -3, 5, -7, 9, -11}`みたいなテストケースを含めてしまっていたが、これはソートされていないので、二分探索の利用条件を満たさない。 -> 削除した。

- 二分探索において、**重複があった場合に、一番インデックスが小さいものを返すような実装方法が思いつかなかった。**
  - 実装方法として、「`input[m]==target`となった場合に、mの位置から左に１ずつずらしていき、targetと同じ要素の一番小さいインデックスを出力する」と言いた方法をパッと思いついた。-> しかしこの実装の場合、**二重ループとなるために二分探索で計算量を減らしている意味がないと感じた。。。**

### レビュー後修正
#### レビュー指摘
1. `if`の分岐で中間要素`m`を書き換えた後に、違う分岐に入ってしまう場合がある。
2. `target`の要素が見つかった場合に、重複要素があるかどうかを確認する処理の計算量がO(n)となっている。（二分探索の計算量の工夫を潰している）
  - **lower_bound（境界二分探索）を使用することで、計算量をO(logn)に保つことができる。**
3. `mid`のインデックスを`(lo+hi)/2`で求めているがこれはオーバーフローになる可能性があるので、`lo+(hi-lo)/2`に修正する。
4. テストケースにinputの要素よりもtargetが小さい場合、inputの要素よりもtargetが大きい場合のテストケースを追加する。
5. テストケースにソート済みの負の整数が含まれるinputの場合を追加する。
#### レビューに対する自分なりの解釈
1. `if`が並列になっている時に、途中の分岐で`m`を更新すると、その後の分岐に入ってしまう場合がある。
  - `if`の分岐の条件で使用している変数は、途中で変更しない。
2. lower_boundは、真偽が切り替わる**境界を見つけること**である。
- 今回であれば、inputの中にtargetが見つかった場合に、重複しているかどうかを確認するために用いる。
- 言い換えれば、targetとは違う要素が出てくる境界を探すことである。
- アルゴリズム整理：
  1. targetが中間要素と一致しているところから開始する。つまり、初期の探索範囲は`[lo, hi] = [0, mid]`である。
  2. `mid`(`lo+(hi-lo)/2`)を求めて、targetと比較する。
    - `input[mid] != target` の場合：境界は`mid`よりも大きいところにあるので、探索範囲は`[lo, hi] = [mid+1, hi]`となる(`lo`を更新)
    - `input[mid] == target`の場合：境界は`mid`よりも小さいところにあるので、探索範囲は`[lo, hi] = [0, mid-1]`となる(`hi`を更新)
  3. 2を繰り返して、`lo=hi`となる場所が今回見つける境界で、targetの最小のインデックスとなる。
- この**境界探索は、必ず境界が存在する（ターゲットが存在する）。** -> 要素の間の中に必ずターゲットが存在する。
- 一方、**要素を探す二分探索は、ターゲットが存在しない場合があることに注意。**
3. 探索範囲の最小要素`lo`と最大要素`hi`を考えると、データがすごい大きい場合に、かつ、targetがものすごく大きいインデックスにいた場合、`lo`と`hi`はともにものすごく大きくなり、その和`lo+hi`となれば、とてつもなく大きくなり、オーバーフローする可能性が高くなる。
- `lo+(hi-lo)/2`とすることで、`hi`と`lo`が大きかったとしても、`hi-lo`は小さくなり、オーバーフローを防ぐことができる。
### 反省
- 今回、二分探索のアルゴリズムを学んだが、アルゴリズムの方法自体を覚えることは大切だが、それ以上に、**目の前の課題を言語化して、アルゴリズムに適用させるという２段階の考えが必要**であると感じた。
- **アルゴリズムをビジュアル的に捉える**ことが大切だと思った。
  - 今回の二分探索であれば、最小要素および最大要素を更新していき、探索区間が狭まっていくイメージ。
- **`if`の条件で使用されている変数は、変更しない。　** -> バグの元になる。
  - ループ処理の途中などで書き換えると、他の分岐に入る可能性がある。
  - **ループ処理の条件に含まれる変数を途中で書き換えないのと同じ感じ。**

今回レビュー中に出た3つのバグ（① `if`分岐で`m`を書き換えて隣の分岐に入る「二度発火」／② 内側ループが`for lo!=hi`＋`hi=mid-1`で「無限ループ」／③ `hi=mid-1`で候補を捨てて「最左を取り違え」）は、**全部「可変な添字変数（`lo`/`hi`/`mid`）の"変わり方の約束"が曖昧」という同じ根**から出ている。以下は多角的な対策。

1. **可変状態を減らす・局所化する（← 自分が気づいた「変数を変えられなくする」で正解）**
   - 状態（変数の取り得る値）が少ないほど場合分けが減り、off-by-one の隠れ場所が消える。
   - 二度発火の修正＝「`m`を各分岐で書き換える」→「`m := l+(h-l)/2` を周の頭で1回、以後**再代入しない**」＝ *その周だけ実質イミュータブル* にしたこと。**自分の原則を自分で使って直せている。**
   - 手段: 一度だけ代入・二度と書き換えない（assign-once）／`mid`は使い捨て／入力は読み取り専用。極めると**再帰**で`lo`/`hi`を引数にすれば書き換え変数ゼロ。
   - 注: `lo`/`hi`は本質的に変わる。だから「各変数は1周で決まった1通りにしか動かず、隣の分岐が書き換え後の値を読まない」という意味での不変。

2. **不変条件を先に、自分の言葉で固定する（進め方③・今回スキップした宿題）**
   - 更新式は「決める」ものではなく、不変条件から**導かれる**。`hi=mid`か`hi=mid-1`かで迷うのは、区間規約を決めていないサイン。
   - | 区間規約 | 継続条件 | `>=`側の更新 |
     |---|---|---|
     | 半開 `[lo, hi)` | `for lo < hi` | `hi = mid`（候補を残す） |
     | 閉 `[lo, hi]` | `for lo <= hi` | `hi = mid - 1`（mid は除外確定） |
   - ③の最左取り違えは半開の更新と閉の更新を混ぜたミス。②の無限ループはどちらの規約でもない`for lo!=hi`を選んだミス。**規約を1つ決めていれば両方書けなかった。**

3. **「区間規約・継続条件・更新式」の3点を噛み合わせる** ―― 今回のバグは全部この3点のズレ。1つ変えたら3つ揃っているか確認。

4. **跳ぶ添字のループ条件は `<`/`<=`、`!=` は避ける**。`!=`が安全なのは`i++`のように1ずつ動く時だけ。`lo=mid+1`のように跳ぶ添字は飛び越えを検知できず無限ループになる。あわせて「毎周ちゃんと縮むか（`hi-lo`が減るか）」を必ず確認。

5. **排他・不変は"自分で気をつける"より"構文に守らせる"**。3つの裸`if`→`else if`/`switch`で「1つだけ発火」を言語に保証させる（`continue`の付け忘れが事故の入口）。assign-once も「変わっていない」を構文で真にする同種の手。

6. **定石を盗む／車輪を再発明しない**。二分探索は`sort.Search`/`slices.BinarySearch`に正しい不変条件が埋め込み済み。独自の`for{}`・二段構えは自分で守る面積が増える（今回、二段構えのせいで内側に同じバグが再発した）。

7. **勘に頼らずテストで炙り出す**。「バカだが確実に正しい版（O(n)線形スキャン）」と大量ランダムで突き合わせる差分テストが、今回2つのバグを実際に発見した。**停止性（止まるか）と正当性（正しいか）は別々に壊れる**ので別々に検証。最小の難しいケース（`[7,7,7]`, `[1,7,7,7,9]`）は紙で手トレース ―― ハッピーパスでなく「答えがindex 0」「`hi`が下限を割る」端をなぞる。

**まとめ**: 芯は **1〜3**。とくに **2（不変条件を先に書く）** を毎回やれば、`hi=mid`か`mid-1`かで迷う局面自体が消える。

### 意識した点（注意した点など）
- `mid`をループ処理の最初に更新することで、複数の分岐に入らないようにした。
- 半開空間`[lo, hi)`で考えた。 -> ループの継続条件を`lo < hi`にした。
- `mid`の計算について、`mid = (lo + hi)/2`ではなく、`mid = lo + (hi-lo)/2`とすることで、オーバーフローを避けた。
- `mid*mid > n`の計算について、`mid*mid`とすると、オーバーフローが発生してしまうと考えたため、`mid > n/mid`とした。
### 疑問点
- 半開空間`[lo, hi)`で考えたが、`(lo, hi]`で考えるのはダメなのか？
  - `m > n/m`の場合： `hi = m - 1` 
  - `m < n/m`の場合： `lo = m`
  - ループの継続条件：　`lo < hi`
  - 理由：`m > n/m`の場合に、更新を`hi = m`とすると、見つける整数候補にmが入るが、実際、これは候補とはならないことは自明。なので、`hi = m - 1`としても問題ないのでは？
- 回答：良い。ただし、`mid`の計算方法を修正する必要がある。
  - `mid = lo + (hi-lo+1)/2` or `mid = lo + (hi-lo)/2 + 1`
  - `mid = lo + (hi-lo)/2`としてしまうと、`mid = lo`となってしまう。。。
  - 例えば、`(lo,hi]= (1, 2]`の場合
    - `mid = lo + (hi-lo)/2 = 1 + (2-1)/2 = 1 = lo` となり、`lo=mid`となってしまい、無限ループになる。
    - `mid = lo + (hi-lo+1)/2 = 1 + (2-1+1)/2 = 2 > lo` となり、`lo < mid`となり、無限ループを回避することができる。
  - このように`mid`を更新することで、`lo < mid`となる。

### わからなかったところ
1. `mid = n/mid`が完全平方数にならないことがわからなかった
- 結論：`n/mid`の余りは切り捨てられるから。
