# レビュー: `01_filter_map` —「nil/空スライス」と「使わない error」

`01_filter_map`（Phase 1 ドリル）のレビューで出た、**動く／動かないではなく「設計の意図を1つに決める」**段階の観点。

> 大原則（review-rubric の ②道具の良し悪し）: イディオムか・計算量に無駄はないか・データ構造の選択は妥当か。
> ここで扱うのは「型は通るが、意図が二択のまま放置されている」状態をどう潰すか。

## 観点1: `error` は「返すなら使う／使わないなら消す」

`func f(...) ([]int, error)` と書いたのに、本体が常に `return xs, nil` だと、
**エラーを返す経路が存在しない=エラーチャネルが死んでいる**。

```go
// ✗ 型だけ error。非nilを返す経路が無い
func filterSquaredEvens(input []int) ([]int, error) {
    ...
    return squaredEvens, nil   // ← nil しか返らない
}
```

### なぜダメか
- 呼び出し側に **無意味な `if err != nil`** を強制する（読む人は「どんなエラー？」と探して、無いと知る）。
- 「① エラーケースを最低1つ扱えているか」に対し、**器だけ用意して中身ゼロ**。むしろ嘘の signal。

### 判断の指針
- **本質的にエラーが無い処理**（純粋な filter / map / 集計など）→ **1値返しに簡素化**する。
  ```go
  func filterSquaredEvens(input []int) []int { ... }
  ```
- **エラーを学ぶ器として残す**なら、「**どんな入力で・何のエラーを返すか**」を一文で言えること。
  言えないなら、それは消すべき器。
  ```go
  // 例: nil 入力を不正とみなす規約を自分で決めるなら
  if input == nil {
      return nil, errors.New("input must not be nil")
  }
  ```

> 合言葉: **「このエラーは、どんな入力のときに返るか」を一文で言えないなら消す。**

---

## 観点2: nil スライス vs 空スライス

「該当なし」をどう返すかは2通りあり、**どちらも正しい**。問題は**統一されていないこと**。

```go
var xs []int      // nil スライス      (xs == nil は true,  len == 0)
xs := []int{}     // 非nilの空スライス  (xs == nil は false, len == 0)
```

### 罠: `reflect.DeepEqual` は nil と 空を区別する

```go
reflect.DeepEqual([]int{}, []int(nil))   // => false !!
```

→ **実装が `[]int{}` を返す・テストが `want: nil` を期待**していると、中身が同じでも**テストが落ちる**。
「ロジックは合っているのにテストが赤」の典型原因。

### 判断の指針
- Go では **「該当なしは nil を返す」が一般的**（`append` は nil スライスにそのまま使える）。
  ```go
  var squaredEvens []int            // nil 始まり
  for _, v := range input { ... squaredEvens = append(squaredEvens, v*v) }
  return squaredEvens               // 1件も無ければ nil が返る
  ```
- 「常に非nil を返す」と決めるなら、**テストの want も `[]int{}` に合わせる**。
- どちらでもよいが、**実装・テスト・（あれば）ドキュメントで1つに揃える**。根拠を言えること。

> 合言葉: **nil か空かは好みでよい。だが実装とテストで食い違わせない。**

## 観点3: エラーは「どう作るか」より「どう見分けるか」

`errors.New(...)` で返すこと自体は**正しい**。`error` は `errors.New` で作るのが最も普通。
詰まるのは作り方ではなく、**呼び出し側／テストが「そのエラーかどうか」をどう識別するか**。

### 鉄則: エラーは「値の同一性」で比較される（メッセージ文字列ではない）

```go
errors.New("X") == errors.New("X")   // => false（毎回べつの *errorString）
```

`errors.New` は呼ぶたび**別物**を返す。だから両側で別々に `errors.New("同じ文")` しても一致しない。
文字列が同じでも無関係。

### `errors.Is` は「必要だが、それだけでは不十分」

```go
errors.Is(got, want)  // got が want と「同一」か、got が want を「包んで(%w)」いるかを辿る
```

→ メッセージは見ない。**同じ1個の値を両側で使う**のが揃って初めて true。
別々の `errors.New` 同士は `errors.Is` でも `false`（今回ハマった所）。

### 識別の3択（必要な強さで選ぶ）

| | 何をする | 比較 | いつ |
|---|---|---|---|
| **A. sentinel** | `var ErrNilInput = errors.New(...)` を共有 | `errors.Is` | 呼び出し側が**この特定エラーで分岐**する |
| **B. 独自型** | `type NilInputError struct{...}` | `errors.As` | エラーが**データを持つ**（どの引数か等） |
| **C. 有無だけ** | その場で `errors.New` を返す | `(err != nil) == wantErr` | **どのエラーか不問**。出たかだけ見る |

### 「グローバル変数でエラー」への違和感について

sentinel（A）は**可変なグローバル状態の共有ではない**。`io.EOF` / `sql.ErrNoRows` / `os.ErrNotExist`
と同じ標準作法で、**書き換えない識別トークン**（const にできないから `var` なだけ／慣習上イミュータブル）。
ただし「この特定エラーで分岐したい時だけ」必要。識別が要らないなら C で十分、グローバルも `errors.Is` も不要。

> 合言葉: **エラーは識別子（値）で見分ける。文字列一致でも errors.Is 単体でもダメ。「同じ値を共有」か「型で見る」か「有無だけ」かを、必要な強さで選ぶ。**
