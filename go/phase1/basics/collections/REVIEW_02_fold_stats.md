## 観点0【最重要・現に赤】: テストの `bytes.Buffer` がサブテスト間で共有されている

`go test` を回すと **`nilSlice` が落ちる**。ロジックの問題ではない。

```
=== RUN   TestCalcSumAndMaxAndMin/nilSlice
    02_fold_stats_test.go:29: 期待する結果が違います。
      合計=31, 最大=9, 最小=1入力されたスライスがnilです。, 入力されたスライスがnilです。
--- FAIL
```

### なぜ落ちるか

```go
var buf bytes.Buffer          // ← ループの外で1個だけ宣言

for _, c := range cases {
    t.Run(c.Name, func(t *testing.T) {
        calcSumAndMaxAndMin(&buf, c.Input)  // 同じ buf に Fprintf で追記
        gotValue := buf.String()            // ← 前ケースの出力が残ったまま
        ...
    })
}
```

`bytes.Buffer` への `Fprintf` は **追記**。`buf` を1個しか作らず使い回すと、
`normal` の `"合計=31, 最大=9, 最小=1"` が残った状態で `nilSlice` が走り、
`"合計=31...入力されたスライスがnilです。"` という **連結ゴミ** が `gotValue` になる。

### 判断の指針 — テストは「毎ケース新品の状態」で始める

- **A（推奨）: `buf` をサブテストの中で宣言**する。スコープで毎回新品になる。
  ```go
  t.Run(c.Name, func(t *testing.T) {
      var buf bytes.Buffer          // ← 中に入れる
      calcSumAndMaxAndMin(&buf, c.Input)
      gotValue := buf.String()
      ...
  })
  ```
- **B: 使い回すなら毎回 `buf.Reset()`** を先頭で呼ぶ。ただし「リセットを忘れたら汚染」する分Aより弱い。

> 合言葉: **テストケースをまたいで状態を共有しない。バッファは毎ケース新品で。**

## 観点1: 空スライス `[]int{}`（非nil）で「合計=0, 最大=0, 最小=0」を返してよいか

`01` の観点2「nil か空か」の **集計版**。今回は nil はガードしているが、
**非nilの空 `[]int{}` が素通り** する。ループが1回も回らず、`sum=max=min=0`（ゼロ値）のまま、

```
合計=0, 最大=0, 最小=0
```

と表示される。

### なぜ引っかかるか

- 「最大・最小」は **要素が1つも無いと数学的に定義できない**（fold の単位元が無い演算）。
  合計の `0` は単位元として正しいが、最大・最小の `0` は **嘘の値**。
  入力が `[]int{5,5,5}` でも `[]int{}` でも「最大=…」が出るが、後者の `0` には根拠が無い。
- `min` の初期値 `0` は危険でもある。仮に nil ガードを外して `[]int{3,5,9}` を渡すと、
  `i==0` で `min=3` に上書きされるから今は助かっているが、**「ゼロ値初期化 + 初回上書き」は
  初回上書きを1か所でも書き損ねた瞬間に `min=0` が紛れ込む**。今の `if i == 0` 方式はギリギリ。

### 判断の指針

- **空入力を nil と同じく「不正」とみなす**なら、`len(input) == 0` でまとめてガードする。
  （nil も len 0 なので、これ1本で nil ケースも吸収できる）
  ```go
  if len(input) == 0 {
      fmt.Fprint(w, "入力が空です。")
      return
  }
  ```
- **空でも合計0は出したい**なら、最大・最小だけ「該当なし」表示にするなど **演算ごとに単位元を分けて扱う**。
- 初期値は **`input[0]` を明示的に種(seed)にして1番目から畳む** と、`if i == 0` 分岐が消えて事故が減る。
  ```go
  sum, max, min := input[0], input[0], input[0]   // 先頭を初期値に
  for _, num := range input[1:] {                 // 2個目以降を畳む
      sum += num
      if num > max { max = num }
      if num < min { min = num }
  }
  ```

> 合言葉: **fold の初期値は「ゼロ値」ではなく「先頭要素 or 真の単位元」。最大/最小に単位元は無い＝空は別扱い。**

## 観点2: コメントと実体がズレている（「要素2個目以降」）

```go
// 要素1個目は初期値を代入
if i == 0 {
    max = num
    min = num
}

// 要素2個目以降

sum += num            // ← これは「1個目も含めて」毎回走る
if max < num { ... }  // ← 同上
```

`// 要素2個目以降` の下のコードは **1個目でも実行される**（`i==0` でも `sum += num` する）。
コメントが嘘になっている。実害は無いが、**「初回だけ初期化／2回目以降だけ畳む」と読み手に誤解させる**。
観点1の `input[0]` シード方式に変えると、このコメント自体が不要になる（構造で意図が表現される）。

---

## 観点3: `max` / `min` という変数名は組み込み関数を隠す（Go 1.21+）

Go 1.21 以降、`max` と `min` は **組み込み関数**。ローカル変数名に使うと **そのスコープで組み込みが使えなくなる**（shadowing）。

```go
var max int   // ← 以後このスコープで組み込みの max(...) が呼べない
```

動くが、`max(a, b)` を使いたくなった時に詰まる地雷。`hi/lo`、`maxV/minV`、`largest/smallest` など別名が無難。
（このドリルでは使っていないが、観点1の畳み込みで `max = max(max, num)` と書けると綺麗、という観点でも別名が効く）

---

## 観点4: テストケースが薄い（空・1要素・負数・最大最小の位置）

現状は `normal` と `nilSlice` の2本。しかも `normal` は **最大=末尾付近・最小=先頭** で、
「最大/最小の入れ替えロジック」を十分には突いていない。fold 系は境界で壊れやすいので足したい:

- `[]int{}`（非nilの空）… 観点1の挙動を仕様として固定する
- `[]int{42}`（1要素）… `sum==max==min` を確認、初期値ロジックの最小ケース
- `[]int{-3, -1, -5}`（全負数）… `min` 初期値0バグ（観点1）の検出器になる。**0始まりだと max=0 で落ちる**
- 最大が先頭・最小が末尾の並び … 入れ替え条件の向き（`<` / `>`）を両方向で突く
