# レビュー: `04_count_frequency` —「集計の map」と「決定的な順序」、そして公開境界

`04_count_frequency`（Phase 1 ドリル）のレビュー。
お題は「要素ごとの出現回数を数え、回数の降順・同数ならキー昇順で返す」。
**`01`〜`03` で踏んだ地雷（nil/空の統一・map 順不同のフレーキー・容量先取り）が、ここで一気に「踏まずに済んでいる」**。
今回の主題は「正しく動いている緑を、なぜ信用してよいのか」を言語化することと、残った設計の二択（公開境界）。

> 大原則（review-rubric の ②道具の良し悪し）: イディオムか・計算量に無駄はないか・データ構造の選択は妥当か。
> 前提: `go test -run TestCountElements -count=5` が **5 回連続で緑**。`gofmt` 差分なし・`go vet` クリーン。
> そして今回は、**この緑は信用してよい**（観点1）。

---

## 観点1【良い・最重要】`map`＝集計の係、順序＝`sort` が握る ―― `03` のフレーキー教訓が効いている

`03` の最大の山場は「`map` を走査して作ったスライスは順不同 → `reflect.DeepEqual` と衝突 → たまに緑」だった。
このドリルは構造的に**同じ罠を踏みうる**（`map[string]int` で集計している）。が、踏んでいない。理由はここ:

```go
counts := make([]CountElement, 0, len(m))
for k, v := range m {                       // ★ map 走査の順序は不定（ここだけ見ると 03 と同じ危険）
    counts = append(counts, CountElement{element: k, count: v})
}

sort.Slice(counts, func(i, j int) bool {    // ★ だが直後に全順序でソートし直す
    if counts[i].count == counts[j].count {
        return counts[i].element < counts[j].element   // 同数 → キー昇順
    }
    return counts[i].count > counts[j].count           // 回数 → 降順
})
```

`for k, v := range m` の並びは実行ごとにバラけるが、**その後の `sort.Slice` が並びを完全に上書きする**。
しかもソートキーが「(count 降順, element 昇順)」の**全順序**で、element は map のキー＝**一意**。
だから比較結果に同値（タイ）が残らず、**出力は決定的**。`reflect.DeepEqual`（順序に厳密）とぶつかってもフレーキーにならない。

> ここが `03` との決定的な差。`03` は「順序を `map` 由来のスライスに委ねた」→ 踊った。
> `04` は「順序を `sort` の全順序比較に委ねた」→ 安定。**順序の出どころを `map` から引き剥がせている**。

### 自問（合言葉の確認）
- `map` 走査の並びに依存していないか？ → していない（直後に sort で確定）。
- ソートキーは**全順序**か（タイが残らないか）？ → count が同数でも element で必ず割れる。element は map キーで一意 → タイ無し → 決定的。

> 合言葉（`03` から継承）: **`map` に順序を期待しない。順序が要るなら、順序は別の道具（ここでは `sort` の全順序比較）が握る。**

## 観点2【良い】nil / 空スライスの統一 ―― `01` の学びを踏襲。ただし早期 return は冗長

`01` の学び「実装とテストで nil/空を食い違わせない」を満たせている。

- 実装は**常に非 nil**を返す（`make([]CountElement, 0, ...)` 始まり）。
- テストの `want` も空・nil 入力ともに `[]CountElement{}`（非 nil 空）。✓ 食い違いなし。

```go
{"emptyInput", []string{}, []CountElement{}},
{"nilInput",   nil,        []CountElement{}},
```

### ただし: 先頭の早期 return は**実は要らない**（簡素化の余地・②）

```go
if len(input) == 0 {
    return []CountElement{}        // ← このガードが無くても結果は同じ
}
```

入力が空なら `m` も空、`make([]CountElement, 0, len(m))` は `len(m)==0` でも**非 nil の空スライス**を返す。
つまりガードを消しても `nil`/`[]string{}` 入力はそのまま `[]CountElement{}` に落ちる。**動作は不変**。

判断は二択（どちらでもよい、根拠を言えること）:
- **残す**: 「空入力は即返す」という意図の明示／将来ロジックが重くなったときのショートカット。ならコメントで意図を一言。
- **消す**: 「`make` が空でも非 nil を返す」契約に乗っており、分岐が一つ減る。今のロジックなら**消すほうが素直**。

> 合言葉（`01` から継承）: **nil か空かは好みでよい。だが実装とテストで食い違わせない。**ここは満たせている。
> 追加で: **「無くても同じ結果になる分岐」は、意図を語れないなら消す。**

## 観点3【設計の二択】構造体フィールドが非公開 ―― 公開関数が「読めない値」を返している

```go
type CountElement struct {
    element string   // 非公開
    count   int      // 非公開
}

func CountElements(input []string) []CountElement { ... }   // 公開（大文字 C）
```

`CountElements` は**公開**なのに、返す `CountElement` の中身 `element` / `count` は**非公開**。
今テストが通るのは**同一パッケージ `collections` 内**だから。だが**別パッケージから呼ぶと、結果の中身を一切読めない**
（フィールドにアクセスできず、`%v` で覗くか reflection しかない）。**公開境界がちぐはぐ**。

判断の指針（一文で意図を言えるか）:
- **このパッケージ内部の道具**だと決めるなら → 関数も小文字 `countElements` にして閉じる。整合する。
- **他所から使う結果型**にするなら → フィールドを公開: `Element string` / `Count int`。
  公開関数が返すデータは、呼び出し側が**読める**べき。

```go
// 他所から使うなら
type CountElement struct {
    Element string
    Count   int
}
```

> 合言葉: **公開関数が返す型の中身は、呼び出し側から読めるべき。「公開関数 × 非公開フィールド」は、誰が使う型かを決めていないサイン。**

## 観点4 軽微（イディオム・テストの穴）

- **`make(map[string]int, 0)` の `, 0`**: 容量ヒント 0 は無害だが無意味（`03` でも出た指摘）。
  件数の上限が読めるので、むしろ **`make(map[string]int, len(input))`** と先取りすると再ハッシュを減らせる（②nice）。
  結果スライス側は `make([]CountElement, 0, len(m))` で既に先取りできている。✓
- **タイポ**: テストのケース名 `"nomal"` → `"normal"`。
- **テストの穴（軽微）**: 現状 4 ケースで主要動作は押さえている。
  - `countDuplicated`（apple=2, banana=2）が**同数 → キー昇順**（apple→banana）を踏めている。✓ タイブレークは検証済み。
  - `nomal`（3,2,1）が**回数の降順**を踏めている。✓
  - 追加するなら: **単一要素**（`["x"]` → `[{x,1}]`）、**大文字小文字の区別**（`"Apple"` と `"apple"` は別キー）あたり。必須ではない。
- **`reflect.DeepEqual` でよい根拠**: 出力が観点1のとおり決定的なので、`03` のような「ソートしてから比較／集合比較」は不要。
  順序が確定している今のケースでは `DeepEqual` が**最も素直で正しい**。
