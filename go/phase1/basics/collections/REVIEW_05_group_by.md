## 観点1【良い・最重要 / 誤解の訂正】`reflect.DeepEqual` は「マップの順序は見ない・スライスの順序は見る」

`notes.md`（2026/6/27-28）にこう書いてある:

> ただし、`reflect.DeepEqual` ではスライスの並び順までは判定してくれないみたいなので、ここを改善する必要あり。

**これは事実と逆**。実際に動かして確かめた結果がこれ:

```
slice  [a,b] vs [b,a] => false   ← スライスは「順序が違えば不一致」＝順序を見る
slice  [a,b] vs [a,b] => true
map (構築順だけ違う)   => true    ← マップは内部の格納順に関係なく key 一致で比較＝順序を見ない
map (値スライスの順序違い) => false ← マップの中の「値スライス」の順序はちゃんと見る
```

つまり `reflect.DeepEqual` は:

- **マップ本体**: キーで突き合わせて比較する。`for k := range m` の格納順が実行ごとにバラけても、比較結果は変わらない（順序**非**依存）。
- **スライス（マップの値を含む）**: index ごとに突き合わせる。順序が違えば `false`（順序依存）。

### だから、このドリルは `03` のようにフレーキーにならない ―― しかも `04` とは別の仕組みで

`03` の地雷は「`map` を**走査してスライスを作る** → そのスライスの並びが順不同 → フレーキー」だった。
`04` はそれを「`sort` の全順序で並びを確定」して回避した。
**`05` はそもそも `map` を走査してトップレベルの並びを作らない**。出力の型が `map[string][]string` そのものだから:

```go
return m   // ← map をそのまま返す。順序のあるスライスに変換していない
```

- **トップレベルがマップ** → `DeepEqual` は順序非依存で比較 → `for k := range m` の不定順は**比較に影響しない** → フレーキーにならない。
- **各グループの値スライス** → `append` で**入力の出現順**のまま積む（`m[k] = append(m[k], ...)`）→ 決定的。
  そして `DeepEqual` は**この順序をちゃんと検査する**。

ここが核心: `DRILLS.md` の補足「**各グループ内は入力の出現順を保つこと**」は、
**`append`（入力順で積む）＋ `DeepEqual`（スライス順を検査する）** で**すでに担保されている**。
notes の心配「ここを改善する必要あり」は、**改善するものが無い**。むしろ `DeepEqual` は**この要件にとって最も正しい道具**。

### 自問（合言葉の確認）
- マップ本体の走査順に依存していないか？ → していない（マップを返すだけ。`DeepEqual` がキーで突き合わせる）。
- 各グループ内の順序は決定的か？ → `append` が入力順で積むので決定的。`DeepEqual` がその順序を検査する。
- だから順序の要件（入力順保持）はテストで守られているか？ → 守られている。

> 合言葉（`03`→`04`→ここで完結）: **`map` に順序を期待しない。**
> ただし今回の学びは一段深い: **`reflect.DeepEqual` は「マップは順序非依存・スライスは順序依存」で比較する。**
> だから「マップを返す＋各グループは入力順スライス」という今回の設計では、`DeepEqual` が**そのまま正しい**。直す箇所は無い。

> **notes.md の該当行は訂正対象。** 「並び順を見ない」のはスライスではなく**マップ本体**で、スライスの並び順は**ちゃんと見る**。

## 観点2【良い／簡素化】nil・空の統一は OK。ただし `len(input)==0` ガードは `04` と同じく冗長

`01`/`04` の学び「実装とテストで nil/空を食い違わせない」を満たせている。

- 実装は**常に非 nil** を返す（先頭で `m := make(map[string][]string, len(input))`）。
- テストの `want` も空・nil 入力ともに `map[string][]string{}`（非 nil 空マップ）。✓ 食い違いなし。

```go
{name: "EmptyInput", inputPersons: []person{}, want: map[string][]string{}},
{name: "NilInput",   inputPersons: nil,        want: map[string][]string{}},
```

### ただし: `len(input)==0` の早期 return は**要らない**（`04` 観点2 と同型）

```go
// inputが空もしくはnil
if len(input) == 0 {
    return m // 空        ← このガードが無くても結果は同じ
}
```

入力が空／nil なら、続く `for _, person := range input` は**0 回しか回らず**、そのまま空の `m` を返す。
つまりこのガードを消しても `[]person{}` / `nil` 入力は同じ `map[string][]string{}` に落ちる。**動作は不変**。
（`04` でまったく同じ指摘をし、最終的に削除した。同じ判断が使える。）

### 一方で：`key` 検証ガードは**消してはいけない**（こちらは効いている）

```go
// keyが正しく指定できていない
if key != "name" && key != "dept" {
    return m // 空
}
```

こちらは**load-bearing（効いている分岐）**。消すと、不正キー `"age"` でも `for` が回り、
`keyFunc("age")` が **`else` 分岐で `p.dept` を返す**（後述・観点3/4）。
結果、`groupBy("age", ...)` が**「dept でグループ化」と同じ挙動**になってしまう（テスト `invalidKey` が赤になる）。
だからこのガードは残す。

> 二つのガードは見た目が似ているが役割が違う。**`len==0` は消せる（冗長）／`key` 検証は残す（効いている）。**
> 合言葉（`04` から継承）: **「無くても同じ結果になる分岐」は、意図を語れないなら消す。** ＋ **逆に、消すと赤になる分岐は load-bearing。両者を見分ける。**

> ※ ただし「`key` 検証ガードが必要」という状況そのものが、観点3 の設計の匂い（文字列キーだから実行時検証が要る）。
> 観点3 を採れば、このガードごと消える。

## 観点3【設計の二択・最重要設計】`key string` でフィールドを選ぶ ―― あなたが詰まった所の「イディオムな答え」

notes にこう書いてある:

> 構造体のフィールドをキーとして指定する方法がわからなかった。

今のコードはそれを **`key string` ＋ `keyFunc`/`valueFunc` の振り分け**で解いている:

```go
func groupBy(key string, input []person) map[string][]string {
    ...
    if key != "name" && key != "dept" { return m }     // 文字列を実行時に検証
    ...
    m[person.keyFunc(key)] = append(m[person.keyFunc(key)], person.valueFunc(key))
}

func (p person) keyFunc(key string) string {           // key と同名のフィールド
    if key == "name" { return p.name } else { return p.dept }
}
func (p person) valueFunc(key string) string {         // ★ key と「反対」のフィールド
    if key == "name" { return p.dept } else { return p.name }
}
```

これは動く。が、**「文字列でフィールドを選ぶ（stringly-typed）」という設計の匂い**がある。問題点:

1. **タイポがコンパイルで止まらない**。`"Name"` や `"dept "` を渡すと、`else` 分岐に落ちるか、検証で空マップになる。**型システムが守ってくれない**（実行時まで分からない）。
2. **`invalidKey` という失敗モードが存在する**こと自体が症状。テストに `invalidKey` ケースがあるのは、「本来コンパイルで防げるはずの不正入力」を実行時に処理しているから。
3. **フィールドが増えると 3 箇所直す**（`groupBy` の検証・`keyFunc`・`valueFunc`）。
4. **`valueFunc` の「反対のフィールドを返す」が暗黙すぎる**。`groupBy("dept", ...)` を呼んだ人は、値に**名前**が入って返るとは普通読めない（`valueFunc` を読むまで分からない）。しかもこの「反対」は **`person` がちょうど 2 フィールドだから**成立する芸当で、3 個目のフィールドが増えた瞬間に「反対」は**定義不能**になる。

### イディオムな答え：キーを「文字列」ではなく「関数（key selector）」で渡す

Go の group-by の定石は、**「どのフィールドでグループ化するか」を関数で受け取る**こと:

```go
// キー選択関数を受け取る。値は「person そのもの」を集める（最も汎用）
func groupBy(keyOf func(person) string, input []person) map[string][]person {
    m := make(map[string][]person)
    for _, p := range input {
        k := keyOf(p)
        m[k] = append(m[k], p)
    }
    return m
}

// 呼び出し側（タイポはコンパイルエラー。検証も keyFunc/valueFunc も不要）
groupBy(func(p person) string { return p.dept }, people)
```

これで観点3 の問題が**まとめて消える**:
- 不正キーが**そもそも渡せない**（`p.dept` はコンパイル時に存在チェックされる）→ `invalidKey` ガードも検証も不要。
- `keyFunc`/`valueFunc` が**不要**。
- フィールドが増えても**呼び出し側でセレクタを変えるだけ**。
- 「何でグループ化するか」と「何を集めるか」が**分離**できる（値も `func(person) string` で選びたいなら引数をもう一つ）。

### 判断は二択（どちらでもよい、根拠を言えること）

- **このパッケージ内の練習用の小道具**と割り切るなら → 最低限、**文字列をやめて型付き列挙**にする。タイポがコンパイルで止まる:
  ```go
  type field int
  const ( byName field = iota; byDept )
  func groupBy(key field, input []person) map[string][]string { ... }
  ```
  （ただし `valueFunc` の「反対のフィールド」問題は残る。）
- **イディオムに寄せる**なら → 上の **key selector 関数**。これが「構造体のフィールドをキーに指定する」という notes の問いへの**正攻法の答え**。

> 合言葉: **「文字列でふるまいを選ぶ」設計は、型システムに任せられる検査を実行時に押し戻しているサイン。**
> 「フィールドをキーにしたい」の Go 的な答えは**文字列ではなく関数（`func(T) K`）**。`invalidKey` テストが要る時点で、設計が一段ずれている合図。

## 観点4 軽微（イディオム・効率・テストの穴）

- **`keyFunc(key)` を 1 行で 2 回呼んでいる**（`05_group_by.go:25`）:
  ```go
  m[person.keyFunc(key)] = append(m[person.keyFunc(key)], person.valueFunc(key))
  ```
  キーを 2 回計算し、マップ索引 `m[...]` も 2 回引いている。ローカルに束ねるのが素直（②nice）:
  ```go
  k := p.keyFunc(key)
  m[k] = append(m[k], p.valueFunc(key))
  ```
- **ループ変数 `person` が型名 `person` を覆い隠している**（`05_group_by.go:24`）:
  ```go
  for _, person := range input { ... }   // 変数 person が type person をシャドーイング
  ```
  ループ内で型 `person` が使えなくなる。コンパイルは通るが匂う。**`p` にする**（メソッドのレシーバ `p person` とも揃う）。
- **`valueFunc` の doc コメントが実体とややズレ**（`05_group_by.go:39`）: 「keyに対応する要素を返す関数」とあるが、実際は**反対のフィールド**を返す。インラインコメント（`keyがnameだったらdeptを返す`）の方が正確。コメントは「やること」を書く。
- **マップ容量の先取り `make(map[string][]string, len(input))`（`05_group_by.go:11`）は ✓**。`04` の学び（`make(map, len(input))` で再ハッシュを減らす）を引き継げている。`len(input)` はグループ数の**上限**（実際のグループ数はもっと少ないことが多い）だが、上振れの無害なヒントなので問題なし。
- **`keyFunc`/`valueFunc` の `else` が「name 以外は全部 dept 扱い」**（`05_group_by.go:34,44`）。これが安全なのは `groupBy` が**先に検証している**から。ヘルパー単体では防御していない＝結合が強い。観点3 の selector 化で消える。
- **テストの穴（軽微）**: 6 ケースで主要動作は押さえている。
  - `duplicateName`（key="name"）が **valueFunc が dept を返す**ことを実データで固定できている。✓
  - `normal`/`duplicateNameAndDept`（key="dept"）が**入力順保持**を踏めている（`{"Dev": ["Sato","Sato"]}` の重複も）。✓
  - 追加するなら: **単一要素**（`[{name:"X",dept:"Y"}]` → `{"Y":["X"]}`）、**全員別グループ**（重複なし）あたり。必須ではない。

## 観点3 ―― 「値セレクタ版」を選んだのは良い判断

二択（①型付き列挙／②key selector 関数）のうち**②**を採用。さらに「何を集めるか」を `valueOf` で受けることで、元コードの**暗黙の「反対のフィールドを値にする」**を**明示的な引数**に昇格できた。

```go
func groupBy(keyOf func(person) string, valueOf func(person) string, input []person) map[string][]string {
    m := make(map[string][]string, len(input))
    for _, p := range input {
        k := keyOf(p)
        m[k] = append(m[k], valueOf(p))
    }
    return m
}
```

これで観点3 が挙げた問題が**まとめて消えた**:
- 不正キーが渡せない（`p.dept` はコンパイル時チェック）→ `invalidKey` 検証も削除できた。
- `keyFunc`/`valueFunc` が不要に。
- フィールドが増えても呼び出し側のセレクタを差し替えるだけ。`valueOf` があるので「反対のフィールド」の 2 フィールド前提も解消。

> テストも `keyOf`/`valueOf` をケースごとに注入する形に追従できている。`duplicateName` が `name→dept`、他が `dept→name` と、**両方向**を実データで踏めているのも良い。
