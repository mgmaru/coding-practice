## 観点1【良い・最重要】順序の出どころは「入力スライスの走査順」。`map` は存在判定の係に徹している ―― 系譜の完成形

`03`→`04`→`05` で繰り返してきた合言葉「**`map` に順序を期待しない。順序が要るなら、順序は別の道具が握る**」。
このドリルは、その合言葉の**一番素直な実装**になっている。

```go
noDuplicateSlice := make([]any, 0, len(input)) // 出力。順序はこのスライスが握る
m := make(map[any]struct{}, len(input))        // ★ map は「見たことがあるか」の判定だけ

for _, i := range input {                       // ★ 入力を index 順に走査
    if _, ok := m[i]; !ok {                     //   初めて見た要素か？
        m[i] = struct{}{}                       //   見た印を付ける（順序情報は持たせない）
        noDuplicateSlice = append(noDuplicateSlice, i) // ★ 出現順のまま積む
    }
}
return noDuplicateSlice
```

ここが核心: **`m` を `for k := range m` で走査して出力を作っていない**。
出力は `input` を走査して `append` した結果＝**入力の index 順**。`map` はあくまで「初出かどうか」の判定にしか使っていない。
だから `for k := range m` の不定順は**そもそも出力に触れない**。出力は決定的で、`reflect.DeepEqual`（順序に厳密）と衝突してもフレーキーにならない。

### 系譜の中での位置づけ（ここが今回の見どころ）

| ドリル | 順序の作り方 | フレーキーとの関係 |
|---|---|---|
| `03` | `map` を**走査してスライス化** | 踏んだ（並びが順不同 → たまに緑） |
| `04` | `sort` の**全順序**で並びを確定 | 回避（順序を `sort` に握らせた） |
| `05` | `map` を**そのまま返す**（`DeepEqual` はマップ順序非依存） | 回避（トップレベルを並べ替えない） |
| **`06`** | **入力スライスの走査順をそのまま使う** | 回避（`map` は判定のみ・順序に一切関与しない） |

`04` は「順序を `sort` に委ねた」、`05` は「並べないで `map` のまま返した」。
`06` は**そもそも順序を作る加工が無い**――入力の出現順を `append` で写すだけ。**`map` から順序を最も綺麗に引き剥がせている**。

### 自問（合言葉の確認）
- `map` 走査（`for k := range m`）の並びに依存していないか？ → **していない**（`m` を走査して出力を作っていない。出力は `input` を走査して `append`）。
- 出力の順序は決定的か？ → `input` の index 順。決定的。
- だから `reflect.DeepEqual`（順序厳密）で安全か？ → 安全。出力が決定的なので `03` のような集合比較／ソート後比較は不要。

> 合言葉（`03`→`04`→`05`→ここで完成）: **`map` に順序を期待しない。** `06` はその最終形 ――
> **順序は入力スライスの走査順が握り、`map` は存在判定だけを受け持つ。** 役割分離が最もクリーンに出ている回。

## 観点2【良い】`map[any]struct{}` ＝ set の正しいイディオム ＋ 容量先取り ＋ nil/空の統一

`01`〜`04` の学びが、ここでも**予防として効いている**。三点とも踏めている。

### (a) `struct{}` を値にした set ―― `notes.md`（`03`）の言語化を実践できている

```go
m := make(map[any]struct{}, len(input))
m[i] = struct{}{}
```

`notes.md`（2026/6/16）に自分でこう書いた:

> 値には **struct{}** つまり、**空の struct** を実装する。… **空の struct は 1 バイトも消費しない**。… 余計な意味を持たずに、要素の存在自体を表すことができる。

それが**そのまま実装に出ている**。`map[any]bool` ではなく `map[any]struct{}` を選べているのは、set のイディオムを理解している証拠。✅

### (b) 容量先取り ―― スライスも map も両方

```go
make([]any, 0, len(input))          // 出力スライス：cap を先取り
make(map[any]struct{}, len(input))  // map：size hint を先取り
```

`len(input)` は**両方とも妥当な上限**: 重複ゼロ（全要素が初出）が最悪ケースで、そのとき出力は `len(input)` 要素・map も `len(input)` エントリになる。
だから `append` の再確保も map の再ハッシュも先回りで抑えられる。`01`/`04` の「容量先取り（②nice）」を**両方の器に**効かせられている。✅

### (c) nil / 空の統一 ―― `01` の学び

- 実装は**常に非 nil** を返す（`make([]any, 0, ...)` 始まり。`input` が nil でも `len(nil)==0` で `make([]any,0,0)` ＝非 nil 空スライス）。
- テストの `want` も空・nil 入力ともに `[]any{}`（非 nil 空）。✓ 食い違いなし。

```go
{name: "emptySlice", input: []any{}, want: []any{}},
{name: "nilSlice",   input: nil,     want: []any{}},
```

> 合言葉（`01` から継承）: **nil か空かは好みでよい。だが実装とテストで食い違わせない。** ここは満たせている。
> しかも今回は `04`/`05` で何度も出た「冗長な `if len(input)==0` 早期 return」**すら無い**。`make` の契約（空入力でも非 nil 空を返す）に最初から素直に乗れている。**語れない分岐を、そもそも書かなかった**回。

## 観点3【設計の二択・最重要設計】`[]any` は「comparable を実行時に要求する」契約 ―― panic の地雷を型で防ぐ

ここがこのドリル唯一の本質的な設計論点。`map` のキーの型が `any` になっている:

```go
func deleteDuplicate(input []any) []any {
    ...
    m := make(map[any]struct{}, len(input))
    for _, i := range input {
        if _, ok := m[i]; !ok {   // ★ i を map キーに使う＝i は comparable でなければならない
```

Go では**値を map のキーに使うには comparable でなければならない**。`int`/`string` なら問題ない。
だが `any` は**何でも受け取れてしまう**ので、`input` に **uncomparable な型**（スライス・map・関数）が紛れると、`m[i]` の評価で**実行時 panic** する:

```go
deleteDuplicate([]any{[]int{1}, []int{1}})
// → panic: runtime error: hash of unhashable type []int
```

つまり**シグネチャ `[]any` は「何でも入れていい」と約束しているのに、実装は「comparable な物しか入れるな」と要求している**。契約がズレている。
そしてこれは、`notes.md`（2026/6/16・`03`）で**あなた自身が表にした内容**と正面からぶつかる:

> キーに使用できない型：スライス `[]int` / `map` / 関数

`03` で「map のキーに使えない型」を列挙したのに、`06` のシグネチャ `[]any` は**まさにその使えない型を呼び出し側に許してしまっている**。知識はある。シグネチャがそれを裏切っている、という状態。

### イディオムな答え：`any` をやめて**ジェネリクスの `comparable` 制約**に倒す（Go 1.18+）

```go
// 要素型 T に「comparable であること」を型レベルで要求する
func deleteDuplicate[T comparable](input []T) []T {
    out := make([]T, 0, len(input))
    seen := make(map[T]struct{}, len(input))
    for _, v := range input {
        if _, ok := seen[v]; !ok {
            seen[v] = struct{}{}
            out = append(out, v)
        }
    }
    return out
}
```

これで観点3 の問題が**まとめて消える**:

1. **panic が構造的に起こせなくなる**。`deleteDuplicate([]int{...})` の `[]int` 要素は**コンパイル時に弾かれる**（`[]int` は `comparable` を満たさない）→ 実行時 panic の余地が無い。
2. **検査が実行時 → コンパイル時に戻る**。`05` の合言葉「**型システムに任せられる検査を実行時に押し戻しているサイン**」がそのまま当てはまる。`any` は comparability の検査を実行時に押し戻している。`[T comparable]` はそれを型システムに返す。
3. **`any` のボクシングが消える**（②nice・効率）。`[]any` は要素を一つずつインターフェースに**箱詰め**する（各 `int`/`string` がヒープ上の interface 値になる）。ジェネリクスなら `[]int` は `[]int` のまま扱え、箱詰めも比較時の型タグ照合も無い。
4. **同じ関数が型ごとに型安全に使える**。`deleteDuplicate([]string{...})` も `deleteDuplicate([]int{...})` も、戻り値が `[]string`/`[]int` で返る（`any` だと呼び出し側が型アサーションで開け直す必要がある）。

### 判断は二択（どちらでもよい、根拠を言えること）

- **「`[]any` 混在スライスを 1 本で重複削除したい」が要件**なら（`notes.md` 03 の「いつか実施したい課題：`[]any` の混在スライス」に連なる狙い）→ `any` を**意図して残す**。ただし**契約をコメントで明示**する:
  ```go
  // 注意：要素は comparable であること。slice/map/関数を含むと m[i] で panic する。
  ```
  「何でも入る」ように見える型の**実際の制約を、読み手に言葉で渡す**。
- **「重複削除という汎用処理を型安全に書きたい」が狙い**なら → **ジェネリクス `[T comparable]`**。これが現代 Go の dedupe の**定石シグネチャ**で、panic の地雷もボクシングも消える。`05` で `key string` → key selector 関数に倒したのと**同じ構図**（実行時検査を型に返す）。

> 合言葉（`05` から一般化）: **型システムに任せられる検査を、実行時に押し戻すな。**
> `05` は「文字列でふるまいを選ぶ」だった。`06` は「`any` で何でも受ける」。どちらも **`invalidKey` / `panic` という失敗モードの存在そのものが、設計が一段ずれているサイン**。
> 「重複削除を comparable な何かに対してやりたい」の Go 的な答えは `any` ではなく **`[T comparable]`**。

> ※ 補足：`deleteDuplicate` は**非公開**（小文字始まり）なので、`04` のような「公開関数 × 非公開フィールド」の公開境界の不整合とは別。とはいえ panic はパッケージ内の呼び出しからでも起こせるので、契約のズレ自体は実在する。閉じた道具でも、`[T comparable]` に倒せば「同一パッケージ内の誰か」が `[]int` 要素を渡して落ちる事故を**型で**防げる。

## 観点4 軽微（イディオム・テストの穴）

- **ループ変数名 `i`**（`06_dedupe_ordered.go:10`）:
  ```go
  for _, i := range input {   // i は index に見えるが、実体は「要素（値）」
  ```
  `i` は慣習上**インデックス**を連想させるが、ここでは `_` がインデックスで `i` が**要素**。読み手が一瞬迷う。`v` / `item` / `elem` が素直（`05` の `person`→`p` と同型のイディオム指摘）。
- **`any` の同値は「動的型＋値」で決まる ―― テストで固定すると学びが残る**: Go では `any(1)`（int）・`any(int64(1))`・`any(1.0)`（float64）は**すべて別キー**（map のキー比較は動的型も突き合わせる）。今のテスト `duplicateMultiSlice`（`06_..._test.go:16`）は string と int の混在は踏んでいるが、「**同じ数字でも型が違えば別物**」は踏んでいない。1 ケース足すと、この性質を実データで固定できる:
  ```go
  {name: "sameNumberDifferentType", input: []any{1, int64(1), 1.0}, want: []any{1, int64(1), 1.0}}, // 3 つとも残る
  ```
  `04` の `mixUpperCaseAndLowerCase`（大文字小文字は別キー）や `notes.md` 03 の comparable 型の表と地続きの学び。任意だが教育価値は高い。
- **テストの穴（軽微）**: 7 ケースで主要動作は十分押さえている。
  - `duplicateIntSlice` / `duplicateStringSlice` で**型ごとの重複削除**、`duplicateMultiSlice` で**混在**、`twoDuplicateSlice` で**離れた位置の重複**、`noDuplicateSlice` / `emptySlice` / `nilSlice` で**境界** ―― ハッピーパスの被覆は良好。✓
  - 追加するなら: **全要素が同一**（`[]any{1,1,1}` → `[]any{1}`）、**単一要素**（`[]any{"x"}` → `[]any{"x"}`）。いずれも必須ではない。
- **`reflect.DeepEqual` でよい根拠**（`06_..._test.go:26`）: 出力が観点1 のとおり決定的（入力順を保つ）なので、`03` のような「ソートしてから比較／集合比較」は不要。順序が確定している今のケースでは `DeepEqual` が**最も素直で正しい**。✓（`04`/`05` と同じ結論）
- **命名（ごく軽微）**: `deleteDuplicate`（単数）より `dedupe` / `removeDuplicates` の方が英語として素直で、ファイル名 `06_dedupe_ordered` とも揃う。好みの範囲。

# 再レビュー記録 — ジェネリクス化は正しい方向。ただし「コンパイル時の安全」は T=any では実現しない

レビューを元にした修正の再レビュー。**観点1・2・4 はクローズ**。観点3 は**「形」は実装できた**が、`any` と `comparable` の Go 1.20 以降の関係により、狙った「コンパイル時の安全」が**テストの呼び出し方では実現していない**。ここが今回の山場。

> 前提: 本プロジェクトは `go 1.26.4`（`go.mod`）。`go test` は未実行（手元で裏取りのこと）。

## 修正内容と結果

| 観点 | 修正 | 状態 |
|---|---|---|
| 観点3 | `[]any` → ジェネリクス `func deleteDuplicate[T comparable](input []T) []T` | ✅ 形は実装（ただし下記の注意） |

| 観点4 | ループ変数 `i` → `v` | ✅ |

## 観点4 ―― `seen` は提案より良い改名

`m`→`seen` は、こちらが出した `v`/`item` 系の提案より一段良い。`seen` は「もう見たか？」という**判定の責務が変数名から読める**定番名で、観点1 の「map は存在判定の係に徹する」を**名前のレベルで自己説明**できている。`m[i] = struct{}{}` より `seen[v] = struct{}{}` の方が、本文を読まずに意図が伝わる。良い改名。

## 観点3【最重要・再】―― `any` は Go 1.20 以降 `comparable` を満たす。だから T=any では panic は消えていない

ここが今回いちばん大事な点。ジェネリクス化は**正しい方向**で、シグネチャは元の `[]any` より**厳密に汎用**（`[]int` でも `[]string` でも呼べる）になった。だが、狙った「**コンパイル時に slice/map 要素を弾く**」は、テストの呼び出し方では効いていない。理由:

- **テストは今も `input []any` を渡している**（`06_dedupe_ordered_test.go:11,29`）。よって `deleteDuplicate(c.input)` は **`T = any` でインスタンス化**される。
- そして **Go 1.20 以降、`any`（interface 型）は `comparable` 制約を満たす**（本プロジェクトは `go 1.26.4`）。だから `deleteDuplicate[any]` は**問題なくコンパイルが通る**。
- つまり `T = any` の経路では、comparability の検査は**また実行時に戻っている**。元レビューで挙げた panic の例:
  ```go
  deleteDuplicate([]any{[]int{1}, []int{1}})  // T=any → コンパイルは通り、実行時に panic
  ```
  は**今も panic する**。ジェネリクスにしても、`[]any` で呼ぶ限り「実行時 panic の地雷」は**消えていない**。

### コンパイル時の安全が効くのは「具体型で呼んだとき」だけ

`[T comparable]` の検査は**型引数 T に対して**かかる。slice 要素を弾けるのは、**要素型を具体型として渡したとき**:

```go
deleteDuplicate([]int{3, 1, 3, 2, 4})     // T=int  → OK・箱詰め無し
deleteDuplicate[[]int]([][]int{{1}, {1}}) // T=[]int → コンパイルエラー（[]int は comparable を満たさない）← ここで初めて型が守る
```

`[]any` で渡すと slice 要素が `any` の箱の**中**に隠れるので、コンパイラからは見えず、T=any として通ってしまう。**箱詰め（boxing）も T=any の経路では残ったまま**。

> つまり現状は「シグネチャはジェネリクス、でも唯一の呼び出し元（テスト）が T=any」という**中間状態**。
> 元レビュー 観点3 の二択でいうと、`[]any` の混在ケース（`duplicateMultiSlice`・`sameNumberDifferentType`）を残した時点で、実は**①「`any` を意図して残す」側に寄っている**。②「型安全を取る」を本当に取るなら、テストを具体型に変える必要がある。

### 二択の決着のさせ方（どちらでもよい・両取りが理想）

- **(A) 混在 dedup を使いたい**（`[]any`・型混在）→ 今のテストでカバー済み。**ただし T=any なので、slice/map/func 要素では今も panic する**ことを理解しておく。`sameNumberDifferentType` は「型が違えば別キー」を示す良いケースだが、これは **T=any の経路だからこそ**成立する（具体型では `int`・`int64`・`float64` を 1 スライスに混在できない）。
- **(B) 型安全な dedup を使いたい**（`[]int`/`[]string`）→ ジェネリクスの本当の旨味（コンパイル時に弾く・箱詰め無し）はここで出る。**今のテストはこの経路を一度も踏んでいない**。具体型で呼ぶケースを足すと、安全側を実データで固定できる。

理想は両方。テーブルが `[]any` 固定なので、具体型ケースは別テーブル／別テスト関数に分けるのが素直:

```go
func TestDeleteDuplicate_Concrete(t *testing.T) {
    if got := deleteDuplicate([]int{3, 1, 3, 2, 4}); !reflect.DeepEqual(got, []int{3, 1, 2, 4}) {
        t.Errorf("got=%v", got)
    }
    if got := deleteDuplicate([]string{"a", "b", "a"}); !reflect.DeepEqual(got, []string{"a", "b"}) {
        t.Errorf("got=%v", got)
    }
}
```

これで「ジェネリクスにした意味（具体型で型安全・箱詰め無し）」が**テストで見える**ようになる。
