`07_lookup`（Phase 1 ドリル）のレビュー。
お題は「リストをキーで引ける表に変換し、別のキー列から引く」（`DRILLS.md` 7 番）。狙いは「**繰り返し引くなら先に索引化する**」という判断を身につけること。
今回は **`04`〜`06` と違って「緑は信用してよい」回ではない** ―― `go test` を回すと **`usersEmpty` が赤**。だから今回の主題はこうなる:

2. **`m[v]` が欠損キーで「ゼロ値」を黙って返す ―― これがテストを赤にしている**（観点2）。`DRILLS.md` の Go 罠表がまさに挙げている `v, ok := m[k]` を無視している。
3. **その根っこは「欠損キーの契約」が未定義なこと**。実装（ゼロ値を積む）とテスト（`usersEmpty` の want は `[]string{}`＝skip）が**食い違っている**（観点3）。

> 大原則（review-rubric の ②道具の良し悪し）: イディオムか・計算量に無駄はないか・データ構造の選択は妥当か。

## 観点1【良い・最重要】索引化の定石は正しい。順序は `input` が握り、`05`/`06` の学びが予防として効いている

赤を先に言ったが、**骨格は良い**。このドリルの狙い「繰り返し引くなら先に索引化する」は、計算量の面で正しく実現できている。

```go
m := make(map[T]K, len(users)) // ① users を 1 回走査して索引を作る … O(n)
for _, user := range users {
    m[KeyOf(user)] = ValueOf(user)
}
for _, v := range input {       // ② 引くたびに O(1) で引く … O(m)
    result = append(result, m[v])
}
```

毎回 `users` を線形探索（`for u := range users { if u.ID == v ... }`）すれば **O(n×m)**。
先に `map` へ索引化してから引けば **O(n+m)**。`DRILLS.md` の補足「毎回リストを線形探索せず、先に map へ変換してから引く」を**そのまま満たせている**。✅

### 順序の出どころは `input`（引くキー列）。`map` は索引の係に徹している ―― `06` の系譜を継承

`03`→`04`→`05`→`06` で繰り返した合言葉「**`map` に順序を期待しない。順序が要るなら別の道具が握る**」。
`07` もこの系譜の上にいる:

```go
for _, v := range input {                 // ★ 出力の順序は input の走査順
    result = append(result, m[v])         //   map を for k := range m で走査していない
}
```

- 出力 `result` の並びは `input`（引くキー列）の index 順 → **決定的**。
- `m` は `for k := range m` で走査していない（索引参照 `m[v]` にしか使っていない）→ map の不定順は**出力に触れない**。
- だから `reflect.DeepEqual`（順序に厳密）と衝突しても**フレーキーにならない**。コメント `// inputはスライスから取り出しているので、順序も保証` が、その理解を言葉にできている。✓

> `06` は「順序＝入力スライスの走査順／`map` は**存在判定**の係」だった。
> `07` はそれを一歩進めて「順序＝`input`（引くキー列）の走査順／`map` は**索引（key→value）**の係」。
> `map` の役割が `set`（存在判定）から `lookup table`（値を引く表）に変わっても、**順序を `map` から引き剥がす**骨格は同じ。系譜が効いている。

### キー衝突は「後勝ち」で決定的 ―― `IDDuplicate` が固定している

```go
// users = [{1,A},{2,B},{1,B}], input = [1,2,1]  → want ["B","B","B"]
m[1] = "A"   // users[0]
m[2] = "B"   // users[1]
m[1] = "B"   // users[2] が上書き（後勝ち）
```

同じキーが複数あると `m[KeyOf(user)] = ValueOf(user)` が**上書き**する。これが決定的なのは、**`users` をスライス index 順に走査している**から（`for k := range m` の不定順ではなく、`users` の並びが後勝ちを決める）。`IDDuplicate`（`07_lookup_test.go:20`）がこの「後勝ち」を実データで固定できている。✓

### `05`（関数注入）と `06`（ジェネリクス）の学びが、両方そろって予防に効いている

```go
func findUsersByKey[T, K comparable](users []User, input []T, KeyOf func(User) T, ValueOf func(User) K) []K
```

- **`05` の学び（関数注入 / key・value セレクタ）**: 「どのフィールドで引くか」を `KeyOf`/`ValueOf` の**関数で注入**している。`05` で `key string`（stringly-typed）を倒した答えが、最初から実装に出ている。`invalidKey` のような実行時検証はそもそも要らない。✅
- **`06` の学び（ジェネリクス `[T comparable]`）**: キー型 `T` を `comparable` で型レベルに要求。`map[T]K` のキーに非 comparable 型を渡せばコンパイルで弾かれる。`06` の「`any` を `[T comparable]` に倒す」がそのまま身についている。✅

しかも `TestFindUsersByKey_ID`（T=int, K=string）と `TestFindUsersByKey_Name`（T=string, K=int）で、**ジェネリクスの両方向**を踏めている。`06` の「両経路をテストで踏み分ける」と同じ良さ。✓

> 合言葉（`03`→`06` を継承）: **`map` に順序を期待しない。順序が要るなら別の道具（ここでは `input` の走査順）が握る。**
> ＋ `05`/`06` の学び（関数注入・ジェネリクス）が、**書く前から予防として効いている**。骨格は文句なし。

## 観点2【バグ・最重要】欠損キーで `m[v]` がゼロ値を黙って返す ―― これが `usersEmpty` を赤にしている

ここが今回の核心。`go test` は緑ではない:

```
=== RUN   TestFindUsersByKey_ID/usersEmpty
    07_lookup_test.go:30: 期待する値と違います。gotValue= [  ], want= []
--- FAIL: TestFindUsersByKey_ID/usersEmpty
```

原因はこの 1 行:

```go
for _, v := range input {
    result = append(result, m[v])   // ★ v が m に無いとき、m[v] は K のゼロ値("")を「黙って」返す
}
```

Go の `map` 索引は、**キーが無くても panic せず、値型のゼロ値を返す**。`K=string` ならゼロ値は `""`。
だから `usersEmpty`（users 空 → m 空、input `[2,1,2]`）は:

```go
m = {}                 // 空
input = [2, 1, 2]
result = ["", "", ""]  // m[2]="" , m[1]="" , m[2]="" を append
```

`gotValue = ["", "", ""]`（`%v` で `[  ]` と表示）。だがテストの `want = []string{}`。
**3 要素 vs 0 要素**で `reflect.DeepEqual` は `false` → 赤。これは観点1 で褒めた骨格とは別の、**欠損キーの扱い**の問題。

### これは `DRILLS.md` が名指しで挙げている Go の罠

`DRILLS.md`（言語別に踏み抜く罠）の Go 行にこうある:

> Go | … / `v, ok := m[k]`

`m[v]`（単値）は「在る／無い」を区別できない。区別したいなら **`val, ok := m[v]`** の `ok`（在ったか）で受ける。
今のコードは `ok` を見ていない ―― **このドリルが踏ませにきている罠を、いままさに踏んでいる**。`usersEmpty` の赤は、その罠の現れ。

### `01` の合言葉の「一段上」の食い違い

`01` の合言葉「**実装とテストで nil/空を食い違わせない**」は、ここでは nil/空ではなく**欠損キーの契約**で破れている:

- 実装の挙動: 欠損キー → **ゼロ値を積む**（だから `usersEmpty` は `["","",""]`）。
- テストの期待: `usersEmpty` の want は **`[]string{}`**（＝欠損は**積まない/skip**したい、という意図）。

**実装は「ゼロ値プレースホルダ」なのに、テストは「skip」を期待している**。同じ「食い違い」でも、`01` は nil/空、`07` は**欠損キーの契約**という一段上のレイヤーで起きている。直し方は観点3（契約をどちらに倒すか）で決める。

> 合言葉（新規）: **`m[k]` は欠損キーでもゼロ値を黙って返す。「在る／無い」を区別したいなら `val, ok := m[k]` で受ける。**
> `usersEmpty` の赤は、`v, ok` を無視したことの直接の結果。

## 観点3【設計の二択・最重要設計】欠損キーの「契約」を決める ―― 実装・テスト・コメントを揃える

観点2 の赤は、**「引くキーが表に無いとき、どうするか」が決まっていない**ことの症状。`DRILLS.md` 7 番は欠損キーの挙動を**規定していない**ので、これは**あなたが決める設計**。候補は 3 つ:

### ① skip（在ったものだけ積む）― `usersEmpty` の want=`[]string{}` はこれを意図している

```go
for _, v := range input {
    if val, ok := m[v]; ok {        // ★ 在ったときだけ積む
        result = append(result, val)
    }
}
```

- `usersEmpty`（全キー欠損）→ `result = []string{}`。**テストの現在の want とそのまま一致**（＝今のテストが暗に求めているのはこれ）。
- 注意点: **出力長が input 長と一致しなくなる**。`input=[2,999,1]`（999 が欠損）→ `[B, A]`。「どの位置が落ちたか」は失われる。フィルタ＆ルックアップとしては自然だが、位置対応は捨てる。

### ② ゼロ値プレースホルダ（今の実装の挙動）― なら**テストの want を直す**

```go
// 実装は今のまま。ただし契約をコメントで明示する:
// 注意：input のキーが users に無い場合、K のゼロ値を返す（位置対応を保つ）。
result = append(result, m[v])
```

- これを採るなら、`usersEmpty` の want を **`[]string{"", "", ""}`** に直す（実装に合わせる）。
- 利点: **出力長が input 長と必ず一致**（位置対応が保てる）。
- 欠点: 「キーが無い」と「値がたまたまゼロ値」が**区別できない**。契約をコメントで読み手に渡すこと。

### ③ 厳密（欠損はエラー/panic）

```go
val, ok := m[v]
if !ok {
    return nil, fmt.Errorf("キー %v は表に存在しません", v) // 戻り値を ([]K, error) に変える
}
```

- 「欠損はバグ」という強い契約。シグネチャを `([]K, error)` に変える必要があり、このドリルの規模では重い。今回は採らなくてよいが、選択肢として把握。

### 判断の指針（一文で意図を言えるか）

- `usersEmpty` の want が `[]string{}` である以上、**あなたの頭の中の契約は ① skip**に見える。ならば実装を `val, ok := m[v]` の skip 版にするのが素直 ―― **テストを変えずに緑になる**。
- もし「位置対応を保ちたい（input 長＝output 長）」が要件なら ②。**そのときはテストの `usersEmpty` を `["","",""]` に直し、契約をコメントに書く**。

どちらでもよい。**大事なのは「実装・テスト・コメント」の三つを同じ契約に揃えること**。今は三者がバラついているから赤になっている。

> 合言葉: **欠損キーの「契約」を一つ決め、実装とテストと説明を揃える。**「`m[k]` が黙ってゼロ値を返す」ことに**乗る（②）か・乗らない（①/③）か**を、意図として言えること。

## 観点4 軽微（イディオム・効率・テストの穴）

- **パラメータ名 `KeyOf` / `ValueOf` が大文字始まり**（`07_lookup.go:9`）。Go で識別子の大文字始まりは「パッケージ外公開」を意味するが、**関数パラメータは常にローカル**なので大文字にしても公開はされない ―― ただし**読み手に「公開シンボル？」と誤読させる**。イディオムは小文字。`05` で `keyOf`/`valueOf`（小文字）にしたのと**揃えるべき**。`keyOf`, `valueOf` に。
  ```go
  func findUsersByKey[T comparable, K any](users []User, input []T, keyOf func(User) T, valueOf func(User) K) []K
  ```
- **`K` の制約 `comparable` は過剰**（`07_lookup.go:9`）。`K` は **map の値型**であって、map の**値**に comparable 制約は不要（必要なのはキー型 `T` だけ）。`K` はどこでも比較していない（`append` するだけ）。`K comparable` → **`K any`** に緩めてよい。そうすれば値が `[]string` 等の非 comparable 型でも引ける。型を不必要に狭めない（②nice）。
- **容量先取りは両方できている**（`07_lookup.go:12,14`）。`make(map[T]K, len(users))` ＋ `make([]K, 0, len(users))`。`01`/`04`/`06` の「容量先取り」を**索引 map と結果スライスの両方**に効かせられている。✓（ただし `result` の cap は `len(users)` だが、本来の上限は `len(input)`。①skip なら `len(input)` 以下、②なら丁度 `len(input)`。`len(input)` の方が見積りとして素直 ―― 軽微）
- **`var result []K` でも結果は同じだが、`make([]K, 0, len(users))` の方が良い**。`01` の学び（nil スライスより非 nil 空スライス）に乗れている。✓
- **テストの穴（最重要の穴）**: 現状 7 ケースだが、**「一部だけ欠損」のケースが無い**。
  - 今あるのは「全キー在る」（`Normal` 等）か「全キー欠損」（`usersEmpty`）の両極だけ。
  - **観点2/3 を定義づけるのは、まさに「一部欠損」**。例: `users=[{1,A},{2,B}], input=[1,3,2]`（3 が欠損）。
    - ① skip 契約なら want=`["A","B"]`（3 は落ちる）。
    - ② ゼロ値契約なら want=`["A","","B"]`（3 はゼロ値）。
  - **このケースを足すと、欠損キーの契約がどちらなのかが一目で固定される**。今は `usersEmpty`（全欠損）でしか効いておらず、しかもそこで赤になっている。
- **テストの穴（軽微）**: 追加するなら **単一 user**（`[{1,A}]`, input `[1]` → `["A"]`）、**引くキーに重複**（`Normal` の input `[2,1,2]` で既に踏めている ✓）。`Name` 側はケースが 1 つだけ ―― ID 側と同程度に増やしてもよい（必須ではない）。
- **`reflect.DeepEqual` でよい根拠**: 出力は観点1 のとおり `input` 順で決定的なので、`03` のような「ソートしてから比較」は不要。順序が確定している今のケースでは `DeepEqual` が最も素直で正しい。✓（`04`〜`06` と同じ結論）

## 観点3 ―― skip を選び、`IDDeficiency` で契約を固定できたのは良い判断

二択（①skip／②ゼロ値／③エラー）のうち **①skip** を採用。`usersEmpty` の want（`[]string{}`）を**変えずに**緑にできたのは、元レビューで言った「`usersEmpty` の want はそもそも skip を意図している」と整合する、最も素直な決着。

そして `IDDeficiency` を足したことで、**skip の本質**が実データに乗った:

```go
// users=[{1,A},{2,B}], input=[1,3,2]（3 が欠損）→ ["A","B"]
```

- 3 が落ちる＝**欠損は積まない**（skip 契約）。
- ここで**出力長（2）≠ 入力長（3）**になる ―― これが skip 契約の代償（位置対応は捨てる）。`IDDeficiency` はそれを**承知の上で固定**できている。契約が「実装・テスト・コメント」で揃った。✅

> `06` の `seen` 改名と同じく、**cap のコメント**（`len(users)` では `input=[2,1,1,2,3]` で足りない）はこちらの提案を一段上回った。
> 「なぜ `len(input)` か」を**反例つきで**言語化できているのは、容量見積りを"なんとなく"でなく根拠で選べている証拠。

## 残課題1【`04`/`05` の再来】`if len(users) == 0` の早期 return は**いまや冗長** ―― comma-ok が同じ仕事をしている

ここが今回いちばん大事な再指摘。バグを **2 通り**で直してしまっている:

```go
if len(users) == 0 {          // ★(a) 早期 return … usersが空なら即 []K{}
    return result
}
...
for _, v := range input {
    if _, ok := m[v]; ok {    // ★(b) comma-ok skip … 欠損キーは積まない
        result = append(result, m[v])
    }
}
```

**(b) を入れた時点で、(a) は要らなくなっている**。証明（動作不変）:

- `users` が空 → `m` は空マップ → 入力ループで全ての `v` が `ok==false` → **何も append されない** → `result` は `[]K{}` のまま。
- つまり **(a) を消しても `usersEmpty` は `[]string{}` を返す**。(a) の有無で結果は変わらない。

そして (a) のコメントが**実体とズレている**:

```go
// 修正：usersが空の場合、空文字が入るので、弾く   ← ★ もう「空文字は入らない」
```

「空文字が入る」のは **comma-ok を入れる前**の話。いま空文字を防いでいるのは **(b) の comma-ok** であって (a) ではない。**(a) はその防御に寄与していない**。
これは `04` 観点2・`05` 観点2 で何度も出た「**無くても同じ結果になる分岐**」そのもの。`04` では最終的に削除した。

判断は二択（どちらでもよい・根拠を言えること）:
- **消す（素直）**: comma-ok が空 users も欠損キーも一手で捌くので、(a) は丸ごと不要。分岐が一つ減る。
- **残す（要・理由の書き換え）**: もし残すなら理由は「空文字を弾く」ではなく **「users が空なら全 lookup が必ず外れると分かっているので、入力ループ（O(m)）を丸ごと省くショートカット」** という**マイクロ最適化**。これなら語れる。ただし効果は薄く、コメントは実体（comma-ok が本体・これは早期脱出）に直すこと。

> 合言葉（`04`/`05` から再掲）: **「この分岐は、どんな入力のときに効くか一文で言えるか」**。
> 答えが「効く入力は無い（comma-ok が同じ結果を出す）」なら消す。残すなら「空文字を弾く」ではなく**正しい理由**を書く。

## 残課題2【`05` の再来・②nice】ループ内で `m[v]` を**二重に**引いている

```go
if _, ok := m[v]; ok {
    result = append(result, m[v])   // ★ m[v] をもう一度引いている
}
```

comma-ok の `_` で**値を捨てて**、直後に `m[v]` で**同じ索引をもう一度**引いている。`05` 観点4 の「キー計算を 1 行で 2 回」と同型。値を束ねれば 1 回で済む（②nice）:

```go
if val, ok := m[v]; ok {
    result = append(result, val)
}
```

`_` を `val` にするだけ。map 索引が 1 回になり、意図（「在ったらその値を積む」）も読みやすくなる。
