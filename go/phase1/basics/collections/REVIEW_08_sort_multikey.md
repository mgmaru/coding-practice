# レビュー: `08_sort_multikey` —「複合キー」は正しい。だが**緑が主題（安定性）を測っていない**

`08_sort_multikey`（Phase 1 ドリル, Tier 2 の最後）のレビュー。
お題（`DRILLS.md` §8）は「**姓の昇順 → 年齢の降順**で並べる」、そして狙いは明文で **「カスタム比較と*安定性*を扱う」**、補足は **「同姓内で元の相対順が崩れないこと（*安定ソート*）」**。
複合キーの比較ロジックは**正しい**（テストの `want` すべてと一致）。が、このドリルの主題は比較ロジックではなく**安定性**であり、そこに穴がある。

> 大原則（review-rubric の ②道具の良し悪し）: イディオムか・計算量に無駄はないか・**道具の選択は仕様と一致しているか**。
> 前提: `go test -run TestSortStable -count=5` が **5 回連続で緑**。`gofmt` 差分なし・`go vet` クリーン。
> だが今回の論点は「緑が正しいか」ではなく **「緑は*何を*保証しているか」**。

今回は `07` のような**赤**ではない。`04`〜`06` のような**バグの無い回**でもない。
**緑なのに、その緑がドリルの主題（安定性）を一切観測していない**という、シリーズで新しい型の指摘になる。

## 観点1【最重要・要修正】ドリルの主題は「安定ソート」。だが `sort.Slice`（非安定）を使い、テストは安定性を観測できない

`DRILLS.md` §8 を読むと、このドリルが要求しているのは2つ:

```
- 狙い: カスタム比較と「安定性」を扱う。複合キーの並べ替え。
- 補足: 同姓内で元の相対順が崩れないこと（安定ソート）。
```

関数名も `sortStable` ―― **「安定」を約束している**。ところが実装はこう:

```go
sort.Slice(input, func(i, j int) bool {   // ★ sort.Slice は「安定でない」
    if input[i].Last == input[j].Last {
        return input[i].Age > input[j].Age
    }
    return input[i].Last < input[j].Last
})
```

Go の標準ライブラリのドキュメントは明言している ―― **`sort.Slice` は「The sort is not guaranteed to be stable.」**。
安定版は別関数 **`sort.SliceStable`** だ。つまり**名前と仕様（安定）に対して、道具（非安定）が食い違っている**。

### では、なぜテストは通るのか？ ―― ここが `04` 観点1 と同じ顔をして、結論が逆

`04` の観点1は「`map` 走査は不定だが `sort` の**全順序**で並びが確定し、キーが一意なのでタイが残らない → 決定的 → 緑は信用してよい」だった。
ここも一見同じ理屈で説明できる。比較器 `(Last 昇順, Age 降順)` のもとで**2要素がタイになるのは「姓も年齢も同じ」とき**。
だが `Person` は `{Last, Age}` の**2フィールドしか持たない**。姓も年齢も同じ＝**値として完全に同一**。

```go
type Person struct {
    Last string
    Age  int
}
```

同一の値を入れ替えても `reflect.DeepEqual` には見えない。だから `sort.Slice`（非安定）でも `sort.SliceStable`（安定）でも、
**この構造体では出力がビット単位で一致する**。安定／非安定の差が**観測不能**なのだ。

> ここが `04` との決定的な差。
> `04`: 決定的な緑 ＝ **要求（正しい順序）が満たされた証拠**。
> `08`: 決定的な緑 ＝ **要求（安定性）とは無関係**。緑が証明しているのは「複合キーの順序が正しい」だけで、「安定である」は**一切測っていない**。

### 自問（合言葉の確認）

- このコードの「安定」は、どのテストが保証している？ → **どれも保証していない。** 安定／非安定で出力が変わるケースが存在しない（タイ＝値が同一）。
- 関数名 `sortStable` の約束は、実装が果たしている？ → **果たしていない。** `sort.Slice` は非安定。

> 合言葉（新規）: **「緑」は「正しい」ではなく「テストが見ている範囲で矛盾が無い」。*ドリルの主題が緑の射程に入っているか*を必ず確かめる。**
> ここでは主題（安定性）が射程の外にある。緑は本物だが、**測っているものが違う**。

### 直し方は二段（どちらも要る）

**(1) 道具を仕様に合わせる ―― `sort.Slice` → `sort.SliceStable`。**
現行の6ケースは出力が同一なので、**変えても緑のまま**。名前 `sortStable` と狙い「安定性を扱う」に**実体が追いつく**。コストはほぼゼロ。

```go
sort.SliceStable(input, func(i, j int) bool { ... })   // 名前と仕様に一致
```

**(2) 安定性を*観測できる*テストにする ―― ソートキーに含まれない第3フィールドを足す。**
2フィールドのままでは「安定」は永遠に検証できない。**ソートキー外の識別子**（例: 入力順 `Order int`、または名 `First string`）を持たせると、
「姓も年齢も同じだが別人」を表現でき、**入力順が保たれるか**をテストで主張できる。

```go
type Person struct {
    Last  string
    Age   int
    Order int   // ソートキーには使わない。入力順を観測するためだけのタグ
}

// 安定性を踏むケース（非安定だと割れて落ちる ＝ ここで初めて主題に牙が生える）
input := []Person{{"Sato", 30, 1}, {"Sato", 30, 2}, {"Ito", 25, 3}}
want  := []Person{{"Ito", 25, 3}, {"Sato", 30, 1}, {"Sato", 30, 2}}  // Order 1→2 が保たれる
```

このケースは `sort.Slice` だと **割れて赤になりうる**／`sort.SliceStable` だと**必ず緑**。
そこで初めて「安定」がテストに乗る。**安定を名乗るなら、安定を踏むテストを置く。**

> 合言葉（再掲・`04` の一段上）: **緑が決定的でも、それが*主題*を測っているとは限らない。「この緑は、ドリルの狙いのどの一文を検証しているか」を言えること。**

## 観点2【設計の二択】in-place で並べ替えるのに、新しいスライスを返したように見える ―― 破壊性の二重人格

```go
func sortStable(input []Person) []Person {
    ...
    sort.Slice(input, ...)   // ★ input を「その場で」並べ替える＝呼び出し側のスライスも順序が変わる
    return input             // ★ さらに同じ input を返す
}
```

`sort.Slice` は**引数を破壊的に並べ替える**（in-place）。標準ライブラリの作法としては普通だ。
問題は、この関数が**破壊しつつ、同じスライスを戻り値としても返す**こと。呼び出し側にはこう見える:

```go
sorted := sortStable(people)   // people も sorted も、同じ並べ替え済み配列を指す
```

`people` は黙って並べ替わる。`sorted := ...` と書いた人は「`people` は無傷」と誤解しやすい。**「返す」＝「新しく作った」と読めてしまう**のが罠。

さらに**素性が経路で食い違う**:

| 入力 | 返すスライス | input を別名参照しているか |
|---|---|---|
| 空 / nil | `[]Person{}`（**新規確保**） | しない（input とは別物） |
| 非空 | `input`（並べ替え済み） | **する**（input そのもの） |

非空のときだけ戻り値が入力の別名 ―― 「戻り値は入力と独立」と仮定するコードは非空で破綻する。

### 二択（意図を一文で言えること）

- **破壊的（in-place）で行く**: 戻り値は省く、あるいは「チェイン用」と割り切り、コメントで **「この関数は引数を並べ替える（破壊的）」** と明記。呼び出し側は元順を失う前提。
- **非破壊で行く**: 先頭でコピーしてからソート。呼び出し側のスライスは無傷。**公開境界をまたぐなら非破壊が安全**。

```go
// 非破壊にするなら
out := append([]Person(nil), input...)   // 入力をコピー
sort.SliceStable(out, ...)
return out
```

ドリルとしてはどちらでもよい。だが **「破壊するのか・しないのか」を意図として決め、コメントと戻り値の形を揃える**こと。今は「破壊するのに非破壊に見える」中間状態。

> 合言葉（新規）: **「破壊的に変更する」と「新しい値を返す」は別の契約。両方の顔をすると、呼び出し側は必ずどちらかで誤解する。一つに倒す。**

## 観点3【良い・`04`の逆】早期 return は、ここでは load-bearing ―― 消すと赤になる

```go
if len(input) == 0 {
    return []Person{}   // input が空 or nil のとき、共通で非 nil の空スライスを返す
}
```

`04` ではこの形の早期 return は**冗長**だった（本体が `make([]..., 0, len(m))` 始まりで、空でも**必ず非 nil** を返すため、ガードを消しても結果不変）。
**`08` は逆**。本体は最後に `return input` で**入力をそのまま返す**。ガードを消すとどうなるか:

| 入力 | ガード無しの戻り値 | テストの `want` | 判定 |
|---|---|---|---|
| `nil` | `sort.Slice(nil,…)` は安全 → `return nil`（**nil のまま**） | `[]Person{}`（非 nil） | **赤**（`DeepEqual(nil, []Person{})==false`） |
| `[]Person{}` | `return []Person{}` | `[]Person{}` | 緑 |

つまり**このガードは「nil 入力を非 nil の空スライスに正規化する」ために効いている**。消すと `NilSlice` ケースが赤。
**「この分岐は、どんな入力のときに効くか一文で言えるか」** に対し、答えは **「nil 入力のとき、nil を非 nil の空に正規化する」** ―― 言える。だから **load-bearing。残す。**

> 合言葉（`04`→`05`→`07` を継承）: **「無くても同じ結果になる分岐」は語れないなら消す。逆に、*消すと赤になる*分岐は load-bearing。両者を見分ける。**
> `04` と `08` は**同じ見た目の早期 return が、本体の作り（`make` 始まり vs `input` 返し）次第で正反対の運命**になる好例。見た目で判断せず、**「消したら赤か」で判定する**。

補足: ガードは空 `[]Person{}` も拾うが、空のほうは無くても緑（上表）。厳密に効いているのは **nil 経路だけ**。だが「空も nil もここで揃える」と読める分、今の形は**意図が明快**で良い。コメント（呼び出し側が nil/空を意識せず済むようにする）も実体と一致している ―― これは `01` の合言葉の正しい踏襲。

> 合言葉（`01` から継承）: **nil か空かは好みでよい。だが実装とテストで食い違わせない。** 実装は常に `[]Person{}`、テストの `want` も nil/空ともに `[]Person{}`。✓ 食い違いなし。

## 観点4 軽微（タイポ・イディオム・テストの穴）

- **コメントのタイポ（`08_sort_multikey.go:14`）**: `// inputがいk空もしくはnilの時` の **「いk」は誤字**（`// input が空もしくは nil の時`）。挙動には無関係だが、コメントは正確に。
- **比較器の正しさ**: `(Last 昇順, Age 降順)` はテストの `want` 全件と一致 ―― `DuplicateLast`（Sato 40 → Sato 30 で Age 降順 ✓）、`DuplicateAge`（Ito < Sato < Suzuki で Last 昇順 ✓）。**ロジックは正しい。** ✓
- **`AllDuplicate` は安定性を踏んでいない（`08_sort_multikey_test.go:17`）**: 3要素すべて `{Sato, 30}` で**値が同一**。並べ替えても見えないので、これは「**全要素同値でも壊れない**」を確認しているだけ。**「安定」の検証にはなっていない**（→ 観点1 の第3フィールドが必要）。名前から「安定性テスト」と誤読しないこと。
- **`reflect.DeepEqual` でよい根拠**: 出力は決定的（タイ＝値同一）なので `DeepEqual` が最も素直。✓ ―― ただし `04` と**決定的の理由が違う**。`04` は「全順序＋キー一意でタイ無し」、`08` は「タイはあるが値が同一で観測不能」。**結論（DeepEqual でよい）は同じでも、根拠は別**。ここを取り違えると観点1 を見落とす。
- **イディオム**: `sort.Slice` ＋クロージャは一回限りの比較ソートとして正攻法（`sort.Interface` 実装は不要）。✓ コメント付きで比較器が読みやすいのも良い。
