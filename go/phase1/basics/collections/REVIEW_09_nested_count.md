# レビュー: `09_nested_count` —「二段集約」は正しい。主眼は "数える係の重複" と "順序いらずの再確認"

`09_nested_count`（Phase 1 ドリル・Tier 3「ネストと結合」の1発目）のレビュー。
お題は「日付ごと × レベルごとの件数を数える（`map[date]map[level]int`）」＝**ネストした map を構築する**。`logstat` 本体と地続き。
このドリルは `05_group_by`（キーごとにリストを溜める）と `04_count_frequency`（数える）を**合成**したもの。実装もまさにその二段構えになっている。

結論から言うと **コードは正しく、緑も信用してよい**（バグ無し・`gofmt`/`vet` クリーン）。
今回の主題は「なぜこの緑は `03` のようにフレーキーにならないのか（しかも `04` とは*違う理由*で）」の言語化と、**`04` で一度覚えた `m[k]++` を `09` で手放している**という②道具の後退の指摘。

> 大原則（review-rubric の ②道具の良し悪し）: イディオムか・計算量に無駄はないか・データ構造の選択は妥当か。
> 前提: `go test -run TestAggregateDateStatus -count=5` が **7 サブテスト × 5 回連続で緑**。`gofmt` 差分なし・`go vet` クリーン。
> そして今回も、**この緑は信用してよい**（観点1）――ただし `04` とは根拠が違う。

## 観点1【良い・最重要】出力が **map** だから `DeepEqual` は順序非依存 ―― `03`→`07` の「map に順序を期待しない」スレッドの終着点

`03` 以来ずっと追ってきた合言葉「**`map` に順序を期待しない**」。`04` は「順序が要るからスライス＋`sort` の全順序で確定」、`08` は「安定性が要るから `SliceStable`」と、**"順序が要る" 側で**この合言葉を消化してきた。
`09` はその**逆側**――**そもそも順序が要らない**。ここが終着点。

```go
func aggregateDateStatus(input []Status) map[string]map[string]int { ... }
//                                        ^^^^^^^^^^^^^^^^^^^^^^^^^^  出力そのものが map
```

出力が `map[string]map[string]int` なので、`reflect.DeepEqual` は**キーと値の対応だけを見て、走査順を一切見ない**（map 比較は順序非依存）。
だから第1ループ `for _, s := range input` も第2ループ `for key, vals := range m` も**実行ごとに並びがバラけてよい**――その並びは**出力に一切漏れない**（出力は map で、順序という概念を持たない）。

> `04` との決定的な差:
> - `04`: 出力が**スライス** → 順序が結果に漏れる → `sort` の全順序で確定させて初めて決定的（緑を信用できる）。
> - `09`: 出力が**map** → 順序が結果に**そもそも存在しない** → 何もしなくても決定的。`DeepEqual` が**最も素直で正しい**唯一の道具。

### ただし: コメント「ソートが必要」は**誤解の化石**（②・観点4 とも連動）

```go
out := make(map[string]map[string]int, len(input))
for key, vals := range m { // ... 注意：map mからforで取り出しているので、並び順が保証されていない。 -> ソートが必要
```

`09_nested_count.go:23` のコメント末尾 **`-> ソートが必要`** は事実と食い違っている。
このコードには `sort` は**無い**。そして**無くて正しい**（出力が map だから、上記の通り順序は結果に漏れない）。
「`map` 走査は順不同」までは正しい観察だが、そこから「だからソートが必要」は**誤った結論**――正しくは「**だが出力も map なので、ソートは不要**」。

> 合言葉（`08` から継承）: **コメントはコードが実際にやることを書く。願望や途中の誤解を残さない。**
> ここは「`map` 走査は順不同 → *だが出力も map なのでソート不要*」に直すと、観点1 の理解がコメントに正しく刻まれる。

### 自問（合言葉の確認）
- `map` 走査の並びに依存していないか？ → **していない**。出力が map なので並びは結果に漏れない。
- ではなぜ `04` は `sort` が要ったのに `09` は要らない？ → **出力の型が違う**。`04` はスライス（順序が結果）、`09` は map（順序は非結果）。

> 合言葉（`03`→`04`→`06`→`07`→ここで完結）: **`map` に順序を期待しない。**
> ―― `04`/`08` は「順序が要る側」で、順序を別の道具（`sort`）に握らせて消化した。
> ―― `09` は「順序が要らない側」で、**出力自体を map にして順序の問題を消した**。同じ合言葉の、もう一つの倒し方。

## 観点2【②道具・簡素化の主眼】"数える係" の重複 ―― `04` で覚えた `m[k]++` を、`09` で手放している

ここが今回いちばん手を動かす価値のある指摘。**カウントのロジックが、`04` より後退している**。

```go
// 09_nested_count.go:25-32
for _, v := range vals {
    if _, ok := n[v]; ok { // もし、nの中にLevelがあったら、出現回数をカウントアップ
        n[v]++
        continue // 忘れずに
    }
    // もしなかったら、キー(レベル)と初期値を加える
    n[v] = 1 // 初期値
}
```

この 8 行は、**まるごと 1 行に潰れる**:

```go
for _, v := range vals {
    n[v]++
}
```

理由は `07` の合言葉そのもの: **`m[k]` は欠損キーでもゼロ値を黙って返す**。
`n` に `v` が無ければ `n[v]` は `0`、`n[v]++` で `1` になる。**"有ったら +1／無かったら 1" の分岐は、map の仕様が自動でやってくれる**。

> `07` では「`m[k]` が黙ってゼロ値を返す」ことが**罠**だった（欠損キーと "値が 0" が区別できない）。
> `09` では同じ性質が**武器**になる（カウンタの初期化を map に任せられる）。同じ仕様の、罠と武器の両面。

### しかも ―― `04` では既にこの綺麗な形を書けていた

```go
// 04_count_frequency.go:29-31（過去の自分）
for _, v := range input {
    m[v]++          // ← ここでは既に一撃で書けている
}
```

`04` で `m[v]++` を書けた人が、`09` で `if _, ok { n[v]++; continue } n[v] = 1` に戻っている。**これは新しい誤りではなく、覚えた道具の手放し**。

### なぜ手放したか ―― `_, ok` パターンの適用範囲を取り違えている

`_, ok := m[k]` パターン自体は、過去ドリルで**正しく**使われていた:

```go
if _, ok := m[e]; !ok { ... }   // 03_intersection.go / 06_dedupe_ordered.go：存在集合（set）
```

だがそれは**存在判定（在る/無い）が目的で、カウントしない**場面だった。
`09` は**カウンタ**。カウンタに `_, ok` は要らない（`m[k]++` が欠損を吸収する）。**存在集合のイディオムを、カウンタにそのまま持ち込んだ**のが後退の正体。

> 合言葉（新規）: **`_, ok := m[k]` は "在る/無い" を区別したい存在集合（set）の道具。単に数えるだけの*カウンタ*には要らない ―― `m[k]++` が欠損キーをゼロ値経由で吸収する。**

### さらに簡素化 ―― 中間 `map[string][]string`（第1パス）は要らない

現状は**二段パス**:

```go
m := make(map[string][]string, len(input)) // 第1パス：日付ごとにレベルを "スライスに溜める"（＝05 の group_by）
for _, s := range input {
    m[s.Date] = append(m[s.Date], s.Level)
}
out := make(map[string]map[string]int, len(input)) // 第2パス：溜めたスライスを数える（＝04 の count）
for key, vals := range m { ... }
```

設計コメント（`09_nested_count.go:8-11`）の「1. スライスに溜める → 2. 数える」は**頭の中の分解**としては正しい。
だがコードでは**この2段は融合できる**――中間スライス `[]string` を**materialize する必要が無い**。数えながら書けばよい:

```go
func aggregateDateStatus(input []Status) map[string]map[string]int {
    out := make(map[string]map[string]int, len(input))
    for _, s := range input {
        if out[s.Date] == nil {          // 内側 map は書き込む前に必ず初期化（下の注意）
            out[s.Date] = make(map[string]int)
        }
        out[s.Date][s.Level]++           // 欠損レベルはゼロ値 0 → ++ で 1
    }
    return out
}
```

- 中間 `map[string][]string` が消える → **O(N) の余分なメモリ（全レベル文字列を溜める）が不要**。
- ループが 1 本になる → 読み手が追う状態が減る（drill 02 の狙い「複数の集計を1パスにまとめる」と地続き）。
- **二段パスが間違いなわけではない**（正しいし読める）。だが単一パスは**同じ結果をより軽く・より素直に**出す。②nice の範囲。倒すなら単一パス推奨。

> **ネスト map の唯一の勘所（drill 09 の狙いそのもの）**: 内側 map は**書き込む前に `make` で初期化**しないと `nil` map への書き込みで**panic** する。
> 一方、**読み取り**は `nil` map でも安全（ゼロ値を返す）。だから `out[s.Date][s.Level]` を*書く*前に、`out[s.Date]` の初期化（lazy init）が要る。ここだけは単一パスでも省けない。

## 観点3【②道具・軽微】容量ヒントの粒度 ―― 内側 map の `len(input)` は過大

`04` のレビューでは「`make(map[..], len(input))` で先取り」を良しとした。`09` でも先取り自体は良い。ただし**粒度**が合っていない箇所がある。

```go
n := make(map[string]int, len(input)) // 09_nested_count.go:24
```

- **内側 map（`n`）の `len(input)` は明確に過大**。`n` が持つのは**1 日付ぶんの distinct なレベル**（INFO/ERROR/WARN… 数個）。それを毎回 `len(input)` で確保すると、日付が D 個あれば **D 個の map をそれぞれ N 件ぶん**に膨らませる。`make(map[string]int, len(vals))`（そのスライス長）か、単に `make(map[string]int)` で十分。
- **日付キーの map（`m`/`out`）の `len(input)`** は "安全な上限"（distinct 日付数 ≤ `len(input)`）で無害だが、通常はかなり緩い（日付は少ない）。`04` の `len(input)` は「要素キーが最大 N 個」で**タイト**だったのと対照的で、ここは**上限としては正しいが実測とは乖離**。害は無いので任意。

> 合言葉（`04` から継承）: **容量ヒントは "だいたいの上限" を渡す道具。だが "何個のキーが入る map か" を取り違えると、内側 map のように何倍も過剰確保する。**

## 観点4 軽微（命名・コメント・公開境界・テストの穴）

- **`Status` の命名 と コメント「ログ集計結果」（`09_nested_count.go:3`）**: この構造体は**入力の1レコード（ログ1件）**であって、集計*結果*ではない（結果は返り値の `map[string]map[string]int`）。コメントが実体と逆。`LogEntry`/`LogRecord` 等に寄せ、コメントも「入力: ログ1件」に。
- **`// nilは入らない`（`09_nested_count.go:4,5` と test:14）**: 不正確。`string` のゼロ値は `""` で、そもそも **`nil` は string に存在しない概念**。テストが実際に踏んでいる契約は「**空文字列 `""` は入りうる（しかもキーになりうる）**」――`MissingDate`/`MissingLevel` 群がまさにそれ。コメントも「ゼロ値は `""`。空文字列はキーとして入りうる」に直すと、テストの意図と一致する。
- **`aggregateDateStatus` の命名**: 実際は「日付 × レベルの**件数**」を作る。名前に level も count も出てこない。`countByDateLevel` 等のほうが返り値を語る。任意。
- **公開境界（`04` 観点3 の "逆"・ただし無害）**: `Status`（公開・フィールドも公開）× `aggregateDateStatus`（非公開）。`04` は「**公開関数 × 非公開フィールド**（結果が読めない）」という**害のある**ちぐはぐだった。`09` はその逆で、**公開型を非公開関数の入力に使っているだけ**。返り値は `map[string]map[string]int`（組み込み型）で**完全に読める**ので**害は無い**。整合を取るなら「`Status` を外部に使わせるなら関数も公開／内部専用なら `Status` を小文字に」。優先度は低い。
- **テストの穴（実は良い）**: カバレッジは十分。空文字列の Date/Level・全空まで 7 ケースで押さえている。
  - **litmus（`08` から継承）**: `normal` ケースは `06-01:{INFO:2, ERROR:1}` と `06-02:{INFO:1}` を持つ。もしカウントがバグる（常に 1 等）なら `INFO:2` で赤。もし内側 map が**日付をまたいで汚染**されるなら、両日に居る `INFO` の件数がずれて赤。**退行をちゃんと見張れている**。
  - `reflect.DeepEqual` でよい根拠 = **観点1**（出力が map で順序非依存）。`03` のような「ソートしてから比較」は不要。
  - 追加するなら「同じレベルが複数日付で**異なる件数**」を1ケース明示（`normal` が部分的に踏んでいるので必須ではない）。

## 光った点 ―― `07` の "罠" が `09` で "武器" に変わった

```go
out := make(map[string]map[string]int, len(input))
for _, s := range input {
    if out[s.date] == nil {          // ← ネスト map の唯一の勘所：書く前に必ず lazy init
        out[s.date] = make(map[string]int)
    }
    out[s.date][s.level]++           // ← 07 の「欠損キーはゼロ値」を、今度は "利用" している
}
return out
```

- `out[s.date][s.level]++` の一行が、`07` で赤を出した「`m[k]` は欠損キーでゼロ値を返す」性質を**そのまま利用**している。内側 map に `s.level` が無ければ `0` → `++` で `1`。初期化分岐が消えた。
- そして「内側 map は**書き込む前に** `make`」（`out[s.date] == nil` の lazy init）も正しく踏めている ―― これがネスト map の唯一の勘所（drill 09 の狙いそのもの）。
- `07` では罠、`09` では武器。**同じ仕様の両面を、両方とも自分の手で踏んだ**のが良い到達点。

## 残る軽微ポイント（任意・バグではない）

### 1【観点4 が半分だけ動いた】`LogEntry` は公開・フィールドは非公開 ―― また "公開境界のちぐはぐ"

```go
type LogEntry struct { // 公開（大文字 L）
    date  string // 非公開（小文字）
    level string // 非公開
}
func aggregateDateStatus(input []LogEntry) ... // 非公開
```

これは `REVIEW_04` 観点3 の **smell そのもの**（公開型 × 非公開フィールド）。今回フィールドを小文字化したことで、**公開の型名と非公開のフィールドがちぐはぐ**になった。
`aggregateDateStatus` が**非公開**（内部専用）である以上、いちばん素直なのは **型も小文字 `logEntry`** にして「この型はパッケージ内部の道具」と足並みを揃えること。

- **内部専用に倒す（推奨）** → `logEntry` / `date` / `level` / `aggregateDateStatus`。**全部小文字で一貫**。
- **将来 logstat 本体で外から使う型にする** → 逆に全部公開（`LogEntry` / `Date` / `Level` / `AggregateDateStatus`）。

> 合言葉（`04` から再掲）: **公開／非公開は "誰が使う型か" を決めてから、型・フィールド・関数で*足並みを揃える*。片方だけ大文字/小文字にすると、必ずちぐはぐが残る。**

### 2 コメントの取りこぼし（極軽微）

- `09_nested_count.go:3` `// ステータス1件` → 型名を `LogEntry` にしたので **「ログ1件」** に（まだ「ステータス」のまま）。
- `09_nested_count.go:10` `全て空スライスで返る` → 返るのは **map**。**「空の map で返る」** に（スライスではない）。
- `09_nested_count_test.go:14` コメントが旧フィールド名 `Date`/`Level` のまま → `date`/`level` に。「nilは入らない」も「空文字は入りうる」に揃えると本文と一致。

### 3 テストのケース名（任意）

`MissingAllevel` / `MissingAlldate` / `Missinglevel` は読みづらい（"All-evel" に見える）。挙動には無関係だが、標準的な PascalCase なら `MissingAllLevel` / `MissingAllDate` / `MissingLevel` が素直。
