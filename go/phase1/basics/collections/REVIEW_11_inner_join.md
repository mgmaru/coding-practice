# レビュー: `11_inner_join` —「索引化」は正しく再利用できた。主眼は "容量ヒントの取り違え（`07` の宿題再来）" と "なぜスライス出力なのに決定的か"

`11_inner_join`（Phase 1 ドリル・Tier 3「ネストと結合」の2発目）のレビュー。
お題は「`users` と `orders` を `userId` で内部結合し、`{name, item}` のリストを返す」＝**2つのスライスを結合（join）する**。`09_nested_count` がネスト map の "構築" だったのに対し、`11` は **`07_lookup` の索引化を "結合" に応用**した回。

結論から言うと **コードは正しく、緑も信用してよい**（バグ無し・`gofmt`/`vet` クリーン・`-count=5` で 10 サブテスト × 5 回連続 緑）。
今回の主題は2つ:
1. **観点1**: 出力は**スライス**（順序が結果に漏れる）なのに、なぜ `03` のようにフレーキーにならないのか ―― `09` とは*逆*の理由（`09` は出力が map で順序が消えた／`11` は出力がスライスだが**順序を map から取っていない**）。
2. **観点2（②道具の主眼）**: 出力スライスの容量ヒント `len(users)` が**取り違え**。`07_lookup` で一度踏んだ「cap は `len(users)` ではなく引く側の長さ」の宿題が、そっくり再来している。

> 大原則（review-rubric の ②道具の良し悪し）: イディオムか・計算量に無駄はないか・データ構造の選択は妥当か。
> 前提: `go test -run TestInnerJoinById -count=5` が **10 サブテスト × 5 回連続で緑**。`gofmt` 差分なし・`go vet` クリーン。

## 観点1【良い・最重要】出力は**スライス**なのに決定的 ―― map を "引く側"、スライスを "回す側" に使い分けている

`09` は「出力が map だから順序がそもそも存在しない → `DeepEqual` は順序を見ない」だった。
`11` は**逆**。出力は `[]UserOrderInfo`（スライス）なので、**順序は結果に漏れる**。`04` と同じ側 ―― なのに `sort` は無く、それで**正しい**。なぜか。

```go
func innerJoinById(users []UserInfo, orders []OrderInfo) []UserOrderInfo {
    userOrderInfo := make([]UserOrderInfo, 0, len(users))
    userIdItemList := make(map[int][]string, len(orders)) // ← map は「引く」ためだけに使う

    for _, order := range orders {                        // ① orders スライスを回して索引化
        userIdItemList[order.userId] = append(userIdItemList[order.userId], order.item)
    }
    for _, user := range users {                          // ② users スライスを回す（← 出力順の親）
        for _, item := range userIdItemList[user.id] {    //   map は user.id で「引く」だけ（回さない）
            userOrderInfo = append(userOrderInfo, UserOrderInfo{name: user.name, item: item})
        }
    }
    return userOrderInfo
}
```

**出力順を決めているのは、2本の `for` がどちらも "スライス" を回していること**:
- 外ループ `for _, user := range users` → 出力の**大枠の順序は `users` スライス順**。
- 内ループ `for _, item := range userIdItemList[user.id]` → **`[]string` の値スライスを回す**。この並びは索引化フェーズの `append` 順＝**`orders` スライス順**。

`map` は `userIdItemList[user.id]` の**単発の引き（lookup）**にしか使っていない。**`for k := range map` で map を "回して" いない**。だから map の走査順が結果に漏れる余地が無い ―― 順序は最初から最後まで**2つの入力スライス由来**で、実行ごとに一切バラけない。

> 合言葉（`03`→`07` から継承）: **`map` に順序を期待しない。**
> ―― `04` は「順序が要る側」で `sort` に握らせた。`09` は「順序が要らない側」で出力を map にして消した。
> ―― `11` は「順序が要る側」だが、**順序を最初から map に握らせず、入力スライスに握らせている**。だから `sort` も要らない。これが3つ目の倒し方。

### `07` との地続き ―― 「索引化して、もう片方のスライスを回す」

これは `07_lookup` でやったことそのもの。`07` は「引く表を map に索引化 → 引く側のキー列を回す」。
`11` は「`orders` を map に索引化 → `users` を回す」。**"回す側" が出力順の親になる**、という構造まで同じ。

> 設計の含意（重要）: **どちらのスライスを索引化し、どちらを回すかで、出力順が変わる。**
> もし逆に「`users` を `map[int]string`（id→name）に索引化して `orders` を回す」設計にすると、出力順は**`orders` 順**になり、`OneUserPlacesMultipleOrders`（期待は `A:x, A:i, B:y, C:z` の**ユーザーまとめ**）は**赤**になる。
> つまり今の「`orders` を索引化して `users` を回す」は、テストの契約（ユーザー単位でまとまる）に**合致した意図的な選択**。ここは良い。

### 自問（合言葉の確認）
- `map` 走査の並びに依存していないか？ → **していない**。map は「引く」だけで「回して」いない。順序は `users`／`orders` の2スライス由来。
- ではなぜ `04` は `sort` が要ったのに `11` は要らない？ → **順序の出どころが違う**。`04` は「値そのものを並べたい」（全順序が要る）。`11` は「入力スライスの並びをそのまま流す」（入力が既に順序）。

## 観点2【②道具・主眼】出力スライスの容量ヒント `len(users)` は**取り違え** ―― `07` の宿題の再来

ここが今回いちばん手を動かす価値のある指摘。**`07_lookup` で一度言語化した cap の教訓が、そのまま踏み直されている。**

```go
userOrderInfo := make([]UserOrderInfo, 0, len(users)) // 11_inner_join.go:20 ← cap が過小になりうる
```

出力の行数は「**マッチした order の数**」。1つの order は、対応する user が居れば**ちょうど1行**を生む（居なければ0行）。
したがって**出力の行数のタイトな上限は `len(orders)`**であって、`len(users)` **ではない**。

- **`len(users)` は過小になりうる**: 1人が複数 order を持つと（`OneUserPlacesMultipleOrders`: user 1 が `x` と `i` の2件）、出力は `len(users)` を超える → `append` が**途中で再確保**する。cap ヒントの意味が無い。
- **同時に過大にもなりうる**: order を持たない user が居ると、その分は0行 → `len(users)` は緩い上限にすらならない。
- つまり `len(users)` は**下限でも上限でもない**、ただの取り違え。正しくは:

```go
userOrderInfo := make([]UserOrderInfo, 0, len(orders)) // 出力は order 1件につき最大1行 → 上限は len(orders)
```

これは `07_lookup` で書いた教訓と**同一**:

> `07` の反省（notes.md より）: **「結果スライスの cap は `len(input)`。`len(users)` だと、引くキー列に重複があると足りない（例 `input=[2,1,1,2,3]`）」**

`11` の `orders` はまさにその「重複しうるキー列」。**`07` で `len(users)` を否定したのに、`11` で再び `len(users)` を渡している** ―― 新しい誤りではなく、**覚えた道具の踏み直し**。ここが観点2の芯。

> 合言葉（`07` から継承・再掲）: **cap ヒントは "生む要素は最大何個か" で決める。"元テーブル（users）が何行か" ではなく "回す/生む側（orders）が何行か"。結合では出力＝マッチ order 数 ≦ `len(orders)`。**

### 逆に ―― 中間 map の `len(orders)` は正しい

```go
userIdItemList := make(map[int][]string, len(orders)) // 11_inner_join.go:21
```

こちらの `len(orders)` は**妥当**。この map のキーは distinct な `userId` で、その数は `len(orders)` を超えない（＝安全な上限）。`09` の「内側 map に `len(input)` は過大」とは違い、ここはキー数の上限として素直。**map 側は正しく、スライス側だけ取り違えている**のが今回の構図。

## 観点3【良い】学んだ道具が正しく再利用できている ―― `09` からの前進

`09` は「覚えた道具を手放した（`m[k]++` を `if _, ok` に後退させた）」回だった。`11` は**その逆で、道具がちゃんと定着している**:

- **`_, ok` の冗長分岐が無い**: 索引化ループ `userIdItemList[order.userId] = append(userIdItemList[order.userId], order.item)` は、キーの有無を**判定せず一撃**。`09` レビューで指摘した「存在判定はカウンタ/蓄積に要らない」を**今回は最初から踏めている**。
  - 理由は `05`／`07` の合言葉: **nil スライスへの `append` は安全**（`map[k]` が欠損なら値は `nil` スライス、それに `append` すると新スライスが生えて代入される）。`05_group_by` の "キーごとにスライスに溜める" と同型。
- **ネスト値（`map[int][]string`）の書き込みが正しい**: `09` の勘所「内側 map は書く前に `make`」に相当する罠が、ここでは**そもそも起きない**（値が map ではなく**スライス**なので、nil への `append` が安全に効く）。データ構造の違いを踏まえて正しく書けている。
- **nil/空の扱いが `01` の教訓通り**: `make([]UserOrderInfo, 0, ...)` は常に**非 nil の空スライス**を返す。テストの `want: []UserOrderInfo{}` と一致し、`NilUser`／`EmptyOrder` 等が全て緑。`01` の「`var s []T`（nil）ではなく `[]T{}`（空）で返す」を踏めている。
- **内側ループのコメントが正しい観察**: `11_inner_join.go:29` の「usersはスライスなので並びも保証」は、**観点1の核心を自分の言葉で書けている**。良い。

> `09` は「道具の再装着」が課題だった。`11` は**再装着済み**で臨めている ―― Tier 3 の狙い「既に持っている道具の合成」が効いた回。

## 観点4 軽微（命名・コメント・テストの穴）

- **`userIdItemList` の命名が実体と食い違い（`11_inner_join.go:21`）**: 型は `map[int][]string`（map）なのに、名前は **`...List`**。読み手は「スライス」を期待する。中身は「userId ごとに item を束ねた map」なので、`itemsByUserID` / `ordersByUserID` のほうが型と役割を正しく語る。
- **コメント `// 一次マップ`（`11_inner_join.go:21`）**: おそらく **`一時マップ`（temporary）** の誤変換（`一次`＝first-order/primary）。意図は「索引用の一時的な map」なので `一時マップ` が正。極軽微。
- **`UserInfo.name` が公開フィールド × `innerJoinById` が非公開**: `09` 再々レビューで詰めた「公開境界の足並み」の観点。`UserInfo`/`OrderInfo`/`UserOrderInfo` は全フィールド公開だが、関数は非公開・返り値も組み込み型で**完全に読める**ので**害は無い**（`09` と同じく "公開型を非公開関数の入力に使うだけ"）。内部専用に寄せるなら型・フィールドも小文字に揃える手はある。優先度は低い。
- **テストの穴（実は良い）**: カバレッジは厚い。全マッチ／user に order 無し／**order に user 無し（＝マッチしない order は落ちる）**／空・nil の全組合せ／1人が複数 order、まで 10 ケースで押さえている。
  - **litmus**: `SomeItemsOrderNotIncludedUser` は `orders` に `userId:4`（`users` に居ない）を混ぜ、`want` から除外している。**「マッチしない order を黙って落とす」内部結合の契約**を正しく赤で見張れる。
  - **litmus**: `OneUserPlacesMultipleOrders` は、出力が**ユーザー単位でまとまる**こと（`A:x, A:i` が連続し、`orders` 順の `A:x,...,A:i` にならない）を固定 ―― 観点1「回す側が `users`」の退行を検出できる。
  - `reflect.DeepEqual` でよい根拠 = **観点1**（順序は入力スライス由来で決定的だから、順序込みの `DeepEqual` が正しい）。
  - 追加するなら「**同一 order 内で同じ item が重複**」や「**同じ userId が users に2回**」は未カバー（挙動仕様が曖昧になりやすい所）。必須ではない。
