# レビュー: `12_invert` —「出力は map なのに、なぜ `09` と違って `sort` が要るのか」が主眼。手を動かすのは "命名(`invert_map`→camelCase)" と "`SliceStable`→`slices.Sort`"

`12_invert`（Phase 1 ドリル・Tier 3「ネストと結合」の3発目）のレビュー。
お題は「`map[string]int` のキーと値を入れ替えて `map[int][]string` を返す」＝**多対一を一対多へ組み替える**。値が重複するのでキーごとにスライスへ束ねる。

結論から言うと **コードは正しく、緑も信用してよい**（バグ無し・`gofmt`/`vet` クリーン・`-count=5` で 6 サブテスト × 5 回連続 緑）。
今回の主題は3つ:
1. **観点1（最重要・理解）**: 出力は **map**（`09` と同じ「順序が消える側」）なのに **`sort` が要る**。なぜか ―― `11` の*逆*。`09` は出力 map で順序が丸ごと消えた／`12` は出力 map でも**値スライスが "map を回して" 詰められる**ので、その並びだけは `03`/`04` のフレーキー地帯に残る。だから `sort` で決定性を取り戻す。**「`map` に順序を期待しない」の4つ目の現れ方**。
2. **観点2（②道具・手を動かす芯）**: `sort.SliceStable` は**この場面では過剰**。並べる要素（元 map のキー）は**必ず distinct** なので "同値タイ" が起きず、安定性が無意味。`sort.Slice`、より良くは **`slices.Sort(value)`**（Go 1.21+／このリポジトリは 1.26）で `[]string` を直接ソートするのがイディオム。
3. **観点2（②道具・字面）**: 変数 `invert_map` は **snake_case**。Go は mixedCaps（`inverted` / `invertedMap`）。`gofmt`/`vet` は見逃す（`revive` 領域）。

> 大原則（review-rubric の ②道具の良し悪し）: イディオムか・計算量に無駄はないか・データ構造の選択は妥当か。
> 前提: `go test -run TestInvertKeyValue -count=5 ./phase1/basics/collections` が **6 サブテスト × 5 回連続で緑**。`gofmt` 差分なし・`go vet` クリーン。

## 観点1【良い・最重要】出力は **map** なのに `sort` が要る ―― `09` とも `11` とも違う "3つ目/4つ目" の倒し方

過去3ドリルで「順序」を3通りに倒してきた。`12` は**4つ目**。まず整理する。

| ドリル | 出力の型 | 順序は結果に漏れるか | 順序の出どころ | `sort` |
|---|---|---|---|---|
| `04` count_frequency | **スライス** | 漏れる | 値そのものを全順序で並べたい | **要る** |
| `09` nested_count | **map** | 漏れない（map に順序なし） | ―― | 不要 |
| `11` inner_join | **スライス** | 漏れる | **入力スライス**由来（決定的） | 不要 |
| **`12` invert** | **map** | **値スライスだけ漏れる** | **入力 map を回して詰める**（＝ランダム） | **要る** |

`12` の肝は「出力が map だから安心」ではないところ。

```go
func invertKeyValue(input map[string]int) map[int][]string {
    invert_map := make(map[int][]string, len(input))
    for key, val := range input {                 // ← input(map) を回している = 走査順ランダム
        invert_map[val] = append(invert_map[val], key) // ← その順で値スライスに key が積まれる
    }
    for _, value := range invert_map {
        sort.SliceStable(value, func(i, j int) bool {  // ← だから並べ直して決定性を回収
            return value[i] < value[j]
        })
    }
    return invert_map
}
```

- 出力 `map[int][]string` の **キー(`int`)の並び**は `DeepEqual` が見ない ―― ここは `09` と同じ、安心してよい。
- だが **値の `[]string` の並びは `DeepEqual` が見る** ―― ここは `04`/`03` と同じ、順序が結果に漏れる。
- その値スライスは **`for key, val := range input`（＝ map を回す）**の中で `append` されるので、**積まれる順序は input の map 走査順＝実行ごとにランダム**。
- 例 `DuplicatedValue`（`{"a":1,"b":2,"c":1}`）: `sort` が無ければ `1: {"a","c"}` になる回と `1: {"c","a"}` になる回が混じる ―― **`03`/`04` で踏んだフレーキーそのもの**。`sort` はこの非決定性を潰す**必須の一手**であって、飾りではない。

> 合言葉（`03`→`07` から継承・4回目）: **`map` に順序を期待しない。**
> ―― `04` は「値を並べたい」ので `sort` に握らせた。`09` は「順序が要らない側」で出力 map にして消した。`11` は「順序が要る側だが入力スライスに握らせた」ので `sort` 不要。
> ―― `12` は「出力は map で**キー順は消える**が、**値スライスは map を回して詰める**」。だから**値スライスにだけ** `03`/`04` の病が残り、`sort` で決定性を回収する。これが4つ目の型。

### 自問（合言葉の確認）
- 「出力が map だから順序は気にしなくていい」で止まっていないか？ → **止まってはいけない**。map の**値がスライス**なら、その中身の並びは結果に漏れる。しかも今回はその並びを**map 走査から得ている**ので、`sort` 無しでは非決定。
- `11` はなぜ `sort` 不要で `12` は必要？ → **値スライスの詰め元が違う**。`11` は "入力スライスを回して" 詰めた（並びが既に決定的）。`12` は "入力 map を回して" 詰める（並びがランダム）。**詰め元がスライスか map か**が分水嶺。

### ⚠ テストは "`sort` の抜け" を確実には守れない（`03`/`04` と同じ限界）
今 `sort` があるので緑は安定している。だが**もし将来 `sort` を消したら、このテストは "たまに赤" になるだけ**。`DuplicatedValue` の衝突キーは2個（`a`,`c`）なので、1回の実行で並びが入れ替わる確率はおよそ 1/2。`-count=5` でも取りこぼしうる。
→ **`map` 由来の順序の正しさは "テストで証明" できない。"推論" で担保する**（＝観点1を自分の言葉で言えること）。`03` の反省「`map` に順序を期待しない」が、テストの守備範囲の外側にあることの再確認。

## 観点2【②道具・主眼の手を動かす】`sort.SliceStable` は過剰 ―― キーは distinct なので安定性が無意味。`slices.Sort` が正解

`08_sort_multikey`（notes 6/30）で `sort.Slice` と `sort.SliceStable` の違いを学んだ。**`SliceStable` は "`less` が等しい要素同士の元順序を保つ"** のが値打ち。では今回、**"等しい要素" は起きるか？**

```go
sort.SliceStable(value, func(i, j int) bool { return value[i] < value[j] })
```

- `value` に入るのは **元 map `input` のキー**。map のキーは**重複しない**。ゆえに、ある値スライスの中の文字列は**すべて distinct**（同じ key が2つの値を持つことは map ではありえない）。
- distinct ⇒ **`value[i] == value[j]` となるタイが1つも存在しない** ⇒ **安定・不安定で結果が1ビットも変わらない**。
- つまり `SliceStable` の保証は**丸ごと空振り**。害はないが、"安定性が要る場面だと誤解している" サインになりうる。

**直し方(推奨)**: `[]string` を直接ソートする標準関数を使う。このリポジトリは **Go 1.26**（`go.mod`）なので `slices`（1.21+）が使える。

```go
import "slices"
// ...
for _, value := range invert_map {
    slices.Sort(value) // []string を昇順に。クロージャ不要・文字列の < 比較と同義
}
```

- `slices.Sort` は**クロージャを書かなくてよい**分、読み手のノイズが減る。比較は `<`（＝現状のコメント「大文字先・小文字後・空文字最小」）と**完全に同じ**。
- どうしても `sort` パッケージで通すなら、少なくとも **`sort.Strings(value)`**（`[]string` 専用）にすれば同じくクロージャが消える。`SliceStable`+クロージャは今回いちばん遠回り。
- 教訓の地続き: `08` で **"`SliceStable` は安定性が要るときに選ぶ"** と学んだ。`12` はその裏返し ―― **"タイが起きない（distinct）と分かっているなら安定版を選ぶ理由はない"**。道具の**適用条件**まで込みで覚える回。

### 変数名 `invert_map` は snake_case ―― Go は mixedCaps
```go
invert_map := make(map[int][]string, len(input)) // 12_invert.go:7
```
- Go の命名規約は **mixedCaps（camelCase）**。`invert_map` は Python/Ruby 風の snake_case で浮く。`gofmt`・`go vet` は**通してしまう**（整形と正当性しか見ない）が、`revive`/`golint` は指摘する領域。
- さらに `invert`（反転する＝動詞）より、**結果を持つ変数**なので `inverted` / `invertedMap` / `result` のほうが「これは反転済みの結果だ」と読める。`11` の `itemsByUserId` で「型と役割を名前で語る」を踏んだのと同じ観点。

### 逆に ―― map の容量ヒント `len(input)` は**正しい**（`11` の宿題を今回は踏み直していない）
```go
invert_map := make(map[int][]string, len(input)) // ← このヒントは妥当
```
- この map のキーは distinct な `int` 値で、その数は **`len(input)` を超えない**（各 input エントリはたかだか1つの新キーを生む）。ゆえに `len(input)` は**安全な上限**。値が衝突すれば過大側に振れるが、map の `sizeHint` は**過大なら無害**（ただのヒント）。
- **`11` では出力スライスの cap を `len(users)` に取り違えた**が、`12` は容量指定が **map の sizeHint だけ**で、そこは正しく `len(input)`。`07`/`11` で言語化した cap の教訓を、今回は**踏み外していない**。良い前進。
- なお値スライス（`invert_map[val]`）には cap ヒントが無いが、**各値が何個のキーを集めるかは事前に読めない**ので、ここは指定しないのが素直。`10_flatten` のように「事前に総量を数える」パスを1本足せば理論上は right-size できるが、**費用対効果が薄く任意**。

## 観点3【良い】学んだ道具が正しく効いている ―― `05`/`01`/`04` の再利用と、スライス意味論の勘所

- **索引化ループが `_, ok` の冗長分岐なしで一撃（`12_invert.go:9`）**: `invert_map[val] = append(invert_map[val], key)` は、キーの有無を**判定せず**書けている。`09` レビューで手放しかけた「蓄積に存在判定は要らない／nil スライスへの `append` は安全」を**今回は最初から**踏めている。`05_group_by`・`11_inner_join` と同型。
- **`range` で受けた `value`（スライスヘッダのコピー）を `sort` すると、map の中身が本当に並ぶ**（`12_invert.go:13`）: これは**地味だが重要なスライス意味論**。`for _, value := range invert_map` の `value` は**ヘッダ（ptr,len,cap）のコピー**だが、**指す先の backing array は map が持つ実体と同じ**。`sort` は backing array を **in-place** に並べ替えるので、**map 越しにも並びが反映される**。もし `value = ...` と**再代入**したら map には書き戻らないが、`sort` は "書き戻し" ではなく "同じ配列の並べ替え" なので効く。**なぜ動くかを説明できると強い**。
- **常に非 nil の空 map を返す（`01` の教訓）**: `make(map[int][]string, ...)` は `input` が空でも**非 nil の空 map** を返す。`01` の「`var`(nil) ではなく make/リテラル(空) で返す」を踏めている（ただしテストで固定できていない ―― 観点4）。
- **ASCII 順のコメントが正確（`04` の教訓）**: `12_invert.go:15` の「大文字先・小文字後（大文字の方が ASCII 小）／空文字は最小」は、`04_count_frequency`（notes 6/17）の ASCII 大小と一致。`IncludedUpperCaseKey`（`{1:{"A","a"}}` ＝ 65<97）・`...AndEmptyKey`（`{1:{"","A","a"}}` ＝ 空文字最小）で**実際に固定できている**。コメントが「コードが実際にやること」を正しく述べている（`08` の合言葉）。

## 観点4【軽微】テストの穴（nil/空）と字面

- **テストの穴：`nil` 入力・空 map 入力が未カバー（`01` の教訓の固定漏れ）**: `notes.md` 01 で「**`input` には `nil` が入ってくるのでガードを設ける**」と決めたが、`invertKeyValue(nil)` / `invertKeyValue(map[string]int{})` のケースが無い。
  - 実挙動は**正しい**（nil map の `range` は 0 回・`make` が非 nil 空 map を返す → `want: map[int][]string{}` と `DeepEqual` 一致）。**ガード分岐も不要**（`02`/`04` の「無くても同じ結果の分岐は消す」に沿って、書かないのが正しい）。
  - ただし**契約がテストで固定されていない**。下2ケースを足すと「空入力→非 nil 空 map」を退行から守れる:
    ```go
    {name: "NilInput",   input: nil,                 want: map[int][]string{}},
    {name: "EmptyInput", input: map[string]int{},    want: map[int][]string{}},
    ```
- **litmus は効いている（実は良い）**: `DuplicatedValue`（多対一の束ね）・`AllDuplicatedValues`（全部同値→1キーに集約）・`IncludedUpperCaseKey`/`...AndEmptyKey`（**`sort` の昇順契約＝観点1の退行検出**）まで押さえている。とくに大文字・空文字ケースは「`sort` が消えた／比較を誤った」を赤で見張れる良い番人。
- **テスト名の typo（極軽微）**: `IncludedEnptykey`（`Enpty`→`Empty`）、`IncluededUpperCaseKeyAndEmptyKey`（`Inclueded`→`Included`）。挙動には無関係だが、`-run` で名指しするとき混乱するので直すと良い。
- **`func` 直後の空行（`12_invert.go:6`）**: `gofmt` は許すが、この関数だけ本体頭に空行があり他ドリルと不揃い。詰めると読みやすい。極軽微。
