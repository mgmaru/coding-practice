# レビュー: `13_cumulative_sum` —「バグは無い」。主眼は "狙いの『状態を持ち越す』を **変数で持っていない**（`output[i-1]` で読み返している）" と "`02` の『余計な分岐』宿題の再来"

`13_cumulative_sum`（Phase 1 ドリル・**Tier 4「順序・ウィンドウ」の1発目**）のレビュー。
お題は「先頭からの累積和を返す」＝`[1,2,3,4] → [1,3,6,10]`。狙いは **「前の状態を持ち越しながら走査する」**。`11`/`12` までの「集約・索引・結合（＝ある時点のデータをまとめる）」から、**Tier 4 は「1つ前の状態を運ぶ」＝走査に *時間軸/順序* が入る**回に移った。

結論から言うと **コードは正しく、緑も信用してよい**（バグ無し・`gofmt`/`vet` クリーン・`-count=5` で 5 サブテスト × 5 回連続 緑）。
だが今回は「正しいのに、狙いを外している」回。主題は2つ:

1. **観点1（②道具・主眼）**: このドリルの狙いは **「状態を持ち越す」**。ところが実装は状態を **変数で運んでいない** ―― 毎回 `output[i-1]`（出力スライス）を **読み返して** 前の累積を得ている。狙いを一番素直に表すのは **走る合計（running sum）を1変数で運ぶ** 形。ここが今回いちばん手を動かす価値のある指摘。
2. **観点2（②道具・`02` の宿題）**: `len(output) == 0` の **特殊分岐**（先頭要素だけ別扱い）は要らない。これは `02_fold_stats` で一度言語化した **「先頭要素の `if i == 0` は余計な分岐」** の踏み直し。コード中の `// i == 0でも良い？` という自問は、その匂いを自分で嗅ぎ当てている ―― 答えは **「どちらでも良いが、そもそも要らない」**。

> 大原則（review-rubric の ②道具の良し悪し）: イディオムか・計算量に無駄はないか・データ構造の選択は妥当か。
> 前提: `go test -run TestCalcCumulativeSum -count=5` が **5 サブテスト × 5 回連続で緑**。`gofmt` 差分なし・`go vet` クリーン。

## 観点1【②道具・主眼】狙いは「状態を持ち越す」―― なのに状態を **変数で運んでいない**（`output[i-1]` で読み返している）

現状の実装:

```go
func calcCumulativeSum(input []int) []int {
    output := make([]int, 0, len(input))
    for i, num := range input {
        if len(output) == 0 { // i == 0でも良い？        ← 13_cumulative_sum.go:10（観点2）
            output = append(output, num)
            continue
        }
        output = append(output, output[i-1]+num)         // ← 13_cumulative_sum.go:14
    }
    return output
}
```

**なぜ正しいか（先に確定させる）**: ループが index `i` を処理する時点で `output` は **ちょうど `i` 要素** 入っている（毎周 append 1回・skip 無し）。よって `output[i-1]` は **直前に積んだ最後の要素＝ index `i-1` までの累積**。これに `num` を足すのは定義通り。**帰納法で正しく、緑は信用してよい**。

だが狙いは **「前の状態を持ち越しながら走査する」**。持ち越すべき状態＝「ここまでの合計」は、本来 **1つのスカラ変数** に載せて運ぶのが素直。現状はその状態を **どこにも持たず**、必要になるたびに **出力スライスを `output[i-1]` で読み返して** 再取得している。「持ち越す」ではなく「毎回取りに行く」になっている ―― **狙いの核心を、動く別の方法で迂回している**。

素直な形（狙いをそのまま表す）:

```go
func calcCumulativeSum(input []int) []int {
    output := make([]int, 0, len(input))
    sum := 0                          // ← これが「持ち越す状態」
    for _, num := range input {
        sum += num                    // 前の状態に今の値を足して
        output = append(output, sum)  // 積む
    }
    return output
}
```

この形の効きどころ:
- **狙いに直撃**: `sum` が「前の状態」そのもの。`sum += num` が「持ち越しながら走査」を一行で語る。ドリルが鍛えたい反射はこれ。
- **`i` も `len(output)` も要らなくなる**: `range` を `for _, num` に落とせる（index 不要）。**観点2 の特殊分岐も同時に消える**（後述。`sum` は 0 始まりなので先頭も自然に処理される）。
- **出力スライスへの後方参照が消える**: `output[i-1]` という **読み書きの往復** が無くなる。

### なぜ `output[i-1]` は "匂う" のか ―― 2つの独立した添字を癒着させている

`output[i-1]` は、**入力側の添字 `i`** で **出力側の位置** を引いている。今は両者が **ロックステップ（1:1・skip 無し）** だからたまたま一致するが、本質的に別物:

- 欲しい値は「**直前の累積**」＝ `output[len(output)-1]`（出力の最後）。
- 書いてある値は `output[i-1]`（**入力の添字**から引いた出力位置）。

もしこの先「偶数だけ累積する」等の **filter/skip が1つでも入る** と、`i` と `len(output)` はズレて **即バグる**。`01`（filter＝skip する走査）と地続きの罠。**走る合計 `sum` を変数で運べば、そもそも出力位置を計算する必要が消える**ので、この癒着は起こりようがない。

> 合言葉（この回で刻む）: **「持ち越す状態」は変数に載せて運ぶ。出力スライスを後ろから読み返して状態を"再取得"しない。** ―― `04`/`09` が「map をカウンタとして運ぶ」だったのと同型で、Tier 4 は「スカラを状態として運ぶ」。

## 観点2【②道具・`02` の宿題】`len(output) == 0` の特殊分岐は要らない ―― `02_fold_stats`「先頭要素の別扱い」の踏み直し

```go
if len(output) == 0 { // i == 0でも良い？   ← 13_cumulative_sum.go:10
    output = append(output, num)
    continue
}
output = append(output, output[i-1]+num)
```

先頭要素だけ「前の累積が無い」から別扱い ―― という分岐。これは **`02_fold_stats` で一度潰した宿題そのもの**:

> `02` の反省（notes.md 2026/6/15 より）: **「入力スライスの最初の要素について `if i == 0 { sum=num; max=num; min=num }` としていたが、余計な分岐でよくない。初期値を代入してあげる（`sum=input[0]` …）。余計な分岐をすると、テストの対象になりうるので注意。」**

`13` も構図は同じ「**先頭要素の特殊扱い**」。潰し方も同型 ―― **状態の初期値を先に置く**。`02` は `input[0]` を初期値にしたが、`13` は **`sum := 0`（累積の単位元）を初期値** に置けばよい。0 に先頭 `num` を足せば先頭要素は自然に正しく出る。**分岐も `continue` も消える**（観点1の `sum` 版がそのまま答え）。

### `// i == 0でも良い？` への回答

この自問（`13_cumulative_sum.go:10`）は良い嗅覚。答えを分解すると:

- **`len(output) == 0` と `i == 0` は等価か？** → **等価**。skip が無く append が毎周1回なので、「output が空」⇔「i が 0」。どちらで書いても今は同じ。
- **ではどちらが良いか？** → **どちらも要らない**、が正解。`i == 0` は「入力の添字」に、`len(output)==0` は「出力の状態」に依存する ―― どちらも "先頭だけ別扱い" という **余計な分岐** を temporarily 正当化しているだけ。`sum := 0` の初期化に寄せれば、判定する対象が消える。
- **強いて優劣を言うなら**: `len(output)==0` の方がまだ「出力の状態を見ている」ぶん観点1の思想に近い。が、`02` の教訓は **「等価な分岐で悩む前に、分岐を消せないか」** を問うこと。

> 合言葉（`02` から継承・再掲）: **先頭要素の別扱いは "初期値を先に置く" で消える。等価な条件式のどちらが良いかを悩む前に、その分岐が要るかを疑う。**

## 観点3【良い】今回 cap は **正しい** ―― `07`/`11` の cap 取り違え宿題との対比

```go
output := make([]int, 0, len(input)) // ← 13_cumulative_sum.go:8
```

`07_lookup`・`11_inner_join` では出力 cap を **取り違えて**いた（`len(users)` にしていた）。**今回の `len(input)` は正しい。** 累積和は **入力1要素につき出力ちょうど1要素**（filter も展開も無い、完全な 1:1）なので、出力長は **常に `len(input)` に一致**。過小でも過大でもない、**タイトな右サイズ**。

- `10_flatten` は「入力より増える（各内側リストの総和）」ので cap は総和計算が要った。
- `07`/`11` は「入力より増減しうる（重複キー/欠損）」ので `len(input)` 側を取り違えた。
- **`13` は 1:1 なので `len(input)` が過不足なく正しい** ―― データ構造の写り方（入力→出力の要素数関係）を正しく読めている。**ここは良い。**

> 対比の効用: 「cap は "生む側が最大何個生むか" で決める」の当てはめ方が、お題ごとに違う（`10`＝総和／`11`＝マッチ数／`13`＝1:1）。`13` で **1:1 なら `len(input)`** を素直に置けたのは、`07`→`11` の宿題が効いている証拠。

## 観点3b【良い】nil/空の扱いが `01` の教訓通り

- `make([]int, 0, len(input))` は入力が `nil`/空でも **常に非 nil の空スライス** を返す（`len(nil)==0` なので cap 0 の空スライス）。ループは0回、`output` は `[]int{}` のまま返る。
- テストの `EmptyInput`/`NilInput` はどちらも `want: []int{}`。**`[]int(nil)` と `[]int{}` は `DeepEqual` で `false`**（notes.md 2026/6/14）という `01` の罠を、`make(...,0,...)` の一手で回避できている。**良い。**

## 観点3c【良い・この回は論点が消える】決定性 ―― map が無く「順序」論点は主眼から外れる

`03`→`12` を貫いた合言葉「**`map` に順序を期待しない**」は、`13` では **出番が無い**。入力も出力も **スライスのみ**、map を一切使わないので、走査順＝入力順で **完全に決定的**。`reflect.DeepEqual`（順序込み比較）が正しいのも自明。

> 位置づけ: Tier 1〜3 の主眼は繰り返し「順序（map の非決定 vs スライスの決定）」だった。`13` からの Tier 4 は **主眼が「順序の"出どころ"」から「状態の"持ち越し方"」へ移る**。同じ「順序」でも、`13` は "入力順をそのまま累積に流す" だけなので論点にならない ―― 主戦場は観点1（状態の運び方）。

## 観点4【軽微】テストの穴 ―― 「本当に *合計* か」を締めるケースが薄い

現状 5 ケース（`Normal`/`Normal2`/`SingleInput`/`EmptyInput`/`NilInput`）。**境界（単一・空・nil）は押さえていて良い**。ただし値のバリエーションが「正の増加列」だけで、以下が未カバー:

- **負数・混在（litmus）**: `[3, -1, -1] → [3, 2, 1]` や `[-1, -2, -3] → [-1, -3, -6]`。
  - これは **「本当に *累積和* か」を締める** 一手。今の正例（単調増加）だけだと、たとえば「累積 *最大値*」のような別実装でも一部たまたま通りうる。負数を混ぜると **加算でしか通らない** ので、契約が締まる。
- **0 を含む先頭**: `[0, 1, 2] → [0, 1, 3]`。先頭 `num` が 0 でも `len(output)==0` 分岐（および `sum:=0` 版）が正しく初項 0 を積むか、を明示できる。
- **オーバーフロー（任意・スコープ外）**: 累積和は大きな入力で `int` を溢れうる。ドリルの範囲外だが、「累積系は溢れる」ことは notes に1行残す価値がある（`14` 移動平均・`15` Top-N でも効く）。

> 補足: 現状テストが全て「単調増加の正例」なので、**観点1の `output[i-1]` 癒着（filter が入ると壊れる）は、どのテストでも露見しない**。これはお題に filter が無い以上テストの責任ではないが、「負数を1本入れておく」だけで *累積＝加算* の契約が明示され、将来のリファクタ（`sum` 版への置換）の退行検出にもなる。

func calcCumulativeSum(input []int) []int {
    output := make([]int, 0, len(input))
    sum := 0 // 修正：一時変数をおいて、デバッグ容易性を向上

        output = append(output, sum)

## 補足 ―― `sum` の効き目は「デバッグ容易性」より上流にある（notes.md への注記）
