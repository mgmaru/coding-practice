# レビュー: `14_moving_average` —「バグは無い」。主眼は "狙いの『窓を **滑らせる**』を、窓和を持ち越さず毎回組み直している（`13` で刻んだ『状態は変数で運ぶ』の踏み直し・O(n·w)→O(n)）" と "出力を `int` にした契約が **spec（`2.0, 3.0, 4.0`）と食い違い・truncation を pin するテストが無い**"

`14_moving_average`（Phase 1 ドリル・**Tier 4「順序・ウィンドウ」の2発目**）のレビュー。
お題は「直近 N 件の移動平均を返す」＝`[1,2,3,4,5], N=3 → [2,3,4]`。狙いは **「固定幅の窓を滑らせる。境界（窓が満たない先頭）の扱い」**。`13_cumulative_sum` が「1つ前の状態を運ぶ（累積）」だったのに対し、`14` は **「幅 N の窓を1つずつ右へ滑らせる」** ―― Tier 4 の「状態を持ち越す」が *窓* に進化した回。

結論から言うと **コードは正しく、緑も信用してよい**（バグ無し・`go vet` クリーン・`-count=5` で **10 サブテスト × 5 回連続 緑**）。
だが `13` と同じく「**正しいのに、狙いを最短で表していない**」回。主題は2つ:

1. **観点1（②道具・主眼）**: 狙いは「窓を **滑らせる**」。ところが実装は窓を *滑らせて* おらず、位置ごとに **内側ループで窓和を毎回ゼロから組み直している**（`for j := range number` で N 個を再合計）。計算量は **O(n·N)**。窓を滑らせる本来の形は **窓和を1変数で持ち越し、右へ動くたび「出る要素を引き・入る要素を足す」**（O(n)）。これは `13` で刻んだ合言葉 **「持ち越す状態は変数に載せて運ぶ」** の、次のお題での踏み直し。しかも `13` の *累積和* を再利用すれば（prefix sum）、もう一つの O(n) 解にもなる。
2. **観点2（③仕様・契約）**: 出力を `[]int` にし、`targetNumsSum / number` で **整数除算（truncation）** している。だが (a) DRILLS の出力例は **`[2.0, 3.0, 4.0]`（float）**、(b) そもそも「平均」は非整数になりうる、(c) **割り切れない/負のケースのテストが1本も無い** ので truncation の挙動が **どこにも pin されていない**。`07` の合言葉「**契約を先に決めて、実装・テスト・コメントを揃える**」の踏み直し。

> 大原則（review-rubric）: ②道具（イディオム・計算量・データ構造）／③仕様（契約を決めて実装・テスト・コメントで揃える）。
> 前提: `go test -run TestCalcMovingAverage -count=5` が **10 サブテスト × 5 回連続で緑**。`go vet` クリーン。`gofmt`（無印）差分なし ―― ただし **`gofmt -s` は差分あり**（観点4）。

## 観点1【②道具・主眼】狙いは「窓を **滑らせる**」―― なのに窓和を持ち越さず、毎回ゼロから組み直している（O(n·N)）

現状の実装:

```go
for i := range input {                       // 14_moving_average.go:13  窓の左端を1つずつずらす
    if i+number > len(input) {               // 14_moving_average.go:14  窓が右端を超えたら終わり
        return movingAverageResult
    }
    targetNumsSum := 0                        // 14_moving_average.go:18  ← 毎周ゼロから作り直し
    for j := range number {                  // 14_moving_average.go:19  ← N 個を毎回 再合計（O(N)）
        targetNumsSum += input[i+j]
    }
    movingAverage := targetNumsSum / number  // 14_moving_average.go:22
    movingAverageResult = append(movingAverageResult, movingAverage)
}
```

**なぜ正しいか（先に確定）**: 外ループの各 `i` で、内ループが `input[i..i+N-1]` を **その場で全部足して** 平均を出す。窓の位置・要素数とも定義通りで、**バグは無い・緑は信用してよい**。

だが狙いは **「窓を *滑らせる*」**。「滑らせる」の核心は ―― **隣り合う窓は N-1 個を共有している**、という事実にある。窓が1つ右へ動くと、変わるのは **端の2要素だけ**（左から1個 *出て*、右から1個 *入る*）。真ん中の N-2 個は前の窓と同じ。だから本来は:

```go
func calcMovingAverage(input []int, number int) []int {
    if number <= 0 || number > len(input) {
        return []int{}
    }
    result := make([]int, 0, len(input)-number+1)

    windowSum := 0                         // ← これが「持ち越す窓の状態」
    for j := 0; j < number; j++ {          // 最初の窓だけ素直に合計（1回きり）
        windowSum += input[j]
    }
    result = append(result, windowSum/number)

    for i := number; i < len(input); i++ { // 窓を1つずつ滑らせる
        windowSum += input[i] - input[i-number] // 入る要素を足し・出る要素を引く（O(1)）
        result = append(result, windowSum/number)
    }
    return result
}
```

この形の効きどころ:

- **狙いに直撃**: `windowSum += input[i] - input[i-number]` の一行が「**窓を滑らせる**」をそのまま語る。ドリルが鍛えたい反射はこれ。内側ループが消え、各位置 **O(1)** ＝全体 **O(n)**。現状の **O(n·N)** から窓幅 N のぶん丸ごと落ちる。
- **`13` の合言葉の踏み直し**: `13` は「累積という *状態* を `sum` 変数で運ぶ」だった。`14` は「窓和という *状態* を `windowSum` 変数で運ぶ」―― **同型**。`13` レビューの締めに書いた「Tier 4 の合言葉『持ち越す状態は変数に載せて運ぶ』が、次の `14`（移動平均＝窓の状態を運ぶ）に地続きで効く」が、まさにここ。**現状の実装は、その持ち越しをしていない**（毎回 `targetNumsSum := 0` から組み直す＝`13` の `output[i-1]` で「毎回取りに行く」と同じ匂い）。

### もう一つの O(n) ―― `13` の *累積和* を再利用する（prefix sum）

窓和は **累積和の差** で出せる。`13` で作った `calcCumulativeSum` があれば:

```
prefix = [p0, p1, ..., pn]（p0=0, pk = input[0..k-1] の和）
窓 [i, i+N) の和 = prefix[i+N] - prefix[i]
```

`13`（累積和）→`14`（窓和＝累積和の差）は **道具の再利用**として綺麗に地続き。実装はどちらでもよいが、**「窓和を毎回ゼロから作らない」** という一点が主眼。滑らせる方式（`windowSum` の +in/−out）が最もお題の名前（スライディングウィンドウ）に忠実。

> 合言葉（`13` から継承・`14` で確定）: **窓は "滑らせる"。隣の窓と N-1 個は共有しているのだから、毎回 N 個を足し直さず、端の2個（出る・入る）だけ更新する。持ち越す状態（窓和）は変数に載せて運ぶ。**

### 補足 ―― これは「早すぎる最適化」ではない

「naive O(n·N) でも正しいのだから十分では」と思うかもしれない。だが **このドリルの狙いそのものが「窓を滑らせる」**（DRILLS.md #14）。滑らせない実装は *お題の主眼を素通り* している ―― `13` が「正しいが状態を持ち越していない」で主眼を外したのと同じ構図。正しさの問題ではなく、**狙った反射が身についたか** の問題。だからここは 主眼・要。

## 補講：スライディングウィンドウを図で理解する

> 観点1 の「窓を滑らせる」が掴みにくい人向けの、図つきステップ解説。例は本ドリルと同じ `input = [1, 2, 3, 4, 5]`, `N = 3`。

### 1. そもそも「移動平均」は何をしている？

幅 `N=3` の「窓」を左から右へ1つずつずらし、**窓の中身の平均**を並べるだけ。

```
入力:  [ 1  2  3  4  5 ]
         └─窓1─┘              → (1+2+3)/3 = 2
            └─窓2─┘           → (2+3+4)/3 = 3
               └─窓3─┘        → (3+4+5)/3 = 4

出力:  [ 2  3  4 ]
```

窓は 3 か所にしか置けない（`5 - 3 + 1 = 3` か所）。だから出力は 3 個 ―― これが cap `len(input)-number+1`（観点3-1）の正体。

### 2. 今のコードのやり方（毎回ゼロから足す＝O(n·N)）

窓が動くたび、中の 3 個を**毎回イチから全部足し直している**:

```
窓1: 1 + 2 + 3  = 6   ← 3回 足し算
窓2: 2 + 3 + 4  = 9   ← また 3回 足し算
窓3: 3 + 4 + 5  = 12  ← また 3回 足し算
```

足し算の回数 = **窓の数 × N** = `3 × 3 = 9回`。入力 n 個・窓幅 N なら `n × N` 回 ＝ **O(n·N)**。

### 3. ここが「もったいない」ポイント

窓1 と 窓2 を**縦に並べて**見る:

```
窓1:  [ 1  2  3 ]  4    5
窓2:     1 [ 2  3  4 ]  5
             ↑↑↑
          2 と 3 は 両方の窓に入っている！
```

窓が1つ右にずれても、**真ん中の `2, 3` は変わらない**。変わったのは端の2つだけ:

- **`1` が窓から出ていった**（左端）
- **`4` が窓に入ってきた**（右端）

なのに今のコードは、変わっていない `2, 3` まで毎回足し直している。ここが無駄。

### 4. スライディングウィンドウの発想：「差分だけ」更新する

窓の合計 `windowSum` を **1個の変数で持ち歩き**、窓がずれるたびに **「出た数を引いて、入った数を足す」** だけにする:

```
窓1 の合計 = 1 + 2 + 3 = 6            ← 最初の窓だけ、ちゃんと合計する

窓2 の合計 = 6  − 1  + 4  = 9
             ↑    ↑    ↑
          前の合計 出た数 入った数

窓3 の合計 = 9  − 2  + 5  = 12
             ↑    ↑    ↑
          前の合計 出た数 入った数
```

窓がいくつずれても **1回の引き算 + 1回の足し算 = 2回** で済む。N がどれだけ大きくても関係ない ＝ **O(n)**。

### 5. 「滑る」様子を1ステップずつ

`windowSum` という箱を1つ持って、窓を右へ滑らせる:

```
STEP 0：最初の窓だけ、素直に合計する
        ┌───────┐
 [   1   2   3 ] 4   5          windowSum = 1+2+3 = 6
        └───────┘               → 出力に 6/3 = 2

STEP 1：窓を1つ右へ滑らせる
              ┌───────┐
   1  [  2   3   4  ] 5         windowSum = 6 − 1 + 4 = 9
   ↑              ↑             （出た1を引き / 入った4を足す）
  出る           入る            → 出力に 9/3 = 3

STEP 2：さらに1つ右へ
                  ┌───────┐
   1   2  [  3   4   5  ]       windowSum = 9 − 2 + 5 = 12
       ↑              ↑         （出た2を引き / 入った5を足す）
      出る           入る        → 出力に 12/3 = 4

出力: [2, 3, 4]  ✅
```

「窓を **滑らせる（slide）**」＝ `windowSum` という状態を持ち歩き、端の出入りだけ更新する、というイメージ。

### 6. コードとの対応

```go
func calcMovingAverage(input []int, number int) []int {
    if number <= 0 || number > len(input) {
        return []int{}
    }
    result := make([]int, 0, len(input)-number+1)

    // ── STEP 0：最初の窓だけ、素直に合計 ──
    windowSum := 0
    for j := 0; j < number; j++ {
        windowSum += input[j]          // 1+2+3 = 6
    }
    result = append(result, windowSum/number)   // 6/3 = 2

    // ── STEP 1, 2, ...：窓を滑らせる ──
    for i := number; i < len(input); i++ {
        windowSum += input[i]          // 入ってきた数を足す（4, 5）
        windowSum -= input[i-number]   // 出ていった数を引く（1, 2）
        result = append(result, windowSum/number)
    }
    return result
}
```

`input[i]` が「今 入ってくる数」、`input[i-number]` が「今 出ていく数」。`i-number` の意味:

```
i = 3（入る数 input[3]=4）のとき、出る数は input[3-3] = input[0] = 1  ✅
i = 4（入る数 input[4]=5）のとき、出る数は input[4-3] = input[1] = 2  ✅
```

窓の幅は N なので、「今入る位置」からちょうど N 個左が「今出る位置」になる。

### 7. `13_cumulative_sum` との関係（同じ「状態を運ぶ」）

前回の `13`（累積和）で学んだ **「前の状態を変数（`sum`）で持ち越す」** と、まったく同じ考え方:

| | 持ち越す変数 | 更新の仕方 |
|---|---|---|
| `13` 累積和 | `sum` | `sum += num`（足すだけ） |
| `14` 移動平均 | `windowSum` | `windowSum += 入る − 出る`（足して引く） |

`13` は「ずっと足し続ける」、`14` は「窓の外に出た分は引く」だけの違い。**状態を1変数に載せて持ち歩く** 反射は同じ ―― これが Tier 4「順序・ウィンドウ」で身につけたい型。

> 補講の一言: **隣の窓は中身をほとんど共有している。だから毎回全部足し直さず、「出た数を引いて・入った数を足す」だけにする。** 合計を `windowSum` という1つの変数で持ち歩くのがコツ。

## 観点2【③仕様・契約】出力 `int` × 整数除算 ―― spec は `float`、しかも truncation を pin するテストが無い

```go
movingAverage := targetNumsSum / number // 14_moving_average.go:22  ← 整数除算（切り捨て）
```

いま `func calcMovingAverage(...) []int` は `int` を返し、平均を **整数除算** で出している。テスト10本は **全て割り切れる**（`{1,2,3}=6/3=2`、`{-1,-2,-3}=-6/3=-2` …）ので緑。だが問題は3つ:

1. **DRILLS の出力例は float**: `DRILLS.md #14` の出力は **`[2.0, 3.0, 4.0]`**。「移動平均」は意味的に非整数になりうる量。`int` に丸めるのは *設計判断* だが、**spec と食い違っている**。
2. **truncation の挙動が pin されていない**: 割り切れない例（`[1,2,4], N=3 → 7/3`）が **1本も無い**。`int` 除算だと `7/3 = 2`（`2.33…` を切り捨て）。この「切り捨てる」という契約が **どのテストにも固定されていない** ―― 実装を `float64` に変えても、`math.Round` にしても、**今のテストは全部緑のまま**通ってしまう。契約がザルになっている。
3. **負のとき Go は 0 方向へ切り捨て**（floor ではない）: `[-1,-1,-2], N=3 → -4/3 = -1`（`-1.33…` → `-1`、`-2` ではない）。この非自明な挙動も未テスト。

これは `07_lookup` で刻んだ教訓の踏み直し:

> `07` の反省（notes.md 2026/6/29）: **「欠損キーの『契約』を先に決める。① skip ② ゼロ値 ③ エラー ―― どれを選んでも良いが、実装・テスト・コメントを同じ契約に揃えること。」**

`14` の「割り切れないときどうするか」も同じ *契約* の問題。選択肢は:

- **(a) spec 通り `[]float64` を返す**（`float64(targetNumsSum)/float64(number)`）。`2.0,3.0,4.0` と一致し、平均の意味に忠実。テストの `want` も `[]float64` に。
- **(b) 意図的に `[]int`（切り捨て）で通す**。それならコメントで「整数除算・0方向切り捨て」を明記し、**割り切れない/負のケースのテストで契約を pin** する（`[1,2,4],N=3 → [2]` 等）。

**どちらでも良いが、決めて・揃える**。今は「実装＝int切り捨て／spec＝float／テスト＝割り切れる例のみ」で **三者が食い違ったまま**、その食い違いが緑に隠れている。ここを締めるのが観点2。

> 合言葉（`07` から継承）: **契約（float か・切り捨て int か）を先に決め、実装・コメント・テストの三者を揃える。「たまたま割り切れる例」だけで緑にすると、契約が pin されない。**

## 観点3【②道具・軽微】cap は "安全だが緩い"／余計なガード1つ／`return` 脱出

### 3-1. 出力 cap `len(input)` は **過大**（正しい上限は `len(input)-number+1`）

```go
movingAverageResult := make([]int, 0, len(input)) // 14_moving_average.go:5
```

出力の要素数は **`len(input) - number + 1`**（窓が置ける位置の数）。`len(input)` は **常にこれ以上** なので **再確保は起きない＝安全**。ただし `number-1` 個ぶん **過大**に確保している。`07`/`11` の cap 取り違え（*過小* で足りない）とは逆で、こちらは *過大* ―― 害は小さいが、**タイトな右サイズが計算で分かる**のに緩く置いている。

- `13`（累積和）は 1:1 なので `len(input)` が **ちょうど**だった。
- `14` は N-1 個縮む（窓が満たない先頭を出さない）ので、タイトには **`len(input)-number+1`**。
- 観点1の書き換え（`windowSum` 版）では、この cap を `make([]int, 0, len(input)-number+1)` にすると過不足ない。

「cap は *生む要素の数* で決める（`10`＝総和／`11`＝マッチ数／`13`＝1:1／`14`＝`n-N+1`）」の当てはめ ―― お題ごとに式が違う、を意識できるとよい。**優先度は低い（安全側の緩さ）**。

### 3-2. 先頭ガード `if number > len(input)` は **余計**（ループのガードに吸収される）

```go
if number > len(input) { // 14_moving_average.go:7  ← このガードは無くても結果は同じ
    return movingAverageResult
}
if number <= 0 { //         14_moving_average.go:10  ← こちらは必須（後述）
    return movingAverageResult
}
for i := range input {
    if i+number > len(input) { // 14_moving_average.go:14  i=0 のとき number>len を既に判定している
        return movingAverageResult
    }
    ...
```

`number > len(input)` のとき、7 行目を消しても **ループ初回 `i=0` で `0+number > len(input)` が真** → 即 `return` で、**結果は同一**（空スライス）。空入力でも `range` が0回で空返しになり同じ。つまり 7 行目は **`06`/`07`/`13` で潰した「無くても同じ結果の分岐」** の再来。消せる。

> ⚠ **重要な但し書き（この "余計" 判定は naive 構造限定）**: 上の「消せる」は、**内側ガード `if i+number > len(input) { return }`（14_moving_average.go:14）が `number > len(input)` を吸収している** という、*旧・naive 構造* を前提にした話。**観点1のスライディングウィンドウ版に書き換えると、この内側ガードごと消える**ので、吸収役がいなくなり **`number > len(input)` を弾く場所が消滅する** ―― その瞬間 **「余計」だったガードは "必須（load-bearing)" に反転する**。実際、滑らせる版は「最初の窓」を**無条件で `input[0..number-1]` まで読む**ため、`number > len(input)` だと (a) `make([]int, 0, len(input)-number+1)` の cap が **負**（例 空入力＋`number=3` → `0-3+1=-2` → `panic: makeslice: cap out of range`）、(b) 最初の窓ループが **範囲外アクセス panic**、の2重で壊れる。
> **結論**: 観点1の書き換えを採るなら、**`number > len(input)` は削除してはならない**。観点1の rewrite が `if number <= 0 || number > len(input) { return []int{} }` と **1本に束ねて維持** しているのはこのため。**「このガードは余計」は "今の制御構造" を前提にした判定** ―― 構造をリファクタしたら **どのガードが load-bearing に戻ったかを必ず見直す**（今回の実地の学び）。なお `make` は必ず **このガードの後ろ** に置くこと（前に置くと負 cap で panic）。

> ただし **`number <= 0` のガード（10 行目）は必須・load-bearing**。これを消すと `number == 0` で内側ループが0回→`targetNumsSum == 0`→`0 / 0` で **panic（整数のゼロ除算）**。「余計なのは 7 行目だけ、10 行目は消してはいけない」を区別できること。（観点1の書き換え例では `if number <= 0 || number > len(input)` と1本にまとめ、ループ境界 `i < len(input)` 側で右端を見ている。）

### 3-3. ループ途中の `return` は `break`／ループ境界化が素直

`14_moving_average.go:14` は、まだ結果を積み終える前の **ループ内 `return`**。今は「以降どの `i` も条件を満たさない」ので `return` でも `break` でも結果は同じ。だが *途中で組み立てを打ち切る* 意図は `break`、あるいは **ループ境界そのものに条件を畳む** ほうが読みやすい:

```go
for i := 0; i+number <= len(input); i++ { ... } // 「窓が収まる間だけ回す」を境界で語る（内側ガード不要）
```

`13` の「`output[i-1]` を後方参照して匂う」と同種で、**制御を式（ループ境界）に載せると、途中脱出そのものが消える**。観点1の書き換えは自然にこの形になる。

## 観点4【②道具・字面】`gofmt -s` 差分あり（`for i, _ :=`）／`number` の命名

- **`gofmt -s` が `14_moving_average.go:13` を指摘**: `for i, _ := range input` → **`for i := range input`**。range の2つ目が `_` のときは blank を **書かない** のが simplify 規則。無印 `gofmt` は通すが **`gofmt -s` は差分を出す**。`go vet` は無関係。**A項目（字面）** として潰す。
  - `13_cumulative_sum.go` は `for _, num := range input` と既に綺麗。`14` だけ `i, _` が残っている ―― 手癖の揺れ。`gofmt -s` を常用チェックに入れると自動で拾える。
- **`number` は窓幅を語らない命名**: 引数 `number int` は「窓の幅 N」だが、`number` は「何かの数」としか読めない。`windowSize` / `window` / `n`（お題の N）のほうが役割を語る。内側ループの `targetNumsSum`・`movingAverage` は妥当。**任意**。
- **良い点**: `for j := range number`（Go 1.22 の range-over-int）を使えている。モダンで読みやすい ―― これ自体は good。

## 観点5【③テスト】カバレッジの穴 ―― 「割り切れない」「N=1」が無い／サブテスト名の重複

10 ケースは **境界がよく効いている**（`number==len`＝`InputSizeIsSameNumberInput`／`number>len`／`number<=0`／`0`／空／nil／負数混在）。`01` の「空・nil を `[]int{}` で揃える」も踏めている。その上で穴が3つ:

1. **割り切れない平均（litmus・観点2の要）**: 全ケースが割り切れる。`[1,2,4], N=3`（和 7 → `int` で 2）を1本入れると、**int切り捨てという契約が pin** される。これが無いと `float64` 実装でも `math.Round` 実装でも緑になり、**契約がザル**（観点2）。
2. **負の割り切れない（0方向切り捨て）**: `[-1,-1,-2], N=3`（和 -4 → `int` で `-1`。floor なら `-2`）。Go の「0方向切り捨て」を明示でき、負値の丸め方向を退行から守れる。
3. **`number == 1`（窓幅1＝恒等）**: `[1,2,3], N=1 → [1,2,3]`。窓幅1では入力がそのまま出る。窓境界 `i+number` の off-by-one 検出に効く軽い litmus。未カバー。

さらに **テスト字面のバグ（軽微だが実害）**:

- **サブテスト名の重複**: `14_moving_average_test.go:15` と `:17` が **どちらも `name: "AllPositiveIntegers"`**。だが `:17` は実際には **全負数** `{-1,-2,-3,-4,-5}` のケース。名前と中身が食い違い、かつ `t.Run` の名前重複で **失敗時の識別子が `AllPositiveIntegers#01` に化けて** どちらが落ちたか読みにくい。`:17` は `AllNegativeIntegers` に直す。

> 補足: 観点2で述べた通り、**「たまたま割り切れる例だけ」だと truncation 契約が pin されない**。#1・#2 の2本を足すだけで「int 切り捨て」の契約がテストで固定され、将来 `float64` へ切り替える/切り替えないの判断も緑で守れる。
