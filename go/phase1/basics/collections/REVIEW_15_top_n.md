# レビュー: `15_top_n` —「頻度で並べて上位N件」。主眼は "上位N件の切り出しはスライス式一発（手動 for + copy は冗長）" と "`07` の冗長分岐がまた出た"

`15_top_n`（Phase 1 ドリル、Tier 3 の締め）のレビュー。
お題は「`[]Item{Name, Frequency}` を **頻度の降順**で並べ、**上位 `topN` 件**を返す。負の頻度は除外・同点は名前の昇順・`topN<=0` や空入力は空スライス」。
これは **`04`（頻度でソート）＋ `08`（同点タイブレーク）＋ `01`（filter で負を落とす）** の合成回。新しい道具は無く、**既に持っている道具を組み合わせて正しく畳めるか**が主眼。

結論から言うと **コードは正しく、緑も信用してよい**（バグ無し・`gofmt`/`vet` クリーン・`-count=5` で 11 サブテスト × 5 回連続 緑）。
今回の主題は3つ:
1. **観点1（②道具の主眼）**: 上位N件の切り出しが **手動 `make`＋分岐＋copy ループ** になっている。Go では **スライス式 `validItems[:topN]` 一発**で書ける。`10`（`...`展開）・`13`/`14`（余計な分岐/ループを消す）の延長線。
2. **観点2（②道具・`07` の宿題再来）**: 空入力ガード `len(input)==0` は、後段の `len(validItems)==0` ガードと **同じ結果**で、**冗長分岐**。`07` で言語化した「無くても同じ結果の分岐は消す」がまた出ている。
3. **観点3（良い）**: `sort.Slice` に**名前のタイブレークを付けて全順序**にしている ―― `08`（多キーソート）を再利用しつつ、`12` の「タイブレークがあるなら `SliceStable` は過剰」も守れている。ここは**光った点**。

> 大原則（review-rubric の ②道具の良し悪し）: イディオムか・計算量に無駄はないか・データ構造の選択は妥当か。
> 前提: `go test -run TestDisplayTopN -count=5` が **11 サブテスト × 5 回連続で緑**。`gofmt` 差分なし・`go vet` クリーン。

## 観点1【②道具・主眼】上位N件の切り出しは **スライス式一発** ―― 手動 `make`＋分岐＋copy ループは冗長

今回いちばん手を動かす価値のある指摘。末尾の切り出しブロック:

```go
items := make([]Item, 0, topN)               // 15_top_n.go:38
if len(validItems) < topN {                  // ① 全件で足りるなら…
	items = append(items, validItems...)     //   全部 copy して返す
	return items
}
for i := range topN {                        // ② topN 件を1つずつ copy
	items = append(items, validItems[i])
}
return items
```

やっていることは「**`validItems` の先頭 `min(topN, len)` 件を返す**」だけ。Go はこれを**スライス式**で一撃で書ける:

```go
if topN > len(validItems) {
	topN = len(validItems)          // topN を実在件数に丸める
}
return validItems[:topN]            // 先頭 topN 件のビュー
```

`min` を使えばさらに1行:

```go
return validItems[:min(topN, len(validItems))]   // Go 1.21+ の組み込み min
```

**なぜこれで良いか（安全性の根拠）**: `validItems` は `make([]Item, 0, len(input))` で**この関数が新たに確保した内部スライス**。`input` を指してはいない（filter で要素を append したコピー）。だから **`validItems[:topN]` を返しても呼び出し側の入力は一切汚れない**（`08` の「破壊/非破壊」の非破壊を保てている）。返り値が同じ配列を共有するのは `validItems` 自身だけで、これは関数終了後に捨てられる。

**この書き換えで消えるもの**:
- 2本目の `make([]Item, 0, topN)` の**確保**（＝観点2の cap 問題ごと消える）。
- `if len(validItems) < topN` の**分岐**。
- `for i := range topN` の**手動 copy ループ**。

3つの操作が**式1本**に畳まれる。これは `10_flatten` で「`for` 1個ずつ append → `...` 展開一撃」に畳んだのと同じ話。`13`/`14` で「余計な分岐/内側ループを消す」を繰り返してきた流れの、今回の現れ方。

> 合言葉（`10`→`13`→`14` から継承）: **「先頭N件が欲しい」はループではなくスライス式。`s[:n]`（＋ `n` を `len(s)` で丸める）で一撃。手で copy し直すのは、既にメモリ上に並んでいるものを二度並べているだけ。**

> 補足（任意・cap を締めたいなら）: `validItems[:topN]` の返り値は cap が `len(input)` のまま（背後の配列を丸ごと保持する）。上位N件だけを長く保持するなら三点スライス `validItems[:topN:topN]` で cap も切れる。ただし top-N の用途では誤差なので**任意**。

### 小さな前進として ―― 7/22 の修正は「途中まで正しい」

notes.md（7/22）で、`if len(validItems) < topN` を **`for` の内側から外へ出した**のは正しい前進（`02` の「ループに関係ない分岐はループの外」）。**ただしゴールはもう一歩先**で、外に出した分岐そのものが**スライス式にすれば要らない**。「分岐を外に出す」→「分岐ごと消す」まで行けると、`13`/`14` の畳み方と同じ高さに乗る。

## 観点2【②道具・`07` の宿題再来】空入力ガード `len(input)==0` は冗長 ―― 後段の `len(validItems)==0` と同じ結果

```go
if topN <= 0 || len(input) == 0 {   // 15_top_n.go:15  ← len(input)==0 は要らない
	return []Item{}
}
...
if len(validItems) == 0 {            // 15_top_n.go:27  ← こちらが空入力も面倒を見る
	return []Item{}
}
```

**`len(input)==0` を消しても結果は完全に同じ**。理由: 入力が空（または nil）なら、filter ループは 0 回回り `validItems` は空のまま → **`len(validItems)==0` ガードが同じ `[]Item{}` を返す**。空入力は「有効要素が0件」の**特殊ケースにすぎない**ので、後段のガードに吸収される。

実際に検証済み: `len(input)==0` を外した版で、既存 11 ケース（空・nil 含む）＋ `topN=-1` が**全て一致**した。

これは `07_lookup` で言語化した宿題と**同型**:

> `07` の反省（notes.md より）: **「バグを二通りで直すと片方が冗長分岐になりやすい。comma-ok を入れたのに `if len(users)==0` の早期 return も残してしまい、後者が冗長だった。無くても同じ結果の分岐は消す（`04`/`05`/`07`/`09`）。直したら『片方で足りないか』を問う。」**

今回もまさに「片方（`len(validItems)==0`）で足りる」。残すべきは **`topN<=0`** だけ（これは filter の後段では拾えない独立した契約）。直すと:

```go
if topN <= 0 {
	return []Item{}
}
```

> 合言葉（`07` から継承・再掲）: **早期 return を2つ書いたら「後ろのガードが前のを含まないか」を問う。空入力は "有効0件" の一種 ―― 有効件数のガードが既に見張っているなら、入力長のガードは重複。**

> 注記: 「消すと空入力でも `make` して filter ループ（0回）に入るぶん一瞬遅いのでは」という反論はあり得るが、コストは無視できる（0回ループ＋容量0の make）。可読性のため `len(input)==0` を**明示的な早期 exit として残す**判断も一応あり得るが、`07` の合言葉に忠実なら**消す**。優先度は中。

## 観点3【良い・最重要の "できている点"】`sort.Slice` に名前タイブレーク ―― `08` を再利用し、`12` の「Stable は過剰」も守れている

出力は**スライス**（順序が結果に漏れる）。`03` のようにフレーキーにならないのは、**`sort` が全順序を握っている**から ―― これは `04_count_frequency` と同じ側の倒し方。ここが正しく書けている:

```go
sort.Slice(validItems, func(i, j int) bool {
	if validItems[i].Frequency == validItems[j].Frequency {
		return validItems[i].Name < validItems[j].Name   // 同点は名前の昇順（タイブレーク）
	}
	return validItems[i].Frequency > validItems[j].Frequency // 第一キーは頻度の降順
})
```

- **多キーソート（`08`）の再利用**: 第一キー「頻度 降順」、第二キー「名前 昇順」。`AllItemsTheSameFrequency`（全部同頻度）でも `a,b,c,d` に**一意に**決まる。タイブレークが無ければここは**フレーキー**（`sort.Slice` は非安定）になっていた ―― それを**自分で塞げている**。
- **`sort.Slice` の選択が正しい（`12` の教訓）**: `12_invert` で「1キーだけなのに `SliceStable` を使うのは過剰」と学んだ。今回は**タイブレークで全順序を作った**ので、`SliceStable` に頼る必要が無い ―― `sort.Slice` で十分。**同点キー(頻度)だけで並べて `Stable` で元順を保つ**のではなく、**タイブレークで曖昧さ自体を消す**方を選べている。これは `12` の一歩先の正解。
  - 補足: 仮に `Name` も同一な2要素があっても、それらは**同一の `Item`** なので `DeepEqual` は順不同で通る。だから非安定でも決定的。全順序が (頻度, 名前) で張れている限り安全。
- **非破壊（`08` の教訓）**: filter で `validItems` という**新スライス**を作ってから sort しているので、**呼び出し側の `input` は並べ替わらない**。`08` の「他人に使われる関数はデフォルト非破壊」を自然に踏めている。
- **`validItems` の cap は正しい**: `make([]Item, 0, len(input))` ―― 有効要素は最大でも `len(input)` 個。`07`/`11` で cap を取り違えた（`len(users)`）のと違い、**ここは上限を正しく取れている**。観点1でこのスライスをそのまま返せるのも、この確保が素直だから。

> `12` は「1キーで `SliceStable` は過剰」だった。`15` は**多キーで `sort.Slice`＋タイブレーク** ―― 「安定性で誤魔化さず、比較関数で全順序を張る」という、より本質的な倒し方に乗れている。Tier 3 の狙い「道具の合成」が効いた点。

## 観点4【altitude・軽微】`make` がガード節より前 ―― 早期 return 時に無駄な確保

```go
validItems := make([]Item, 0, len(input))   // 15_top_n.go:12 ← ガードより前
if topN <= 0 || len(input) == 0 {           // 15_top_n.go:15
	return []Item{}
}
```

`topN<=0`（や空入力）で早期 return する場合、**`validItems` を確保してから捨てている**。ガード節は関数の**先頭**に置き、確保はガードを抜けた後にするのがイディオム:

```go
if topN <= 0 {                              // まずガード
	return []Item{}
}
validItems := make([]Item, 0, len(input))   // 抜けてから確保
```

コストは軽微だが、「**入力チェック → 早期 return → 本処理**」の並びは読み手にも優しい（`02` の「先頭要素は初期値代入、余計な段取りをしない」と同じ、段取りの整頓）。観点2で `len(input)==0` を消すなら、ガードは `if topN <= 0` 一行になり、この並べ替えと自然に噛み合う。

## 観点5【テストの穴】ラベルと中身の食い違い1件＋境界1件

カバレッジ自体は厚い（通常／同点／`topN=1`／`topN=0`／空／nil／全同点／負要素あり／負が topN より多い／全負／空名前、の 11 ケース）。ただし2点:

- **`TopNIsNegativeInteger` が実は負を試していない（`15_top_n_test.go:19`）**: このケースの `topN` は **`0`** で、直前の `TopNisZero`（:18）の**完全な重複**。名前は「Negative」なのに **`topN<0` の経路を一度も通っていない**。`topN<=0` の `<` 側（例 `topN: -1`）が未検証。ラベルが嘘をついている状態なので、`topN: -1` に直すべき（検証済み: `-1` でも実装は正しく `[]Item{}` を返す）。
  ```go
  {name: "TopNIsNegativeInteger", input: []Item{...}, topN: -1, want: []Item{}}, // 0 → -1 に
  ```
- **`Frequency == 0` の境界が未カバー**: filter は `e.Frequency >= 0`。つまり**頻度0は残す**契約だが、テストに頻度0の要素が1件も無い。「0 は残る／負は落ちる」という境界（`>=` の `=` 側）を1ケースで固定しておくと、うっかり `> 0` に書き換わる退行を捕まえられる。
- **（任意）同点かつ同名**: `Name` も `Frequency` も同一の2要素は未カバー。非安定ソートでも `DeepEqual` は通る（観点3）ので**必須ではない**が、「タイブレークが全順序を張る」ことの明示にはなる。

> `reflect.DeepEqual` でよい根拠 = **観点3**（順序は (頻度降順, 名前昇順) の全順序で決定的だから、順序込みの `DeepEqual` が正しい）。`04` と同じ「sort が順序を握る側」なので `DeepEqual` は妥当。
