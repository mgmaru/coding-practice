# 設計メモ

## ドキュメント概要
実装で工夫した点とわからなかった点をメモのように記載する。

## 工夫した点
- ガード節を利用。エラーが起きた際には、早期リターンすることを意識した。

## わからなかった点
- コマンド不正のエラー分岐が、イマイチわからなかった。
    - `--by <変数>`や`--top <変数>`の部分がわからなかった。
    - 自分の実装では、`--`と`<変数>`をわけてしまった。これだと、`--by <変数>`および`--top <変数>`のコマンド不正パターンが検出できない。
    - 本当は、`--by <変数>`とまとめて処理できれば、コマンド不正パターンを認識できる気がした。
- コマンド不正のif文の注意
    - `if by != "status" && by != "path" && by != "ip" ` は合ってる。
    - `if by != "status" || by != "path" || by != "ip" ` はだめ。
        - `by == "status"`の場合、`by != "path"`および`by != "ip"`も`true`になってしまう。
        - 正しくは、「by が status でもない　かつ　by が path でもない　かつ　by が ip でもない」場合に、コマンド不正となる。
- `parseCommand()`は、コマンドを文字列型のスライスで返している。
    - ただし、これだと、コマンドを利用する`main()`側で、コマンドの順番を知らないとダメな気がした。
    - 例えば、スライスの２番目が`--by`で、3番目が`--top`など。
    - これが良いのかわからない。
- ファイルを開く操作の実装がわからなかった。
- ファイルを開いて、行単位に処理する実装がよくわからなかった。(重要)
    - 最初、`ReadLine()`を使おうとした。
    - どうやら、`bufio.NewScanner()`の方が使いやすいらしい。
    - `for scanner.Scan()`の中で、`line := scanner.Text()`で１行ずつ読み取っていくのが良い（らしい）。
- `readFile()`の計算量が不安。
- `readFile()`の命名が微妙。単純なファイルの読み込みだけではなくて、有効なリクエスト行を抽出している。
    - 結局、`extractValidRequestLines()`にした。
- おそらく、ファイル読み込む時にはバッファを設けた方が良さそう。。。
- ソートするんだったら、スライスが良いのか？どのデータ型が良いのか？
    - 今回は、`sort.Slice()`を使用した。
    - `sort.Slice(validRequests, func(i, j int) bool { return m[validRequests[i][3]] > m[validRequests[j][3]] })`
        1. カウント用の`map[string]int`を定義する。
        2. スライス`validRequests`の中の出現回数をカウントする。
        3. スライス`validRequests`の中の２つの`status`の**出現回数を比較**して、最初の方が大きくなるようにソートする。
    - ソートの判断を、`validRequests[i][3]> validRequests[j][3]`のようにしてしまうと、`status`の出現回数ではなく、`status`自体を比べていることになるので違う。
- ただし、ソートについて間違っている気がする。
    - 同じ出現回数のコマンドが乱立してしまう場合があり。
- 一瞬、`m[status] = +1`と`m[status] += 1`の違いがわからなかった。。。
    - `m[status] = +1`：`status`の値に`1`を代入する。
    - `m[status] += 1`：`status`の値に`1`を加算する。

- 関数の中で、`topSortValidRequests[i][0]`のように、スライスの何番目で指定しているが、これは果たして良いのだろうか？
- `JSON`への変換は、`json.Marshal`を利用した。
    - 配列の構造を知っている必要がある。
    - 別々の開発者が開発していた場合、どうなんだろうか？
    - 構造体で指定していればOKか？
        - 構造体で指定しておけば、開発者誰でもわかる。
- `sortByDescend()`関数について、エラーを返していないが良いのか？返すべき？
- `sortByDescend()`関数の中で、`if`文でコマンドを分岐させているが、ここをインターフェースで書き換えるとができるのではないかと思った（ただし、インターフェースの知識が浅く、修正できなかった）。
    - インターフェースで書き換えることで、呼び出し元のインスタンスによって処理を書き換えられるのではないかと思った。
    - しかし、よく考えてみると、インターフェースで処理を切り出したとしても、関数の中身の処理が同じなので、そこまで恩恵がないような気がした。
    - それよりも、出現回数でソートする共通関数として切り出した方が良い気がした（`for`以下）。

## 反省（２回目のレビュー後）
【go/phase1/tools/logstat/review.md】を元に再度修正した結果を以下に示す。

### 修正した点
- 構造体`Count`を新たに定義して、フィールドの件数のカウントをしやすくした。
- `extractValidRequestLines()`：`for`の中で`strings.Fields(requestline)`を変数`fields`に格納し、`fields[0]`などで、構造体にマッピングすることにした。
    - 変数`skipped`を追加し、不正なリクエスト行数をカウント。
    - 不正な行かどうかのバリデーションを`continue`でスキップした。
- `displayTopN()`：入力された`top`の数に対して、有効なリクエスト数が少ない場合のバリデーションを修正
    - 今までの実装では、「top数 < 有効なリクエスト数」と「top数　> 有効なリクエスト数」でそれぞれループを回していた。
    - `for`の条件を「`i` < top数」かつ「`i` < 有効なリクエスト数」とすることで、どちらかが`false`になった時点でループを抜けるようにした。
    - これで、`for`ループを１つにまとめることができた。
- `aggregate()`：`--by`で指定されたフィールド（`ip`/`status`/`path`）について、カウントする関数を追加した。
    - `Count`という構造体で保持していることにより、集計しやすくなっている。
    - 今までの実装では、コマンドを関数に渡して、関数の中で`if`文で分岐していたため、万が一、`Request`のフィールドが増えた場合（`ip`/`status`/`path`以外が増える）に、関数の中で`if`を追加して、新しいフィールドに対応することができない。
    - そこで、**呼び出しもとでコマンドごとに`if`文で分岐して、関数を引数として渡す**ことで、関数内部で具体的なコマンドに依存しなくても、コマンドに対応する`Request`のフィールドの出現回数をカウントできるようになった。1本化を実現。
- `sortByDecend()`：`Request`のフィールドの出現回数のカウントに関して、カウントが同数だった場合に、キーの昇順でソートする処理を追加。
    - 自分の実装では、カウントが同数だった場合に、ソートが安定しなかった。
        - ソートが安定したデータ：`[{Key:"a", Count:10}, {Key:"b", Count:10}, ...]`
        - ソートが不安定のデータ：`[{Key:"b", Count:10}, {Key:"a", Count:10}, ...]` → `b`が`a`よりも先にきている。
    - ここでもやはり、構造体`Count`を定義したことで、キーでソートしやすくなっている。

### わからなかった点
- コマンドライン引数（`os.Arg`もしくは`flag`）と標準入力（`stdin`）がよくわからなかった。
    - コマンドライン引数：**プログラムへの指示、命令**
    - 標準入力：**データ本体を受け取る場所**
    - 今回であれば例えば、`--by status`というのは、`status`というデータというより、「**statusごとに集計しなさいという命令**」になる。
- 構文：
```go
flag.String("名前", "デフォルト値", "説明")
flag.Int("名前", デフォルト値, "説明")
flag.Bool("名前", デフォルト値, "説明")
flag.Parse()
```
- `flag.Parse()`：コマンドライン引数を受け取って、定義したフラグに値を反映する処理
- `args := flag.Args()`：コマンドライン引数以外の何かしらの値を受け取る。
- `flag.Bool()`：コマンドライン引数が指定されたら、真偽値が反転。（デフォルトで`false`を指定していれば、`true`）
- **最大の注意点**
    - Go言語の標準の`flag`は、**最初のフラグではない引数が出てきた時点で、そこでフラグ解析が止まる挙動がある。**
    - `sample.log --by status --top 10`のようにしてしまうと、`access.log`で解析が終了し、`--by`以降のコマンドライン引数が全て`flag.Args()`に入ってしまう。
    - 指定するときは、フラグを先に置く形が良い。
        - 正しい：`--by status --top 10 sample.log`
        - 間違い：`sample.log --by status --top 10`
