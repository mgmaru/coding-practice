# 課題: ファイル整理・リネームCLI `refile`

## 概要

ディレクトリ内のファイルを、ルールに従って整理（サブフォルダへ移動）・改名するCLIツールを作る。
**デフォルトは dry-run（変更計画を表示するだけで、ファイルには一切触れない）**。`--apply` を付けたときだけ実際に反映する。

- 言語: Go
- 制約: 標準ライブラリのみ（外部依存なし）
- logstat（`read → 集計 → 出力`）との違い: 本課題は **`read → 変更計画を立てる → 安全に適用する`**。副作用（破壊的操作）を安全に扱うのが主題。

> **対象は「1つのディレクトリの中身」。** 指定した `<dir>` の中のファイル群を、`<dir>` の**内側に作ったサブフォルダ**へ自己整理する。移動元と移動先を別々に渡す「2フォルダ間の移動」ではなく、サブフォルダの位置は常に `<dir>` 基準で決まる（コマンドはどのディレクトリから実行してもよい）。整理する対象は**ファイル**で、ディレクトリ自体を移動・改名するわけではない。

## この課題で養うこと（学習目的）

logstat が「読み取り → 集計 → 出力」だったのに対し、refile は **副作用（ファイルの移動・改名）を安全に扱う**のが主題。
この課題の目的には優先順位がある。**一番は実装力、次点で設計力**。

### 主目的: 実装力（自力で動くものを完走する）

ロジックを自分で組み、設計 → 実装 → 動作確認までを一人で回しきる。具体的には:

- ディレクトリ走査・パス操作・移動／改名といった標準ライブラリを実際に使えるようになる
- dry-run と apply、衝突検知、件数サマリといった仕様を、DoD を満たすコードに落とせる
- エラーや部分失敗を実際に踏んで、「途中で落ちない・黙って壊さない」コードを書ける

> まず自分で書く（汚くてよい）。AI には後でレビューさせる（先に書かせない）。

### 次の目的: 設計力（構造を自分で判断する）

仕様（DoD）は「満たし方」を縛らない。**どう作るかは自分で決める**。とくに:

- ルール（`--by`）が増えても破綻しない構造をどう作るか
- 「計画を作る（副作用なし）」と「適用する（I/O）」の境界をどこに引くか
- 冪等性・部分失敗・衝突を、どの層でどう扱うか

> これらは README で答えを出していない（後半の「自分で決める設計判断」に問いとして置いてある）。**自分で決めること自体が設計力の練習**になる。

## 進め方（推奨ステップ）

実装力を主目的に据えるため、順番を固定する。

1. 「入力 → 処理 → 出力」を 3 行で書く（設計メモ）
2. まず自分で実装する（動けば汚くてよい）
3. DoD を 1 つずつ自分で確認する（自己検収）
4. AI にレビューさせ、自分のコードとの差分を読む

## 対象（入力）

- 入力は「対象ディレクトリ」と「適用するルール（`--by`）」。
- ルールごとに、各ファイルの「現在のパス → 変更後のパス」の一覧（＝**変更計画**）を組み立てる。
- テスト用には `testdata/` に意図的にエッジケースを含む構成を置く。

```
testdata/sample/
  report.pdf
  invoice.pdf
  cat.png
  noext            # 拡張子なし
  IMG_001.jpg
  IMG_002.jpg
  nested/photo.jpg # --recursive 検証用
```

## コマンド仕様

```
refile <dir> --by ext|date|seq [--prefix P] [--apply] [--recursive] [--on-conflict skip|error]
```

| 項目 | 説明 | デフォルト |
| --- | --- | --- |
| `<dir>` | 整理対象のディレクトリ | （必須） |
| `--by` | 整理ルール（ext / date / seq） | （必須） |
| `--prefix P` | 連番リネームの接頭辞（`--by seq` のとき必須） | （なし） |
| `--apply` | 実際にファイルを移動・改名する | dry-run（無変更） |
| `--recursive` | サブディレクトリも対象にする | false |
| `--on-conflict` | 変更後パスが衝突したときの方針（skip / error） | error |

ルールの意味:

| `--by` | 変更後パス |
| --- | --- |
| `ext` | `<dir>/<拡張子>/<元名>` へ移動（拡張子なしは `noext/` など） |
| `date` | `<dir>/<更新月 YYYY-MM>/<元名>` へ移動 |
| `seq` | `<prefix>-001`, `<prefix>-002` … へ連番リネーム |

> `ext`/`date` は**ファイルをサブフォルダへ移動**する（ファイル名は維持）。`seq` は**ファイル名を連番に改名**する（フォルダ名ではなくファイル名を変える）。つまりこのツールは移動と改名の両方を行う。

各ルールの具体例（`<dir> = testdata/sample`）。`<元名>` は元のファイル名（拡張子込み）を指す:

- **`ext`** — 拡張子をサブフォルダ名にして振り分ける（ファイル名はそのまま。拡張子なしは `noext/`）。

  | 元ファイル | 変更後パス |
  | --- | --- |
  | `report.pdf` | `testdata/sample/pdf/report.pdf` |
  | `cat.png` | `testdata/sample/png/cat.png` |
  | `noext`（拡張子なし）| `testdata/sample/noext/noext` |

- **`date`** — 更新月（`YYYY-MM`）をサブフォルダ名にして振り分ける（ファイル名はそのまま。下の更新月は例）。

  | 元ファイル（更新月）| 変更後パス |
  | --- | --- |
  | `report.pdf`（2026-05 更新）| `testdata/sample/2026-05/report.pdf` |
  | `cat.png`（2026-06 更新）| `testdata/sample/2026-06/cat.png` |

- **`seq`** — 対象ディレクトリ内のファイルを順番に `<prefix>-001`, `<prefix>-002` … と連番へ改名する（サブフォルダは作らない）。連番を振る順序は DoD の「変更計画の並び順が安定している」に従う。`--prefix img` の例:

  | 元ファイル | 変更後（名前）|
  | --- | --- |
  | （1番目）| `img-001` |
  | （2番目）| `img-002` |

## 受け入れ条件（DoD）

- [ ] 引数なし、または対象がディレクトリでない／存在しない場合、わかりやすいエラーを標準エラー出力に出し、終了コード 1 で終わる
- [ ] `--apply` を付けない場合は **ファイルを一切変更せず**、変更計画（現在 → 変更後）のみを出力する
- [ ] `--by ext` で、各ファイルの変更計画を出力できる
- [ ] `--by seq` で `--prefix` が無い場合はエラーにする（オプションの組み合わせ検証）
- [ ] 複数ファイルが同じ変更後パスになる「衝突」を、**計画段階で**検知して報告する（apply 前に止まる、または `--on-conflict` に従う）
- [ ] `--apply` 指定時のみファイルを移動・改名し、件数サマリ（移動 / スキップ / エラー）を出力する
- [ ] `--apply` 中に個別ファイルの操作が失敗（権限なし／実行中に元ファイルが消えた 等）しても、全体を中断せず残りを続行する。失敗はサマリにエラー件数として計上する（部分失敗を許容し、ロールバックはしない）
- [ ] 同じコマンドを 2 回適用しても破綻しない（2 回目は「変更なし」になる）＝ 冪等
- [ ] 変更計画の並び順が安定している（元パスの辞書順など）

- 配置: `go/phase1/tools/refile/`（テスト用のファイル群は `testdata/` に置く）

## 発展（任意）

- `--replace <regexp> <repl>` で正規表現による改名に対応する
- `--json` で変更計画を機械可読に出力する
- undo: 直前の `--apply` の内容を記録し、巻き戻せるようにする
- 変更計画を作る処理を関数として切り出し、テストを 1 本書く（正常系 / 衝突あり / 空ディレクトリ）

## 自分で決める設計判断（設計力の練習）

> ここは **仕様として決めていない**。DoD を満たす範囲で、構造は自分で判断する。これが本課題の設計力パート。実装に入る前に一度考え、実装後に「なぜそうしたか」を自分の言葉で説明できる状態を目指す。

- ルール（`--by`）が 3 種類ある。「ファイル 1 つ → 変更後パス 1 つ」を計算する部分だけ差し替えれば増やせる構造をどう作るか（logstat の `--by` と同じ問題）
- 「計画を作る」処理と「計画を適用する」処理をどう分けるか。**副作用のない部分**をどこまで広げられるか（広いほどテストしやすい）
- 衝突の定義（複数の元ファイルが同じ宛先になる／宛先に既存ファイルがある）。どの段階で検知し、どう出し分けるか
- dry-run と apply は **同じ計画ロジック**を使い、差は「実行するか否か」だけにできるか
- エラー（対象なし・権限なし）と警告（スキップした衝突）を、出力先・終了コードでどう区別するか
- 冪等性をどう担保するか（すでに正しい場所にあるファイルを計画から除くか）
- 部分失敗（apply の途中で失敗）をどの層で受け止め、サマリにどう集約するか
