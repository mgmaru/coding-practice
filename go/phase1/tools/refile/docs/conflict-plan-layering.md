# 「計画（事実）」と「方針の適用（アクション）」を2層に分ける設計

## 0. このドキュメントの目的

`refile` の `--apply`（ext / date）において、**衝突（conflict）** をどのステータスとして扱い、`--on-conflict skip|error` をどこで適用するかを整理する。

議論の途中で、`--on-conflict` の意味や、衝突を `skip` ステータスに含めてよいか、という点で認識のズレがあった。このドキュメントは、

- **どこで認識が間違っていたか（混乱の履歴）**
- **たどり着いた「2層に分ける」設計とその理由**

を、後から読み返せる形で残すことが目的。

> ⚠️ このドキュメントには実装コードは載せない。**考え方（設計）**だけを示す。

---

## 1. 用語の再確認（README準拠）

| 用語 | 意味 | いつ分かるか | 性質 |
| --- | --- | --- | --- |
| **冪等 / unchange** | そのファイル自身が既に行き先にいる（現在パス == 変更後パス） | 計画時 | 決定的 |
| **衝突 / conflict** | **別々の**ファイルが同じ変更後パスを取り合う | 計画時（FSを触らず判定できる） | 決定的・再現する |
| **Renameエラー** | `os.Rename` が実際に失敗（権限なし／実行中に元ファイルが消えた 等） | **適用時にしか分からない** | 非決定的 |

この3つは **発生タイミングも性質も違う**。ここを混ぜたことが、後述の混乱の原因だった。

---

## 2. 混乱していた点（何が違って、何が間違っていたか）

設計を詰める過程で、認識が次のように変わっていった。**間違い → 訂正** の順で残す。

### 誤解① 「衝突をエラーで数える。でも適用は1件ずつ動かすから片方は成功してしまい、計画と適用が食い違う」

- **何が心配だったか**：計画では「2件エラー」なのに、適用で1件成功すると「1成功/1エラー」になり、計画と適用が乖離する。
- **実際どうだったか**：適用（`os.Rename`）を **`complete` のファイルにしか呼ばず、conflict/unchange は適用対象外にする**設計になっていた。
- **結論**：➡ **食い違いは既に解決済み**だった。conflict の2件を両方 skip（適用対象外）にすれば、計画も適用も「2 skip / 0 complete」で一致する。心配していた乖離は起きない。

> 教訓：食い違いは「衝突をどう**数える**か」の問題ではなく、「適用が計画に**従属**しているか」の問題。適用が計画を無視して自前で動かさない限り、乖離は起きない。

### 誤解② 「`--on-conflict` は、`os.Rename` が失敗したときに続けるか止めるかのフラグ」

- **何が間違いか**：`--on-conflict` は名前のとおり **衝突（conflict）専用**のフラグ（README L141〜144）。`os.Rename` の実行時失敗の方針ではない。
- **正しい整理**：
  - **衝突** → `--on-conflict` が支配する。
  - **Renameエラー** → `--on-conflict` とは**無関係**。DoD L122 が「全体を中断せず残りを続行・エラー計上・ロールバックしない」と**固定**している。ここに選択の余地はない。
- **結論**：➡ 「on-conflict error だから Rename失敗で中断する」は **DoD違反**。2つの軸を混ぜていた。

### 誤解③ 「衝突は `skip` ステータスに含めればよい」

- **何が引っかかるか**：`skip` は「結果（どうなったか＝アクション）」、`conflict` は「原因（何が起きたか＝事実）」で、**層が違う**。
- **なぜ混ぜると破綻するか**：同じ衝突でも `--on-conflict error` のときは skip されず「apply前に全体停止」になる。つまり **conflict → skip は必ずしも成り立たない**。conflict を skip に畳むと error モードを表現できない。
- **結論**：➡ **conflict は独立した「原因」ステータスにする**。これが本ドキュメントの核。

---

## 3. たどり着いた設計：計画（事実）と 方針の適用（アクション）を2層に分ける

### 3.1 全体像

```
┌─────────────────────────────────────────────┐
│ 第1層：計画（--on-conflict を知らない）        │
│   入力：各ファイルの 現在パス → 変更後パス       │
│   出力：方針に依存しない「事実」だけ             │
│                                             │
│     ├ unchange … 自分自身が既に行き先にいる      │
│     ├ movable  … 単独で行ける（衝突なし）        │
│     └ conflict … 別ファイルと行き先がぶつかる     │
└─────────────────────────────────────────────┘
                     │
                     ▼   ← ここで初めて --on-conflict を見る
┌─────────────────────────────────────────────┐
│ 第2層：方針の適用（--on-conflict を見る）       │
│                                             │
│   conflict を…                               │
│     ├ skip モード  → skipして「残り」は適用       │
│     └ error モード → 何も適用せず全体を止める     │
└─────────────────────────────────────────────┘
                     │
                     ▼   ← 適用時のみ・別軸
┌─────────────────────────────────────────────┐
│ 適用中の os.Rename 失敗（--on-conflict と無関係）│
│   → 常に「続行＋エラー計上」（DoD L122・固定）    │
└─────────────────────────────────────────────┘
```

### 3.2 2つの層の責務

| | 第1層：計画（事実） | 第2層：方針の適用（アクション） |
| --- | --- | --- |
| 知っていること | 現在パスと変更後パスだけ | 第1層の結果 ＋ `--on-conflict` |
| `--on-conflict` を見るか | **見ない** | 見る |
| 副作用 | なし（純粋・テストしやすい） | 適用の可否を決める |
| 出力の性質 | 決定的な事実 | 事実に方針を適用した結果 |

### 3.3 「原因（事実）」と「アクション（結果）」は別の軸

ステータスを設計するとき、次の2軸を**混ぜない**のが要点。

- **原因（事実）**：`unchange` / `movable` / `conflict` /（適用時のみ）`rename-error`
- **アクション（結果）**：`complete` / `skip` / `aborted`

`--on-conflict` は、この **原因（conflict）を アクションへ写像する対応表**にすぎない。

| 原因（第1層の事実） | `--on-conflict skip` でのアクション | `--on-conflict error` でのアクション |
| --- | --- | --- |
| `unchange` | 何もしない | 何もしない |
| `movable` | 適用（complete） | 適用（complete） |
| `conflict` | **skip**（残りは続行・終了コード0） | **aborted**（apply前に全体停止・終了コード1） |

> ❌ やってはいけない：`conflict-skip`, `conflict-error` のように「原因 × 方針」の組み合わせごとにステータスを作ること。数が爆発する。原因と方針は別々に持つ。

---

## 4. なぜこの2層が良いのか（設計上の利点）

1. **計画が方針から独立する（純粋になる）**
   第1層は `--on-conflict` を引数に取らない。同じディレクトリなら `--on-conflict` が skip でも error でも第1層の出力は**同じ**。→ README の設計目標「副作用のない部分をどこまで広げられるか」に沿う。**テストが書きやすい**（衝突あり／なし／空ディレクトリを、方針と無関係に検証できる）。

2. **`error` モードが自然に表現できる**
   「conflict という事実」を持っていれば、第2層で「conflict が1件でもあれば apply前に停止」を素直に書ける。conflict を skip に畳んでいると、この分岐が表現できなかった（誤解③）。

3. **曖昧なステータスを消せる**
   `error` モードを「衝突を検知したら apply前に停止・何も動かさない」と定義すれば、「処理されずに中途半端に残ったファイル」という状態自体が生まれない。→ いまの `cannot` のような曖昧ステータスは**不要になる**。

4. **軸が混ざらないので、Renameエラーを正しく扱える**
   衝突（第1・2層）と Renameエラー（適用時・別軸）が構造的に分かれているので、「Rename失敗は on-conflict に関係なく常に続行」（DoD L122）を破りにくい。

---

## 5. まとめ

- **食い違い問題**（誤解①）は、適用を計画に従属させる（conflict/unchange を適用対象外にする）ことで**既に解決済み**。カウント方針の問題ではない。
- **`--on-conflict` は衝突専用**（誤解②）。`os.Rename` の実行時失敗は別軸で、常に「続行＋エラー計上」（DoD L122・固定）。
- **conflict は独立した「原因」ステータス**にする（誤解③）。`skip` は「結果」なので層が違う。
- 設計は **2層**にする：
  - 第1層＝**計画（事実）**：`unchange` / `movable` / `conflict` を、`--on-conflict` を知らずに決める。
  - 第2層＝**方針の適用（アクション）**：`--on-conflict` を見て、conflict を skip か aborted に写像する。
- **原因（事実）** と **アクション（結果）** は別の軸として持ち、組み合わせごとのステータスは作らない。

> 一文で言うと：**「何が起きたか（事実）」を先に確定させ、「それにどう対応するか（方針）」は後段に分離する。** これで計画は純粋になり、error モードも自然に表現でき、曖昧ステータスも消える。
