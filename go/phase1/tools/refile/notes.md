## 実装前
### 仕様理解
- ツール：ディレクトリ(`<dir>`)および、適用ルール(`--by`)を指定して、その中のファイル群をサブフォルダに移動する（振り分ける）。

### わからなかった点
- [x] 要は、「ディレクトリを指定して、３つのルールに基づいて、別のサブフォルダへ移動させる」という認識で良いか？ファイルのリネームはしない認識で良いか？
- [x] `--recursive`は、指定したディレクトリの中にあるサブフォルダも一緒に移動するかどうかのオプション？ -> 多分そう。
    - そしてこの仕様より、おそらく、移動元のディレクトリは残しておくという仕様の方が良い。
    - あくまで移動させるのはファイル群であって、元のディレクトリを移動させるわけではない。</br>
→ **対象のディレクトリの下にサブフォルダを作成するというツールなので、当然、元のディレクトリは残す。**
- [x] [重要]**最初に移動したいファイル群のディレクトリに移動してから、移動先のフォルダを指定してコマンドを実行する**認識？</br>
それとも、**任意のディレクトリから、`<移動元のディレクトリ>`と`<移動先のディレクトリ>`を相対パスで指定して実行する**認識？</br>
それとも、**現在のディレクトリの下にサブディレクトリを作成して、そこにファイルを振り分けるイメージ**？　←これかも！</br>
→ **指定したディレクトリの下にサブフォルダを作成して、そこにファイルを振り分ける。**</br>
→ もしくは、**指定したディレクトリのファイルを連番にリネームする（サブフォルダは作成しない。）**
- [x] ディレクトリとして指定するのは、相対パス？それとも絶対パス？それとも、両方に対応する？ →これは自分で決める。
- [x]「冪等性をどう担保するか（すでに正しい場所にあるファイルを計画から除くか）」がわからない。
    - 正しい場所にあるというのは、移動先のディレクトリにすでに同じファイルがある場合のこと？</br>
→ 違う。同じコマンドを２回流した時に、変更なしと出すこと。</br>
→ ただし、これは１回目のコマンドを保持しなくても実装できる。変更しようとしているパス計画と現在のディレクトリの構造の差分を比較して、差分がなければ変更なし。差分があれば変更できる。</br>
→ ただし、**この「差分」をどこまで比較するのかは仕様次第（サブフォルダの構成まで比較するのか、ファイルの中身まで比較するのか）**
- [x] `--by`のルールについての疑問
    - [x] `ext`：`<dir>/<拡張子>/<元名>` へ移動というのがわからない。`<拡張子>`というのは何を示すのか？元のフォルダのファイルを拡張子ごとに振り分けるイメージ？ → あってる。元のディレクトリに存在するファイルを拡張子ごとのサブフォルダに振り分ける。
    - [x] `date`：`<dir>/<更新月 YYYY-MM>/<元名>`は、ファイルの更新月ごとに振り分けるイメージ？ → あってる。
    - [x] `seq`：「`<prefix>-001`, `<prefix>-002` … へ連番リネーム」のルールがわからない。移動元のフォルダを連番リネーム？
    それとも、移動元のファイルを連番リネーム？ → ファイルをリネーム。サブフォルダへの移動は行わない。

## 設計
### 決めるべき仕様
- 動作OS：Winodws / Mac /Linux 
    - 備考：OSによってパスの作り方が違うような気がする。
- 対処ディレクトリの指定
    - **ユーザPC全体**（`refile`内に留まらない）。
    - **絶対パス、相対パスどちらも指定可能**とする。
    - もし、指定したパスのディレクトリが存在しなかったりした場合は、エラーを表示する。
- 比較方法（ファイルの差分比較）：ファイルのパス（名前）まで。ファイルの中身は比較しない。
    - **ファイルの名前が同じで内容が違っても、それは同じファイル**として扱う。
    - 理由①：ファイルの中身をパースすると処理的に重くなってしまう。
    - 理由②：PDFなどのファイルをパースする（同じものか違うものかを比較する）のは結構むずしそうだから。
- 冪等(べきとう)時：同じコマンドが実行された時、ファイルを比較して、同一とみなされた場合は「変更なし」と表示して、操作は実行しない。
- `--on-conflict`の仕様
    - 適用範囲：計画および実行時
    - `--on-conflict skip `：衝突したファイルをスキップとして扱い、以降のファイル操作を実行する。
    - `--on-conflict error `：衝突したファイルをエラーとして扱う。エラーが起きた時点で、残りのファイル操作は実行しない。
    - 迷った点：計画時も`--on-conflict`の設定（`skip`|`error`）によって、件数を変えるべきか悩んだ。
        - 同じようにすることにした。
        - 理由：計画時はスキップだったのに、実行時はエラーとなって大きくずれてしまい、ユーザが混乱すると思ったため。
- コマンド、引数の必須 / オプション
    1. 引数：
        - `<dir>`（対象ディレクトリ）：**常に必須** -> len(Arg()) < 1 でバリデーション
    2. コマンド：
        - `--by `（ルール）：**常に必須**
        - `--prefix P`：**`--by seq`が指定された場合に必須**
        - `--apply` ：オプション
        - `--recursive`：オプション
        - `--on-conflict`：オプション
- `dry-run`時（計画）のサマリー出力：
    1. `ext`, `date`： 
    - すべてのファイル操作ができる：「⚪︎件のファイルをサブフォルダに移動します。適用しますか？ Y/n」
    - 衝突時：「⚪︎件のファイルをサブフォルダに移動します。⚪︎件のファイルの移動をスキップします。適用しますか？ Y/n」
    - 冪等時：「ファイルの変更がありません。」
    - 一部のファイル操作：「⚪︎件のファイルを移動します。⚪︎件のファイルは移動できません。適用しますか？　Y/n」
    - 操作ファイルがない：「ファイルが移動できません。」
    2. `seq`：
    - すべてのファイル操作ができる：「⚪︎件のファイルをサブフォルダに移動します。適用しますか？ Y/n」  
    - 衝突時：「⚪︎件のファイルをリネームします。⚪︎件のファイルのリネームをスキップします。適用しますか？ Y/n」
    - 冪等時：「ファイルの変更がありません。」
    - 一部のファイル操作：「⚪︎件のファイルをリネームします。⚪︎件のファイルは移リネームできません。適用しますか？　Y/n」
    - 操作ファイルがない：「ファイルがリネームできません。」
- `--apply`時（実行）のサマリー出力：
    1. `ext`, `date`：
    - すべてのファイル操作完了時：「⚪︎件のファイルをサブフォルダに移動しました。」
    - 衝突時：「⚪︎件のファイルをサブフォルダに移動しました。⚪︎件のファイルの移動をスキップしました。」
    - 冪等時：「ファイルの変更がありません。ファイル操作を実行しませんでした。」
    - 一部のファイル操作：「⚪︎件のファイルを移動しました。⚪︎件のファイルは移動できませんでした。」
    - すべてのファイル操作ができない時：「ファイルが移動できません。」
    2. `seq`：
    - すべてのファイル操作完了時：「⚪︎件のファイルをリネームしました。」
    - 衝突時：「⚪︎件のファイルをリネームしました。⚪︎件のファイルのファイルのリネームをスキップしました。」
    - 冪等時：「ファイルの変更がありません。ファイル操作を実行しませんでした。」
    - 一部のファイル操作ができない時：「⚪︎件のファイルを移動しました。⚪︎件のファイルはリネームできませんでした。」
    - すべてのファイル操作ができない時：「ファイルがリネームできません。」
- `--recursive`について
    - 「サブフォルダ」の定義：対象のディレクトリにあるフォルダ全て。n階層。
    - 指定された場合：
        - **(注意)**対象ディレクトリに`/nested/nested/...`という、多段になったディレクトリが存在した場合、そのディレクトリの最下層にあるファイルの拡張子を調べる。
        - 厄介なのが、n階層目までにちょくちょく、ファイルが含まれている場合がある。つまりn階層目にディレクトリとファイルが混在している可能性も考慮する必要がある。
            - 例：`/nested/nested/ main.go, sample.log/nested/ `
    - 指定されていない場合：
        - `nested/`などのフォルダは無視する。
    - 実装方法：おそらく、`--recursive`を指定した場合と、指定していない場合で分岐させた方が良い（無駄な計算は減らしたい）。
- コマンド順番
    - `flag`を使用する。
    - プログラムの実行方法：`go run main.go <--by ext|date|seq [--prefix P] [--apply] [--recursive] [--on-conflict skip|error] <dir> >`
    - `dir`は最後に指定する（`flag`の仕様より）。
- `seq`コマンド機能の仕様について
    - 仕様：拡張子ごとに分類して連番にするのではなく、拡張子で区別なく一括で連番にリネームする仕様とする。
        - ただし、、まず、拡張子ごとにソートしてから連番にリネームする。
- `seq`+`--recursive`コマンドの実行についての仕様
    - 仕様：`seq`を指定した際には、`--recursive`コマンドを指定しても、サブディレクトリは対象にしない。
        - **`seq`かつ`--recursive`を選択された場合は、プログラム上で自動的に`--recursive`を`false`にする。**
    - 理由：直感的に、連番にリネームするのは同じディレクトリが圧倒的に多い。
    - 理由：勝手に移動するのは、ユーザの意思に反するものかもしれない。
    - 追加機能：`seq`を選んで、かつ、`--recursive`コマンドを実行した際には、「サブディレクトリはリネームの対象になりません。サブディレクトリのファイルを対象にする場合は、指定するディレクトリに移動してから実行してください。」のようなメッセージを出す。
- 作成されるファイルの並びはOS差があるため、どこかで吸収する必要がある。
    - 計画後ファイル順序：ファイル名昇順
    - ただし、`seq`だけはソートするロジックを変える。
        - まず、拡張子ごとにファイルを並びかえてから、その拡張子の中でファイルの昇順にソートする。
        - ファイルの昇順にソートしてから、連番の名前を付与する。
    - 実行後のファイル順序：ファイル名昇順
- ソートは、計画後、実行後に一括で実施する。
    - 関数単位でソートを意識するのは、実装コストが高い。
    - 関数単位でソートをするのは、計算量も多くなる。
    - 注意：あくまで、**ソートするのはこのプログラム上でのファイル順序であって、物理的な並び順ではない。**
        - 物理的な並びはOSが決めることなので、また別の話。
        - 物理的な順序はOSによるものなので、プログラムからはどうしようもない。

### 設計意思
- **冪等は、最初にガードして、そもそもファイル操作の判断も実行もしない。**
- `dry-run`で計画した後に、`apply`した場合、計画時と実行時で結果が変わる可能性がある。
    - **計画と実行の整合性は保証しない仕様**とする。
    - 別に、トランザクションなどのロールバックはしない（READMEより）。

## 初回実装
### ロジック設計
1. 対象ディレクトリ内のファイルをリスト化する。 -> 構造体`FileBaseInfo`
2. リストのファイルのファイルの中で、操作予定のファイルとそうでないファイルを分ける。 -> 構造体`IsFileMove`
3. コマンドごとに処理しやすいデータ（構造体）へ変換　
    - ext: 構造体`ExtFileMove`
    - date: 構造体`DateFileMove`
    - seq: 構造体`SeqFileMove`
4. 変更予定のパスを作る
    - ext: 関数`makeExtPathPlan()`
    - date: 関数`makeDatePathPlan()`
    - seq: 関数`makeSeqPathPlan()`
5. 冪等を判定する（関数`isIndempotent()`）
6. ファイルパスごとに衝突を判定する（関数`hasConflict()`）　※ `ext`および`date`のみ。（`seq`は連番でファイルをリネームするかつサブディレクトリは対象にならないので、衝突が起きない。）
    1. `BeforePath`と`AfterPath`が同じものと、違うものをグループ分けをする。
    2. 同じグループは衝突しないので（現時点で存在しているファイルなので）、`HasConflict`を`false`に設定する。
    ここで、衝突判定が確定したものを構造体`FileOperationResult`にマッピングする。
    3. まず、同じグループと違うグループで衝突判定をし、違うグループの中で衝突したファイルパスは、`HasConflict`を`true`とする。ここで、衝突判定が決定したファイルパスを`FileOperationResult`にマッピングする。
    4. 違うグループの中で衝突安定をして、衝突したファイルは`HasConflict`を`true`として、ファイルパスを`FileOperationResult`にマッピングする。
7. 移動前のファイルパスを昇順にソートする。　※ `ext`, `date`に対して。`seq`は連番に並べているので、ソートしない。
8. `--on-conflict`に基づいて、7でソートした順番にファイル操作計画を実行し、サマリを返す。
9. 衝突結果を見て、実行結果をサマリする。

### 工夫した点
- コマンドをパースする際に、最初に引数に対象のディレクトリが指定されていない場合について、早期リターンを実施。
    - 理由：対象ディレクトリが指定されていないと以降の処理が何もできないため、最優先でチェックした。
- なるべく関数は分割するようにした。
    - 理由：変更点を最小にするため。
- **対象ディレクトリの存在条件とともに、対象ディレクトリが空かそうでないかを判定**した。
    - 空ディレクトリであると、何もする必要がないので、早期リターン
- **１ファイルの移動前のパスと移動後のパスを格納する構造体`FilePathMove`を実装した。**
    - これによって、冪等や衝突を判定しやすいようにした。
- **冪等ロジックについて**
    - 入力：対象ディレクトリの移動前のパスと移動後のパス
    - ロジック：ファイルごとの移動前のパスと移動後のパスを比較して、全て同じだった場合は、冪等判定。
- **計画時の衝突のロジックについて** ← ここが難しい！！！！
    - 入力：対象ディレクトリの移動前のパスと移動後のパス
    - ロジック：
        1. まず、入力のスライスの中で、移動前のパスと移動後のパスが「同じもの」と「違うもの」をグループ化する（それぞれ変数に格納）。
            - 分ける理由：「同じもの」は、移動後のパスでもあるが、移動前のパスでもあって、すでに実現されている状態である。
            - **グループ化しない状態で総当たりをすると、同じもののファイルも衝突としてカウントしてしまう。**これは正しくない。
            - **同じものはそのままで、違うもののみを衝突として扱う必要**がある。
        2. 変更予定なしのパスを`FileOperationResult`に`append`する（予定が確定しているため）。
        3. 違うものから要素を１つ取り出して、違うもののグループの移動後のパスと比較する。
            - パスが被った「違うもの」グループのパスは、衝突としてカウント
            - かぶらなければ、次の要素へ
            - 違うもの分だけループ処理
        4. **変更予定なしのパスと被った変更予定のパスを。変更予定のパスグループから除外する。**　←重要！！
        5. 残った変更予定のパスのグループの中で、パスの被りがないか判定。 ← **ここが難しかった！！（後述）**
            - 被ったものは、衝突としてカウントする。
            - かぶらなかったものは、衝突なし(`complete`)でカウント。
    - 工夫：
        - ポイント：**予定が確定したものから**スライス`FileOperationResult`に`append`していく。
        - 変更のないものは、計画が決まっているので、最初に`FileOperationResult`に`append`する。
        - 次に、変更予定のないものと、変更予定のものを比較した時に、衝突が決まったパス（結果が決まったもの）について、`FileOperationResult`に`append`する。
        - 最後に、変更予定どうしの衝突の際に、すでに`FileOperationResult`に`append`されているファイルは、スライスへの`append`はしないようにする。
            - このすでにスライスに含まれているかどうかは、`BeforePath`で弾く（`BeforePath`は現在のパスであり、必ず一意になるので）。
    - 注意：`seq`は仕様上、衝突は起きない。
        - 理由：対象ディレクトリに対して、連番でファイルをリネームするので、リネーム後のファイルの衝突は起きない。
        - なので、衝突の判定`hasPathConflict()`は実行しない。
            - 理由：`seq`は、パスの作成時にソートしているので、その並びを崩してしまう場合がある（`hasPathConflict`は並びを保証しないため）。

### 重要：スライスの中の要素（パス）の被りの判定方法について
- 要素を削除しながら、ループは回さない方が良い！！
例：
```go
	for _, notChangePath := range notChangePathes {
		for i, changePath := range changePathes {
			if notChangePath.BeforePath == changePath.AfterPath { // 同じもののグループの現在のパスと、違うものの変更予定のパスが同じ

				filesOperationResult = append(filesOperationResult, FileOperationResult{CurrentFilePath: changePath.BeforePath, PlannedPath: changePath.BeforePath, Result: "skip"})

				// changePathの中で、notChangePathと被ったものについては、予定が確定したので、変更予定のグループ（changePathes）から除外する。
				changePathes = slices.Delete(changePathes, i, i+1) // 要素のi番目を削除 // バグ！！！！！
			}
			// かぶらなければ何もしない（理由：まだ計画が決まっていないため）
		}
	}
```
- 目的：このコードは、変更しないパスと変更予定のパスの衝突を判定している。
- 変更なしのパスと変更予定のパスが被った時に、その変更予定のパスについて、変更結果が確定する（そのパスについては、変更しないことを決定する）。
- バグ：衝突した時に、変更予定のパスが格納されているスライス`changePathes`からそのパスを除外しようとしているが、ここにバグが潜んでいる。
    - 理由：`chabgePathes`の`i`番目の要素が衝突したと判断し、その`i`番目の要素を削除しているが、イテレータが指す要素（パス）が、要素の削除によってずれている。
    - `changePathes`が、`[path0, path1, path2, ...]`ってあった時に、例えば、`path0`に衝突した場合に、`path0`を`changePathes = slices.Delete(changePathes, 0 , 1)`で削除するまでは良い。
    - **しかし、その後に、`i=1`とイテレータがカウントアップした時に、仮に、`path1`が衝突した場合、本来であれば、`changePathes = slices.Delete(changePathes, 0 , 1)`で`path1`を削除しないといけないのに、イテレータが`i=1`となっているために、`changePathes = slices.Delete(changePathes, i = 1 , 2)`となって、`i=1`番目である、`path2`が削除されてしまう。**
- つまり、**ループで取り出しているスライスに対して、要素を削除したり、増やしたりするのはバグの原因となりうると考えられる。**

### 補足
```go
	for _, notChangePath := range notChangePathes { // notChangePathは一意で、被りはない。
		for _, changePath := range changePathes {
			if notChangePath.BeforePath == changePath.AfterPath { // 同じもののグループの現在のパスと、違うものの変更予定のパスが同じ
				filesOperationResult = append(filesOperationResult, FileOperationResult{CurrentFilePath: changePath.BeforePath, PlannedPath: changePath.BeforePath, Result: "skip"})
			}
			// かぶらなければ何もしない（理由：まだ計画が決まっていないため）
		}
	}
```
- このコードで、衝突を起こした`changePath`が2回`append`されることはない！
    - 理由：`notChangePathes`の要素は必ず一意であることを使えば、「**ある`changePath`に対して、`notChangePath`と衝突した場合、`changePath`は他の`notChangePath`と被らない。**」つまり、`changePath`は2回`append`はされない。
- このコードでは、ある`notChangePath`に対して、`changePath`を比較しているように見えるが、`changePath`→`notChangePath`のような方向で考えるとわかりやすい。`notChangePath`は一意だから、ある`changePath`が、ある`notChangePath`と被った場合は、他の`notChangePath`とは衝突しない。つまり、重複することはないことがわかる。
- 実際、内ループと外ループを入れ替えた実装にしても結果は同じ。

### 苦手なこと
- **`for`の中で`if`分岐して、スライスの中に要素を詰め込んでいくときに、`continue`を忘れることがある。**
    - `continue`忘れて、同じ要素が２回スライスに`append`されてしまうことがあった。。。
例：
```go
for _, file := range fileBaseInfo {
	path := strings.TrimPrefix(file.FilePath, targetDir+"/") //　パスから対象ディレクトリのパスを除外
	if strings.Contains(path, "/") {                         // 最初の文字が「/」だったら、ディレクトリと判断して除外。
		isFilesPathAndMove = append(isFilesPathAndMove, IsFileMove{FileBaseInfo: file, IsMove: false})
		continue　// ← ここでcontinueしないと、１つの要素に対して、分岐した後と分岐を抜けたあとで２回appendされてしまう！！（バグ）
	}
	isFilesPathAndMove = append(isFilesPathAndMove, IsFileMove{FileBaseInfo: file, IsMove: true})
}
```
